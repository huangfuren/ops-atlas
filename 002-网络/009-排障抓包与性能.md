## 9.1 分层排除决策树

排障难的从来不是命令，是**顺序**。固定顺序的价值是保证不在错误的层上浪费超过 5 分钟。

```text
现象：打不开 / 连不上 / 很慢 / 时好时坏
  │
  ├─ ① 用域名还是 IP？ → 域名先解析
  │     dig +short 域名
  │     ├─ 无结果  → 003 册（DNS）
  │     └─ 有结果  → 继续
  │
  ├─ ② 路由通吗？ → ip route get 目标IP
  │     ├─ 无路由  → 001 册 1.3
  │     └─ 有路由  → 继续
  │
  ├─ ③ 二层能到吗？（同网段时）
  │     ip neigh show 目标IP
  │     ├─ FAILED  → 二层不通，别再往上查（001 册 1.4）
  │     └─ OK      → 继续
  │
  ├─ ④ 端口通吗？ → nc -vz IP 端口
  │     ├─ refused   → 服务没起（002 册 2.3）
  │     ├─ timed out → 防火墙 / 路由黑洞（007 册 7.8）
  │     └─ 通了      → 继续
  │
  ├─ ⑤ TLS 握手过吗？ → openssl s_client
  │     ├─ 证书错  → 005 册 5.6
  │     └─ 通过    → 继续
  │
  ├─ ⑥ 应用返回什么？ → curl -v
  │     ├─ 4xx → 请求本身的问题（004 册 4.4）
  │     └─ 5xx → 006 册 6.10（上游 / LB / 超时）
  │
  └─ ⑦ 慢在哪？ → curl -w 时间分解（004 册 4.8）
        └─ 分解结果决定是 DNS、握手、服务端还是客户端
```

### 9.1.1 每一步的证据

| 步 | 命令 | 通过的样子 | 不通过的样子 |
|---|---|---|---|
| ① | `dig +short www.example.com` | 输出 IP | 空 |
| ② | `ip route get 1.2.3.4` | 有 via 和 dev | `Network is unreachable` |
| ③ | `ip neigh show 10.0.0.5` | `REACHABLE` / `STALE` | `FAILED` / `INCOMPLETE` |
| ④ | `nc -vz 1.2.3.4 443` | `succeeded` | `refused` / `timed out` |
| ⑤ | `openssl s_client -connect ...` | `Verify return code: 0` | 证书错误 |
| ⑥ | `curl -v` | 200 | 4xx / 5xx |
| ⑦ | `curl -w` | 各段耗时合理 | 某一段异常大 |

**核心纪律：每一步都要有命令输出作为证据。** 不允许「我觉得是 DNS」直接跳步——跳步的代价是改了半天发现方向错了，而现场已经被改乱。

## 9.2 工具矩阵

| 工具 | 解决什么 | 一条典型命令 | 输出怎么读 |
|---|---|---|---|
| `ping` | 三层可达性、RTT、丢包 | `ping -c 4 1.2.3.4` | `ttl` 推系统，`time` 看延迟，丢包率看末行 |
| `traceroute` / `mtr` | 路径上哪一跳有问题 | `mtr -rw -c 20 1.2.3.4` | 某一跳开始持续丢包 = 问题在那之后 |
| `ss` | 连接状态、端口、队列 | `ss -lntp` / `ss -s` | `Recv-Q`/`Send-Q`、状态分布 |
| `nc` | 端口通不通 | `nc -vz 1.2.3.4 443` | `succeeded` / `refused` / `timed out` |
| `curl` | 应用层、耗时分解 | `curl -w '@fmt' -o /dev/null -s URL` | 各阶段耗时 |
| `dig` | 解析结果、链路 | `dig +trace 域名` | 哪一层没给答案 |
| `tcpdump` | 包到底有没有到 | `tcpdump -i any -nn port 443` | 有无 SYN、有无 RST、有无重传 |
| `openssl` | 证书与握手 | `openssl s_client -showcerts` | 链是否完整、协议版本、套件 |
| `iptables` | 规则与计数器 | `iptables -L -n -v --line-numbers` | **pkts 计数有没有涨** |
| `ip route get` | 从哪个口出去 | `ip route get 8.8.8.8` | via / dev / src |
| `ethtool` | 物理层 | `ethtool eth0` | Speed / Duplex / Link |
| `conntrack` | 连接跟踪表 | `conntrack -S` | 是否满、有无丢包 |

## 9.3 tcpdump

### 9.3.1 过滤语法

| 需求 | 写法 |
|---|---|
| 指定主机 | `host 10.0.0.11` |
| 指定网段 | `net 10.0.0.0/24` |
| 指定端口 | `port 443` |
| 源/目的端口 | `src port 443` / `dst port 80` |
| 指定协议 | `tcp` / `udp` / `icmp` / `arp` |
| 排除 | `not port 22` |
| 组合 | `host 10.0.0.11 and port 443` |
| 只看 SYN/FIN/RST | `'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'` |
| 只看 SYN | `'tcp[tcpflags] & tcp-syn != 0'` |
| 只看 RST | `'tcp[tcpflags] & tcp-rst != 0'` |
| 排除 SSH（避免抓到自己） | `not port 22` |
| HTTP 请求方法 | `'tcp[((tcp[12:1] & 0xf0) >> 2):4] = 0x47455420'`（GET） |

### 9.3.2 常用组合

```bash
# 抓指定主机的所有流量，不解析域名和端口名
tcpdump -i any -nn host 10.0.0.11

# 抓 443 端口，写文件供 Wireshark 分析（-s 0 抓完整包）
tcpdump -i any -nn -s 0 port 443 -w /tmp/cap.pcap

# 只看握手与挥手
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0 and host 10.0.0.11'

# 带时间戳、绝对序列号（分析重传必用）
tcpdump -i any -nn -S -tttt 'host 10.0.0.11 and port 80' -c 20

# 抓 ICMP（ping、traceroute、PMTUD 的"需要分片"报文）
tcpdump -i any -nn icmp

# 抓 ARP
tcpdump -i any -nn arp

# 抓 VLAN 标签
tcpdump -i any -nn -e vlan

# 边抓边看，只显示前 100 个包
tcpdump -i any -nn -c 100 'port 3306'

# 只在某个接口抓（any 抓不到某些虚拟设备的完整信息）
tcpdump -i eth0 -nn
```

**`-i any` 有个坑**：在 Linux 上它用的是伪设备，抓到的包可能显示不出完整的二层信息（MAC 地址），而且同一个包可能被抓到两次。查二层问题（ARP、VLAN）要用具体接口 `-i eth0`。

### 9.3.3 读包速记

| 抓到的现象 | 结论 |
|---|---|
| 只有 `[S]`，没有 `[S.]` | SYN 到不了对端：防火墙 DROP / 路由不通 / 对端不在 |
| `[S]` 后立刻 `[R]` | 端口没监听（RST 回应） |
| `[S.]` 后没有 `[.]` | 客户端异常；或服务端半连接队列满 |
| 大量重复 seq | 丢包导致重传 |
| `[R]` 出现在传输中 | 一方主动重置（应用崩溃、超时、中间设备） |
| `[F]` 只走一半 | 一方应用异常退出 |
| `flags [P.]` 但长度 0 | 保活探测或窗口探测 |
| `win 0` | 接收方处理不过来 |

**TCP flags 含义**：

| 标记 | 含义 |
|---|---|
| `[S]` | SYN |
| `[S.]` | SYN+ACK |
| `[.]` | ACK |
| `[P.]` | PSH+ACK（有数据） |
| `[F.]` | FIN+ACK |
| `[R]` | RST |
| `[R.]` | RST+ACK |

### 9.3.4 三个必须掌握的场景

**场景一：证明「不是我这条链路的问题」**

```bash
# 在自己机器上抓，看包到底有没有发出去 / 有没有回来
tcpdump -i any -nn host <对端IP> and port <端口>
```

- 有出无回 → 问题在对端或中间
- 有出有回但应用报错 → 应用层问题
- 根本没出 → 本机路由或防火墙

**场景二：判断丢包发生在哪一跳**

```bash
mtr -rw -c 50 <目标IP>
```

某一跳开始持续丢包、后面几跳也一样 → 丢包在那一跳之前。**注意：中间跳丢包但末跳不丢包是正常的**（ICMP 限速），只有末跳丢包才是真丢包。

**场景三：抓 HTTPS 的握手失败**

```bash
tcpdump -i any -nn -s 0 'host 1.2.3.4 and port 443' -w /tmp/tls.pcap
# 然后用 Wireshark 打开，看 ClientHello 里的 SNI、ServerHello 里的套件
# 或者直接看是不是 TCP 层就没建起来（那就是 007 册的事）
```

## 9.4 性能四要素

「网络慢」这四个字太笼统。所有网络性能问题都能拆成四个可测量的量。

| 要素 | 含义 | 怎么测 | 典型阈值 |
|---|---|---|---|
| **带宽** | 单位时间能传多少 | `iperf3`、网卡计数器 | 利用率 > 70% 要关注 |
| **时延** | 一个包来回多久 | `ping`、`mtr` | 同机房 < 1ms，跨省 20–40ms |
| **丢包** | 多少包没到 | `mtr`、`netstat -s` | 千分之一以上就有感知 |
| **抖动** | 时延的波动 | `mtr` 的 stddev | 实时业务敏感 |

**四者的关系**：带宽够但时延高 → 用户感觉"卡"；时延低但丢包 → 用户感觉"时快时慢"；带宽和时延都好但抖动大 → 视频会议卡顿。

### 9.4.1 带宽不是唯一指标

```bash
# 看网卡实际速率与错误
ethtool eth0 | grep -E "Speed|Duplex"
ethtool -S eth0 | grep -Ei "error|drop|discard"

# 看实时流量
sar -n DEV 1 5
iftop -i eth0
nload eth0

# 看丢包与错误（累计值）
ip -s link show eth0
# RX: bytes packets errors dropped overrun mcast
# 关注 errors 和 dropped 是否在增长
```

**「带宽跑不满」的常见原因**（按概率）：

| 原因 | 判断 |
|---|---|
| 单条 TCP 连接受窗口/RTT 限制 | 多并发能跑满，单条不行 → 正常，加并发或用多连接 |
| 双工不匹配 | `ethtool` 显示 Half，或 errors 增长 |
| 网卡/交换机端口协商成 100M | `ethtool` 看 Speed |
| 中间设备限速 | 换路径测，或看 QoS 配置 |
| 磁盘或应用是瓶颈 | `iostat`、CPU 使用率 |

**单条 TCP 连接的吞吐上限 = 窗口大小 / RTT**。RTT 40ms、窗口 64KB 时，单连接最多 1.6MB/s，跟带宽多大完全无关。这是「我明明有千兆带宽，为什么传文件只有 1.6MB/s」的答案。

## 9.5 MTU 与 PMTUD

### 9.5.1 MTU 与 MSS

| 概念 | 含义 | 典型值 |
|---|---|---|
| MTU | 链路层一次能传的最大帧载荷 | 以太网 1500 |
| MSS | TCP 一次能传的最大数据段 | MTU - 40（IP 头 20 + TCP 头 20）= 1460 |

**MTU 是链路的属性，MSS 是 TCP 协商出来的。** TCP 在握手时会互相通告自己的 MSS，取较小值。

### 9.5.2 PMTUD 黑洞：最隐蔽的一类故障

**现象**：能 ping 通、能打开网页，但**上传大文件、大查询、拉镜像时卡死或超时**。

**机制**：

```text
① 发送方按自己的 MTU（1500）发了一个 1500 字节的包
② 中间某条链路 MTU 只有 1400，路由器应该回一个 ICMP "需要分片"（Type 3 Code 4）
③ 但很多防火墙/安全设备把 ICMP 全禁了 → 这个通知到不了发送方
④ 发送方不知道要减小包，一直重传，永远发不过去
```

这就是 **PMTUD 黑洞**：路径 MTU 发现机制被 ICMP 拦截破坏了。

### 9.5.3 探测

```bash
# 从大到小试，找到能通过的最大值（-M do 禁止分片）
ping -M do -s 1472 -c 2 目标IP      # 1472+28=1500
ping -M do -s 1400 -c 2 目标IP
ping -M do -s 1200 -c 2 目标IP

# 输出 "Frag needed and DF set" 说明这一档过不去
```

`-s` 的值 + 28（IP 头 20 + ICMP 头 8）就是实际包大小。

**在容器/隧道环境里必须从容器内部测**，宿主机的 MTU 和容器的不一样：

```bash
kubectl exec <pod> -- ping -M do -s 1400 -c 2 <另一个pod IP>
docker exec <容器> ping -M do -s 1400 -c 2 8.8.8.8
```

### 9.5.4 处置

| 场景 | 做法 |
|---|---|
| 能改中间链路 | 统一 MTU（推荐 1500，Overlay 环境统一 1450） |
| 不能改中间链路 | 在端点下调 MTU：`ip link set eth0 mtu 1400` |
| 临时缓解 | 开 TCP MSS clamping：`iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu` |
| 排查用 | 放行 ICMP Type 3 Code 4（很多防火墙默认拦） |

**MSS clamping 是隧道环境的标准做法**：在隧道的两端把 MSS 强行改小，避免依赖 PMTUD。

## 9.6 容量与监控

### 9.6.1 关键指标

| 指标 | 命令 | 关注点 |
|---|---|---|
| 连接数 | `ss -s` | 与 QPS 是否匹配 |
| 各状态分布 | `ss -tan \| awk ...` | CLOSE_WAIT / TIME_WAIT 是否堆积 |
| 队列溢出 | `netstat -s \| grep -i overflow` | 非零且增长 = 应用 accept 慢 |
| conntrack | `cat /proc/sys/net/netfilter/nf_conntrack_count` | 接近 max 就危险 |
| 网卡错误 | `ethtool -S eth0 \| grep -i err` | 持续增长 = 物理层问题 |
| 重传率 | `ss -tin \| grep retrans` / `netstat -s \| grep retrans` | 超过 1% 要查 |
| 带宽利用率 | `sar -n DEV 1 5` | 持续 > 70% 要扩容 |

### 9.6.2 三个容量天花板

```text
① 带宽：网卡速率 / 交换机端口速率
② PPS：小包场景下，CPU 处理包的能力（通常 100 万 PPS 是单核瓶颈）
③ 连接数：端口范围（约 2.8 万）+ 内存（每个连接占 fd 和 buffer）
```

**PPS 常被忽略**：1Gbps 带宽传 1500 字节的大包是 8 万 PPS，传 64 字节的小包是 **148 万 PPS**。所以「带宽只用了 10% 但 CPU 打满」的典型原因是小包太多（DDoS、DNS 查询、游戏心跳）。

### 9.6.3 软中断

高 PPS 场景下，网络包的处理会打满 CPU 的 `si`（软中断）。

```bash
top                        # 看 si 这一列
mpstat -P ALL 1            # 看每个核的软中断分布
cat /proc/interrupts | grep eth0    # 网卡中断落在哪个核

# 如果所有包都落在 CPU0，就是单核瓶颈
# 调整：开多队列 + RPS/RSS
ethtool -l eth0            # 看队列数
ethtool -L eth0 combined 8 # 设成 8 个队列
```

**`si` 高但 CPU 总利用率不高**，是典型的网络处理瓶颈，不是应用问题。

## 9.7 故障剧本

每个剧本都是「现象 → 判据 → 命令 → 结论」的固定套路，可以直接做 RCA 骨架。

### 剧本一：网站打不开，用户报 502

```bash
curl -v https://www.example.com/           # 复现，看状态码
# ① 在后端机器上确认服务
ss -lntp | grep 8080
# ② 从 LB 测后端
nc -vz 10.0.0.11 8080
curl -H 'Host: www.example.com' http://10.0.0.11:8080/health
# ③ 看 LB 日志的 upstream 变量
tail -100 /var/log/nginx/error.log | grep upstream
```

| 结果 | 结论 |
|---|---|
| 后端端口不在听 | 服务挂了，看应用日志 |
| 端口在听但 nc 不通 | 中间有防火墙（007 册 7.8） |
| 健康检查返回 5xx | 后端应用问题，看应用日志 |
| `$upstream_status` 为空 | 根本没连上，是连接层问题 |

### 剧本二：连接超时，但 ping 通

```bash
ping -c 4 1.2.3.4          # 通
nc -vz 1.2.3.4 443         # timed out
tcpdump -i any -nn host 1.2.3.4 and port 443   # SYN 发出去了吗？有回应吗？
```

| 抓包结果 | 结论 |
|---|---|
| 只有出向 SYN，无回应 | 中间防火墙 DROP（不是 REJECT，所以不回 RST） |
| 有 SYN 有 RST | 对端拒绝，但 nc 应该报 refused，检查是否有中间设备伪造 RST |
| 根本没出 | 本机路由或本机防火墙 |

### 剧本三：服务时好时坏，高峰必坏

```bash
ss -s
ss -tan | awk 'NR>1 {++s[$1]} END {for (k in s) print k, s[k]}' | sort -k2 -rn
netstat -s | grep -Ei "overflow|drop|retrans"
cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
```

| 发现 | 结论 |
|---|---|
| `CLOSE_WAIT` 上千 | 应用没 close，代码问题（002 册 2.5.3） |
| 队列溢出计数增长 | accept 太慢或 backlog 太小 |
| conntrack 接近 max | 表满，新连接被丢（007 册 7.2） |
| 大量重传 | 链路丢包，`mtr` 定位 |

### 剧本四：改了 DNS 不生效

按 003 册 3.7 的六步走，核心是**先确认权威上改了没**：

```bash
dig @ns1.yourdns.com 域名          # 权威上有新记录吗
dig @8.8.8.8 域名                  # 公共 DNS 拿到了吗
dig 域名                            # 本地呢
getent hosts 域名                  # 系统层面呢
cat /etc/hosts                     # 有没有写死
```

### 剧本五：证书报错，但浏览器正常

```bash
openssl s_client -connect 域名:443 -servername 域名 -showcerts </dev/null
# 数一下返回了几张证书
```

只有一张 → 缺中间证书。这正是「浏览器正常、curl 和小程序报错」的原因（005 册 5.4.3）。

### 剧本六：能 ping 通，传大文件卡死

```bash
ping -M do -s 1472 -c 2 目标IP     # 1500 能过吗
ping -M do -s 1400 -c 2 目标IP
ip link show eth0 | grep mtu
```

在 1400 能过、1472 不能过 → MTU 问题。容器/隧道环境里 MTU 通常不是 1500（009 册 9.5）。

### 剧本七：VIP 漂移失败或双主

```bash
# 两台机器都执行
ip addr show eth0 | grep <VIP>
systemctl status keepalived
journalctl -u keepalived -n 50 | grep -i "state\|transition"
tcpdump -i eth0 -nn vrrp -c 10
```

两台都有 VIP → 脑裂（006 册 6.6.4）。只有一台有但不通 → 看 ARP 是否更新，触发免费 ARP。

### 剧本八：K8s 里 Pod 通、Service 不通

```bash
kubectl get endpoints <svc>          # 有没有后端
kubectl get pods -o wide             # Pod 状态与 IP
kubectl exec <pod> -- nslookup <svc>
iptables -t nat -L KUBE-SERVICES -n | head    # kube-proxy 规则在不在
systemctl status kube-proxy
```

`Endpoints` 为空是第一位原因——selector 写错或 readinessProbe 一直失败（008 册 8.3.3）。

## 9.8 排障纪律

| 纪律 | 原因 |
|---|---|
| **一次只改一个变量** | 同时改三处，好了不知道是哪处起的作用，坏了不知道是哪个导致的 |
| **改之前先备份** | `iptables-save`、`nginx -T > bak.conf`、`cp 配置 配置.bak` |
| **留证据** | 抓包文件、命令输出、时间点。事后复盘靠这些，不靠记忆 |
| **不在生产上试** | 「我 ping 一下」「我重启试试」都是事故来源 |
| **先止损再定位** | 用户还在受影响时，优先回滚/切流，根因事后查 |
| **记录时间线** | 几点几分做了什么、现象有什么变化。RCA 全靠这个 |

### 9.8.1 一个反直觉的建议

**排障时先写下你的假设，再去验证。**

不写假设的后果是：查了半小时，忘了最初怀疑什么，变成漫无目的地敲命令。写下来就变成「假设 A → 验证 → 排除 → 假设 B」，每一步都有痕迹，即使最后没找到根因，也能把范围缩到最小。

## 9.9 七个坑

| # | 坑 | 现象 | 处置 |
|---|---|---|---|
| 1 | 从 `ping` 开始反复重试 | 查了半天没进展 | 先 `ip neigh`，先 `ss -lntp` |
| 2 | 把 `refused` 当网络问题 | 查防火墙查了很久 | `refused` = 服务没起，网络是通的 |
| 3 | 用 `-i any` 抓二层 | 看不到 MAC，包重复 | 用具体接口 `-i eth0` |
| 4 | 中间跳丢包就断定丢包 | 误判 | 只有末跳丢包才是真丢包 |
| 5 | 只看带宽不看 PPS | 带宽 10% 但 CPU 满 | 小包场景看 PPS 和软中断 |
| 6 | 单连接测带宽 | 以为带宽不够 | 单连接受窗口/RTT 限制，多并发测 |
| 7 | 改配置不备份不留回退 | 把自己关在外面 | 改前 `iptables-save`，留定时恢复 |
