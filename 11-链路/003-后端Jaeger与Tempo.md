## 3.1 后端的职责：存 span、按 trace_id 还原

追踪后端做三件事：**接收 span**（OTLP）、**按 trace_id 聚合并存储**、**按 trace_id 查询并还原调用树**。

一个关键的设计分野：追踪后端**不是全文搜索引擎**——日常查询入口是"我知道 trace_id（从日志/告警跳过来），还原这棵树"。需要"按属性搜索历史 trace"的场景（审计、异常模式分析）是附加能力，各后端支持度不同——选型时先确认你的查询习惯（003 §3.4）。

spanmetrics 是后端的增值共性：**把 span 聚合成 RED 指标**（每服务/每接口的请求率、错误率、耗时直方图）回吐给 Prometheus——链路与指标由此互相成全（000 §0.3 的握手落地）。

## 3.2 Jaeger：架构与存储选择

Jaeger 是老牌 CNCF 追踪后端（组件：collector → 存储 → query）：

| 存储 | 特点 | 适用 |
|---|---|---|
| Elasticsearch/OpenSearch | 支持属性**搜索** | 已有 ES 运维经验、需要按属性查历史 |
| Cassandra | 写入吞吐高 | 大规模、按 ID 查为主 |
| ClickHouse | 新兴、压缩好 | 大体量 + 想要 SQL 分析 |

运维要点：ES 存储时索引按天滚动与 ILM 思路同「日志」002（ES 磁盘水位与 red/yellow 判读直接适用）；Jaeger 1.35+ 原生接收 OTLP——**Collector 直发 Jaeger，不再需要 Jaeger agent 中转**（旧架构注记）。查询能力是它的相对优势：按 service、operation、tags、耗时搜索历史 trace。

## 3.3 Tempo：对象存储与 TraceQL

Tempo 的设计哲学：**不做重索引，trace 压缩后直接进对象存储**——用"查 trace_id 精确还原"换存储成本的大幅下降：

- **写入**：span 按.trace_id 分块压缩，直写 S3/GCS/MinIO——存储近无限且便宜；
- **查询**：两种方式——①按 trace_id 精确还原（主要用法：从日志/告警跳过来）；②TraceQL 按属性/结构查询（v2 起能力增强，但有吞吐上限意识）；
- **单机可起步**：单体模式 + 本地盘即可跑通，与 Loki 的部署心智一致。

TraceQL 速览：

```traceql
{service.name="order" && status=error}          # 按属性查
{resource.service.name="order" && duration > 2s}  # 慢调用
```

运维纪律：**Tempo 的查数能力不及 ES 全文**——"全局搜某关键词出现在哪些 trace"不是它的设计目标，那类需求回「日志」册（日志正文本来就该搜得到）。

## 3.4 对比与选型

| 维度 | Jaeger（+ES） | Tempo |
|---|---|---|
| 属性搜索历史 trace | ✅ 强 | ⚠️ TraceQL，吞吐有限 |
| 按 trace_id 还原 | ✅ | ✅ |
| 存储成本 | 高（索引） | **低（对象存储）** |
| 运维复杂度 | ES 集群运维 | 对象存储 + 单组件 |
| 生态 | 独立 UI + 插件 | **Grafana 同屏**（与 Loki/Mimir 一家） |

决策口诀：**已用 Grafana 全家桶 + 查询以"从日志/告警跳转"为主 → Tempo**；**需要属性搜索、已有 ES 集群与经验 → Jaeger**。000 §0.5 的口径在此完整化。两者都吃 OTLP，切换成本在后端侧——前向兼容靠 OTel 标准兜底。

## 3.5 保留策略与成本

链路数据是三大支柱里**单条最大、采样后总量可控**的一类。两把成本旋钮：

1. **采样率**决定进来多少（005 册）；
2. **保留期**决定留多久：Jaeger 按 ES ILM 删（与「日志」002 §2.5 同机制）；Tempo 按 object store 生命周期或 compactor 配置。

经验值：生产 trace 保留 7–14 天已覆盖绝大多数排障场景（更老的排证据"当时有没有留"决定——与日志保留分级思想一致）。成本核算公式：**日 span 数 × 平均 span 大小 × 保留天数 × (1+副本/冗余)**——采样率与保留期两个旋钮联动调节。

## 3.6 六个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | Tempo 没配对象存储容量规划 | 写入失败=trace 丢 | 容量按采样率估算并监控 |
| 2 | ES 集群与日志共用 | 相互拖累、水位连坐 | 独立集群或独立索引+独立资源 |
| 3 | 保留期默认值直接上生产 | 成本失控或排查期不够 | 业务签字定 7–14 天 |
| 4 | 按属性搜索当主用法（Tempo） | 查询超时与吞吐受限 | 主路径=trace_id 跳转 |
| 5 | 服务图/指标没启用 | 三支柱握手缺失 | 开 spanmetrics/metrics-generator |
| 6 | 升级后老 trace 查不到 | 保留期认知错位 | 查证后端实际保留天数 |

第 2 条展开：**追踪 ES 与日志 ES 共用集群**是最常见的"省资源"决策，也是最危险的——两者的写入曲线不同步（日志全天均匀、trace 随流量脉冲），峰值叠加会互相触发水位；且故障域连坐：日志集群抖动=链路同时失明。独立部署（哪怕小规格）是 SRE 向的默认建议。
