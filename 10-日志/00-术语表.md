# 00 术语表

> **这一文档回答**：某个词是什么意思、两个长得像的概念差在哪、「只知道现象、不知道该翻哪一册」时往哪走。  
> **怎么用**：三种查法——按名字（下面按册分组）、按英文或缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和命令回对应册；这里只保证你「认得出、分得清、找得到」。

## 000 日志全貌

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 可观测性 | observability | 从系统外部输出判断内部状态的能力。指标、日志、链路是三根支柱 |
| 三支柱 | three pillars | 指标（出告警）→ 日志（解释原因）→ 链路（定位跨服务路径） |
| 集中日志 | centralized logging | 把散在各机器的日志收拢到一个可搜索的地方——本套的主线 |
| 结构化日志 | structured logging | 日志按 JSON 等固定字段输出，机器可解析。治理的起点（005） |
| EFK | Elasticsearch + Filebeat + Kibana | 本套主线的技术栈缩写 |
| ELK | Elasticsearch + Logstash + Kibana | 老称呼：Logstash 做采集，如今采集多换成轻量的 Filebeat |
| 采集器 | log shipper / collector | 把日志从产生地搬运到存储端的组件：Filebeat / Promtail / Alloy |
| 倒排索引 | inverted index | 从「词」反查「哪些文档含它」的结构——ES 搜索快的根基 |
| 保留策略 | retention | 日志留多久、过期怎么清。成本治理的第一杠杆 |
| 近实时 | near real-time, NRT | 写入后约 1 秒才可搜（refresh 机制）——不是实时，也别当实时用 |

## 001 采集 Filebeat

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| input | input | Filebeat 的输入段：盯哪个文件/容器/端口 |
| harvester | harvester | 单个文件的收割协程：逐行读、发往队列。一文件一 harvester |
| spooler | spooler | 聚合事件的发送队列，攒一批再输出 |
| registry | registry | 断点账本：记录每个文件读到哪。**续传与不丢的机制** |
| 多行合并 | multiline | 把 Java 异常栈的多行并成一条事件。不配它，栈被拆成碎片 |
| 字段加工 | fields / processors | 采集时附加主机、环境、服务名等元数据 |
| DaemonSet | — | K8s 里每节点跑一个采集 Pod 的形态。**容器日志采集的标准姿势** |
| 容器元数据 | container metadata | 采集器从容器运行时补出的 k8s pod/namespace/镜像信息 |
| 背压 | backpressure | 下游（ES）写不进时，采集端暂停读取——不丢日志的代价是延迟 |
| Promtail | Promtail | Loki 生态的采集器（004）；官方继任者为 Grafana Alloy |
| Alloy | Grafana Alloy | Grafana 生态统一采集器，Promtail 的官方继任者 |

## 002 Elasticsearch 入门

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 索引 | index | 日志的存放单位，通常按天/按量滚动（如 `logs-2026.11.01`） |
| 文档 | document | 一条日志在 ES 里的形态（JSON） |
| mapping | mapping | 字段的类型声明：决定能不能搜、怎么搜 |
| text / keyword | — | text 分词做全文匹配；keyword 整串精确匹配/聚合。**配错是搜不到的头号原因** |
| 分词 | analyzer | 把文本切成词的规则。中文需要 IK 等分词器，默认按单字切 |
| 分片 | primary shard | 索引的水平切分单元。数量建索引时定，事后改要重建 |
| 副本 | replica | 分片的只读拷贝：高可用与读加速。**关副本省磁盘是高危动作** |
| refresh | refresh | 内存缓冲刷成可搜段的动作（默认 1s）——「近实时」的来源 |
| translog | transaction log | 写入先落 translog 再刷段——崩溃恢复的凭据 |
| 段合并 | segment merge | 后台把小段并大段。占 IO，删除的文档在合并时真正消失 |
| ILM | Index Lifecycle Management | 索引生命周期：hot → warm → cold → delete 自动流转 |
| 磁盘水位 | disk watermark | 85% 不再分配 / 90% 迁移分片 / **95% 索引只读**——ES 变只读的元凶 |
| 集群健康 | cluster health | green 全部就位 / yellow 副本缺 / **red 主分片缺** |

## 003 Kibana 查询

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 数据视图 | data view | Kibana 的查询入口：声明看哪些索引、以哪个字段当时间轴 |
| Discover | Discover | 逐条翻日志的界面。排障主战场 |
| KQL | Kibana Query Language | Kibana 默认查询语法：`field: value`，可 and/or/not 组合 |
| Lucene 语法 | — | KQL 之外的经典语法（正则、模糊更强），切换开关在搜索框 |
| exists 查询 | exists: field | 查"有没有这个字段"——找异常日志利器 |
| 聚合 | aggregation | 分组统计：错误率、TOP IP、按服务计数 |
| 仪表盘 | dashboard | 多张可视化拼成的观测面。告警的配套观测 |
| 保存对象 | saved object | 存在 Kibana 里的查询/视图/仪表盘，可导出共享 |

## 004 Loki 轻量路线

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| Loki | Grafana Loki | 只索引**标签**不索引正文的日志库——便宜，代价是查询要先圈标签 |
| 标签 | label | Loki 的索引键（如 `service`、`env`）。**设计错了查不动** |
| 基数 | cardinality | 一个标签的取值个数。**基数爆炸是 Loki 的头号事故** |
| LogQL | LogQL | Loki 的查询语言：`{label} |= "文本" | 统计管道` |
| chunk | chunk | 日志按标签分组压缩后的存储块 |
| Promtail | Promtail | Loki 配套采集器（抓文件、提标签），继任者为 Alloy |
| 管道阶段 | pipeline stages | 采集端对日志行的解析/提取/打标流程 |
| 单二进制 | monolithic mode | Loki 最简部署形态——中小规模的起步姿势 |

## 005 日志规范与治理

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| JSON 日志 | JSON logging | 每行一个 JSON 对象——字段天然可解析，采集零成本 |
| 日志级别 | log level | DEBUG/INFO/WARN/ERROR。**ERROR 要与告警语义绑定** |
| request_id | — | 一次请求的唯一编号，贯穿各服务——跨服务排障的钥匙 |
| trace_id | — | 链路追踪的 ID。与 request_id 合一或映射（000 §0.1 的第三支柱衔接） |
| 脱敏 | data masking | 密码/token/证件号出日志前打码——合规与泄漏防线 |
| 采样 | sampling | 只记录部分请求的日志。高流量下控成本的刀 |
| 冷热分层 | hot/warm tiering | 新日志在快盘（常查），旧日志挪慢盘（偶查）——ILM 的落地形态 |
| 日志风暴 | log storm | 某服务异常时狂打日志，把存储与采集带宽打爆 |

## 006 排障与治理

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 四段取证 | — | 产生 → 采集 → 存储 → 查询，日志链路的排障分段法（006 §6.1） |
| 采集断流 | — | 文件在写但 Kibana 没新数据——registry、权限、输出三处查 |
| 只读锁 | read_only_allow_delete | 磁盘过 95% 后 ES 给索引加的锁——清理后要手动解 |
| 写入拒绝 | 429 / es_rejected_execution | 批量队列打满，ES 把写入弹回来 |
| 查询超时 | query timeout | 范围太大/分片太多——缩小时间窗或加条件 |
| 幂等重放 | — | registry 丢失后从checkpoint重收——**下游要能按 ID 去重** |

## 缩写速查

| 缩写 | 全称 | 意思与出处 |
| --- | --- | --- |
| EFK | Elasticsearch + Filebeat + Kibana | 本套主线栈（000） |
| ELK | Elasticsearch + Logstash + Kibana | 老称呼，采集层已多被 Filebeat 取代（000） |
| ES | Elasticsearch | 存储与搜索引擎（002） |
| ILM | Index Lifecycle Management | 索引生命周期管理（002） |
| JSON / NDJSON | JavaScript Object Notation / Newline-Delimited JSON | 结构化日志格式 / 逐行 JSON（005） |
| KQL | Kibana Query Language | Kibana 查询语法（003） |
| OTel | OpenTelemetry | 可观测性数据采集标准，链路支柱的载体（000 注记） |
| RBAC | Role-Based Access Control | Kibana/Harbor 等的权限模型（003 注记） |
| RWO | — | 见「容器」术语表：Read-Write-Once，本册不涉及 |
| WORM | Write Once Read Many | 一次写多次读的合规存储——日志归档的可选形态（005 注记） |

## 最容易混的 14 对

| 容易混 | 一句话差别 | 怎么确认 | 册 |
| --- | --- | --- | --- |
| Logstash vs Filebeat | 重型处理管道 / 轻量采集搬运 | 占内存几百 MB vs 几十 MB | 000 / 001 |
| Elasticsearch vs Loki | 全文倒排索引 / 只索引标签 | 查正文关键词快=ES；先圈标签才快=Loki | 002 / 004 |
| text vs keyword | 分词全文匹配 / 整串精确匹配 | mapping 里的 type；搜不到先查它 | 002 |
| 分片 vs 副本 | 水平切分的主体 / 主体的只读拷贝 | `_cat/shards` 里 p=主 r=副 | 002 |
| refresh vs flush | 缓冲变可搜 / 段真正落盘 | 近实时来自 refresh；丢数据看 translog | 002 |
| ILM vs 保留策略 | 自动流转机制 / "留多久"的业务决定 | ILM 的 delete 阶段执行保留策略 | 002 / 005 |
| KQL vs Lucene 语法 | Kibana 默认简语法 / 经典强语法 | 搜索框右侧的切换开关 | 003 |
| Promtail vs Alloy | Loki 传统采集器 / 官方继任者 | 新部署选 Alloy，存量 Promtail 照常维护 | 001 / 004 |
| 标签 vs 正文（Loki） | 索引键 / 只能顺序扫的内容 | `{}` 里的是标签，`\|= "…"` 匹配的是正文 | 004 |
| 结构化 vs 非结构化日志 | JSON 字段 / 自由文本 | 采集端要不要解析管道 | 005 |
| request_id vs trace_id | 业务请求编号 / 追踪系统 ID | 二者合一或映射，别各发各的 | 005 |
| 冷热分层 vs 归档 | 同集群挪盘 / 出集群进对象存储 | 查询频率决定去向 | 002 / 005 |
| stdout vs 文件日志（应用侧） | 容器时代的标准 / 传统常驻的习惯 | `docker logs`/`kubectl logs` 能看到的是 stdout | 005 |
| 采集丢失 vs 查询查不到 | 数据真没进来 / 进来了没搜到 | 先查存储端有没有原始文档 | 006 |

## 按症状反查

| 现象 | 大概是 | 去哪 |
| --- | --- | --- |
| 文件在涨，Kibana 没新数据 | 采集断流：registry / 输出 / 权限 | 006 §6.2 |
| Filebeat 起了但 output 报错 | ES 凭据 / 地址 / 证书 | 001 §1.6 |
| ES 集群变只读 | 磁盘过 95% 水位锁 | 002 §2.7 / 006 §6.3 |
| 集群 health red | 主分片未分配 | 002 §2.6 / 006 §6.3 |
| 写入报 429 rejected | 批量队列打满，下游跟不上 | 006 §6.3 |
| 查询一直超时 | 时间窗太大 / 分片数失控 | 003 §3.2 / 006 §6.4 |
| 搜中文搜不到 | 没装/没配 IK 分词，text 用了默认分词 | 002 §2.4 |
| 字段搜不到但日志里有 | mapping 类型错 / 未建 data view 字段 | 002 §2.4 / 003 §3.1 |
| Java 异常栈被拆成几十条 | 没配 multiline 多行合并 | 001 §1.4 |
| Kibana 时间轴没数据 | timestamp 字段选错 / 时区错 | 003 §3.1 |
| Loki 查询极慢或报错 | 标签基数爆炸 / 查询没圈标签 | 004 §4.3 |
| 容器日志重复采集 | 重启后 registry 失效 + 无幂等去重 | 001 §1.8 / 006 §6.2 |
| 日志里出现明文密码 | 没脱敏 | 005 §5.4 |
| 存储账单翻倍 | 级别失控 / 保留期没定 / DEBUG 上生产 | 005 §5.6 |
