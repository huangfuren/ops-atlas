## 6.1 容量公式：worker × connections，还有 nofile 天花板

接入层能扛多少并发，三层天花板从里到外：

```plain
单 worker 连接数（worker_connections，默认 512/1024，看版本）
    × worker 数（worker_processes）
        ≤ 系统 fd 上限（worker_rlimit_nofile 与 OS nofile）
```

一条最容易被忽略的换算：**`worker_connections` 数的是"每个 worker 的所有连接"**——代理场景下一个请求占**两条**连接（客户端↔Nginx、Nginx↔后端），静态场景占一条。所以反向代理场景的真实并发 ≈ `worker_connections × workers ÷ 2`。计算示例：4 worker × 4096 ÷ 2 = **8192 并发请求**。

系统侧的天花板：`worker_rlimit_nofile 65535;`（Nginx 自己设 fd 上限）要 ≤ OS 的 `ulimit -n`（systemd 下还要看 `LimitNOFILE`）——**三个数一起看，取最小值才是真实容量**。006 的调优从算账开始，不是从改参数开始。

## 6.2 worker_processes 与 CPU：auto 起步

`worker_processes auto`（= CPU 核数）几乎总是对的，原因在 000 §0.3 的模型：worker 是 CPU 密集的事件循环，多于核数的 worker 只增加上下文切换。两个例外场景：

- **SSL 密集**：TLS 握手吃 CPU，核数仍是瓶颈，auto 不变，靠会话复用（004 §4.5）降握手量；
- **多网卡/NUMA 大机器**：可以按网卡中断绑定调 worker 数与亲和（`worker_cpu_affinity`）——这是进阶项，先确认瓶颈真在 CPU。

调优的观察手段：`top` 看 worker 进程的 `%CPU`——**所有 worker 接近 100% = CPU 瓶颈实锤**，才轮到后续的 gzip/SSL 优化（6.8 的压测验证）。

## 6.3 静态文件加速：sendfile / tcp_nopush / tcp_nodelay

静态文件（图片、下载包）是 Nginx 的强项，三个开关的组合拳：

```nginx
sendfile on;           # 文件直接从页缓存进网卡，跳过用户态拷贝（零拷贝）
tcp_nopush on;         # 配合 sendfile：等数据包攒满 MTU 再发（大文件吞吐↑）
tcp_nodelay on;        # 小包立即发（交互型响应延迟↓）——两者并不冲突
```

读法：`sendfile` 是根基（省两次内存拷贝），`tcp_nopush` 管大文件的包满再发，`tcp_nodelay` 管小响应的即时性——Nginx 默认值已是推荐组合，**确认开着即可，别乱关**。静态资源的另一个大头是**过期头**（`expires 7d` 让浏览器/CDN 缓存，从源头减流量）——它对"扛压"的贡献常常大于所有其他调优之和，因为最好的请求是不发生的请求。

## 6.4 gzip：压什么、不压什么、级别怎么选

文本类响应开启 gzip，传输体积降 60–80%：

```nginx
gzip on;
gzip_comp_level 5;               # 1-9：5 是性价比拐点，更高只费 CPU 少省体积
gzip_min_length 1k;              # 太小的别压（头部开销反噬）
gzip_types text/plain text/css application/json application/javascript
           application/xml image/svg+xml;    # 默认只有 text/html，必加
gzip_vary on;                    # 告诉缓存：按 Accept-Encoding 区分版本
```

三条纪律：**`gzip_types` 必须显式加 JSON/JS/CSS**（默认清单短得可怜，API 全裸奔）；**图片/视频/已压缩文件绝不压**（JPEG/MP4/zip 自己就是压缩格式，再压只烧 CPU 不减体积）；**级别 5 起步**——压缩级别翻倍 CPU 翻倍而体积只降几个点，6.8 的压测会告诉你这个 CPU 花得值不值。

## 6.5 客户端长连接：keepalive_timeout 与 keepalive_requests

HTTP/1.1 的长连接让浏览器复用 TCP 连接跑多个请求（省握手），两个参数：

```nginx
keepalive_timeout 65s;       # 空闲多久关闭（默认 75s，65 均衡）
keepalive_requests 1000;     # 一条连接最多服务多少请求（防单连接长期占用）
```

调它的动机通常是反向的：**入口层高并发时，每条连接占 fd 与内存（6.1 的账），keepalive_timeout 越长，僵尸连接越多**——所以高并发入口反而会**调短**它（如 15s），让连接快速回收。这不是"性能参数越大越好"的反例合集里最典型的一条：长连接省的是握手 CPU，费的是连接内存，天平向哪边倾斜取决于请求密度——压测说话（6.8）。

## 6.6 upstream 长连接：keepalive 池 + Connection 头清空

003 §3.6 已给完整配方，本册从性能账的角度复核它：**到后端每秒上千次 TCP 握手的开销（CPU + 延迟）全部省掉**，这是代理场景收益最大的单项优化。两段配置必须成对（漏一段等于没配）：

```nginx
upstream app {
    server 10.0.1.11:8080;
    keepalive 64;                        # 每 worker 的空闲连接池
}
server {
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";  # 清掉 close
    }
}
```

验证：后端 `ss -s` 或应用连接池指标看 TCP 连接数——**稳定在池规模附近（不再随 QPS 频繁建断）**即生效。这个优化的位置放最后压测也行：它几乎零风险纯收益，可以最先上。

## 6.7 全局基线：超时与缓冲的默认值管理

调优的另一半是"别乱调"——超时与缓冲（002 §2.5/2.6）的默认值是护栏，**改它们的理由要能写进配置注释**。推荐的全局基线管理法：

```nginx
http {
    # —— 基线（全局护栏，收紧优先）——
    proxy_connect_timeout 10s;     # 建连 60s 太宽：后端活着 10s 足够
    proxy_read_timeout    60s;     # 全局保持默认
    proxy_buffer_size     8k;

    # —— 例外（单独 location 单独放行）——
    location /api/report/ {         # 报表类慢接口
        proxy_read_timeout 300s;
    }
}
```

这条管理法与「CICD」007 的发布观同源：**全局默认是护栏，例外是显式登记的债务**——超时清单定期 review（002 §2.9 的同款提醒），每个放行的例外都该有"为什么不能快"的答案。

## 6.8 压测方法：wrk 基本用法、带监控压测

调优没有压测就是玄学。wrk 的基本用法：

```bash
wrk -t4 -c200 -d30s --latency http://app.example.com/
#      │   │     └─ 持续 30 秒，输出延迟分布
#      │   └─ 200 并发连接
#      └─ 4 个线程（驱动连接，不是 CPU 核数）
```

压测的三条方法论：

1. **压对层**：测 Nginx 静态/代理能力就压 Nginx 能直接回答的 URL（静态文件、轻接口）；测"整链路容量"则压真实业务接口——两层结论不能混用；
2. **带监控压**：「监控」册的口径——压测时盯着 CPU（worker 顶格？）、内存、网络带宽、后端水位。**哪层先到顶，瓶颈就在哪层**——"Nginx 慢"的结论必须由证据支撑；
3. **压测机不在被压机上**：同机压测连网络栈都在抢资源，数字没有意义。

安全线：压生产 = 变更（流量会打到后端与数据库），走「CICD」007 的窗口与知会流程；**压测试环境 + 按比例折算**是更常见的姿势。

## 6.9 调优的验证闭环：改前基线 → 改一项 → 对比

把 6.1–6.8 串成工作流，核心纪律是**一次只改一项**（「Linux」009 册的三纪律之一在这里同样适用）：

```plain
① 记录基线：wrk 压测数据 + 当时的关键配置快照
② 改一项：如 keepalive_timeout 75s → 15s
③ 同条件重压：同参数同环境（CPU/网络/后端状态尽量可比）
④ 对比：RPS / 延迟分布 / CPU —— 有明确收益才保留，无收益回滚
⑤ 下一个
```

多数调优的结局是**回到默认**——Nginx 的默认值经过二十年的打磨，乱调的收益常常是负的。真正能带来数量级改善的从来不是参数，是**架构决策**：加缓存（不发生的请求最快）、上 CDN（静态流量出门）、拆热点接口——参数调优是在架构对了之后磨最后 30% 的活。

## 6.10 八个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 不算账直接调参 | 三个天花板里最矮的没动 | 6.1 先算账 |
| 2 | gzip 压图片视频 | 纯烧 CPU | types 精确清单（6.4） |
| 3 | keepalive 越长越好 | 僵尸连接占 fd | 按请求密度调短 |
| 4 | upstream keepalive 漏半段 | 等于没配 | 两段成对（6.6） |
| 5 | 无 timeout 的压测长跑 | 僵尸连接堆积 | wrk -d 必带 |
| 6 | 同机压测 | 数字失真 | 独立压测机 |
| 7 | 一次改五个参数 | 收益归因失败 | 一次一项（6.9） |
| 8 | 把后端慢当 Nginx 慢 | 方向错误白忙 | urt 字段分锅（005 §5.2） |

第 8 条展开，它是"性能问题"工单的第一分流：用户报慢，接入层先看 **`$upstream_response_time`**——urt 极小而 request_time 大 = 慢在 Nginx↔客户端的链路（用户网络/带宽/CDN）；urt 大 = 慢在后端（转「数据库」007 / 应用侧）。这一条日志字段的分析，能把"接入层慢"的工单直接砍掉一半——先分锅，再调优。
