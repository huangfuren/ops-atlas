## 9.1 排错的第一原则：先定位阶段，再看日志，别跳读

流水线排障与「容器」009 的三板斧同构，第一原则都是**先定位，再取证**。流水线的"定位"有天然优势：**每条流水线自带阶段边界**——红了哪一段，嫌疑范围就锁死在那一段的输入/输出里：

```plain
红在 Build  → 看构建日志 + 检查依赖源（不该看 Harbor）
红在 Push   → 看凭据与仓库配额（不该看测试环境）
红在 Deploy → 看目标环境状态（不该看代码）
```

跳读的反面教材：红灯一亮就 SSH 上生产服务器翻日志——而流水线其实红在构建阶段，生产根本还没被碰。**构建号是排障的第一索引**（002 §2.4），从通知消息里的构建号进入，日志、参数、制品、部署记录全部以它关联（008 §8.3 的追溯链在这里兑现）。

最小重放是第二原则：把失败段的操作**摘出来在受控环境复现**（失败的 `npm install` 拿到本机跑一次），比在流水线日志里大海捞针快得多。

## 9.2 Git 侧：推送被拒、历史被改坏

Git 类问题几乎都能在「CICD」001 的体系里对号入座，CI 视角补两条：

**流水线触发的拉取失败**：webhook 触发了但 `checkout scm` 挂——检查 Jenkins 的 Git 凭据（deploy key 过期是常客）、GitLab 的 API 权限。这类问题只在 CI 里出现（开发者本机正常），因为凭据体系不同。

**push 被拒的两种形态**（001 §1.7）：non-fast-forward（远端有新提交）走 `pull --rebase`；被保护分支拒绝走 MR 流程。CI 侧的变体是**流水线里提交变更**（如版本号 bump）被保护分支拒——解法是给 CI 专用账号开白名单，或把版本号计算改成不提交的方式（如 008 §8.3 用 tag 推导）。

## 9.3 构建侧：依赖拉不下来、磁盘满、agent 排队

构建段的三类高频故障：

**依赖拉取失败**（npm/maven/go mod 超时）：先分辨是**偶发网络抖动还是系统性中断**（重跑一次即分辨）——系统性问题配代理缓存（Nexus 的 proxy 仓库，006 §6.2）或私有源。构建机上的依赖缓存（002 §2.5 的 type=cache、003 §3.6 的 cache）损坏也会导致诡异失败，清理缓存重跑是标准动作。

**磁盘满**：构建机的磁盘三吃货——workspace 堆积（002 §2.5 的 `cleanWs` 没配）、构建缓存膨胀（`builder prune`）、日志未轮转。取证 `df -h` + `du -sh /var/jenkins_home/workspace/*` 逐个定位。**根因治理优先**：`df` 报警时临时清理能救急，不配清理策略的构建机每周都会再见。

**agent 排队**：job 一直 pending 在"等待 executor"——并发数限制（003 §3.2 的 `concurrent`）、标签不匹配（job 要 `gpu` 标签而没有带此标签的节点在线）、agent 掉线（节点页面看离线原因）。批量卡 pending 时先看 Runner/agent 全局状态，再查单个任务。

## 9.4 凭据侧：过期、掩码失败、权限不足

凭据问题的三个信号与处置：

| 信号 | 多半是 | 处置 |
|---|---|---|
| 昨天还好今天 401/403 | 凭据过期或被轮换 | 更新 Credentials；**轮换是常态，流水线要易改**（凭据 ID 稳定、值可换） |
| 日志里出现明文 | echo 拼接绕过掩码 | 立即轮换该凭据；改用 stdin 方式（002 §2.7 / 006 §6.3） |
| job 无权限操作目标 | 权限边界收紧了 | 检查 GitLab/GitHub token 的 scope、K8s RBAC（008 §8.10） |

一条预防性纪律：**凭据过期时间进运维日历**。token 类凭据的失效是确定性事件，让流水线红在凌晨三点来提醒你，不如让日历提前三天提醒你。

## 9.5 制品侧：tag 覆盖、拉取 401/404

Harbor/Nexus 的排障聚焦三种报错：

- **push 被 rejected（tag 已存在）**：不可变 tag 规则生效（006 §6.5）——这是**设计行为不是故障**，说明版本号重复（重复构建同一 tag），换 tag 或确认后删旧重建（慎用）；
- **pull 401**：部署环境的凭据失效（robot 账号过期/吊销）、或 K8s 的 `imagePullSecrets` 没配；
- **pull 404**：tag 不存在——上游流水线没推成功就发布了（008 的流水线不该让这发生，手工部署时常见）、或保留策略误删（006 §6.9 的第 4 坑）。

404 的最后一个分支值得单独强调：**部署环境的节点上镜像还在，但仓库里没了**——已运行的 Pod 不受影响，重启/重调度即 ImagePullBackOff。这是 006 保留策略必须覆盖回滚窗口的实锤。

## 9.6 部署侧：Ansible 失败现场、K8s apply 报错

**Ansible 失败现场**（004/005 的知识落点）：看输出里第一红的 task 与它的错误信息——权限类（become 失败）、事实类（连接超时、host key）、模块类（参数错、目标状态冲突）。中断后的标准动作：**修好直接重跑整个 playbook**——幂等保证已完成的机器 ok 跳过，失败的机器从头收敛（004 §4.7 的工程价值）。

**K8s apply 报错**（「容器」009 的知识落点）：常见三类——validation error（YAML 字段错，`kubectl explain` 对着改）、quota exceeded（namespace 配额满了，005 §5.8）、admission rejected（Harbor 扫描拦截，006 §6.8）。部署后的验证永远是 `rollout status` + 冒烟（008 §8.6），"apply 没报错"不等于"服务可用"。

## 9.7 静默失败：绿了但没生效的五类原因

CI/CD 里最危险的故障是**流水线绿色、线上没变化**——所有告警都不会响，靠用户报障发现。五类根因，逐类排查：

| # | 根因 | 取证动作 |
|---|---|---|
| 1 | 发布到错误环境 | 比对 job 参数与部署记录的 ENV |
| 2 | 部署了旧制品（tag 引用错/缓存旧镜像） | 比对线上实际镜像 digest 与 Harbor 里的（006 §6.5） |
| 3 | 触发条件没命中（改的文件不触发/分支没在规则里） | 看 GitLab 的 pipeline 列表有没有建 |
| 4 | 配置层没跟上（K8s 用 env 注入，改了 ConfigMap 没重启） | 「容器」007 §7.2 的更新语义 |
| 5 | 部署目标对象不对（改的是 Deployment A，流量在 Service B） | `kubectl get` 对象谱系对账（容器 005 §5.6） |

预防比排查重要，两条：**部署成功的定义 = "rollout 完成 + 冒烟通过"**（008 §8.6），不接受"命令执行了就算成功"；**每次发布后核对线上版本号**（一条 `kubectl get deploy -o jsonpath` 的例行验证，或发布通知里带上"当前线上版本"的回读）。

## 9.8 环境漂移的发现与收敛

环境漂移（000 §0.1 痛点 5 的存量形态）：**机器的实际状态偏离声明状态**——手工改过的配置、绕过流水线的临时变更、Ansible 没覆盖的角落。两个发现手段：

- **定期审计**：`ansible-playbook site.yaml --check --diff` 定期全量跑（005 §5.8 的演练开关当审计用），diff 输出就是漂移清单；
- **事件驱动发现**：故障复盘时必问"这台机器和标准差在哪"——漂移往往在故障现场暴露。

收敛策略二选一，全团队统一：**只读收敛**（禁止手工改生产，所有变更走 Ansible——严格但要求纪律）或**定期收敛**（允许应急手工改，但周内必须回写 playbook 并重跑收敛——务实，需要审计自觉）。最糟的是两边都不做——漂移会随时间指数增长，直到某台机器成为"只有某人知道怎么运维"的黑洞。

## 9.9 流水线自身的监控与告警

流水线是生产系统的一部分（000 §0.8 误解 10 的正面表述），它自己也要进监控：

| 指标 | 告警阈值示例 | 意义 |
|---|---|---|
| 构建失败率（按 job） | 主干构建连续 3 次红 | 门禁失守或环境劣化 |
| 构建时长趋势 | 超基线 50% | 缓存失效/依赖变慢的早期信号 |
| 队列等待时长 | > 5 分钟 | agent 容量不足 |
| 上次成功部署距今 | 超过 N 天（按团队节奏） | 长期没发布=大爆炸风险积累 |

实现上不必造轮子：Jenkins 的构建记录 + Prometheus 的 jenkins exporter，或 GitLab 自带的 pipeline 统计页。**流水线的告警进同一个值班通道**——构建连续红三天没人管，比线上故障更致命（它是所有故障修复的通道）。
