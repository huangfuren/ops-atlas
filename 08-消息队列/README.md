# 消息队列运维手册

> **定位**：两大主流消息中间件（RabbitMQ / Kafka）的运维文档。000 讲价值与选型，001–002 按产品分册，003 讲堆积与可靠性治理（运维 MQ 的主战场），004 收在故障剧本——每一册对应一类真实任务。  
> **读者**：具备 Linux 与监控基础（本库水平）、应用侧用了 MQ 而你负责它不炸的运维人员。  
> **口径**：**RabbitMQ 3.12+（仲裁队列为主）**、**Kafka 3.x（KRaft 主线，ZooKeeper 存量注记）**；运维视角不写生产者/消费者代码。  
> **更新**：2026-11-01  
> **术语表**：单独成册 → [00 术语表](00-术语表.md)。38 个术语 · 6 个缩写 · 12 对易混 · 12 条症状反查。

> **与「监控」的衔接**：MQ 的健康度全靠指标（堆积、ISR、水位）——接 Prometheus 的口径在 001/002 各自注记。  
> **与「日志」的衔接**：MQ 也可作日志总线——本套不深入日志采集管线（那是「日志」册边界），只保证 MQ 自身可靠。  
> **与「数据库」的关系**：MQ 解决的是服务间异步，不替代数据库事务——"最终一致性"涉及业务设计，只作边界注记。

## 阅读约定

1. **双产品并列**：RabbitMQ 与 Kafka 概念对照着讲——它们不是竞品关系，是两种消息模型（见 000 §0.2）。
2. **运维视角**：不写生产者/消费者代码；开发侧的接入规范只给"运维要验收什么"。
3. **数字要可查**：水位、副本数、超时等参数给默认值与查证命令（以所用版本文档为准复核）。
4. **危险操作先说后果**：删队列、改分区数、强制重选主，一律先写会丢什么。
5. **每册结构统一**：目录 → 正文 → 六个坑 → 检查清单。
