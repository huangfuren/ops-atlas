# 00 术语表

> **这一文档回答**：某个词是什么意思、两个长得像的概念差在哪、「只知道现象、不知道该翻哪一册」时往哪走。  
> **怎么用**：三种查法——按名字（下面按册分组）、按缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和代码回对应册；这里只保证你「认得出、分得清、找得到」。

## 000 链路全貌

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 分布式追踪 | distributed tracing | 把一次跨服务请求的全部耗时与调用关系记录下来还原的能力 |
| trace | trace | 一次请求的完整调用树，由一个全局唯一的 trace_id 串起 |
| span | span | 调用树上的一个节点：一段有起止时间的工作（一次 HTTP 调用、一次 SQL） |
| 关键路径 | critical path | 瀑布图上真正决定总耗时的一条 span 链 |
| 上下文传播 | context propagation | 把 trace 身份（trace_id 等）随请求跨进程传递的机制 |
| 断链 | broken chain | 某个服务没接/没传上下文，trace 从这里断成两截 |
| 服务图 | service graph | 从 trace 自动汇总出的"服务 A → 服务 B"调用关系图 |
| 第三支柱 | third pillar | 链路——与指标、日志并列的可观测性信号 |

## 001 OTel 数据模型

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| OTel | OpenTelemetry | 可观测性数据（traces/metrics/logs）的开放标准与 SDK 家族 |
| Resource | Resource | 描述"数据是谁产生的"：service.name、version、环境——全局附加一次 |
| SpanContext | — | span 的身份：trace_id（16 字节）+ span_id（8 字节）+ 采样标志 |
| SpanKind | — | span 类型：SERVER/CLIENT/INTERNAL/PRODUCER/CONSUMER |
| attributes | attributes | span 上的键值属性：http.method、db.statement 等 |
| status | span status | Unset / Ok / **Error**——错误 span 是尾部采样的关键信号 |
| 语义约定 | semantic conventions | OTel 规定的标准字段名（http.method 而非自造 method） |
| Baggage | — | 随请求传播的业务键值（如租户 ID），不参与 trace 组树 |

## 002 采集与 Collector

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| OTLP | OpenTelemetry Protocol | OTel 原生传输协议（gRPC/HTTP），后端普遍支持 |
| Collector | OTel Collector | 遥数据的统一中转站：收（receiver）→ 处理（processor）→ 发（exporter） |
| receiver / exporter | — | Collector 的收与发插件：OTLP/Jaeger/Prometheus…… |
| batch / memory_limiter | — | 攒批发送 / 内存保护——Collector 两个必配 processor |
| tail_sampling processor | — | 在 Collector 看完整 trace 后再决定留不留（005） |
| Agent / Gateway | — | 两级部署：节点侧就近收（DaemonSet）/ 中心侧统一处理 |
| 自动埋点 | auto-instrumentation | agent/库插桩自动生成 span，不改业务代码 |

## 003 后端 Jaeger 与 Tempo

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| Jaeger | Jaeger | CNCF 追踪后端：支持 Cassandra/ES/ClickHouse 存储 |
| Tempo | Grafana Tempo | 对象存储友好的追踪后端：按 trace_id 查，成本低 |
| TraceQL | TraceQL | Tempo 的查询语言：按属性/结构查 trace |
| spanmetrics | — | 从 span 聚合出 RED 指标（请求率/错误率/耗时）——指标与链路的握手 |
| exemplar | exemplar | 指标数据点携带的 trace_id 引用——从告警一键跳 trace |

## 004 trace 贯通实战

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 入口 span | root/server span | trace 的第一个 SERVER span——网关或入口服务生成 trace_id |
| 传播载体 | propagation carrier | 上下文搭车的地方：HTTP 头（W3C traceparent）、MQ 消息头 |
| 消费者 span | consumer span | MQ 消费侧的 span，kind=CONSUMER，与生产侧 PRODUCER 用 link 关联 |
| span link | — | 关联"另一条 trace"的指针——异步跨 trace 场景的粘合剂 |
| 时钟偏移 | clock skew | 不同主机的时钟差——后端会校正，微小的 span 时间重叠属正常 |

## 005 采样与成本

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 采样 | sampling | 只保留部分 trace——链路成本治理的核心手段 |
| 头部采样 | head sampling | 入口处掷骰子决定留不留，后续 span 跟随父决策——简单但有盲区 |
| 尾部采样 | tail sampling | 收齐整个 trace 后再决策——能"错误全留、慢的全留"，代价是缓存与算力 |
| 父子跟随 | parent-based | 子 span 沿用父 span 的采样决定——保证 trace 完整的机制 |
| 保底 | — | 低流量服务的最小采样量——否则安静服务永远留不下证据 |

## 006 排障实战

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 瀑布图 | waterfall | trace 的时间线视图：每个 span 一条横条，缩进=父子嵌套 |
| 关键路径 | critical path | 决定总耗时的 span 链——**优化它才缩短总延迟** |
| RED 方法 | Rate/Errors/Duration | 每服务的请求率/错误率/耗时三指标——spanmetrics 自动产出 |

## 最容易混的 12 对

| 容易混 | 一句话差别 | 怎么确认 | 册 |
| --- | --- | --- | --- |
| trace vs span | 完整调用树 / 树上一个节点 | trace_id 相同 = 同一棵树 | 000/001 |
| trace_id vs span_id | 全局身份 / 节点身份 | traceparent 头里两段十六进制 | 001 |
| parent vs root | 我的上游 span / trace 的第一个 span | parent_span_id 为空 = root | 001 |
| SDK 埋点 vs 自动埋点 | 手写精度高 / 零改码覆盖广 | 通常自动打底 + 关键路径手写 | 001 |
| Agent vs Gateway 部署 | 节点就近收 / 中心统一处理 | 流量与治理需求决定，两级可叠加 | 002 |
| 头部 vs 尾部采样 | 入口掷骰子 / 看完整 trace 再决策 | 想留全部错误与慢请求 = 尾部 | 005 |
| Jaeger vs Tempo | 存检索数据库 / 存对象存储按 ID 查 | 要全文搜索=Jaeger+ES；要低成本=Tempo | 003 |
| span link vs child span | 关联另一棵树 / 同树内的父子 | MQ 异步跨 trace 用 link | 004 |
| Baggage vs attributes | 随请求传播的业务键值 / span 上的遥测属性 | Baggage 会传播，attributes 只在本 span | 001 |
| trace_id vs request_id | 追踪系统生成 / 业务生成——可合一也可映射 | 日志与 trace 用同一个 ID 才能互跳 | 004 / 「日志」005 |
| 采样率 vs 保留期 | 留多少进来 / 留多久 | 两个独立的成本旋钮 | 005 |
| Error status vs 5xx 日志 | span 的结构化信号 / 文本里的线索 | 尾部采样认 status，不认日志 | 005 |

## 按症状反查

| 现象 | 大概是 | 去哪 |
| --- | --- | --- |
| trace 从某服务起断成两截 | 该服务没接传播/没埋点 | 004 §4.5 |
| trace 里少某个服务 | 该服务采样决策不一致 / 未埋点 | 001 §1.5 / 005 |
| 后端查不到已知存在的 trace | 采样没留 / trace_id 错 / 后端写入失败 | 005 §5.4 |
| span 时间线重叠错乱 | 主机时钟偏移——后端会校正，忽略微差 | 006 §6.4 |
| 总耗时 ≠ 子 span 之和 | 正常：有排队/未埋点段落——找"空隙" | 006 §6.2 |
| 全是 INTERNAL span，看不出调用方向 | SpanKind 与语义约定没配 | 001 §1.2 |
| 尾部采样后错误 trace 丢了 | status 没标 Error / 策略没配 status_code | 005 §5.3 |
| 链路存储账单爆炸 | 采样率过高 / 高基数属性全留 | 005 §5.5 |
| P99 慢但瀑布图每段都快 | 缺采样段落 / 客户端网络——找空隙与"消失的时间" | 006 §6.2 |
| 异步消息的上下游 trace 对不上 | PRODUCER/CONSUMER span 没用 link 关联 | 004 §4.3 |
