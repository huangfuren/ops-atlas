# 链路追踪手册

> **定位**：可观测性第三支柱——分布式链路追踪。000 讲为什么微服务离不开它，001–002 讲 OpenTelemetry 的数据模型与采集管线，003 讲后端存储，004–006 收在贯通实战、采样成本与排障——每一册对应一类真实任务。  
> **读者**：已用「监控」册出告警、用「日志」册取证，但跨服务问题仍靠 grep 时间线硬拼的运维/SRE。  
> **口径**：**OpenTelemetry（traces 信号，OTLP 协议）为数据标准**；后端主线 **Jaeger 与 Grafana Tempo** 对照；示例语言 Python（与「Python」板块衔接），机制语言无关。  
> **更新**：2026-11-01  
> **术语表**：单独成册 → [00 术语表](00-术语表.md)。

> **与「监控」的衔接**：指标发现异常（哪慢/错多少），链路解释原因（哪一跳）——span metrics（RED 指标）与 exemplars 是两支柱的握手。  
> **与「日志」的衔接**：日志里的 trace_id（日志 005 §5.3）是链路的入口——从一条报错日志一键跳到完整调用瀑布。  
> **与「SRE」的衔接**：SLO 的延迟 SLI 深挖、故障复盘的时间线还原（SRE 003），链路是最强证据源。

## 阅读约定

1. **OTel 为数据标准**：Jaeger/Tempo 都原生吃 OTLP——学的是模型与管线，不是某厂商 API。
2. **机制语言无关，示例用 Python**：与「Python」板块衔接；Java/Go 的自动埋点思想相同。
3. **给输出**：查询与命令给预期结果形态，读者靠输出判断自己对不对。
4. **采样是成本决策**：每册把"这会让链路量/存储怎么变"写在决策旁边。
5. **每册结构统一**：目录 → 正文 → N 个坑 → 检查清单。
