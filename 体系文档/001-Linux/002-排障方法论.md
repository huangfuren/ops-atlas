# 排障方法论

> **这一册回答**：面对一台出问题的 Linux，思考顺序是什么——不教任何具体命令，只教判断框架。命令在哪册，框架指路。
> **给谁读**：接到报警不知道第一步看哪里的新人；也给出老手默认在用的那套显式化流程。
> **工具无关**：本册不重复任何模块册的操作细节；每节末尾给「去哪册落地」。

## 排障四步

一切排障都是四步循环，**顺序不能乱**：

1. **取数**——先把事实拿到手：什么时间、什么现象、报错原文、能复现吗。禁止跳过取数直接猜。
2. **判断**——把事实对到一层/一个组件上：「现象属于启动、进程、权限、存储、网络、服务中的哪一类」。
3. **处置**——最小动作处置，动作前先备份，动作后验证。
4. **记录**——留下「现象 → 判断 → 动作 → 结果」，下次同类问题直接命中。

**落地**：每类问题的取数命令与判断树在各册「排错路径」节；133 的五条故障树是这套循环在性能问题上的完整展开。

## 五维模型（USE）

判断「系统慢」时，对每种资源问四个维度——**利用率、饱和度、错误、容量**：

| 资源 | 查什么 | 册 |
| --- | --- | --- |
| CPU | 利用率（top）、饱和度（load vs 核数）、错误（OOM/oops） | 133 |
| 内存 | 可用量、换页饱和度、OOM 事件 | 112 / 133 |
| 磁盘 IO | 利用率（iostat %util）、队列饱和（await） | 133 |
| 网络 | 丢包/重传错误、带宽饱和、队列溢出 | 121 |
| inode/文件描述符 | 用尽即错误，不表现为慢 | 114 |

**原则**：慢不等于 CPU 高——「负载高但 CPU 低」几乎总是 IO 或队列饱和，先查饱和度再查利用率。

## 分层排查

问题在栈的哪一层，就从那层截断：

- **启动问题**按屏幕现象定位（卡 GRUB？卡内核？卡服务？）→ 111 的起不来决策树。
- **连不通问题**按五层顺序逐层截断：链路 → 路由 → 端口 → 防火墙 → 应用 → 121 的五层排查。
- **权限问题**按三步比对：属主 → 位 → ACL，每层都要 x 才能进 → 113。

**原则**：每层只回答「通/不通」，通了就上移一层，不通就在这层取数——不要跨层猜测。

## 先诊断后修

- **不直接甩修复命令**：任何处置先给「取数 → 判断」依据，再给动作。
- **危险动作先备份**：`rm`、`mkfs`、`dd`、改分区、改网络、重启服务，一律标 ⚠️ 并先写备份命令。
- **改动必有回滚**：配置修改给前后验证命令，写明改错了怎么退。

## 反模式

- ❌ 上来就重启——重启销毁现场，取数窗口永远没了。
- ❌ 只看 CPU——五维里只查一维，漏掉 IO/内存饱和是新手最常见的误判。
- ❌ 改一堆配置再看结果——一次一个变量，否则不知道哪个动作起效。
- ❌ 无记录——同一类故障第二次还在从头猜。

## 自测

1. 排障四步的顺序是什么？为什么不能乱？（取数→判断→处置→记录；乱序会销毁现场或盲目处置）
2. 负载 20、CPU 使用率 5%，先查哪个维度？（饱和度——IO 或队列）
3. 「能 ping 通但端口不通」卡在哪层？（端口层，往上查监听，往下查防火墙）
4. 为什么不先重启？（销毁现场）
5. 本册写具体命令吗？（不写——只给判断框架，命令在各册排错路径）
