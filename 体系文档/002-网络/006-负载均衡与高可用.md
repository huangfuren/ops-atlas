## 6.1 为什么需要负载均衡

| 目的 | 具体 |
|---|---|
| 可用性 | 一台后端挂了，流量自动切走，用户无感 |
| 扩展性 | 加机器就能扩容，不用改架构 |
| TLS 集中 | 证书只装在一处，不用每台后端都配 |
| 灰度与分流 | 按权重、按 Header、按地域分配流量 |
| 隐藏后端 | 用户只看到 VIP，看不到真实拓扑 |

第 3 条经常被忽略：如果没 LB，100 台后端就要配 100 份证书，每次换证 100 个地方要改，漏一个就有一批用户报错。

## 6.2 四层与七层

### 6.2.1 判据只有一条

**看它认不认 HTTP。**

| 维度 | 四层（L4） | 七层（L7） |
|---|---|---|
| 工作层次 | TCP/UDP | HTTP/HTTPS |
| 转发依据 | 源 IP、目的 IP、端口 | URL、Host、Header、Cookie |
| 能不能看到 URL | **不能**（流量是加密或二进制） | 能 |
| 性能 | 高（内核态转发，几万到几十万 CPS） | 低（要解析应用层，几千到几万 QPS） |
| TLS 终止 | 只能透传（除非做 SSL offload） | 可以终止并解密 |
| 典型产品 | LVS、F5、云 SLB | Nginx、HAProxy、Envoy、云 ALB |

**四层看不到 URL，这是最本质的差别。** 所以「按路径分流」「按域名分流」「改 Header」这些需求，四层做不到。

### 6.2.2 选型

| 需求 | 选 |
|---|---|
| 纯性能、大流量、不需要看内容 | 四层 |
| 按域名/路径路由、要 A/B、要改 Header | 七层 |
| 既要性能又要灵活 | 四层在前、七层在后（两层 LB） |

生产上常见的结构是**两层**：

```text
用户 → 四层 LB（LVS，扛量、做 HA）→ 七层 LB（Nginx，做路由和 TLS 终止）→ 后端
```

四层负责把流量分到几台 Nginx，Nginx 负责按域名和路径分到具体服务。

## 6.3 LVS 四种模式

LVS 工作在四层，核心是 Director Server（DS，调度器）和 Real Server（RS，后端）。

### 6.3.1 NAT 模式

```text
客户端 ──> DS（VIP）──> RS（内网）
              ↑            │
              └────────────┘
              回包也经 DS

① 客户端请求到 VIP
② DS 做 DNAT：目的 IP 由 VIP 改成 RIP，转发给 RS
③ RS 处理，回包给 DS（因为网关指向 DS）
④ DS 做 SNAT：源 IP 由 RIP 改成 VIP，回给客户端
```

| 属性 | 值 |
|---|---|
| 改什么 | **只改目的 IP**（去程），回程改源 IP |
| RS 看到真实 CIP 吗 | **看得到**（去程没改源地址） |
| RS 网关 | **必须指向 DS** |
| 网络要求 | DS 需要两块网卡，RS 与 DS 内网口同网段 |
| 端口映射 | 支持（VIP:80 → RIP:8080） |
| 性能 | 低（双向流量都过 DS，DS 是瓶颈） |
| 规模 | ≤ 20 台 |

### 6.3.2 DR 模式（直连路由）

```text
客户端 ──> DS ──改目的MAC──> RS
                             │
                             └──直接回客户端（源IP = VIP）

① 客户端请求到 VIP
② DS 不改 IP，只把帧的目的 MAC 改成某台 RS 的 MAC，转发
③ RS 收到，发现目的 IP 是 VIP —— 而 VIP 配在自己的 lo 上，所以它接
④ RS 回包：源 IP = VIP，目的 IP = CIP，直接走网关回客户端，不经过 DS
```

| 属性 | 值 |
|---|---|
| 改什么 | **只改目的 MAC**，IP 完全不动 |
| RS 看到真实 CIP 吗 | **看得到** |
| RS 网关 | 不需要指向 DS（这是性能高的原因） |
| 网络要求 | **DS 与 RS 必须同二层**（要能 ARP 到对方 MAC） |
| RS 配置 | VIP 配在 `lo` 上，并且**必须抑制 ARP 响应** |
| 端口映射 | **不支持**（端口不能改） |
| 性能 | **最高**（回包不过 DS） |
| 规模 | 数百台 |

**DR 模式最关键的两个配置**，配错会出大问题：

```bash
# RS 上：VIP 挂在 lo 上
ip addr add 10.0.0.100/32 dev lo

# 抑制 ARP：否则 RS 会响应 "谁是 10.0.0.100" 的 ARP 请求，
# 导致整个二层的流量都打到 RS 上，而不是 DS
echo 1 > /proc/sys/net/ipv4/conf/all/arp_ignore
echo 2 > /proc/sys/net/ipv4/conf/all/arp_announce
```

**为什么必须抑制 ARP**：VIP 同时存在于 DS 和所有 RS 上（RS 是配在 lo 上的）。如果不抑制，ARP 广播会被某台 RS 响应，客户端就直接把包发给 RS 了，绕过 DS，负载均衡失效。

### 6.3.3 TUN 模式（IP 隧道）

```text
客户端 ──> DS ──IP隧道封装──> RS
                               │
                               └──直接回客户端

① 请求到 VIP
② DS 把原始 IP 包整个封装进一个新的 IP 包里（IP-in-IP），目的地址是 RIP
③ RS 解封装，拿到原始包，发现目的 IP 是 VIP（配在 tunl0 上），接受
④ RS 回包直接给客户端
```

| 属性 | 值 |
|---|---|
| 改什么 | **IP 隧道封装** |
| RS 看到真实 CIP 吗 | **看得到** |
| 网络要求 | **可以跨网段**（这是相对 DR 的优势） |
| RS 配置 | VIP 配在 `tunl0` 上，同样要抑制 ARP |
| 端口映射 | 不支持 |
| 性能 | 中高（有封装解封装开销） |
| 规模 | ≤ 100 台 |

### 6.3.4 FULLNAT 模式

```text
客户端 ──> DS ──改源+目的──> RS
              ↑                │
              └────────────────┘
              回包也经 DS

① 请求到 VIP
② DS 同时改：目的 IP（VIP→RIP）、源 IP（CIP→DS 的 Local IP）
③ RS 看到的源是 DS 的内网 IP，不是真实客户端
④ 回包给 DS，DS 再改回去
```

| 属性 | 值 |
|---|---|
| 改什么 | **源 + 目的 IP 都改** |
| RS 看到真实 CIP 吗 | **看不到**（只看到 DS 的 Local IP） |
| RS 网关 | 指向 DS |
| 网络要求 | **可跨网段、跨 VPC**（不要求同二层） |
| 端口映射 | 支持 |
| 性能 | 中低（双向都过 DS，且多一次地址转换） |
| 规模 | ≤ 50 台 |

**FULLNAT 的价值在于解耦网络拓扑**：RS 可以和 DS 不在同一个网段、不在同一个 VPC。云上环境大量使用这个模式。

**代价是拿不到真实客户端 IP**。要拿，得靠 `TOA` 内核模块（在 TCP 选项里带真实源地址）或让应用从 `X-Forwarded-For` 里取（如果前面还有七层）。

### 6.3.5 四模式对比

| 维度 | NAT | DR | TUN | FULLNAT |
|---|---|---|---|---|
| 转发方式 | 改目的 IP | 改目的 MAC | IP 隧道 | 改源+目的 IP |
| 数据路径 | 双向经 DS | 回包直连客户端 | 回包直连客户端 | 双向经 DS |
| RS 见真实 CIP | ✅ | ✅ | ✅ | ❌ |
| 跨网段 | ❌ | ❌ 需同二层 | ✅ | ✅ |
| 端口映射 | ✅ | ❌ | ❌ | ✅ |
| 性能 | 低 | **最高** | 中高 | 中低 |
| 规模 | ≤20 | 数百 | ≤100 | ≤50 |
| 配置复杂度 | 低 | 高（要改 RS 内核参数） | 中 | 中 |

**选型口诀**：

- 同机房、追性能 → **DR**
- 要跨网段、`DR` 做不了 → **TUN**
- 云上、跨 VPC、要端口映射 → **FULLNAT**
- 小规模、简单省事 → **NAT**

## 6.4 调度算法

| 算法 | 逻辑 | 适用 |
|---|---|---|
| `rr` 轮询 | 依次分发 | 后端性能一致 |
| `wrr` 加权轮询 | 按权重分配 | 后端配置不同（新老机器混部） |
| `lc` 最少连接 | 给当前连接数最少的 | 请求耗时差异大 |
| `wlc` 加权最少连接 | lc + 权重 | 常用默认值 |
| `sh` 源地址哈希 | 同一源 IP 固定到同一后端 | 需要会话保持 |
| `dh` 目的地址哈希 | 按目标哈希 | 缓存服务器场景 |
| 一致性哈希 | 节点变动时只影响少量 key | 有状态缓存、减少缓存击穿 |

**一致性哈希的价值**：普通哈希在后端从 4 台扩到 5 台时，**几乎全部 key 的映射都会变**，缓存全部失效，数据库瞬间被打穿。一致性哈希只影响 1/N 的 key。

## 6.5 LVS / Nginx / HAProxy 的定位

三者不是替代关系，是分工关系。

| | LVS | Nginx | HAProxy |
|---|---|---|---|
| 层次 | 四层 | 七层（也能做四层） | 四层 + 七层 |
| 性能 | 极高（内核态） | 中（用户态，但很强） | 高 |
| 功能 | 只做转发 | 转发 + 静态文件 + 缓存 + TLS + 限流 | 转发 + 极强健康检查 + 详细统计 |
| 配置 | 相对简单 | 灵活但复杂 | 专用配置语法，可读性好 |
| 典型位置 | 最前面扛量 | 中间做路由 | 中间做纯代理 |
| 统计与观测 | 弱 | 中 | **强**（内置统计页） |

**生产组合**：LVS 在最前面接流量并做 HA，Nginx 在后面做七层路由和 TLS 终止。HAProxy 适合纯代理场景，尤其是需要精细健康检查和连接统计时。

## 6.6 Keepalived 与 VRRP

### 6.6.1 解决什么问题

一台 LB 本身就是单点。解决办法是两台 LB 共享一个 VIP，主的那台持有 VIP 对外服务，挂了以后 VIP 漂到备机。

### 6.6.2 VRRP 的工作方式

```text
Master（优先级 100，持有 VIP）         Backup（优先级 90）
        │                                    │
        │  ① 每 1 秒发 VRRP 通告（组播 224.0.0.18）
        │ ─────────────────────────────────> │
        │                                    │  ② 收到通告，重置计时器
        │                                    │
   ─── 如果 Master 故障，不再发通告 ───
        │                                    │  ③ 3 秒（3 个周期）没收到
        │                                    │  ④ Backup 抢占，把 VIP 挂到自己身上
```

| 概念 | 说明 |
|---|---|
| VRID | 虚拟路由组 ID，同组必须一致 |
| 优先级 | 0–255，大的当 Master |
| 通告间隔 | 默认 1 秒（`advert_int`） |
| 抢占模式 | 默认开启，Master 恢复后会抢回 VIP |

### 6.6.3 Keepalived 配置

```conf
vrrp_instance VI_1 {
    state MASTER                # 初始状态，最终由优先级决定
    interface eth0
    virtual_router_id 51        # 同组必须一致，不同组必须不同
    priority 100                # 备机设 90
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass 12345678      # 同组必须一致
    }

    virtual_ipaddress {
        10.0.0.100/24
    }
}
```

### 6.6.4 脑裂：最危险的状态

**脑裂 = 两台机器都认为自己是 Master，同时持有 VIP。**

后果：同一个 IP 出现在两个地方，交换机 MAC 表来回翻转，流量时通时断；如果后端有共享存储或数据库，可能造成数据损坏。

| 成因 | 说明 |
|---|---|
| 心跳链路断 | 两台机器之间的 VRRP 通告收不到，但两台都活着 |
| 防火墙挡了 VRRP | 组播 224.0.0.18 被 DROP |
| 交换机隔离 | 两台机器在不同 VLAN 或中间有 STP 阻塞 |
| 优先级配置相同 | 都认为对方优先级不比自己高 |

**防范手段（必须做其中之一以上）**：

| 手段 | 做法 |
|---|---|
| **双心跳链路** | 除了业务网卡，再加一条直连的心跳线，避免单条链路故障导致误判 |
| **仲裁脚本** | `notify` 脚本里 ping 网关或对端，判不清就主动降级或关机 |
| **STONITH** | 用带外管理（IPMI）把对端强制断电，物理上保证只有一个 Master |
| **组播转单播** | 交换机不支持组播时，用 `unicast_peer` 直发对端 |

```conf
# 单播心跳（跨网段或组播不通时用）
vrrp_instance VI_1 {
    ...
    unicast_src_ip 10.0.0.1
    unicast_peer {
        10.0.0.2
    }
}
```

**判断是不是脑裂**：

```bash
# 两台机器上都执行，如果都显示 VIP，就是脑裂
ip addr show eth0 | grep 10.0.0.100

# 看 VRRP 状态变化日志
journalctl -u keepalived -n 50 | grep -i "state\|transition"

# 抓 VRRP 通告，看双方是否互相收不到
tcpdump -i eth0 -nn vrrp -c 10
```

## 6.7 健康检查

### 6.7.1 类型

| 类型 | 层次 | 判据 | 优点 | 缺点 |
|---|---|---|---|---|
| ICMP ping | 三层 | 主机是否存活 | 简单 | 主机活着但服务死了照样判健康 |
| TCP 端口 | 四层 | 端口能否建连 | 快、开销小 | 端口在听但应用卡死照样判健康 |
| HTTP 状态码 | 七层 | 返回 200 | 能反映应用状态 | 开销大，有状态码设计问题 |
| 自定义内容 | 七层 | 响应体是否含特定字符串 | 最准 | 要维护检查页面 |

**默认配 TCP 检查是不够的。** 应用可能端口还在监听，但线程池打满、数据库连不上——TCP 检查它照样是"健康"的，流量继续往里打，用户看到的全是 500。

至少要配 HTTP 检查，且检查接口要真的检查依赖（数据库、缓存），而不是直接返回 200。

### 6.7.2 参数与误判

| 参数 | 含义 | 配错的后果 |
|---|---|---|
| `interval` | 检查间隔 | 太大：故障发现慢；太小：检查本身成为负担 |
| `timeout` | 单次超时 | 太小：网络抖动就误判摘除 |
| `rise` | 几次成功才算恢复 | 太大：恢复慢；太小：抖动时反复上下线 |
| `fall` | 几次失败才算故障 | 太小：抖动就摘除；太大：真故障发现慢 |

典型配置：`interval 5s, timeout 2s, rise 2, fall 3`——15 秒内连续 3 次失败才摘，10 秒内连续 2 次成功才恢复。

**误摘的典型原因**：

| 现象 | 原因 |
|---|---|
| 每天固定时间被摘一次 | 后端在做备份/定时任务，CPU 打满导致检查超时 |
| 高负载时批量被摘 | 检查超时太短，或 `fall` 设为 1 |
| 摘了又立刻恢复，反复 | `rise`/`fall` 都太小的抖动 |
| 后端日志里有很多检查请求 | 检查频率太高，或检查路径没有避开日志 |

## 6.8 会话保持

**会话保持是妥协，不是设计。** 正确做法是把会话放到共享存储（Redis），让后端无状态。但存量系统经常改不动，所以需要它。

| 方式 | 原理 | 缺点 |
|---|---|---|
| 源 IP 哈希 | 同一 IP 固定到同一后端 | NAT 环境下大量用户共用出口 IP，分布严重不均 |
| Cookie 插入 | LB 在响应里插一个 Cookie 标记后端 | 需要 LB 支持，且对非浏览器客户端无效 |
| Cookie 重写 | 改写应用自己的 Cookie | 依赖应用配合 |
| URL 参数 | 把后端标识放 URL | 暴露内部信息，且要改应用 |

**源 IP 哈希最大的问题是 NAT**：一个公司几千人共用几个出口 IP，结果全被哈希到同一台后端，其他后端几乎空闲。看到"流量严重不均"时，先确认是不是开了源 IP 哈希。

## 6.9 Nginx 反向代理配置

```nginx
upstream backend {
    # 调度算法，默认 rr；least_conn 适合请求耗时差异大的场景
    least_conn;

    server 10.0.0.11:8080 weight=5 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 weight=5 max_fails=3 fail_timeout=10s;
    server 10.0.0.13:8080 backup;        # 备用，前面全挂才用

    # 到后端的连接池（不配就是每个请求新建连接）
    keepalive 32;
    keepalive_timeout 60s;
}

server {
    listen 80;
    server_name www.example.com;

    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;                    # keepalive 必须 1.1
        proxy_set_header Connection "";            # 清掉 close，才能复用

        # 传真实客户端信息给后端
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时（三个都要看场景设，默认 60s 往往太长）
        proxy_connect_timeout 5s;                  # 建连超时，要短
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;

        # 上游返回这些错误时换一台重试
        proxy_next_upstream error timeout http_502 http_503 http_504;

        # 缓冲：响应小的时候攒够再发，减少后端连接占用
        proxy_buffering on;
        proxy_buffers 8 16k;
        proxy_buffer_size 16k;
    }
}
```

### 6.9.1 几个必须注意的点

| 配置 | 为什么 |
|---|---|
| `proxy_http_version 1.1` + `Connection ""` | **不配这两行，upstream keepalive 完全不生效**，这是最常见的配置错误 |
| `proxy_set_header Host $host` | 不传 Host，后端拿到的 Host 是 upstream 名字或 IP，虚拟主机路由会错 |
| `X-Forwarded-For` 用 `$proxy_add_x_forwarded_for` | 它会追加而不是覆盖，能保留整条链路；只取第一段时注意伪造风险 |
| `proxy_connect_timeout` 要短 | 默认 60s，后端挂了你得等一分钟才知道 |
| `proxy_next_upstream` 加 `http_502` | 默认不含非幂等请求重试，POST 不会重试（避免重复提交） |

**关于 `X-Forwarded-For` 的安全问题**：客户端可以自己伪造这个头。如果 Nginx 前面没有可信代理，直接取 XFF 第一段就等于取客户端伪造的值。正确做法是从右往左数，跳过可信代理的 IP。

## 6.10 故障判读

### 6.10.1 502 / 503 / 504 在 LB 侧怎么分

```text
$upstream_status 为空、$upstream_response_time 为空
    → 根本没有连上（后端全挂 / 端口不通 / 被防火墙挡）
    → 通常是 502 或 503

$upstream_status 有值且是 5xx
    → 连上了，后端自己返回的错误
    → 继续往应用查

$upstream_status 为空、urt 有值、$status 504
    → 连上了、请求发了、等响应超时
    → 后端卡住：慢 SQL、死锁、GC、下游阻塞
```

| 码 | 一句话 | 先做什么 |
|---|---|---|
| 502 | 上游说了胡话 | 看后端应用日志，是不是崩了返回非法内容 |
| 503 | 上游不在家 | `ss -lntp` 看端口在不在，看健康检查状态 |
| 504 | 上游不应答 | 看后端是不是卡住，`proxy_read_timeout` 是不是太短 |

### 6.10.2 后端全 down

| 检查 | 命令 |
|---|---|
| 后端端口是否在听 | `ss -lntp \| grep :8080` |
| 从 LB 能否连到后端 | `nc -vz 10.0.0.11 8080` |
| 健康检查是否被判失败 | Nginx 错误日志、LVS 的 `ipvsadm -Ln` |
| 是不是批量同时挂 | 看是不是同一个物理机、同一台交换机 |

**批量同时挂**通常不是应用问题，而是网络或上游依赖问题——比如所有后端都连同一个数据库，数据库挂了，全部后端健康检查失败。

### 6.10.3 VIP 双活 / 流量不均

| 现象 | 排查 |
|---|---|
| 两台 LB 都持有 VIP | 脑裂，`ip addr` 两边都看 |
| VIP 只在一台，但流量不均 | 看交换机 ARP 表、看是否有源 IP 哈希 |
| VIP 漂了又漂回 | 心跳抖动，看 `journalctl -u keepalived` |
| 客户端连 VIP 时通时不通 | 中间有设备缓存了旧 MAC，等老化或触发免费 ARP |

## 6.11 命令与坑

```bash
# LVS 规则与统计
ipvsadm -Ln                  # 看虚拟服务和后端
ipvsadm -Ln --stats          # 看每台的连接数和流量
ipvsadm -Lnc                 # 看当前连接

# Keepalived 状态
systemctl status keepalived
journalctl -u keepalived -n 50
ip addr show eth0 | grep 10.0.0.100    # VIP 在不在这台

# Nginx 上游状态
nginx -T | grep -A5 upstream           # 看完整上游配置
tail -f /var/log/nginx/error.log | grep upstream

# 从 LB 测后端
nc -vz 10.0.0.11 8080
curl -H 'Host: www.example.com' http://10.0.0.11:8080/health -v

# 抓 VRRP
tcpdump -i eth0 -nn vrrp -c 10
```

### 6.11.1 七个坑

| # | 坑 | 现象 | 处置 |
|---|---|---|---|
| 1 | DR 模式没抑制 ARP | 流量绕过 DS，负载均衡完全失效 | RS 上设 `arp_ignore=1`、`arp_announce=2` |
| 2 | upstream 没配 `keepalive` | 后端堆 TIME_WAIT，连接数上不去 | `upstream { keepalive 32; }` + `proxy_http_version 1.1` |
| 3 | 配了 keepalive 但没清 `Connection` 头 | 连接照样不复用 | `proxy_set_header Connection "";` |
| 4 | 只做 TCP 健康检查 | 端口在听但应用卡死，流量继续打进去 | 改成 HTTP 检查，且检查真实依赖 |
| 5 | 源 IP 哈希 + NAT 环境 | 流量严重倾斜到一两台 | 改用 Cookie 保持或去状态化 |
| 6 | 没配双心跳 | 单条心跳链路断就脑裂 | 加直连心跳线 + 仲裁脚本 |
| 7 | `proxy_next_upstream` 对 POST 重试 | 重复下单 | 确认不含 `non_idempotent` |
