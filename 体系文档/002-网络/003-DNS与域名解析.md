## 3.1 DNS 的分层结构

```text
                    ┌──────────────┐
                    │   根（.）     │  全球 13 组集群，只告诉你「.com 找谁」
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │ 顶级域 .com  │  告诉你「example.com 的权威服务器是谁」
                    └──────┬───────┘
                           ▼
                    ┌──────────────────┐
                    │ 权威 example.com │  真正存着 www.example.com 的 A 记录
                    └──────────────────┘
```

**DNS 是分布式数据库，没有一台服务器知道全部答案。** 每一层只负责「往下指路」。

这个结构决定了解析失败时该找谁：

| 层级 | 谁维护 | 出问题找谁 |
|---|---|---|
| 根 / 顶级域 | ICANN / 注册局 | 基本不会出问题 |
| 权威 NS | **你自己或你的 DNS 服务商** | 查自己的配置 |
| 递归服务器 | 运营商 / 公共 DNS / 自建 | 换一个 DNS 对比验证 |
| 本地缓存 | 浏览器 / 操作系统 | 清缓存 |

### 3.1.1 四类 DNS 服务器

| 类型 | 作用 | 典型例子 |
|---|---|---|
| 权威服务器（Authoritative） | 存着某个域的正式记录，只回答自己的域 | 阿里云云解析、自建 BIND |
| 递归服务器（Recursive） | 替客户端跑腿问到底，缓存结果 | 运营商 DNS、8.8.8.8、223.5.5.5 |
| 转发器（Forwarder） | 自己不递归，把请求转给上游 | dnsmasq、内网 DNS |
| 根/TLD 服务器 | 只指路 | — |

**运维踩坑点**：公司内网通常有一台 dnsmasq 或自建 DNS 做转发器，它缓存了旧记录，而你在云解析上改的记录已经生效——这时用 `dig @8.8.8.8` 能拿到新记录，用本机 `dig` 拿到的还是旧的。

### 3.1.2 内网域名与公网域名是两套

| 场景 | 解析方式 |
|---|---|
| 公网域名 | 走公网 DNS，任何人都能查 |
| 内网域名（`db.corp.internal`） | 只有内网 DNS 有记录，公网查不到 |
| 两者同名 | **内网 DNS 优先生效，可能和公网解析结果完全不同** |

第二种最容易出事：一台机器迁到云上，DNS 改成了公网记录，但内网 DNS 里的旧记录还在，内网机器访问的还是老 IP。

## 3.2 解析链路：递归与迭代

### 3.2.1 完整路径

```text
浏览器输入 www.example.com
  │
  ├─ ① 浏览器 DNS 缓存（Chrome 约 60 秒）
  ├─ ② 操作系统缓存（nscd / systemd-resolved）
  ├─ ③ /etc/hosts  ← 本地写死，优先级高于 DNS
  │
  ├─ ④ 本地 DNS 服务器（/etc/resolv.conf 里的 nameserver）
  │     └─ 递归查询开始（此后由它替你跑腿）
  │
  ├─ ⑤ 问根服务器：.com 谁管？
  ├─ ⑥ 问 .com 顶级域：example.com 的权威服务器是谁？
  ├─ ⑦ 问权威服务器：www.example.com 的 A 记录是什么？
  │
  └─ ⑧ 拿到 IP，逐级缓存（各按自己的 TTL），返回浏览器
```

### 3.2.2 递归 vs 迭代

| 方式 | 谁在跑腿 | 用在哪 |
|---|---|---|
| **递归查询** | 被问的一方负责给出最终答案 | 客户端 → 本地 DNS |
| **迭代查询** | 被问的一方只给「下一个该问谁」 | 本地 DNS → 根 / TLD / 权威 |

**比喻**：去政务大厅办事，前台（递归服务器）说「你坐着等，我帮你跑完所有窗口」——这是递归。前台自己跑的时候，每个窗口只告诉他「这事归 3 号窗口」——这是迭代。

### 3.2.3 resolv.conf 与解析顺序

```bash
cat /etc/resolv.conf
```

```text
nameserver 10.0.0.2
nameserver 8.8.8.8
options timeout:2 attempts:3
search corp.example.com
```

| 配置 | 作用 | 坑 |
|---|---|---|
| `nameserver` | DNS 服务器，按顺序尝试 | 第一个不通要等 timeout 才试第二个，**表现为所有解析都慢** |
| `options timeout` | 单次超时秒数 | 默认 5 秒，太长会拖慢全部请求 |
| `search` | 短域名自动补后缀 | 配错会让 `ping db` 解析到奇怪的主机 |
| `/etc/nsswitch.conf` 的 `hosts:` | hosts 与 DNS 的先后 | `files dns` 表示先查 hosts |

**高频坑**：`/etc/hosts` 里有一条旧记录，导致「DNS 明明改了，这台机器就是不生效」。查解析问题，**第一步永远是 `cat /etc/hosts`**。

```bash
getent hosts www.example.com    # 走完整 nsswitch 流程，最接近应用的真实行为
```

`getent` 和 `dig` 结果不一致，多半就是 hosts 或 nscd 在起作用。

## 3.3 记录类型

| 类型 | 作用 | 示例 | 运维注意 |
|---|---|---|---|
| **A** | 域名 → IPv4 | `www A 1.2.3.4` | 最常用 |
| **AAAA** | 域名 → IPv6 | `www AAAA 2001:db8::1` | 没配 IPv6 却返回 AAAA 会连不上 |
| **CNAME** | 别名 | `www CNAME cdn.example.net` | **不能与 A 记录共存**；根域不能用 |
| **MX** | 邮件服务器 | `@ MX 10 mail.example.com` | 前面数字是优先级，越小越优先 |
| **TXT** | 文本，用于验证 | SPF、DKIM、域名归属 | 常用来做所有权校验 |
| **NS** | 该域的权威服务器 | `example.com NS ns1.xxx.com` | 改 NS = 换 DNS 服务商 |
| **SOA** | 域的起始授权信息 | 含序列号、刷新间隔 | 主从同步靠序列号 |
| **SRV** | 服务定位 | `_ldap._tcp.example.com` | **AD 域强依赖** |
| **PTR** | IP → 域名（反解） | 需向 IP 所有者申请 | 邮件反垃圾常查 |
| **CAA** | 限制哪些 CA 可签发证书 | `@ CAA 0 issue "letsencrypt.org"` | 配错会导致证书签发失败 |

### 3.3.1 CNAME 的三个硬限制

配错会导致整个域异常，比配错 A 记录严重得多：

1. **CNAME 所在的名称不能再有 A / AAAA / MX 等其他记录。** 一个名字要么是别名，要么是实体，不能既是又不是。
2. **根域（`example.com` 本身）通常不能设 CNAME**，会与 SOA / NS 冲突。要用 A 记录或厂商提供的 ALIAS / ANAME 方案。
3. **CNAME 链越长解析越慢**，每跳都是一次额外查询。生产上不建议超过两层。

### 3.3.2 泛解析

`*.example.com A 1.2.3.4` 表示「任何未单独定义的三级域名都指向这个 IP」。

| 用途 | 风险 |
|---|---|
| 方便，新增子域不用改配置 | **拼错的域名也会解析成功**，问题变成 404 而不是 NXDOMAIN，排查时容易误判 |
| 适合多租户 SaaS | 影响 CAA、证书签发（通配符证书必须配 DNS-01 验证） |

**排查「域名解析出奇怪 IP」时，先确认有没有泛解析。** 有泛解析的话，`dig` 永远有答案，看不出记录到底存不存在。

## 3.4 TTL 与「改了为什么不生效」

### 3.4.1 TTL 的机制

TTL（Time To Live）是这条记录**允许被缓存多少秒**。

```text
权威返回：www.example.com A 1.2.3.4，TTL=3600
     │
     ├─ 本地 DNS 缓存 3600 秒
     ├─ 运营商 DNS 缓存 3600 秒
     └─ 浏览器缓存（自有策略，通常更短）
```

TTL 到期前，**任何一层都不会再去问权威**。所以你改了记录，别人看到的还是旧的。

### 3.4.2 生效时间为什么因人而异

| 因素 | 影响 |
|---|---|
| 各级缓存剩余时间 | 有人缓存刚过期（立刻生效），有人刚缓存（要等满 TTL） |
| 运营商缓存策略 | 有些运营商无视 TTL 强制缓存更久 |
| 浏览器独立缓存 | 清系统缓存不一定清它 |
| 多个权威 NS | 各 NS 之间同步有延迟 |
| 客户端走不同 DNS | 不同出口解析结果可能不同 |

**最坏情况：生效时间 ≈ 原 TTL 的最大值。** 所以理论等待上限就是改之前那条记录的 TTL。

### 3.4.3 变更 DNS 的标准动作

```text
提前 1–2 天：把 TTL 从 3600 降到 60
     ↓（等原 TTL 过期，确保全网都记住了「短 TTL」）
变更当天：改记录
     ↓（60 秒内全网生效，可快速回滚）
稳定 1–2 天后：把 TTL 改回 3600
```

**为什么必须先降 TTL 再改**：原 TTL 是 3600，你直接把记录改成新 IP，但很多人缓存里还是「旧记录 + 还剩 3600 秒」。此时新 IP 出问题想回滚，**回滚也要等一小时**。

先降 TTL 的本质是：**把回滚窗口从一小时压到一分钟。**

### 3.4.4 清缓存

```bash
# systemd 系统
resolvectl flush-caches
resolvectl statistics              # 确认缓存状态

# 老系统 nscd
nscd -i hosts

# 确认系统用的哪个解析器
systemctl status systemd-resolved
```

浏览器缓存要单独清（Chrome：`chrome://net-internals/#dns`）。

## 3.5 CNAME 与 CDN 接入

```text
www.example.com  CNAME  www.example.com.cdn-provider.net
                              │
                              └─ CDN 的权威 DNS 按调度策略返回边缘节点 IP
```

| 事项 | 说明 |
|---|---|
| 接入后源站 IP 不能暴露 | A 记录直接指源站会绕过 CDN，失去防护与加速 |
| 回源 Host | CDN 回源带的 Host 要匹配源站 `server_name`，否则 404 |
| 缓存键 | 决定「什么算同一个资源」，配错会缓存穿透或串内容 |
| 缓存失效 | 发布新版本要主动 purge，否则用户看到旧资源 |
| 证书 | 边缘证书与源站证书是两套，**都要监控到期** |

判断 CDN 是否生效：

```bash
curl -I https://www.example.com/ | grep -Ei "via|x-cache|server|age"

# age 有值 → 命中缓存，数值是已缓存秒数
# x-cache: HIT / MISS → 最直接的判据
```

### 3.5.1 切流与回滚改哪一层：先分清接入形态

同一个域名，内网与公网走的是两条路。切流前先画清楚接入形态，**动手前先回答"这次要改哪一层"**：

| 接入形态 | 解析链 | 切流/回滚改哪层 |
|---|---|---|
| 内网直连域 | 内网 DNS A 记录直指源站 | 内网 DNS 的 A 记录 |
| CDN 加速域 | 公网 CNAME → CDN → 回源源站 | **CDN 控制台的「回源源站（+回源 HOST）」** |
| 公网 A 直连域 | 公网 DNS A 记录直指源站 | 公网 DNS 的 A 记录 |

三条铁律：

1. **CDN 加速域的切流与回滚只改 CDN 控制台回源**，改 DNS 记录无效；反过来，给 CDN 域补 A 记录会让部分流量直连源站、绕开 CDN——与迁移方向相反的反向操作。
2. **内网恢复 ≠ 公网恢复**：判定公网生效一律 `dig @公共DNS`；只改内网 DNS 时，公网用户走的仍是 CDN，两边结果可能完全不同（3.1.2 的双套解析）。
3. **回源目标必须公网可达**：源站填"可达入口"（前层公网 VIP/LB 或厂商提供的回源方式），不能填私网 IP，更不能填即将下线的旧机——回滚填错目标是比不回滚更糟的倒退。

CDN 会把迁移窗口里的失败响应也缓存。判定 404 是"缓存了旧 404"还是"真回源失败"：`X-Cache-Lookup: Hit` → 先 purge 该 URL/目录再判；`Miss` 仍 404 → 回源目标或配置错了，去控制台改。取证靠**带唯一参数的 curl + 源站分域日志行数对比**，不靠 `dig`——CDN 域的 `dig` 永远只回边缘节点 IP，看不出回源打到谁。

## 3.6 命令全集

```bash
# 基本查询
dig www.example.com +short              # 只要答案
dig A www.example.com                   # 指定类型
dig AAAA www.example.com
dig MX example.com

# 指定 DNS 服务器（换服务器对比，判断是不是本地 DNS 的问题）
dig @8.8.8.8 www.example.com
dig @223.5.5.5 www.example.com

# 追踪整个链路（看是哪一层没给答案）
dig +trace www.example.com

# 直接问权威、不走缓存（验证记录是否真的改到权威上了）
dig @ns1.yourdns.com www.example.com

# 看 TTL
dig www.example.com | grep -A1 "ANSWER SECTION"

# 反解
dig -x 1.2.3.4

# 系统层面解析（走完整 nsswitch，最接近应用行为）
getent hosts www.example.com

# 快速查
host www.example.com
nslookup www.example.com
```

### 3.6.1 dig 输出怎么看

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
                          ^^^^^^ 最重要
;; ANSWER SECTION:
www.example.com.  300  IN  A  1.2.3.4
                  ^^^ TTL
;; SERVER: 10.0.0.2#53(10.0.0.2)
          ^^^^^^^^ 实际用的是哪台 DNS
;; Query time: 12 msec
```

| status | 含义 | 判断 |
|---|---|---|
| `NOERROR` | 查询成功 | 但答案可能为空（记录不存在 ≠ 域名不存在） |
| `NXDOMAIN` | 域名不存在 | 记录没配、拼错、或 NS 未生效 |
| `SERVFAIL` | 服务器故障 | 权威不可达、DNSSEC 校验失败、上游超时 |
| `REFUSED` | 拒绝查询 | 该 DNS 不允许递归，或 ACL 限制 |

**`Query time` 是判断解析慢的直接依据**：正常在 10–50ms，超过 200ms 说明链路或 DNS 服务器有问题。

## 3.7 「改了不生效」的排查顺序

```text
① dig @权威NS 域名      → 权威记录改了吗？（没改 = 配置没提交/没生效）
② dig @8.8.8.8 域名     → 公共 DNS 拿到了吗？（没拿到 = 还在旧 TTL 内）
③ dig 域名              → 本地递归缓存呢？
④ getent hosts 域名     → 系统层面呢？（可能命中 hosts 或 nscd）
⑤ cat /etc/hosts        → 有没有写死
⑥ 换一台不同网络的机器测 → 排除本地环境干扰
```

这个顺序的价值：**从源头往终端走**，每一步明确排除一类原因，不会来回打转。

第 ① 步最容易被跳过。很多人直接从「我这边打不开」开始查，其实权威上根本没改成功。

## 3.8 十个坑

| # | 坑 | 现象 | 处置 |
|---|---|---|---|
| 1 | `/etc/hosts` 有旧记录 | DNS 改了本机不生效 | 第一步就 `cat /etc/hosts` |
| 2 | 直接改记录没先降 TTL | 想回滚也要等一小时 | 提前降 TTL 到 60 |
| 3 | CNAME 与 A 记录共存 | 记录失效或行为不确定 | 二选一 |
| 4 | 根域设 CNAME | 与 SOA/NS 冲突，整域异常 | 用 ALIAS/ANAME 或 A 记录 |
| 5 | resolv.conf 首个 DNS 不通 | **所有**解析都慢（每次等超时） | 检查 nameserver 可达性，调小 timeout |
| 6 | 只清系统缓存 | 浏览器仍用旧 IP | 浏览器 DNS 缓存单独清 |
| 7 | 以为 TTL 到期就一定生效 | 部分运营商无视 TTL | `dig +trace` 确认权威已改，再等各级过期 |
| 8 | 给 CDN 加速域加 A 记录"加速切流" | 部分流量直连源站、绕开 CDN，与迁移方向相反 | CDN 域只改控制台回源，不碰 DNS 记录（3.5.1） |
| 9 | 内网恢复就当公网恢复 | 内网直连域与公网 CDN 域是两条路，各自生效 | 判公网一律 `dig @公共DNS`（3.1.2、3.5.1） |
| 10 | 迁移期 404 被 CDN 缓存 | "午饭前 200、饭后 404"，期间无变更 | `X-Cache-Lookup` 分 Hit/Miss：Hit 先 purge 再判，Miss 查回源（3.5.1） |
