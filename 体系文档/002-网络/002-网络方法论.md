# 网络方法论

> **这一册回答**：面对「不通」「慢」「时好时坏」，思考顺序是什么——不重复任何命令细节，只给判断框架。命令在哪册，框架指路。
> **给谁读**：会配 IP、但连不通时不知道先看哪一层的运维。
> **工具无关**：本册不重复模块册的操作细节；每节末尾给「去哪册落地」。

## 分层截断

网络问题的第一原则：**栈是分层的，问题也分层——每层只回答「通/不通」，通就上移，不通就停在这层取数。**

从底向上的截断点：

| 层 | 回答的问题 | 落地 |
| --- | --- | --- |
| 链路 | 网线/交换机/ARP 通吗 | 111 |
| 路由 | 包知道往哪走吗（`ip route get`） | 111 |
| 传输 | 端口通吗——拒绝、超时、被拦三选一 | 112 |
| 防火墙 | 通与不通之间是不是被规则拦了 | 124 |
| 应用 | 服务本身响应吗（HTTP 状态码、TLS） | 121 / 122 |

**ping 九步与跨网段帧头重写**（111）是「链路+路由」两层的完整展开；**端口三态**（拒绝=没听、超时=路上丢、复位=被拦）是传输层的第一判据。

## 四要素拆解（慢 ≠ 不通）

「慢」用四个量拆，拆不出网络证据就转应用侧：

1. **带宽**——打满了没有（吞吐曲线）。
2. **时延**——RTT 多少、耗在哪一段（121 的耗时拆解）。
3. **丢包**——重传率（`nstat`）、哪些流在丢。
4. **抖动**——RTT 方差，交互类业务最敏感。

四要素全部正常而用户仍说慢 → 问题不在网络，转应用与数据库侧。

## 取证优先

- **包是最终证据**：争论「谁的问题」时抓包（tcpdump），看报文而不是看日志互相甩锅 → 131。
- **改动前先取数**：改路由、改防火墙之前先抓包、先记录，回滚路径写在改动旁边。
- **一次一个变量**：同一条链路上不要同时改路由和防火墙规则。

## 信任链思维

证书告警不先看服务器那张证书，**先看整条信任链**：根 → 中间 → 叶子，缺一环即告警（122）。域名「改了不生效」同理——先想 TTL 与缓存链（113），再想配置。

## 反模式

- ❌ 上来就重启网络服务——销毁现场，conntrack、路由缓存全没了。
- ❌ 只 ping 不看端口——ping 通≠端口通，ICMP 与 TCP 是两条路。
- ❌ 跨层猜——「可能是 DNS」之前先证明路由通。
- ❌ 无抓包互甩锅——应用怪网络、网络怪应用，一包定音。

## 自测

1. 端口「拒绝」「超时」「复位」分别指向什么？（没监听 / 路上丢或被丢 / 被防火墙拦）
2. 四要素是哪四个？全正常但用户说慢怎么办？（带宽/时延/丢包/抖动；转应用侧）
3. ping 通但端口不通，卡在哪层？（传输层——查监听与防火墙）
4. 为什么取证优先于改配置？（改了就销毁现场，包没了就说不清）
