## 7.1 定位：与 EFK、Loki 差在哪

| | EFK（001~003 册主线） | Loki（004 册对照） | **Graylog（本册）** |
|---|---|---|---|
| 形态 | 三件自拼：采集+存储+查询 | 两条自拼：采集+存储查询一体 | **一体化平台**：输入→提取→流→告警→角色内置 |
| 管理面 | Kibana 只管查询 | Grafana 顺带 | 平台自带 Web 管理面（Inputs/Streams/Index sets/Roles 全在界面上） |
| 存储引擎 | Elasticsearch | 自研（只索引标签） | Elasticsearch / OpenSearch |
| 适合 | 想完全掌控每个组件 | 不想养 ES 集群 | **想要"开箱的日志管理平台"、多团队分权限共用** |

一句话：EFK/Loki 是"组件集"，Graylog 是"产品"。它的代价是多养一个 Graylog 服务层与一套 MongoDB；收益是提取、分流、告警、权限不用自己拼。选型对照见 000 §0.4。

## 7.2 架构三件套：Graylog / ES / MongoDB

```plain
采集端 ──▶ Graylog 节点（解析/提取/缓冲）──▶ Elasticsearch（消息存储与检索）
                │
                └──▶ MongoDB（Graylog 自身的配置与状态：inputs/streams/users）
```

- **Graylog 自身不存消息**——所有日志都在 ES 里；Graylog 负责接收、提取、分流与查询转发。
- **MongoDB 存的是 Graylog 的配置与状态**（inputs、streams、用户、仪表盘定义）——它坏了不影响已有日志，但平台管理面整体异常。巡检把三件套一起纳：Graylog 进程、ES 集群（002 册）、MongoDB。
- 排障第一步永远是**分清卡点在哪一侧**：消息没到 Graylog（采集/网络）→ 卡在 Graylog 内部队列（接收高峰/写入阻塞）→ ES 写入失败（水位/分片/熔断）。三侧的日志分开看，别混。

## 7.3 接入：Inputs 与字段提取

- **Inputs 类型**：`GELF`（Graylog 原生结构化协议，首选）、`Beats`（复用 Filebeat 采集端——001 册的采集纪律直接沿用）、`Syslog`/`Raw`（设备与遗留系统兜底）。
- **提取两条路**：Extractor（正则/grok，界面点选，适合少量）与 Pipeline 规则（脚本化，适合批量）。纪律：**采集端能结构化的绝不留到服务端正则**——正则提取 CPU 高且脆弱，源端 JSON 化一次到位（005 册的字段公约在采集端就做）。
- 每个 Input 绑定到哪台 Graylog 节点、防防火墙断连——输入断流的取证走 006 册的"采集断流"路线，本册不重复。

## 7.4 索引与保留：index set 的 rotation + retention

Graylog 用 **Index Set** 管理自己的索引（默认前缀 `graylog`，按月可见 `graylog4_YYYYM` 形态），每套 index set 定义：

| 配置 | 语义 | 纪律 |
|---|---|---|
| Rotation（轮转） | 按大小（如 50GB）或按时间（按月/日）切新索引 | 按大小轮转更稳——日志量突增时时间轮转会造出巨索引 |
| Retention（保留） | 轮转出的旧索引怎么处理：删除 / 归档 | **rotation 与 retention 必须配对设**——只轮转不保留策略，磁盘迟早打满触发 ES 只读（002 册水位坑） |
| Shard/Replica | 每索引分片与副本数 | 小集群别照大集群抄分片数——分片过多本身是负担（002 §2.2） |

与 002 册 ILM 的关系：Graylog 的 index set 就是它自己的"ILM"，**走 Graylog 管理就别在 ES 侧再套 ILM**——两套轮转策略叠加会互相打架。

## 7.5 查询与权限：只读角色是默认交付形态

- 查询语法：`message:"timeout" AND source:app-01*`，配时间窗缩小范围；字段过滤 `level:ERROR`；保存为仪表盘给常见场景（错误 TOP、延迟分布）。
- **权限按角色交付**：给开发/业务方查日志，开**只读角色**（可查不可改 inputs/streams）；管理操作收敛在运维侧管理账号。整个链路的权限原则一句话：**查询口只允许查，不允许创建、修改、删除**——需要新查询需求走运维，这同时是审计边界。
- 查询慢的先看 7.6 分卡点，再谈调优——多数"Graylog 慢"是 ES 侧的病。

## 7.6 排障两案

### 案一：日志延迟、部分搜不到（单分片异常）

现象：用户报"日志延迟、部分搜不到"；Graylog 日志**持续刷 `shard_not_found_exception`**（指向某索引某分片）；`_cat/shards` 显示该索引 **shard N 的 primary 无数据、replica 却有几百万条**——主副数据脱节。**最迷惑的一点：ES 集群健康是 `green`、未分配分片 0**——集群级监控完全看不出问题，这是**单分片级异常**的监控盲区。已验证：重启 Graylog 服务无效（错误照旧）——病在 ES 侧分片，重启 Graylog 治不了。

处置四步：① **摸清**：`_cat/shards` 找出异常分片，对比主副文档数定脱节事实；② **止血**：对该索引立即轮转（新流量写新索引，旧索引冻结损失可控）；③ **修分片**：按脱节方向重置异常副本/重建分片（⚠️ 涉及删分片目录，先快照再动手）；④ **收尾**：补一条分片级告警（`_cat/shards` 的 UNASSIGNED/脱节检测），别指望集群健康状态兜底。

### 案二：副本初始化卡死 + 内存熔断（堆内存不足）

现象：某索引副本分片长期 `INITIALIZING` 反复卡死；ES 日志刷 `CircuitBreakingException`——**分片恢复预留内存超出断路器上限**。根因链：**机器内存不小，JVM 堆却配得极小**（如 16G 机器只给 2G 堆，断路器约 1.8G）——分片恢复不仅要传磁盘文件，还要**内存里构建索引结构、回放事务日志**，小堆直接被熔断拦截；恢复反复失败 → 残留分片目录 → 初始化卡死；ES 默认恢复并发限流又加剧排队。

处置五步（全程主分片正常读写，无业务中断，仅短暂缺副本）：① 备份 `jvm.options`；② 调整 `-Xms/-Xmx`（机器内存的 **50%** 是 ES 官方口径）；③ 重启 ES；④ 清 swap；⑤ 验证：`curl -s 'http://localhost:9200/_nodes/jvm?pretty' | grep heap_max_in_bytes` 看生效值。**本案最大的认知坑**：改之前看 `free`，"已用 13G"吓人不敢调——**那大部分是 buff/cache，可回收**；真实常驻只有 3G 出头，调到 8G 堆毫无压力。判断内存够不够，看 `available`，不看 `used`（「Linux」003 的 free 三行判读）。

## 7.7 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | ES 集群 green 就当全健康 | 单分片主副脱节零告警，查询延迟/丢数据 | 分片级巡检：`_cat/shards` 对比主副文档数（7.6 案一） |
| 2 | 查询慢/延迟就重启 Graylog | 病在 ES 分片，重启无效还断查询 | 先分卡点：采集 → Graylog 队列 → ES 写入（7.2、7.6） |
| 3 | `free` 里 used 大就不敢调堆 | 16G 机器配 2G 堆，恢复熔断卡死 | buff/cache 可回收，看 available；堆 = 内存 50%（7.6 案二） |
| 4 | 副本 INITIALIZING 就反复重启 ES | 残留分片目录 + 恢复限流，越搞越卡 | 先查熔断日志修堆，再管恢复（7.6 案二） |
| 5 | MongoDB 不纳巡检 | 平台管理面整体异常才发现它也在这条链上 | 三件套一起监控（7.2） |
| 6 | 给开发开管理账号查日志 | 误改 inputs/streams，审计说不清 | RBAC 只读角色，写操作收敛管理端（7.5） |
| 7 | 服务端正则提取字段 | CPU 高、规则脆弱 | 采集端 JSON 化一次到位（7.3） |
| 8 | index set 只配轮转不配保留 | 磁盘打满触发 ES 只读（002 水位坑） | rotation + retention 配对设（7.4） |
