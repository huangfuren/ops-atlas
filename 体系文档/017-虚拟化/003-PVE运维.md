## 3.1 定位：与 VMware、KVM 的对照

| | VMware vSphere（001 册） | KVM（002 册） | **PVE（本册）** |
|---|---|---|---|
| 形态 | 商业全家桶（ESXi+vCenter） | 裸 hypervisor + libvirt 生态 | **Debian 底座把 KVM+LXC 打包成开源平台** |
| 管理面 | vCenter | 自己拼（virsh/cockpit 等） | **自带 Web 管理面与 REST API** |
| 虚拟机/容器 | VM | VM | **VM + LXC 容器双形态** |
| 成本 | 许可费 | 免费 | 开源免费（可选订阅源） |
| 适合 | 企业存量、需要商业支持 | 云厂商底座、深度定制 | **自建机房想开箱即用的开源方案** |

一句话：PVE 是"KVM 的易用发行版"——002 册的 KVM 概念全部适用，外面套了一层集群化管理面。选型细节见 000 全貌。

## 3.2 节点与集群：归属是动态的

- **实体**：物理服务器加入集群后成为**节点（Node）**；节点上跑**虚拟机（VM，有 VMID）**与 **LXC 容器（CT）**。一台 VM 任一时刻只归属一个节点。
- **集群配置库 pmxcfs**：加入集群后，`/etc/pve` 是分布式的——集群配置（虚拟机定义、存储、网络）全节点一致，改动走管理面，**别绕过它直接改某节点的本地配置**（漂移源头）。
- **仲裁**：集群节点数取奇数，偶数节点加 qdevice 仲裁——防止脑裂。
- **关键推论：VM 的宿主归属随时间变**——在线迁移是常规操作。任何"这台 VM 在 pve01 上"的记录都必须**带采集时间戳**，台账要定期刷新（3.3）。

## 3.3 核心命题：虚拟机 IP → 宿主机

PVE 运维最频繁的真实诉求：**拿到一个虚拟机 IP，它跑在哪台宿主机上？** 信息散落在各节点，排障、变更、关停前都必须先回答。三条查法，从优到兜底：

| 路 | 做法 | 适用 |
|---|---|---|
| ① 管理面一次列全 | API `GET /cluster/resources`（或 Web 的 Datacenter 视图）——全网 VM 列表带所在 node | 集群管理面可用时，**首选** |
| ② 逐节点列 | 每节点 `qm list`（VM）/ `pct list`（CT），对 IP | 集群面异常时 |
| ③ MAC 表兜底 | IP → ARP → MAC → 交换机 MAC 表定位物理端口 → 宿主机 | 管理面与节点都失联（016-005 的溯源实证） |

**治本**：把"IP ↔ 宿主机"做成定期采集的映射台账（带时间戳），接进巡检或数据层——这个映射缺位是 PVE 运维公认的短板，建一次受用一次。

## 3.4 API 优先的运维方式

PVE 的一切操作都有三个入口：Web（:8006）、`pvesh` 命令行、REST API（`/nodes/<node>/qemu/<vmid>/...`）。**生产纪律：API 优先**——

- 用 **API Token**（而非共享账号密码）做权限最小化；
- **全链路 API 操作 = 任务日志天然留痕**：谁在何时对哪个 VMID 做了什么，平台任务列表可回溯——变更审计不靠人记；
- 案例形态：一次虚拟机重启，从优雅关机到强制下电到开机，全程 API 完成，**未登录宿主机执行任何命令**——排查与审计都在管理面闭环。

## 3.5 存储与网络速览

| 域 | 默认 | 进阶 |
|---|---|---|
| 存储 | `local`（ISO/备份）、`local-lvm`（盘镜像） | **ZFS**（快照利器，001 册的快照纪律同样适用）、**Ceph**（生产共享存储，热迁移不依赖同宿主存储） |
| 网络 | `vmbr0` Linux bridge（最常见） | **OVS + VLAN**（多 VLAN 环境；容器/VM 静态 IP 的溯源沿宿主机 OVS 桥拓扑下钻——「安全运维」005 的实证手法） |

数据盘容量在 VM 侧看（盘满 100% 是卡死前兆之一，3.6）。

## 3.6 虚拟机卡死处置全案

**判定先于操作**——五个指标定"是不是真卡死"（对照日常基线看）：

| 指标 | 卡死形态 | 正常 |
|---|---|---|
| CPU | 打满（如 8 vCPU 占满 vs 日常 0.27） | 平稳基线 |
| **Guest Agent** | `last_update` 冻结（分钟级不刷新）= **失联** | 秒级心跳 |
| 网络 | netin/netout 归零 | KB/s 级常态 |
| 磁盘 I/O | 读风暴后骤然归零、idle_time 持续增长 | 有读写 |
| 磁盘容量 | 数据盘 100% 写满 | 有余量 |

**24 小时 RRD 走势比当前值值钱**：真实案例里"读风暴 220~240 MB/s 持续十小时（累计约 7TB）、把磁盘缓存挤掉 → CPU 拉升 → 网络归零"的完整因果链只有走势图能还原；同期的 **VNC 控制台登录记录**（谁在几点开过 70 秒会话）是人为操作介入的关键线索。

**处置顺序**（⚠️ 强制断电 = 未落盘数据丢失 + 文件系统检查 + k8s 类业务负载驱逐，先说后果再动手）：

1. **优雅关机**：`shutdown`（ACPI + Guest Agent）——Agent 失联时会僵死无响应；
2. **僵死任务占锁**：随后再发操作报 lock 冲突——**先终止僵死的 shutdown 任务释放锁**，这不是重试能解决的；
3. **强制下电**：`stop`（等价断电）；
4. **开机**：`start`；
5. **三层复核**：Guest Agent 心跳恢复 → CPU/内存回日常基线 → **业务层验证**（如 k8s 节点回 Ready、全节点数闭合）。

## 3.7 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 只会登录宿主机敲 `qm` | 绕过权限体系，变更无审计留痕 | API 优先 + Token，任务日志即留痕（3.4） |
| 2 | 拿 IP 找宿主机靠逐台翻界面 | 应急定位慢，变更窗口白耗 | 集中映射台账 + `/cluster/resources`，MAC 表兜底（3.3） |
| 3 | 优雅关机无响应就反复发 shutdown | 僵死任务占锁，后续 stop 全部失败 | 先终止僵死任务释放锁（3.6） |
| 4 | 只看当前指标不看 RRD 走势 | 读风暴→缓存挤掉→卡死的因果链不可见 | 24h 走势 + VNC 登录线索（3.6） |
| 5 | Guest Agent 失联不当回事 | 优雅关机永久失效，只能强断电 | Agent 心跳纳入巡检，冻结即告警（3.6） |
| 6 | 绕过管理面直接改节点本地配置 | pmxcfs 同步语义不明，配置漂移 | 集群改动一律走管理面（3.2） |
| 7 | VM 归属记录一次当永久 | 在线迁移后台账全错 | 归属带时间戳、定期刷新（3.2、3.3） |
| 8 | 数据盘写满才处理 | Guest 卡死前兆（100% 写满实案） | 容量告警进监控（3.6） |
