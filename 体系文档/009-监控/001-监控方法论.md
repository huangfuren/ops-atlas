## 1. 监控要回答的四个问题

上一册（000 全貌）画了板块地图；本册先立方法，再谈工具。

任何一条监控规则，背后都应能回答：

| 问题 | 答不上来的后果 |
|---|---|
| 该监控什么 | 指标堆了一屏，故障时不知道看哪个 |
| 怎么采 | 采集间隔、协议选错，数据不可用 |
| 怎么判断异常 | 阈值拍脑袋，误报漏报都来 |
| 告警之后谁做什么 | 告警发出去没人接，等于没告警 |

工具只解决第二个问题。前三个是方法论，第四个是组织流程。

## 2. USE：资源视角

上一节列了四个问题；本节给「资源类」对象一个固定检查表。

USE 由 Brendan Gregg 提出，针对**每一种资源**问三个问题：

| 维度 | 含义 | 典型指标 |
|---|---|---|
| Utilization（使用率） | 资源忙的时间占比 | CPU 使用率、磁盘 IO 利用率、带宽占用 |
| Saturation（饱和度） | 排队/等待的程度 | run queue 长度、IO await、TCP accept 队列 |
| Errors（错误） | 出错计数 | 网卡 drop/error、磁盘 ECC、内存 CE |

**为什么三个都要**：使用率 70% 但 run queue 已经很长，说明已经在排队；使用率 95% 但无排队，可能只是短时突发。只看使用率会误判。

主机与网络设备巡检的最小集：

```plain
CPU：使用率（按核）+ load average + run queue
内存：used / available + swap in/out + OOM 计数
磁盘：util% + await + 剩余空间 + inode
网络：带宽利用率 + drop/error + 重传
```

Zabbix 的默认模板基本覆盖了这三类；Prometheus 侧对应 `node_*` 与 `container_*`。

## 3. RED：服务视角

上一节看资源；本节看「用户感受到的服务」。

RED 由 Tom Wilkie 提出，针对**每一个服务**问三个问题：

| 维度 | 含义 | 指标 |
|---|---|---|
| Rate | 每秒请求数 | `rate(http_requests_total[5m])` |
| Errors | 失败请求比例 | 5xx / 总请求 |
| Duration | 请求耗时分布 | P50/P95/P99，不是平均值 |

**为什么用分位数**：平均 100ms 可能由「99% 请求 50ms + 1% 请求 5s」构成。用户感知的是长尾，告警要盯 P99。

RED 适合有明确请求边界的服务（HTTP/gRPC/队列消费）。批处理任务用「成功率 + 处理时长 + 积压量」替代。

## 4. 四大黄金信号

上一节是服务视角；本节是 Google SRE 给出的通用四件套，适合跨团队统一语言。

| 信号 | 回答 | 例子 |
|---|---|---|
| Latency（延迟） | 请求多快 | P99 接口耗时 |
| Traffic（流量） | 有多少需求 | QPS、并发连接数 |
| Errors（错误） | 失败多少 | 5xx 率、超时率 |
| Saturation（饱和度） | 最紧的资源有多满 | CPU、连接池、队列深度 |

与 USE/RED 的关系：黄金信号是**顶层**，USE 偏资源、RED 偏服务。实际落地时：

- 业务/服务层用 RED + 黄金信号；
- 主机/中间件层用 USE；
- 两者通过「饱和度」这一共同语言对接。

## 5. 五层分层与下钻

上一节给了指标集；本节给「故障时从哪层看起」。

| 层 | 看什么 | 典型告警 |
|---|---|---|
| 业务 | 下单成功率、登录成功率 | 业务指标跌破基线 |
| 应用 | 请求率、错误率、P99 | 5xx 超阈值、P99 劣化 |
| 中间件 | 连接数、队列、缓存命中、慢查询 | 连接池满、队列积压 |
| 主机 | CPU、内存、磁盘、网络 | 磁盘满、OOM、负载高 |
| 网络 | 丢包、重传、带宽、DNS | 端口不通、丢包率上升 |

**下钻顺序**：业务告警 → 看应用 RED → 看依赖中间件 → 看主机 USE → 看网络。不要反过来从 CPU 开始猜业务。

分层的纪律：**每层只回答一个问题**。主机层不要塞业务指标，业务层不要塞磁盘 inode——混层的看板在故障时没人看得懂。

## 6. 监控反模式

上一节给了正向结构；本节列八种常见错法，对照自查。

| # | 反模式 | 为什么错 | 改法 |
|---|---|---|---|
| 1 | 指标堆砌，能采的全采 | 基数爆炸、看板失焦 | 按 USE/RED 选，先问「这条指标触发什么动作」 |
| 2 | 只监控资源，不监控业务 | CPU 正常但用户已经下不了单 | 补业务成功率与关键路径 |
| 3 | 阈值拍脑袋 | 业务有峰谷，固定阈值必误报 | 用近 30 天 P95 做基线，分时段 |
| 4 | 只看平均值 | 长尾被平均掉 | 用 P95/P99 与最大值 |
| 5 | 告警无 owner | 发出去没人认领 | 每条规则绑定团队/值班组 |
| 6 | 告警等级通胀 | 全是 High 等于没分级 | 按响应动作分级，Information 不通知 |
| 7 | 监控系统自身不被监控 | Prometheus/Zabbix 挂了全网盲 | 自监控 + 外部拨测 |
| 8 | 看板只用于展示 | 好看但不支持排查 | 按「从症状到根因」组织面板 |

## 7. 与 SLO 的衔接

上一节讲反模式；本节讲「阈值从哪来」的终极答案——SLO。

| 概念 | 定义 | 与监控的关系 |
|---|---|---|
| SLI | 可量化的服务质量指标 | 直接来自监控（成功率、P99） |
| SLO | SLI 的目标值 | 决定告警阈值与错误预算 |
| 错误预算 | 1 - SLO 的可消耗额度 | 决定发布节奏与故障优先级 |
| Burn rate | 预算消耗速度 | 多窗口燃尽率告警，比固定阈值稳 |

**落地顺序**：先有 SLI（监控采得到）→ 定 SLO（业务能接受）→ 用 burn rate 配告警（SRE 001 展开）。没有 SLI 就直接设阈值，是「拍脑袋」的根源。

Prometheus 侧的 burn rate 告警写法见 `prometheus/006 告警规则实战`；Zabbix 侧可用 `avg()` 窗口 + 多触发器模拟。

## 8. 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | CPU 90% 就告警，但业务正常 | 把资源使用率当业务健康 | 资源告警降级，补业务 RED |
| 2 | 平均延迟正常，用户仍投诉慢 | 长尾被平均 | 改 P95/P99 |
| 3 | 同一含义三个指标名 | 各团队各自埋点 | 统一命名与单位，写进规范 |
| 4 | 指标基数每月翻倍 | 无界 label（user_id、pod 名） | 删高基数 label，聚合后再存 |
| 5 | 采集间隔 1 分钟，故障 30 秒就过去 | 采样太稀 | 核心指标 15~30s，其余放宽 |
| 6 | 扩容后告警全响 | 阈值按旧容量设 | 阈值随容量与基线更新 |
| 7 | 单机看正常，集群已过载 | 只看单实例 | 补聚合视角与集群饱和度 |
| 8 | 新服务上线没有基线 | 直接套模板阈值 | 先观察一周，再设阈值 |

## 9. 检查清单

| # | 问题 | 判据 |
|---|---|---|
| 1 | 每条指标都能对应一个动作吗？ | 答不出「触发后谁做什么」就删 |
| 2 | 资源层三个 USE 维度齐吗？ | 使用率、饱和度、错误都有 |
| 3 | 服务层三个 RED 维度齐吗？ | 速率、错误、时延分布都有 |
| 4 | 用的是分位数不是平均值吗？ | 关键接口有 P95/P99 |
| 5 | 五层都有人负责吗？ | 每层告警有 owner |
| 6 | 阈值有基线依据吗？ | 能说清来自近 30 天哪个分位 |
