# 00 术语表

> **这一文档回答**：某个词的准确定义、两个混用词的分界、「症状出现时病根在哪个机制」往哪走。  
> **怎么用**：按名字（按册分组）、按缩写（缩写速查）、按症状（症状反查）。  
> **只有一句话**：要落地动作回对应册；这里保证「认得出、分得清、找得到」。

## 000 两流派与选型

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 拉模式 | pull | 服务端主动到被监控端取数；Prometheus 的默认模型 |
| 推模式 | push | 被监控端主动上报；Zabbix 主动检查、SNMP trap、StatsD 属于此 |
| 混合模式 | hybrid | Zabbix 同时支持被动检查（server 连 agent）与主动检查（agent 连 server） |
| 数据采集器 | poller | Zabbix server 里负责被动取数的进程，数量由 `StartPollers` 决定 |
| 捕获器 | trapper | 接收主动上报数据的进程，由 `StartTrappers` 决定 |
| 时序数据库 | TSDB | 为时间序列优化的存储；Prometheus 自带，Zabbix 用关系库 |
| 关系库存储 | RDBMS storage | Zabbix 把历史与趋势写进 MySQL/PostgreSQL，靠 housekeeper 清理 |
| 网络设备监控 | network device monitoring | 以 SNMP 为主的交换机、路由器、防火墙监控，Zabbix 的强项 |
| 无代理监控 | agentless | 不装 agent，靠 SNMP/SSH/IPMI 等标准协议取数 |
| 选型分界 | selection boundary | 动态容器环境选 Prometheus，传统 IT 与网络设备选 Zabbix，二者可并存 |

## 001 架构与部署

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| Zabbix server | Zabbix server | 核心进程，负责采集调度、触发器求值、告警分发 |
| Zabbix agent2 | Zabbix agent2 | 部署在被监控机上的采集端，Go 重写，支持插件与主动/被动 |
| Zabbix proxy | Zabbix proxy | 区域代理，替 server 采集并缓存，断网可续传 |
| 前端 | frontend | PHP 写的 Web 界面，读写同一套数据库 |
| Java gateway | Zabbix Java gateway | 接收 JMX 数据的独立进程，端口 10052 |
| 被动检查 | passive check | server 连 agent 的 10050 端口取数，agent 不主动外联 |
| 主动检查 | active check | agent 连 server/proxy 的 10051 端口上报，适合跨网段 |
| 主机名匹配 | Hostname matching | 主动检查靠 `Hostname` 与前端主机名严格一致，不一致即无数据 |
| 配置缓存 | configuration cache | server 内存里的主机/监控项/触发器快照，改完需重载 |
| 历史与趋势 | history / trends | 历史是原始值（按秒/分），趋势是小时聚合，保留期分别配置 |
| housekeeper | housekeeper | 按保留期删历史、趋势、事件的后台进程 |
| 前端时区 | frontend timezone | PHP 时区决定图表时间轴，配错会出现「数据晚 8 小时」 |
| SELinux 布尔值 | SELinux boolean | `httpd_can_connect_zabbix` / `httpd_can_network_connect_db`，不开则前端连不上 |
| 安装向导 | setup wizard | 首次访问 Web 的配置流程，写 `conf/zabbix.conf.php` |

## 002 模板与 LLD

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 模板 | template | 监控项、触发器、图形、LLD 规则的集合，主机通过链接继承 |
| 链接与解除 | link / unlink | 链接是继承模板；解除后可选择保留或删除已生成实体 |
| 宏 | macro | 模板级/主机级的可替换变量，`{$SNMP_COMMUNITY}` 是典型 |
| 用户宏 | user macro | 前端可改的 `{$NAME}` 变量，覆盖模板默认值 |
| 低级发现 | LLD (low-level discovery) | 自动发现磁盘、网卡、接口等动态实体并批量生成监控项 |
| 发现规则 | discovery rule | LLD 的入口，key 如 `vfs.fs.discovery`，返回 JSON 数组 |
| 监控项原型 | item prototype | 发现到一个实体就按原型生成一个监控项 |
| 触发器原型 | trigger prototype | 每个发现实体自动生成对应触发器 |
| 过滤器 | filter | 用 `{#FSNAME}` 等宏条件筛掉不想要的实体（如 tmpfs） |
| 覆盖 | overrides | 对满足条件的实体改阈值、改间隔、禁用，比过滤器更细 |
| 实体宏 | LLD macro | 发现结果里的 `{#IFNAME}`、`{#SNMPINDEX}`，用于命名与取值 |
| SNMP | Simple Network Management Protocol | 网络设备的标准取数协议，v2c 用 community，v3 用用户认证 |
| OID | Object Identifier | MIB 树上的节点地址，如接口状态 `.1.3.6.1.2.1.2.2.1.8` |
| MIB | Management Information Base | OID 的语义字典，`snmptranslate` 靠它把数字翻译成名字 |
| community | SNMP community | v1/v2c 的明文口令，等同于只读密码，必须当凭据管理 |
| SNMP trap | SNMP trap | 设备主动推送的告警事件，与轮询取数互补 |
| snmpwalk | snmpwalk | 从某个 OID 起遍历子树的命令，验证设备可读性的第一步 |

## 003 触发器与告警动作

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 触发器 | trigger | 对监控项求值的布尔表达式，成立即产生问题事件 |
| 表达式 | expression | `min(/host/key,5m)>90` 这类函数式判定，含时间窗口 |
| 恢复表达式 | recovery expression | 单独定义「何时算恢复」，默认是表达式不再成立 |
| 未知状态 | unknown | 取不到数据且未配 nodata 时的状态，不等于正常 |
| nodata | nodata() | 在窗口内没有新数据时成立，用于「采集断了」类告警 |
| 触发器依赖 | trigger dependency | 上游触发器告警时抑制下游，避免一故障刷屏 |
| 事件 | event | 触发器状态变化的记录，问题与恢复各一条 |
| 动作 | action | 事件发生后做什么：发消息、执行远程命令、升级 |
| 操作 | operation | 动作里的具体步骤，可带步骤时长与升级链 |
| 升级 | escalation | 未确认未恢复时逐级通知，按 step duration 推进 |
| 媒体类型 | media type | 投递通道：Email、Webhook、Script、SMS |
| 维护窗口 | maintenance | 计划内变更期间抑制告警，可只抑制某类或全部 |
| 告警抑制 | suppression | 由依赖或维护产生的「不通知但仍记录」状态 |
| 严重级别 | severity | 未分类→信息→警告→一般严重→严重→灾难，六级 |

## 004 分布式 Proxy

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 主动 Proxy | active proxy | Proxy 主动连 server 取配置、送数据，适合 server 不可达 Proxy 的网络 |
| 被动 Proxy | passive proxy | server 连 Proxy 的 10051 取数据，适合 Proxy 有固定公网/可路由地址 |
| 配置频率 | ProxyConfigFrequency | 主动模式下 Proxy 拉配置的间隔，默认 3600 秒 |
| 数据发送频率 | DataSenderFrequency | Proxy 向 server 送数据的间隔，默认 1 秒 |
| 本地缓存 | local buffer | Proxy 断网时把数据写本地库，恢复后按序补传 |
| 队列 | queue | server 内待处理数据积压，队列涨说明后端或数据库跟不上 |
| 代理组 | proxy group | 6.0 起的负载均衡分组，多 Proxy 共管一批主机 |
| 主机可达性 | host availability | 主动/被动检查的可用性状态，影响「无数据」判定 |

## 005 API 自动化

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| JSON-RPC | JSON-RPC 2.0 | Zabbix API 的协议格式，统一 POST 到 `api_jsonrpc.php` |
| 会话认证 | session auth | 6.0 用 `user.login` 换 sessionid，后续请求带 `auth` 字段 |
| API 令牌 | API token | 7.0 起推荐的长期凭据，用 `Authorization: Bearer` 头 |
| 方法 | method | `host.get`、`trigger.get` 这类操作名，命名规律是「实体.动作」 |
| 输出字段 | output | 控制返回哪些字段，`extend` 返回全部，`["hostid","host"]` 只返回指定 |
| 关联查询 | select* | `selectInterfaces`、`selectParentTemplates`，一次取回关联对象 |
| 批量创建 | mass create | 一次传数组建多台主机，失败整批回滚 |
| 幂等导入 | idempotent import | 先查后建、存在即更新，脚本可重复执行的写法 |

## 最容易混的 12 对

| A vs B | 分界一句话 |
| --- | --- |
| 主动检查 vs 被动检查 | 谁发起连接：agent 连 server 是主动，server 连 agent 是被动 |
| 主动 Proxy vs 被动 Proxy | 谁发起连接：Proxy 连 server 是主动，server 连 Proxy 是被动 |
| 模板 vs 主机 | 模板是定义，主机是实例；主机链接模板后继承并可覆盖 |
| 用户宏 vs LLD 宏 | `{$NAME}` 是人写的配置；`{#NAME}` 是发现结果自动填的 |
| 监控项 vs 触发器 | 监控项取数存值；触发器对值求值判状态 |
| 触发器依赖 vs 维护窗口 | 依赖是「上游坏了不报下游」；维护是「计划内不报」 |
| 历史 vs 趋势 | 历史是原始点，趋势是小时聚合；保留期与容量分开算 |
| 未知 vs 正常 | 未知是取不到数，正常是取到且未越界；前者更需要告警 |
| 发现规则 vs 监控项原型 | 规则负责「找到实体」，原型负责「为每个实体生成监控项」 |
| 过滤器 vs 覆盖 | 过滤器决定「要不要」，覆盖决定「生成后怎么改」 |
| 事件 vs 问题 | 事件是状态变化流水；问题是当前未恢复的那一条 |
| community vs v3 用户 | v2c 是明文口令；v3 有认证与加密，安全要求高时必须用 v3 |

## 按症状反查

| 症状 | 最可能病根 | 去哪 |
| --- | --- | --- |
| 主机显示「ZBX 灰色」但 agent 在跑 | 主动检查 Hostname 与前端不一致，或 10051 不通 | 001 §3 |
| 前端打开 502/空白页 | php-fpm 未起、nginx 配置未 include、SELinux 拦截 | 001 §2 |
| 图表时间整体偏 8 小时 | PHP 时区未设 `Asia/Shanghai` | 001 §2 |
| 新加磁盘/网卡没有自动出图 | LLD 规则未跑、过滤器把实体筛掉、原型未启用 | 002 §2 |
| 交换机所有接口都取不到值 | community 错、ACL 拦了 server、OID 不支持 | 002 §3 |
| 一台交换机重启刷出几十条告警 | 未配触发器依赖，接口与主机告警同时爆 | 003 §2 |
| 告警发了但没人收到 | 用户未配媒体、动作条件不匹配、媒体类型未启用 | 003 §3 |
| 同一问题重复发多条 | 恢复表达式缺失，或动作的 update 操作重复触发 | 003 §3 |
| 队列持续增长不下降 | 数据库慢、housekeeper 抢占、poller 不足 | 004 §4 |
| Proxy 断网恢复后数据缺失 | 本地缓存库损坏或 `ProxyConfigFrequency` 过长 | 004 §2 |
| API 返回 `Session terminated` | sessionid 过期（默认 15 分钟空闲）或未带 auth | 005 §1 |
| 批量建主机报 `Host already exists` | 未做先查后建，重复执行不幂等 | 005 §3 |
