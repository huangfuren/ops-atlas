# 00 术语表

> **这一文档回答**：监控领域的词是什么意思、两个混用词的分界、「出现某个现象该往哪查」。  
> **怎么用**：按主题（下面四组）、按缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和命令回对应册；这里只保证你「认得出、分得清、找得到」。Prometheus 工具自身的术语（target/job/series 等）见 [prometheus/00-术语表](prometheus/00-术语表.md)。

## 01 方法与指标设计

| 术语 | 英文 | 一句话 |
|---|---|---|
| 监控 | monitoring | 采集指标、发现异常、触发响应的完整体系 |
| 可观测性 | observability | 监控+日志+链路的统称——从外部输出推断系统内部状态的能力 |
| 指标 | metric | 带名字与维度的时间序列数值，唯一适合做告警源的信号 |
| 时间序列 | time series | 同名指标按时间排列的一串样本 |
| 白盒监控 | white-box | 读系统内部暴露的指标（如 /metrics），知道内部状态 |
| 黑盒监控 | black-box | 从外部探测服务表现（HTTP/端口/拨测），只看结果不看内部 |
| 拨测 | synthetic monitoring | 定时模拟真实请求打关键路径，验证"用户视角还活着" |
| USE 方法 | USE | 对每类**资源**问 Utilization/Saturation/Errors 三件事 |
| RED 方法 | RED | 对每个**服务**问 Rate/Errors/Duration 三个指标 |
| 四大黄金信号 | golden signals | 延迟、流量、错误、饱和度——告警优先围绕它们 |
| SLI | Service Level Indicator | 服务水平的测量值，如"成功率 99.9%"里的成功率 |
| SLO | Service Level Objective | 对 SLI 设定的目标值，如"季度成功率 ≥ 99.9%" |
| SLA | Service Level Agreement | 带对外赔偿条款的协议，SLO 是它的技术内核 |
| 错误预算 | error budget | 1 − SLO 允许的失败额度，花完就冻结发布修可靠性 |

## 02 形态与协议

| 术语 | 英文 | 一句话 |
|---|---|---|
| 拉模式 | pull model | 监控端定期来抓（Prometheus 默认）——目标挂了能被立刻发现 |
| 推模式 | push model | 被监控端主动上报（如 SNMP trap、StatsD）——需要网关承接短命任务 |
| SNMP | Simple Network Management Protocol | 交换机/路由器等网络设备的通用"读数语言"——网管站经 OID 树拉取（GET）与接收设备主动上报（TRAP） |
| OID | Object Identifier | SNMP 管理对象在编号树上的路径 |
| MIB | Management Information Base | 把 OID 编号翻译成可读名字的字典 |
| agent | — | 装在被监控对象上、代为暴露或转发数据的进程 |
| 心跳 | heartbeat | 周期性"我还活着"信号，断了即判故障 |
| 降采样 | downsampling | 把高精度旧数据压缩成低精度长保留数据，控存储成本 |
| 保留策略 | retention | 指标/日志存多久，不配的策略是未来爆盘的根因 |

## 03 响应与运维

| 术语 | 英文 | 一句话 |
|---|---|---|
| 告警 | alert | 指标越过阈值/条件后发给人或自动化系统的通知 |
| 事件 | incident | 需要人介入处置的异常，一组相关告警的业务级汇总 |
| 告警疲劳 | alert fatigue | 告警太多太滥导致没人看——监控体系失效的头号原因 |
| 告警风暴 | alert storm | 一个根因触发成百上千条告警，靠分组与抑制收敛 |
| 静默 | silence | 指定时间段/标签范围不收告警（维护窗口用） |
| 抑制 | inhibition | 某告警触发时压掉由此引起的其他告警（断根因只剩叶子响） |
| 分组 | grouping | 同类告警合并成一条通知，防止刷屏 |
| on-call / 值班 | — | 轮流承担告警响应的制度，纪律见「SRE」002 |
| 升级 | escalation | 告警无人认领时逐级通知下一响应人的机制 |
| runbook | — | 告警附带的处置手册——告警没有动作项就不该存在 |
| MTTD | Mean Time To Detect | 平均发现故障耗时——监控系统存在的第一理由 |
| MTTR | Mean Time To Recover | 平均恢复耗时——含定位、修复、验证全程 |
| MTBF | Mean Time Between Failures | 两次故障的平均间隔，越长越可靠 |
| MTTF | Mean Time To Failure | 不可修复组件的平均寿命 |
| 巡检 | patrol/inspection | 不等告警、按周期主动查水位的例行动作 |
| 自监控 | meta-monitoring | 监控系统自己也被监控——否则挂了全网全盲 |

## 04 数据与生态

| 术语 | 英文 | 一句话 |
|---|---|---|
| 基数 | cardinality | 一个指标下所有标签组合出的序列总数——监控内存的头号变量 |
| 标签 | label | 指标的维度键值对，值域无界的标签是基数炸弹 |
| 仪表盘 | dashboard | 指标的可视化编排，服务于排查路径而非装饰 |
| 数据源 | datasource | 仪表盘从哪读数（Prometheus/Loki/…） |
| TSDB | Time Series Database | 时序数据库：按时间+标签索引的 KV 存储 |
| 预聚合 | pre-aggregation | 高频明细先算成低基数聚合值，查询与基数双省 |
| exporter | — | 把某系统状态翻译成 /metrics 文本的数据源适配器 |
| 保留期 | retention period | 本地/远程数据保留的时长，容量规划的输入 |

## 缩写速查

| 缩写 | 全称 | 一句话 |
|---|---|---|
| MTTD | Mean Time To Detect | 平均发现耗时——越小说明监控越灵 |
| MTTR | Mean Time To Recover | 平均恢复耗时——值班能力的直接体现 |
| MTBF | Mean Time Between Failures | 平均无故障间隔 |
| MTTF | Mean Time To Failure | 不可修复件的平均寿命 |
| SLI | Service Level Indicator | 水平测量值 |
| SLO | Service Level Objective | 水平目标 |
| SLA | Service Level Agreement | 对外协议（含赔偿） |
| SNMP | Simple Network Management Protocol | 网络设备通用监控协议 |
| NMS | Network Management Station | SNMP 的网管站（如 Zabbix Server） |
| APM | Application Performance Monitoring | 应用性能监控（深入归「链路」板块） |

## 最容易混的对

| 对 | 分界一句话 |
|---|---|
| 监控 vs 可观测性 | 监控是"已知问题有没有发生"；可观测性是"未知问题能不能被问出来"——监控是可观测性的子集 |
| 指标 vs 日志 vs 链路 | 指标答"有没有问题"（告警源）；日志答"发生了什么"（取证）；链路答"慢/错在哪一跳"（定位） |
| 白盒 vs 黑盒 | 白盒看内部指标知道"为什么"；黑盒从外部探测知道"用户视角有没有事"——互补不是二选一 |
| SLI vs SLO vs SLA | SLI 是测量值，SLO 是内部目标，SLA 是带赔偿的对外合同 |
| MTTD vs MTTR | MTTD 管"多久发现"（监控的功劳），MTTR 管"多久恢复"（值班与预案的功劳） |
| 拉 vs 推 | 拉由监控端发起、目标死活可判；推由对象发起、需要网关承接——Prometheus 拉为主、trap/短任务推 |
| 告警 vs 事件 | 告警是机器发出的信号；事件是人确认要处置的业务级问题——一个事件常由多条告警汇聚 |
| 静默 vs 抑制 | 静默按时间/范围关掉通知（维护用）；抑制按因果自动压掉衍生告警（风暴治理用） |
| 拨测 vs 探活 | 探活只问"端口通不通"；拨测模拟完整用户路径——关键业务至少一条拨测 |
| 基数 vs 数据量 | 数据量是样本总个数（存的问题）；基数是序列组合数（内存的问题）——两者独立爆 |

## 按症状反查

| 症状 | 最可能的病根 | 去哪 |
|---|---|---|
| 半夜告警响个不停，没人当回事 | 告警疲劳：无动作项的告警混着真告警 | 006 告警疲劳治理 |
| 一出故障手机刷几十条通知 | 缺分组与抑制，根因告警没收敛 | 006 Alertmanager 路由 |
| 指标全部正常，用户却说慢 | 缺黑盒拨测，监控视角≠用户视角 | 007 blackbox |
| 磁盘满了才发现没监控水位 | 巡检缺失或保留策略没配 | 004 容量公式 · 008 保留策略 |
| 监控系统自己挂了，全网全盲 | 没有自监控 | 008 §8.1 |
| 告警响了不知道找谁、干什么 | 无 runbook、无升级路径 | 006 规则五要素 · 「SRE」002 |
| 图表全是锯齿毛刺没法看 | 抓取频率与聚合方式不对 | 002 §2.7 · 005 面板选型 |
| 新服务上线没有任何监控 | 无指标设计规范 | 002 埋点规范 · USE/RED |
| 监控数据出现断点/有洞 | remote_write 队列堆积或 WAL 追不上 | 008 remote write 治理 |
| 内存一路涨到 OOM 才被人力发现 | 基数爆炸或无容量告警 | 008 基数治理 |
| 交换机/网络设备取不到值、Windows 主机纳管不了 | SNMP community/ACL 不通，或 agent2 未装 | zabbix 002 §3 · zabbix 001 §3 |
