## 6.1 告警的哲学

告警的唯一目的是**让某人做某事**——如果一个告警响了但没人需要行动，它就是噪音。告警分级：

| 级别 | 含义 | 响应 | 通知方式 |
|---|---|---|---|
| **P0 · page** | 用户受损，需要立即人工介入 | 手机响、5 分钟内确认 | 电话/IM @all |
| **P1 · ticket** | 需要当天处理，但不紧急 | 工单系统，工作时间内 | IM 群 |
| **P2 · 观测** | 趋势值得关注，暂不需行动 | 仪表盘标注 | 日报汇总 |

**告警疲劳的根源**：P0 级告警太多导致阈值越调越高，真正需要 page 的事件被淹没。治理核心：**每一个 page 都必须可行动**——响的时候你知道"该做什么"。

## 6.2 recording rules：预计算降查询压力

复杂表达式的结果用 recording rule 预计算存为新指标——仪表盘和告警都查这个新指标，不再每次现算：

```yaml
groups:
  - name: precomputed
    rules:
      # 每服务每分钟的错误率
      - record: service:http_errors:rate5m
        expr: |
          sum by (service) (rate(http_requests_total{status=~"5.."}[5m]))
          / sum by (service) (rate(http_requests_total[5m]))

      # 每服务的 P99 延迟
      - record: service:http_p99:seconds
        expr: |
          histogram_quantile(0.99,
            sum by (service, le) (rate(http_request_duration_seconds_bucket[5m])))
```

好处：**告警表达式变简洁**（`service:http_errors:rate5m > 0.05`），仪表盘也用同一指标（口径统一），查询压力从"每次现算"变成"后台定期计算"。

## 6.3 告警规则写法：expr / for / labels / annotations

一条告警规则的五要素：

```yaml
groups:
  - name: service-alerts
    rules:
      - alert: HighErrorRate
        expr: service:http_errors:rate5m > 0.05
        for: 5m                          # 持续 5 分钟才触发——过滤毛刺
        labels:
          severity: critical             # 分级标签——Alertmanager 路由依据
          team: trade
        annotations:
          summary: "{{ $labels.service }} 错误率 {{ $value | humanizePercentage }}"
          description: "过去 5 分钟错误率超过 5%，持续 5 分钟。"
          runbook_url: "https://wiki.internal/runbook/high-error-rate"
```

| 字段 | 作用 | 纪律 |
|---|---|---|
| `expr` | 触发条件 | 必须基于 recording rule，不写裸长表达式 |
| `for` | 持续时间 | **防毛刺的关键**——没有 for 的告警 80% 是误报 |
| `labels.severity` | 分级标签 | critical/page/ticket——Alertmanager 据此路由 |
| `annotations.summary` | 人读摘要 | 必须包含：什么服务、什么问题、多严重 |
| `annotations.runbook_url` | 处置文档链接 | **每个 page 必须有 runbook**（「SRE」002 §2.5） |

## 6.4 SLO burn rate 告警：多窗口多燃烧率

「SRE」001 §1.4 的理论在这里落地。错误预算的燃烧速率告警用**双窗口双条件**避免误报：

```yaml
# 快烧：1h 窗口 burn rate ≥ 14.4 且 5m 窗口同样超
- alert: SLOBurnRateFast
  expr: |
    (
      service:http_errors:rate5m / (1 - 0.999)
    ) > 14.4
    and
    (
      service:http_errors:rate1h / (1 - 0.999)
    ) > 14.4
  for: 2m
  labels: { severity: critical }
  annotations:
    summary: "SLO 快速燃烧：{{ $labels.service }} 错误率过高"

# 慢烧：6h 窗口 burn rate ≥ 6
- alert: SLOBurnRateSlow
  expr: |
    (
      service:http_errors:rate30m / (1 - 0.999)
    ) > 6
    and
    (
      service:http_errors:rate6h / (1 - 0.999)
    ) > 6
  for: 15m
  labels: { severity: warning }
```

双窗口的价值：**短窗口抓突发，长窗口确认持续**——只有两个窗口同时超才触发，排除单点毛刺。burn rate 的计算公式与阈值推导见「SRE」001 §1.4。

## 6.5 分级与路由：Alertmanager 的路由树

Alertmanager 按标签把告警路由到不同接收端：

```yaml
route:
  receiver: default-webhook
  group_by: [alertname, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: [severity="critical"]
      receiver: oncall-phone
      group_wait: 10s
      repeat_interval: 30m
    - matchers: [severity="warning"]
      receiver: team-im
      repeat_interval: 2h

receivers:
  - name: oncall-phone          # 电话/短信 + IM @all
    webhook_configs: [...]
  - name: team-im               # IM 群通知
    webhook_configs: [...]
```

路由树三条纪律：**critical 走电话/IM @all**（不容许漏看）；**warning 走 IM 群**（不 page）；**default 兜底必须有**（否则未匹配的告警静默消失）。`group_by` 按告警名+服务分组——同组内多条告警合并为一条通知（防刷屏）。

## 6.6 告警疲劳治理

告警疲劳是监控系统的慢性病——治理核心：**每个 page 都必须"响的时候你知道该做什么"**：

| 手段 | 做法 | 效果 |
|---|---|---|
| **月度告警审计** | 列出所有告警，删掉"响了也没用"的 | 噪音量降 50%+ |
| **分级强制** | 每条规则必须标 severity | 未标的不允许进生产 |
| **runbook 覆盖率** | page 类告警 100% 有 runbook 链接 | 消灭"响了不知道干嘛" |
| **重复检测** | 同一告警 24h 内触发 3 次 → 升级为事件 | 防止"告警→忽略→告警"循环 |
| **静默纪律** | 计划内维护必须配 silence | 防止维护期误 page |

**告警质量是 SRE 团队的生命线**——噪音告警的价值为负，因为它消耗注意力并降低对真告警的信任。月度审计的成本（1 小时）远低于告警疲劳的代价（漏掉真故障）。

一次黑盒探测告警链路的真实改造（0/28 → 28/28 全覆盖）沉淀出三张实战牌，与上表互补：

| 牌 | 做法 | 解决什么 |
|---|---|---|
| **标签解耦** | 告警规则按业务标签过滤（如 `quality="0"` 只管 P0 目标），**不按 job 名/目标清单硬编码**；通用规则用 `quality!="0"` 反向排除 P0 目标 | 加减服务**零规则改动**；同一故障只进一个群（P0 群），不在通用群里重复响 |
| **采集器聚合** | 采集器离线告警按采集器维度聚合：`max by (blackbox_exporter) (up{...}) == 0` | 采集器挂掉只出 **1 条**，不按 target 逐条刷屏 |
| **告警狗** | 恒真规则 `expr: 1 == bool 1` + `for: 10s`，走专用路由、`repeat_interval` ≈ 8h | 每 8 小时必到一条心跳——**收到即证明 Prometheus → Alertmanager → 通知通道 → 群全链路活着** |

告警狗值得单独记：**告警链路自己也会坏**——最尴尬的不是告警响了，是"链路挂了所以没告警"。恒真规则把"链路是否健康"变成一条持续到达的心跳；反过来，**到点没收到心跳本身就是一个需要人工检查链路的信号**。配套细节：特殊目标（如 401 需登录的接口）用标签跳过状态码判定（`status_check!="false"`），避免"已知非 200"天天误报。

**目标上下线走注册中心，不走变更窗口**：探测目标注册进 Consul（Consul SD 自动发现），实例标签里的 `activate` 是总开关——摘掉即停用，10~30 秒生效，**无需 reload Prometheus**；实例 ID 的组内序号一经分配不重排（新增追加新号），Meta 携带 quality / service_name 等业务标签供规则过滤与路由使用。服务上下线从"改配置 + 部署 + reload"变成注册中心里的一个标签开关——这是"加减目标不进变更流程"的机制基础。

## 6.7 九个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 告警没加 `for` | 毛刺即响，80% 误报 | 必须加 for 持续时间 |
| 2 | 没有 severity 标签 | Alertmanager 无法路由分级 | 每条必标 |
| 3 | 告警不带 runbook 链接 | 响应时不知道做什么 | annotations 加 runbook_url |
| 4 | 复杂表达式直接写在告警里 | 表达式错难调试 | 先写 recording rule |
| 5 | 告警阈值拍脑袋 | 永远误报或永远不报 | 基于历史 P99/P95 数据定 |
| 6 | 缺少 default 路由 | 未匹配的告警静默消失 | Alertmanager 必须有 default receiver |
| 7 | 规则按 job 名/目标清单硬编码 | 每加减一个服务都要改规则发版 | 规则按业务标签过滤，目标交给注册中心（6.6） |
| 8 | 采集器挂掉按 target 刷屏 | 一台探针挂 = 几十条告警，真故障被淹 | 按采集器维度聚合（6.6） |
| 9 | 告警链路自己没监控 | 链路挂了"没告警"，无人知道 | 恒真告警狗 + 长周期重复通知（6.6） |

第 1 条展开：`for: 5m` 的含义是"条件连续满足 5 分钟才发告警"——它的作用是把瞬时毛刺（网络抖动、单次超时）过滤掉。但要注意 **`for` 期间 Prometheus 重启会重置计时**（pending 状态丢失）——这意味着频繁重启 Prometheus 会导致告警永远触发不了。生产上 Prometheus 自身要有高可用（双实例）。
