## 1. K8s 监控为什么不一样

前面八册讲的是静态主机与固定 exporter；本节先说清容器环境多出来的三个变量。

### 1.1 三个差异

| 差异 | 传统主机 | K8s |
|---|---|---|
| 监控对象 | 主机名固定 | Pod 名随滚动更新变化，IP 复用 |
| 指标维度 | 主机 + 资源 | 多了 namespace / pod / container / node |
| 采集目标 | 配置文件写死 | 靠 ServiceMonitor/PodMonitor 动态发现 |

结果：**同一套 PromQL 在 K8s 里更容易遇到基数爆炸**——每次发布都产生一批新的 pod label 值。

### 1.2 监控分层

```plain
集群层    apiserver / etcd / scheduler / controller-manager
节点层    node-exporter（CPU/内存/磁盘/网络）
对象层    kube-state-metrics（Deployment/Pod/PVC 的状态）
容器层    cAdvisor（container_* 资源使用）
应用层    业务自身暴露的 /metrics（RED/黄金信号）
```

排障顺序通常是从上往下：业务告警 → 容器资源 → 节点压力 → 控制面。

## 2. kube-prometheus-stack 与 CRD

上一节知道要看哪几层；本节看它们怎么被自动装配。

### 2.1 组件清单

| 组件 | 作用 |
|---|---|
| Prometheus Operator | 监听 CRD，生成并更新 Prometheus 配置 |
| Prometheus | 实际抓取与存储，通常 2 副本 |
| Alertmanager | 告警分组、抑制、路由 |
| Grafana | 预置看板 |
| node-exporter | DaemonSet，节点指标 |
| kube-state-metrics | 监听 apiserver，输出对象状态指标 |
| prometheus-adapter | 可选，供 HPA 用自定义指标 |

### 2.2 CRD 是配置入口

| CRD | 作用 |
|---|---|
| `Prometheus` | 定义 Prometheus 实例、副本、保留期、选择哪些 ServiceMonitor |
| `ServiceMonitor` | 按 Service 的 label 选择抓取目标 |
| `PodMonitor` | 直接按 Pod label 选目标（无 Service 时） |
| `Probe` | 黑盒探测（配合 blackbox-exporter） |
| `PrometheusRule` | 告警与 recording 规则 |
| `Alertmanager` / `AlertmanagerConfig` | 告警实例与路由配置 |

**关键机制**：Operator 把 ServiceMonitor 翻译成 scrape config，再热加载给 Prometheus。所以「改了 ServiceMonitor 但没生效」，先查 Operator 日志与选择器，而不是改 Prometheus 配置。

### 2.3 最小安装

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install kps prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --set grafana.adminPassword='换成强口令'
```

```bash
kubectl -n monitoring get pods
kubectl -n monitoring get servicemonitor | head
kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090
```

默认 `serviceMonitorSelector` 是 `release: kps`——自己写的 ServiceMonitor **必须带这个 label**，否则不会被选中（第 6 节展开）。

## 3. 四类指标来源

上一节把栈装起来了；本节分清每类指标是谁产的，避免「指标缺失」时乱猜。

### 3.1 cAdvisor：容器资源

kubelet 内置 cAdvisor，暴露在 `/metrics/cadvisor`：

| 指标 | 含义 |
|---|---|
| `container_cpu_usage_seconds_total` | 容器 CPU 累计秒，`rate()` 得核数 |
| `container_memory_working_set_bytes` | 工作集内存，**OOM 判定看这个** |
| `container_network_receive_bytes_total` | 容器网络入流量 |
| `container_fs_usage_bytes` | 容器可写层占用 |

注意 `container_memory_usage_bytes` 包含可回收的 page cache，用它算内存水位会虚高；判断是否接近 limit 用 working set。

### 3.2 kube-state-metrics：对象状态

KSM 不采资源使用，它把 apiserver 里的对象状态翻译成指标：

| 指标 | 含义 |
|---|---|
| `kube_pod_status_phase{phase="Pending"}` | Pod 卡在 Pending |
| `kube_pod_container_status_restarts_total` | 容器重启次数 |
| `kube_pod_container_status_waiting_reason` | 等待原因（CrashLoopBackOff 等） |
| `kube_pod_container_status_last_terminated_reason` | 上次终止原因（OOMKilled 等） |
| `kube_deployment_status_replicas_available` | 可用副本数 |
| `kube_node_status_condition` | 节点压力（MemoryPressure/DiskPressure） |
| `kube_persistentvolumeclaim_status_phase` | PVC 状态 |
| `kube_pod_status_unschedulable` | 调度失败 |

KSM 版本要与 K8s 版本匹配，版本落后时新对象的指标会缺。

### 3.3 node-exporter：节点资源

DaemonSet 跑在每台节点，`node_*` 指标：CPU、内存、文件系统、网卡、load。主机侧的 USE 三个维度主要靠它。

### 3.4 控制面：集群的命门

| 组件 | 端口 | 关键指标 |
|---|---|---|
| kube-apiserver | 6443 | `apiserver_request_total`、`apiserver_request_duration_seconds_bucket` |
| etcd | 2379 | `etcd_server_has_leader`、`etcd_disk_wal_fsync_duration_seconds` |
| kube-scheduler | 10259 | `scheduler_schedule_attempts_total` |
| controller-manager | 10257 | `workqueue_depth` |

控制面指标需要证书与 RBAC，托管集群（EKS/ACK/TKE）通常不暴露 etcd 与 scheduler，只能看云厂商的托管指标。

## 4. 关键指标与告警

上一节知道了来源；本节挑出真正会驱动动作的几条。

### 4.1 Pod 层

```promql
# 15 分钟内重启超过 3 次
increase(kube_pod_container_status_restarts_total[15m]) > 3

# 处于 CrashLoopBackOff
kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"} > 0

# 最近一次因 OOM 被杀
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} > 0

# 内存接近 limit（需要 limits 指标存在）
container_memory_working_set_bytes
  / on(namespace, pod, container) kube_pod_container_resource_limits{resource="memory"} > 0.9
```

### 4.2 节点层

```promql
# 节点内存压力
kube_node_status_condition{condition="MemoryPressure",status="true"} == 1

# 节点磁盘压力
kube_node_status_condition{condition="DiskPressure",status="true"} == 1

# 节点不可调度
kube_node_spec_unschedulable == 1

# 节点 NotReady
kube_node_status_condition{condition="Ready",status="true"} == 0
```

### 4.3 存储与调度

```promql
# PVC 卡在 Pending
kube_persistentvolumeclaim_status_phase{phase="Pending"} == 1

# Pod 无法调度
kube_pod_status_unschedulable > 0

# Deployment 可用副本不足
kube_deployment_status_replicas_available
  < on(namespace, deployment) kube_deployment_spec_replicas
```

### 4.4 采集自身

```promql
# 抓取目标掉线
up == 0

# 指标基数（防 OOM）
prometheus_tsdb_head_series > 1000000
```

监控系统自身必须有告警：Prometheus 挂了，所有业务告警同时静默，这是最危险的故障模式。

## 5. 白盒与黑盒

上一节是「内部状态」；本节补「外部可用性」，两者缺一有盲区。

| | 白盒 | 黑盒 |
|---|---|---|
| 数据来源 | 应用/组件自己暴露的 `/metrics` | 从外部探（HTTP/TCP/ICMP/DNS） |
| 能回答 | 为什么慢、内部哪个环节异常 | 用户能不能访问、响应多久 |
| 工具 | exporter、instrumentation | blackbox-exporter + `Probe` |
| 指标 | `http_request_duration_seconds` | `probe_success`、`probe_duration_seconds` |

`Probe` 示例思路：定义一个 module（http_2xx），选目标 URL 与 job 名，Operator 生成 blackbox 抓取配置。**黑盒探针要放在集群外或独立命名空间**，否则集群整体故障时探针跟着挂，等于没探。

## 6. 排错入口

上一节补了外部视角；本节按「target 没出现 → 出现了但没数据 → 有数据但基数爆炸」三段排查。

### 6.1 target 没出现

```bash
kubectl -n monitoring get servicemonitor <name> -o yaml
kubectl -n <ns> get svc <name> --show-labels
kubectl -n monitoring logs deploy/kps-kube-prometheus-stack-operator | tail -50
```

三个常见原因：

1. ServiceMonitor 的 `selector.matchLabels` 与 Service 的 label 不符；
2. `namespaceSelector` 没包含目标命名空间（默认只选同命名空间）；
3. ServiceMonitor 自己缺 `release: kps`，Prometheus 没选中它。

### 6.2 出现了但没数据

| 检查 | 命令 |
|---|---|
| 端口名一致 | Service 的 `port.name` 与 ServiceMonitor 的 `endpoints.port` 字符串必须相同 |
| 网络可达 | `kubectl -n monitoring exec ... -- wget -qO- http://<svc>:<port>/metrics` |
| NetworkPolicy | 是否阻断 monitoring 命名空间 |
| RBAC | Prometheus SA 是否有 `get/list/watch` endpoints/services/pods |

### 6.3 有数据但基数爆炸

```promql
# 看 series 总量与增长
prometheus_tsdb_head_series
sum by (__name__) ({__name__=~"container_.*"})
```

治理手段：

1. relabel 丢掉 `id`、`image_id`、`container_id` 这类高基数字段；
2. recording rule 先聚合再存（按 workload 而不是 pod）；
3. 缩短原始指标保留期，长期看聚合结果；
4. 限制 `container_*` 只保留需要的 namespace。

## 7. 坑表

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | ServiceMonitor 建了但 target 没有 | 缺 `release: kps` label | 补 label，或改 Prometheus 的 selector |
| 2 | target 出现但 up=0 | 端口名不匹配、NetworkPolicy、路径错 | 三项逐一核对 |
| 3 | cAdvisor 指标全缺 | kubelet 认证/证书问题 | 检查 kubelet serviceMonitor 的 bearerTokenFile 与 CA |
| 4 | KSM 指标缺新对象 | KSM 版本落后于 K8s | 升级 KSM 到匹配版本 |
| 5 | 控制面指标抓不到 | 监听 127.0.0.1、RBAC 不足、托管集群不暴露 | 改监听地址/补 RBAC；托管集群用云指标 |
| 6 | 每次发布 series 暴涨 | pod label 变化，旧 series 未及时回收 | relabel 丢弃高基数 label，聚合后再存 |
| 7 | Prometheus OOM | series 太多、查询范围过大 | 看 `prometheus_tsdb_head_series`，加内存/治理基数 |
| 8 | 告警一直响不停 | 用了 `> 0` 而不是 `increase()` | 状态类指标配 `for`，计数类用增量 |
| 9 | Probe 全失败 | module 名错、目标不可达、探针在集群内 | 核对 module 与目标，探针移出集群 |
| 10 | Grafana 看板空白 | 数据源指向旧 release 名 | 改数据源 URL，核对 namespace |

## 8. 检查清单

| # | 问题 | 判据 |
|---|---|---|
| 1 | 四类来源都有数据吗？ | cAdvisor/KSM/node-exporter/控制面各抽一条验证 |
| 2 | ServiceMonitor 都带选择 label 吗？ | `kubectl get servicemonitor -A -o yaml` 检查 |
| 3 | 关键告警有 `for` 与增量判断吗？ | 不出现「状态指标 > 0 永久触发」 |
| 4 | 基数有上限与治理吗？ | `prometheus_tsdb_head_series` 有阈值告警 |
| 5 | 黑盒探针在集群外吗？ | 集群故障时仍能报警 |
| 6 | 监控自身被监控吗？ | `up == 0` 与 Prometheus 自身告警已配 |
