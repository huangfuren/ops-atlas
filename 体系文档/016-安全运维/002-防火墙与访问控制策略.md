## 1. 默认拒绝原则

防火墙策略只有两种哲学：**默认允许，逐条封禁**（黑名单）与**默认拒绝，逐条放行**（白名单）。生产策略必须用后者：

```bash
# 默认拒绝入方向，只放行已知必需
nft add chain inet filter input { type filter hook input priority 0 \; policy drop \; }
# 再逐条放行：已建立连接、lo、SSH（限源）、业务端口（限源）
```

黑名单模式的问题：你只能封"已知的坏"，新攻击面全部默认开放。**白名单把举证责任倒过来**——想开放的人要说明理由，这是安全策略与故障策略的分界。

## 2. 双层模型：云安全组 + 主机防火墙

云环境的标准形态是**两层防御**（衔接 015 001 §2）：

| 层 | 位置 | 管什么 |
|---|---|---|
| 云安全组 | 实例级白名单（平台层） | 粗粒度：只放 SLB/堡垒机来源的 SSH、业务端口 |
| 主机防火墙 | 系统级规则（nftables） | 细粒度：按服务/来源的精确控制 + 出方向管控 |

两层职责不同：安全组管"谁能碰到这台机器"，主机防火墙管"机器上的哪些服务可被访问、出方向允许去哪"。**只靠安全组的主机防火墙全关**是常见漂移——主机层还负责出方向与日志。

## 3. 策略变更流程

⚠️ 防火墙是唯一能**把自己锁在门外**的变更——流程必须带回滚：

| 步骤 | 动作 | 要点 |
|---|---|---|
| 1 | 导出当前策略备份 | `nft list ruleset > rules.bak.$(date +%s)` |
| 2 | ⚠️ 保留已登录会话不动 | 这是唯一的回滚保险 |
| 3 | 应用新规则（先临时后持久） | `nft -f rules.nft` 生效于临时，验证后再持久化 |
| 4 | **新开连接验证** | 另开终端测试 SSH/业务端口可达 |
| 5 | 验证失败 → 回滚备份 | `nft -f rules.bak` |
| 6 | 验证成功 → 持久化 + 归档 | 保存到配置管理，变更留痕 |

云安全组的变更同理：控制台改规则后**立即用新会话验证**，失败先删刚加的规则。

## 4. 最小规则集基准

生产主机的入方向规则基准（按需增删）：

| 端口/协议 | 来源 | 用途 |
|---|---|---|
| SSH（22/自定义） | 仅堡垒机/办公网段 | 运维入口 |
| 业务端口（80/443/8080…） | SLB/前端网段 | 业务流量 |
| 监控端口（9100 等） | 仅监控网段 | exporter 采集 |
| 节点互联端口 | 内网网段 | 集群组件互访 |

出方向默认允许，但**高危出向**（如任意公网 SMTP）按需封禁——防止沦为垃圾邮件中继。规则注释必须写明**变更单号与理由**——半年后没人记得"这条 5432 是给谁的"。

## 5. 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 改规则前没备份 | 无法回滚 | 先导出再改（§3 步骤 1） |
| 2 | 应用规则后不验证 | 以为生效其实回滚了 | 新开连接验证（旧会话不重连） |
| 3 | 只改临时规则不持久化 | 重启后规则消失，安全回退 | 验证通过后再持久化 |
| 4 | 规则无注释无单号 | 半年后不敢动 | 注释=变更单号+理由 |
| 5 | 云安全组与主机防火墙不一致 | 排障两处来回查 | 以 IaC/配置管理统一维护 |
| 6 | 全网段互信（内网全开） | 一台沦陷全网横向 | 内网也分段白名单 |

## 6. 检查清单

| # | 问题 |
|---|---|
| 1 | 入方向是默认拒绝吗？ |
| 2 | 每条规则有注释（单号+理由）吗？ |
| 3 | 最近一次变更走了备份→临时→验证→持久化流程吗？ |
| 4 | 云安全组与主机防火墙规则一致吗？ |
| 5 | 内网是分段白名单还是全互信？ |
| 6 | 高危出方向（SMTP 等）封了吗？ |
