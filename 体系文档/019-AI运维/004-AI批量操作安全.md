# 004 AI 批量操作安全

## 4.1 默认只读：写操作走授权三件套

AI 的每个数据面入口**默认只读**。写操作必须带齐**三件套**，缺一即拒（exit 1）：

```text
--write  --authorized-by "<授权人>"  --reason "<原因>"
```

三条语义：**授权人是使用者明确说出的那个人**——AI 不得代填、不得猜（"帮我授权"不算，要名字）；**原因写进审计**（半年后回看"为什么当时改了这行"全靠它）；**授权即参数**——口头许可落成结构化参数，本身就是可检索的留痕（与 003 册的身份五件套合流：谁授权、谁执行、何时、改什么，四元组齐）。

## 4.2 永不放行白名单

**即使已授权也结构化拒绝**（exit 2）——授权只覆盖"数据写"，不覆盖"结构性破坏"：

| 类别 | 禁止内容 |
|---|---|
| DDL | CREATE / ALTER / DROP / TRUNCATE / RENAME |
| 权限 | GRANT / REVOKE / CREATE USER / SET PASSWORD |
| 数据搬运 | LOAD DATA / SELECT … INTO OUTFILE / LOAD_FILE |
| 过程与锁 | CALL / DO / HANDLER / LOCK TABLES / FLUSH / PURGE |

设计逻辑：这四类操作的共同点是**影响结构、影响他人、不可逆**——它们不该走"AI + 授权人"的通道，该走人手变更窗口（「SRE」002 的变更纪律）。白名单是写死的结构性拒绝，不是配置项。

## 4.3 批量操作的授权设计：确认码与三步写库

批量动作（全网扫描、批量写库）的授权比单条写更重，两个机制：

**确认码**：发包前必须把**待执行清单完整展示**（网段/目标/时长上限），使用者回复带校验码的确认语（"确认探测 <码>"）后才执行——脚本校验校验码，**AI 不得代填**。这把"AI 理解错了就开扫"从可能变成不可能。

**写库三步**：`backup`（先生成交付件）→ **试算**（不带执行参数，汇报影响行数）→ 用户明确授权后才 `--execute`。配套：回滚预案写进交付件（按批次号回滚）；**补扫校验**——链路对持续探测有静默限速，扫描完必须跑 verify 对漏扫网段如实点名，补扫后仍不达标的**不许假装补齐**；**档位纪律**——默认低档位，"为了快"调高并发跨链路会静默漏掉大半目标。

## 4.4 留痕与归属：动作即证据

四层留痕互为印证：**谁**（身份五件套，003 册）、**何时**（绝对日期时间）、**做了什么**（影响面声明 + 完整命令）、**经谁授权**（三件套参数）。服务端 audit log 按人按天滚动保留；AI 侧操作记录按日成文。复盘时两条证据链对得上，才算闭环——只有一层的留痕在争议时立不住。

## 4.5 凭据红线：密码永不进对话

凭据红线的完整面（003 册 true/false 通道的展开）：

1. 凭据只从系统环境变量读；AI 不接触值；
2. **值载体全禁**：rc 文件、`env`/`printenv`、注册表、终端截图、配置文件截图、"贴出来核对一下"也不行；
3. 缺凭据时：停下来给可复制配置命令，等确认后重跑检查——**不猜、不代设、不向人索要**；
4. 真实值不进任何模板与文档（模板里只允许占位符）；
5. 密码进对话 = 立即停止当前项目动作——这不是流程要求，是泄露边界。

## 4.6 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 把口头"可以"当授权 | 事后无据可查，AI 成背锅位 | 三件套参数化，授权人必须具名（4.1） |
| 2 | 授权覆盖一切 | 一次授权被放大成结构变更 | 永不放行白名单独立于授权（4.2） |
| 3 | AI 代填授权人/校验码 | 授权链断裂，审计失真 | 校验码只来自使用者回复（4.3） |
| 4 | 批量写直接执行 | 影响面不明，坏了没法回滚 | backup → 试算 → 授权 → execute（4.3） |
| 5 | 扫描完不做补扫校验 | 静默限速漏掉整段，结论带洞 | verify 点名漏扫，不假装补齐（4.3） |
| 6 | "贴配置来核对一下" | 凭据进上下文即泄露 | true/false 通道 + 可复制命令（4.5） |
