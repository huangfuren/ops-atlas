## 1. 定位：两阵营之外的第三极

| 维度 | RabbitMQ | Kafka | **RocketMQ** |
|---|---|---|---|
| 模型 | 消息代理（路由灵活） | 分布式日志（分区顺序） | **日志+队列混合**（队列语义 + 高吞吐） |
| 延时消息 | 插件 | 无原生 | **原生（5.x 任意精度）** |
| 事务消息 | 无原生 | 无原生 | **半消息+回查（独门）** |
| 场景 | 企业集成、路由复杂 | 流式、日志、大数据管道 | **电商交易、订单/支付链路** |
| 中文生态 | 一般 | 好 | **极好（阿里系出品，文档中文）** |

一句话：**电商交易链路的消息（订单/支付/库存）RocketMQ 是国内事实首选**——事务消息与延时消息是订单场景刚需。

## 2. 架构：NameServer 与 Broker

| 组件 | 角色 | 运维要点 |
|---|---|---|
| **NameServer** | 无状态路由注册中心——Broker 上报路由，客户端从这里找 Broker | 轻量无状态，多台部署互不通信（与 Kafka 的 KRaft/ZK 演进对照：NameServer 天生无状态） |
| **Broker** | 存储+转发主节点，成组部署（一主多从） | 组内主从复制（同步/异步）；5.x Dledger 组用 Raft 自动切换 |
| Producer/Consumer | 生产/消费端 | Consumer 按消费组订阅；重试与死信按消费组隔离 |

Topic 的队列（queue）分布在多个 Broker——**分区思想与 Kafka 一致**（队列数=并行度上限，扩队列才能扩消费）。

## 3. 消息类型：事务消息是独门

| 类型 | 场景 | 机制 |
|---|---|---|
| 普通消息 | 大多数异步解耦 | 同步/异步/单向（oneway 最快不保证） |
| **顺序消息** | 同一订单的操作按序 | 同一 sharding key 发到同一队列——**消费端也要单线程消费该队列** |
| **延时消息** | 订单 30 分钟未支付自动取消 | 4.x 固定 18 个级别；**5.x 任意时间精度** |
| **事务消息** | 本地事务与发消息要么都成要么都不成 | 半消息→本地事务→**回查**（Broker 主动问"本地事务成没成"）→提交/回滚 |
| 死信消息 | 重试 16 次仍失败 | 进 `%DLQ%消费组` 死信 Topic——人工/定时处理（对账思维，衔接 003 §丢失治理） |

事务消息对照：Kafka 无原生事务消费（只有生产端事务），RabbitMQ 靠外部补偿——**这是选 RocketMQ 的第一理由**。

## 4. 运维命令与堆积治理

```bash
mqadmin clusterList -n nameserver:9876       # 集群与 Broker 状态
mqadmin topicRoute -n ns -t order-topic      # 路由：队列分布在哪些 Broker
mqadmin consumerProgress -n ns -g order-group  # 消费进度：堆积=BrokerOffset-ConsumerOffset
mqadmin topicStatus -n ns -t order-topic     # 各队列堆积明细
mqadmin updateTopic -n ns -c cluster -t t -r 8 -w 8   # 扩读写队列数
```

堆积治理（对齐 003 思路）：**第一步看消费进度**定位是"生产突增"还是"消费变慢"→ 消费慢加实例（注意实例数 ≤ 队列数，多余实例空转）→ 快速跳过堆积可重置 offset 到最新（⚠️ 丢消息需业务确认）。

## 5. 高可用与扩容

| 形态 | 机制 | 取舍 |
|---|---|---|
| **主从（同步双写/异步复制）** | Slave 复制 Master | 切换需人工或 5.x 前 controller——简单但切换慢 |
| **Dledger 组（5.x 主推）** | Raft 多副本自动选主 | 自动切换推荐；消息要落多数派 |
| 扩容 | 新 Broker 加入 + 扩队列 + （可选）迁移数据 | 新 Topic 直接落新 Broker，存量靠双写或迁移 |

## 6. 选型对照

| 场景 | 选 |
|---|---|
| 交易/订单/支付链路（事务+延时刚需） | RocketMQ |
| 日志采集/流计算/超大吞吐管道 | Kafka（002） |
| 企业集成、路由复杂、协议多样 | RabbitMQ（001） |
| 轻量事件流（已在 Redis 体系内） | Redis Stream（「Redis」004 §4——边界注记） |

## 7. 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 消费实例数 > 队列数 | 多余实例空转，扩了没用 | 先扩队列再扩实例 |
| 2 | 顺序消息消费端多线程 | 顺序被打回原形 | 同一队列单线程（或内存内排队） |
| 3 | 事务消息只发半消息不实现回查 | 消息一直"待确认"，下游收不到 | 回查逻辑必须实现（查本地事务状态） |
| 4 | 死信队列没人看 | 失败消息静默堆积 | DLQ 告警 + 定时对账重放 |
| 5 | NameServer 单台 | 路由单点（客户端缓存路由，短期可撑） | ≥2 台无状态多活 |
| 6 | 消费重试风暴 | 下游刚恢复就被重试打垮 | 重试间隔递增 + 消费端限流 |
