# 00 术语表

> **这一文档回答**：某个词是什么意思、两个长得像的概念差在哪、「只知道现象、不知道该翻哪一册」时往哪走。  
> **怎么用**：三种查法——按名字（下面按册分组）、按缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和命令回对应册；这里只保证你「认得出、分得清、找得到」。

## 000 消息队列全貌

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 消息队列 | message queue, MQ | 生产者与消费者之间的缓冲与分发层。三大价值：解耦、削峰、异步 |
| 消息代理 | message broker | 接收、路由、投递消息的服务端（RabbitMQ 是典型） |
| 分布式日志 | distributed log | 以追加写+保留为核心的模型（Kafka 是典型）——与代理是两种思想 |
| 生产者 / 消费者 | producer / consumer | 发消息的一方 / 收消息的一方 |
| 至少一次 | at-least-once | 保证不丢但可能重——**主流默认语义，消费端必须幂等** |
| 精确一次 | exactly-once | 不丢不重——代价高且边界苛刻（Kafka 事务/幂等生产者） |
| 顺序性 | ordering | 消息按生产顺序被消费——通常只在"分区内/单队列"成立 |
| 堆积 | backlog / lag | 已存未消费的消息量——运维 MQ 最核心的观测指标 |

## 001 RabbitMQ 运维

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| AMQP | Advanced Message Queuing Protocol | RabbitMQ 的协议。生产者连的是 exchange，不是 queue |
| exchange | 交换器 | 消息的路由器：按类型与 binding 决定进哪些队列 |
| 四类 exchange | direct / fanout / topic / headers | 精确路由 / 广播 / 模式匹配 / 头属性路由 |
| binding | 绑定 | exchange 与 queue 之间的路由规则 |
| queue | 队列 | 消息真正排队的地方，FIFO |
| vhost | virtual host | 实例内的逻辑隔离单元：权限与资源的边界 |
| connection / channel | 连接 / 信道 | TCP 连接 / 连接内的轻量复用通道。channel 异常不影响连接 |
| 持久化三件套 | durability | durable exchange + durable queue + persistent 消息——**三件齐备才扛重启** |
| 仲裁队列 | quorum queue | 基于 Raft 的复制队列，3.8 起的推荐形态 |
| 镜像队列 | mirrored queue（旧） | 旧复制方案，已废弃（4.0 移除）——存量要迁移 |
| prefetch | 消费端预取 | 单消费者未 ack 消息的上限——**流控与负载均衡的阀门** |
| 内存水位 | memory high watermark | 超限后**阻塞生产者**（连接被 block），不是丢消息 |
| 磁盘空闲限制 | disk free limit | 空闲低于阈值同样阻塞生产者（默认 50MB） |

## 002 Kafka 运维

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| broker | — | Kafka 集群的一个节点 |
| topic | 主题 | 消息的逻辑分类 |
| partition | 分区 | topic 的水平切分，**分区内有序**——扩分区是扩消费能力的前提 |
| offset | 偏移量 | 消息在分区内位置，消费者按 offset 提交进度 |
| 消费者组 | consumer group | 组内分摊分区：**一个分区同组内只归一个消费者** |
| 重平衡 | rebalance | 组成员/订阅变化时重新分配分区——**频繁重平衡是消费不稳的头号症状** |
| ISR | In-Sync Replicas | 与主副本保持同步的副本集合——ISR 收缩=可靠性在降级 |
| acks | — | 生产者确认级别：0 不等 / 1 主写 / **all 全同步副本写** |
| KRaft | Kafka Raft | 内置共识协议替代 ZooKeeper（3.3+ 生产可用，4.0 移除 ZK） |
| retention | 保留策略 | 消息按时间/大小保留——Kafka 消费完不删，到期才清 |
| 日志压缩 | log compaction | 同 key 只留最新值——状态恢复型 topic 用 |

## 003 堆积与可靠性治理

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 消息丢失三环节 | — | 生产端没送达 / broker 没存住 / 消费端先提交后处理——丢在哪个环节修哪个 |
| 毒丸消息 | poison pill | 让消费者每次处理都失败的消息——会卡死整条消费 |
| 死信队列 | dead letter queue, DLQ | 反复失败的消息的去处。RabbitMQ 用 DLX，Kafka 靠应用层约定 |
| 幂等消费 | idempotent consumer | 同一条消息消费多次效果一致——at-least-once 的必配保险 |
| 消费能力 | consume throughput | 每秒能处理多少条。堆积治理的第一杠杆 |
| 顺序保障 | ordering guarantee | 需要"同 key 有序"时：Kafka 按 key 进同分区；RabbitMQ 单队列+单消费者 |

## 缩写速查

| 缩写 | 全称 | 意思与出处 |
| --- | --- | --- |
| AMQP | Advanced Message Queuing Protocol | RabbitMQ 的协议（001） |
| DLQ / DLX | Dead Letter Queue / Exchange | 死信队列 / 死信交换器（003） |
| ISR | In-Sync Replicas | 与主副本同步的副本集合（002） |
| KRaft | Kafka Raft Consensus | 内置共识，替代 ZooKeeper（002） |
| MQ | Message Queue | 消息队列（全册） |
| QoS | Quality of Service | RabbitMQ 消费端 prefetch 的设置名（001） |

## 最容易混的 12 对

| 容易混 | 一句话差别 | 怎么确认 | 册 |
| --- | --- | --- | --- |
| RabbitMQ vs Kafka | 消息代理（路由灵活、投递完就删）/ 分布式日志（高吞吐、消息可回放） | 需要"重放历史"的只有 Kafka 能 | 000 |
| exchange vs queue | 路由器 / 真正排队的地方 | 消息先过 exchange 再进 queue | 001 |
| 镜像 vs 仲裁队列 | 旧复制方案 / Raft 复制（现推荐） | 3.12 上新建队列选 quorum | 001 |
| partition vs replica | 水平切分的单位 / 分区的拷贝 | `_cat`/describe 里 leader 在谁就是谁的分区 | 002 |
| connection vs channel | TCP 连接 / 连接内的复用通道 | 一个连接跑多 channel，省资源 | 001 |
| producer 的 acks vs 消费端 prefetch | 生产确认级别 / 消费未 ack 上限 | 一个防丢（发送侧），一个防压（消费侧） | 001/002 |
| at-least-once vs exactly-once | 不丢可能重 / 不丢不重 | 有没有事务+幂等链路 | 000/003 |
| 重平衡 vs 消费重启 | 组内重新分配分区 / 单个消费者重启 | 日志关键字：rebalance vs reconnect | 002 |
| 堆积 vs 延迟 | 未消费的条数 / 消息从产生到消费的耗时 | lag 是因，延迟是果 | 003 |
| DLX vs 重试队列 | 失败消息的坟场 / 失败消息的二次机会 | 看路由目的与重试次数设计 | 003 |
| ZooKeeper vs KRaft | 外置协调（存量）/ 内置共识（主线） | `zookeeper-shell` 还在不在用 | 002 |
| durable 队列 vs persistent 消息 | 队列定义重启还在 / 单条消息落盘 | 重启后队列在但消息没了=消息没持久化 | 001 |

## 按症状反查

| 现象 | 大概是 | 去哪 |
| --- | --- | --- |
| 队列堆积暴涨 | 消费能力不足 / 生产突增 / 毒丸 | 003 §3.3–3.4 |
| 消费者在线但不消费 | prefetch 打满 / 毒丸反复失败 / 阻塞在下游 | 001 §1.6 / 003 |
| 消息"丢了" | 三环节对账：生产确认 / 持久化 / 消费提交 | 003 §3.1 |
| 消息重复消费 | at-least-once 正常现象，缺幂等 | 003 §3.2 |
| Kafka 消费组反复重平衡 | 成员频繁上下线 / 处理超 max.poll.interval | 002 §2.4 / 003 |
| Kafka 出现 under-replicated | 副本同步异常：节点慢/挂/磁盘满 | 002 §2.6 / 004 |
| RabbitMQ 生产者被阻塞 | 内存/磁盘水位超限 | 001 §1.5 / 004 |
| RabbitMQ 节点间元数据不一致 | 网络分区 | 001 / 004 |
| 消息顺序错乱 | 多消费者/多分区拆掉了顺序 | 003 §3.5 |
| MQ 磁盘满 | 保留/堆积/未配清理 | 004 / 003 §3.4 |
| 管理界面/Grafana 打不开 MQ 面板 | 服务或插件未起 | 004 §4.1 |
| 升级后老客户端连不上 | 协议/特性兼容变化 | 001 / 002 各自升级注记 |
