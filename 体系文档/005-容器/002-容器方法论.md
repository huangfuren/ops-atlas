# 容器方法论

> **这一册回答**：容器领域的两个思维转变——「镜像思维」与「声明式」——想通了它们，Docker 和 K8s 的所有命令都有了为什么。
> **给谁读**：命令会敲但说不清容器和虚拟机差在哪、K8s 和 Docker 差在哪的运维。
> **工具无关**：命令细节在模块册；本册给的是心智模型。

## 心智模型一：镜像思维

**容器 = 一个被隔离和限制的进程**（namespace 给隔离，cgroup 给限制），不是轻量虚拟机。由此推出全部容器直觉：

- **镜像 = 交付物的标准化**：应用 + 依赖 + 启动命令打成一个不可变地址。从此「交付」从「部署文档 + tar 包 + 口头注意」变成「镜像地址 + 配置清单」——CI/CD 的全部地基。
- **镜像分层只读，容器层可写**：容器里改的东西随容器删除而消失——所以「状态」要么外置（卷），要么打进新镜像。
- **进程退出 = 容器退出**：容器里跑的是前台进程，不是守护进程家族；「起不来」先想 PID 1 在干什么。
- **一次构建，处处运行的前提是环境抽象**：配置从环境变量/挂载注入，不烧进镜像——同一镜像跑遍开发/测试/生产。

**落地**：镜像分层与运行时在 111；构建在 112；状态外置在 113。

## 心智模型二：声明式

**从「我跑什么命令」变成「我声明什么状态」**——这是单机 Docker 与 K8s 的分水岭：

| | 命令式（Docker/Compose） | 声明式（K8s） |
| --- | --- | --- |
| 你说 | 「启动这个容器」 | 「保持 3 个副本在跑」 |
| 谁维持 | 没人——崩了就崩了 | 控制平面持续对账，崩了自动拉起 |
| 变更 | 重新跑命令 | 改 YAML，`kubectl apply` |
| 回滚 | 靠 Compose 文件进 Git | `rollout undo` |

**推论**：K8s 里所有操作都走清单文件——手改运行态（`kubectl edit`）会被下一次 apply 覆盖；「漂移」是声明式的大忌。控制平面把「期望状态」记在 etcd，每个控制器只做一件事：**让实际状态逼近期望状态**——这就是 121 册「控制器模式」的全部。

**落地**：架构与对象在 121；发布与回滚在 124；声明式的进阶形态（GitOps）见「CICD」板块。

## 两条工具线的分界

- **一台机器的世界**（Docker）：镜像、构建、数据卷、Compose、网络底层、运行时——运维直接下命令。
- **一组机器的世界**（K8s）：调度、服务发现、滚动发布、自愈——运维写声明，集群执行。
- 概念有延续（镜像、日志、资源限制），心智模型必须切换；跳过 Docker 直接学 K8s 会缺一层排障直觉（容器起不来时，最终还是要在节点上用 `docker`/`crictl` 看现场）。

## 反模式

- ❌ 把容器当虚拟机——进去装东西、当宠物养；容器是牲口，坏了重建不修复。
- ❌ 状态烧进容器层——数据库数据放容器内不挂卷，重启即清零。
- ❌ K8s 里手改运行态——下一次 apply 全部还原，且没人知道改过什么。
- ❌ 单 YAML 巨石清单——拆文件、按应用分目录，清单也是代码，进 Git。

## 自测

1. 容器和虚拟机的本质差别？（隔离的进程 vs 完整 OS）
2. 为什么「状态要外置」？（容器层可写但随容器销毁）
3. 声明式和命令式的分水岭是什么？谁维持状态？（控制平面持续对账）
4. 为什么 K8s 手改运行态是大忌？（被下一次 apply 覆盖，且变更不可追溯）
