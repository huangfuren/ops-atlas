## 13.1 两条安装路线的选择

| 维度 | kubeadm | 二进制 |
| --- | --- | --- |
| 形态 | 控制平面容器化运行 | 全部系统进程（systemd 托管） |
| 难度 | 低（一条命令 + 补齐） | 高（证书/配置逐个手装） |
| 自愈 | kubelet 拉起控制平面（掩盖细节） | 自己管（细节全暴露） |
| 生产 | 大多数团队的主线 | 深度定制、离线、教学理解 |

先 kubeadm 跑起来，再手装一遍二进制——**第二遍装的是理解**，二进制的每个组件配置都能对应回 kubeadm 的产物。

## 13.2 节点初始化基线（每台机器都要做）

RockyLinux 9 的初始化清单，顺序即执行顺序：

1. **网络**：NetworkManager 的 nmcli 配地址（控制面/业务双网卡场景在这里分）；**禁用 swap**（`swapoff -a` 并清 fstab）；
2. **软件源**：换 aliyun/ustc 源，装 ipvsadm、containerd 相关依赖；
3. **SELinux**：`grubby` 内核级禁用（可回滚）——比临时 setenforce 彻底；
4. **防火墙**：firewalld 换成 iptables 管理口径（或按端口清单放行）；
5. **内核参数**：`br_netfilter` 模块 + `net.bridge.bridge-nf-call-iptables=1` + `ip_forward=1`（K8s 网络的前提，005 册 §5.2 的同款）；
6. **ipvs 模块加载**：`ip_vs ip_vs_rr ip_vs_wrr ip_vs_sh nf_conntrack` 写入 modules-load。

这一节的每一条都是"装完集群才发现不对"的返工源——**基线做成脚本，批量执行**。

## 13.3 kubeadm 安装精要

```bash
kubeadm init \
  --image-repository registry.aliyuncs.com/google_containers \
  --kubernetes-version v1.29.1 \
  --cri-socket unix:///var/run/cri-dockerd.sock \
  --service-cidr=10.96.0.0/12 \
  --pod-network-cidr=10.244.0.0/16
```

四个关键点：

1. **镜像仓库**：`--image-repository` 换国内源（控制平面镜像全部走它）；
2. **CRI**：1.24+ 需要 cri-dockerd（手工部署 systemd 单元 + pause 镜像国内源）或直接用 containerd（011 册 6.2 的 config.toml 三要点）；
3. **两个 CIDR**：service-cidr 与 pod-network-cidr **不能与现有网段重叠**，且 pod-cidr 要与 CNI 配置一致；
4. **网络插件收尾**：Calico 部署时**固定网卡探测**——`IP_AUTODETECTION_METHOD=can-reach=www.baidu.com` 或 `interface=eth.*`，多网卡机器不加这个，Calico 会绑错网卡。

Node 加入用 init 输出的 join 命令（含 token 与 CA hash，token 24 小时过期，`kubeadm token create --print-join-command` 重取）。

## 13.4 二进制高可用：架构与证书

生产级二进制高可用的标准架构：

```plain
            VIP（keepalived 或云 LB）
             │ nginx stream 四层反代 6443
   ┌─────────┼─────────┐
master-1    master-2    master-3     （etcd 三节点可独立可混部）
   └──── node-1 ~ node-N ────┘
```

**证书三套，用 cfssl 签发**（1.6.4 版）：

| 证书 | 签给谁 | 要点 |
|---|---|---|
| etcd-ca + etcd | etcd 节点间与客户端 | etcd 对内通信全加密 |
| apiserver-ca + apiserver | kube-apiserver | **hostname 的 hosts 数组要带齐：三 master IP + VIP + 10.96.0.1（service 首地址）+ kubernetes 服务域名**——漏一个就是"某条链路握手失败" |
| 前端 CA | 各组件与 kubelet | |

证书是二进制安装的第一坑：**SAN 列表不全的证书，故障表现为"有的组件握手失败"**——签发前把 hosts 数组逐个核对。

## 13.5 二进制高可用：etcd、控制平面与 Node

**etcd 三节点**：`--config-file etcd.config.yml` 指向各节点配置（name/监听地址/集群成员列表/证书）。raft 协议三状态（follower → candidate → leader），失联转选主——这就是"etcd 要奇数节点"的协议根源。

**控制平面四件套**逐台部署，两条高可用要点：

1. **kube-apiserver 无状态可横向**，前面由 **nginx stream 模块**做四层反代（编译时 `--without-http` 只留四层，`least_conn` + `hash $remote_addr consistent`）；
2. **scheduler / controller-manager 必须 `--leader-elect=true`**——同一时刻只有一个实例在"做决定"，其余热备等选主；它们的选择主依赖 etcd，所以 etcd 先健康。

**Node 侧**：kubelet 用 **TLS Bootstrapping** 自动取证——Node 只带一个 bootstrap token 首连 apiserver，kubelet 的正式证书由 CM 自动签发（省掉"每台节点手工签证书"）。kubelet-conf 三要点：cgroupDriver=systemd、clusterDNS=10.96.0.10、rotateCertificates。kube-proxy 以静态 Pod 或 DaemonSet 跑，随后 Calico、CoreDNS、metrics-server 逐层收尾。

## 13.6 验证与升级纪律

安装完成的验证清单：

```bash
kubectl get nodes                          # 全部 Ready
kubectl get pods -A                        # 控制平面与 CNI/插件的 Pod 全 Running
kubectl run tmp --rm -it --image=busybox -- nslookup kubernetes.default   # DNS 通
kubectl run tmp --rm -it --image=busybox -- wget -qO- http://service-addr # Service 通
```

升级纪律四句（009 §9.9 同源）：一次一个 minor；先控制平面后节点（drain 配合）；升级前查 CNI/CSI 兼容表；先测试集群后生产。**备份 etcd 先于一切升级动作**。

## 13.7 五个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 证书 SAN 漏了 VIP/服务网段 | 部分链路握手失败，难定位 | 签发前逐项核对 hosts 数组 |
| 2 | containerd 的 cgroup driver 与 kubelet 不一致 | 节点 NotReady / Pod 反复重启 | 都用 systemd（011 册 6.2） |
| 3 | pod-cidr 与 CNI 配置不一致 | CNI 起不来，Pod 全 Pending | init 参数与 CNI 清单同一值 |
| 4 | apiserver 证书漏了 service 网段首地址 | Pod 内调 apiserver 握手失败 | SAN 里带上 10.96.0.1 |
| 5 | nginx stream 编译带了 http 模块却没配 | 端口占用/行为困惑 | `--without-http` 只留四层，用途单一化 |
