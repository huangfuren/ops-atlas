## 9.1 排障三板斧

前八册把零件讲完了，本册把它们装成排障的手艺。三板斧的顺序是固定的：

```bash
kubectl describe pod web-7d9f8-x1    # ① 全档案：状态、容器详情、事件时间线
kubectl logs web-7d9f8-x1 -f         # ② 应用输出（① 里知道是哪个容器、什么状态）
kubectl exec -it web-7d9f8-x1 -- sh  # ③ 进去看现场（①②定住范围之后）
```

**先 describe 的理由**：输出末尾的 `Events:` 是 K8s 替你记录的第一现场——拉镜像失败、探针失败、调度失败、OOM，每一条带时间戳。001–008 里所有"某对象为什么这样"的问题，事件先给一半答案。**三板斧是顺序不是清单**：跳过 describe 直接 logs，常见结局是在错误的时间看错误的容器。

大范围排查时的两条加速器：

```bash
kubectl get events --sort-by='.lastTimestamp' | tail -30   # 全集群事件流
kubectl get pods -A --field-selector=status.phase!=Running # 全集群异常 Pod
```

### 三板斧进阶：kubectl debug 的五种姿势

`exec` 进不去的现场（distroless 镜像没有 shell、CrashLoop 根本起不来）交给 `kubectl debug`——五种姿势对应五类现场：

```bash
# ① 临时容器注入：往出问题的 Pod 里挂一个带工具的容器，共享进程与网络
kubectl debug -it web-7d9f8-x1 --image=busybox --target=web
# ② Pod 副本调试：复制一份（共享进程），原 Pod 保持不动
kubectl debug -it web-7d9f8-x1 --copy-to=web-debug --share-processes --container=web -- sh
# ③ 改启动命令的副本：原命令是阻塞点时，换成 sleep 让你慢慢查
kubectl debug web-7d9f8-x1 --copy-to=web-dbg2 --container=web -- sh
# ④ 改镜像的副本：全套换 Ubuntu 排环境问题
kubectl debug web-7d9f8-x1 --copy-to=web-dbg3 --set-image=*=ubuntu
# ⑤ 节点调试：在节点宿主上挂一个调试 Pod，根文件系统挂载在 /host
kubectl debug node/node-1 -it --image=ubuntu
```

临时容器（ephemeral container，v1.25 stable）**不能修改原 Pod 的字段、退出即消失**——它是"现场勘查员"，不是修复工。配套的本地通道：`kubectl port-forward svc/web-svc 8080:80 --address 0.0.0.0` 把集群端口转发到本机（仅 TCP）。

## 9.2 Pod 状态字典

`kubectl get pods` 里每个非 Running 的状态都有明确病因，逐个拆：

| 状态 | 含义 | 病因与取证 |
|---|---|---|
| `Pending` | 调度不下去 | `describe` 看 Events 三大常见：资源不足（Insufficient cpu/memory）、PVC 绑不上、亲和性不满足 |
| `ImagePullBackOff` / `ErrImagePull` | 镜像拉取失败 | tag 写错（最常见）/ 私库缺 `imagePullSecrets` / 网络不通。`describe` 里是具体报错原文 |
| `CrashLoopBackOff` | 反复崩溃退避 | 应用自己挂：`logs --previous` 看上一次死前输出；退避节奏 10s 起步指数上涨到 5min |
| `OOMKilled`（137） | 内存超 limit 被杀 | `describe` 的 `Last State` 明写 OOMKilled；加 limit 或查泄漏（008 §8.5） |
| `Running` 但 READY 0/1 | 容器活着但未就绪 | readiness 探针没过（008 §8.9 的展开） |
| `Evicted` | 被驱逐 | 节点资源压力（磁盘/内存），QoS 与 requests 问题（008 §8.6） |

`CrashLoopBackOff` 的细节值得单独记：**退避机制**意味着 Pod 不是"崩溃后立即重启"而是越等越久——观察到状态码 137 时先别急着定位"重启风暴"，`describe` 里的 `Restart Count` 与 `Back-off restarting failed container` 事件说明它已进入退避循环。取证永远先看 `logs --previous`（当前容器是新一轮，死因在上一轮）。

## 9.3 网络不通的取证：Endpoints → Service selector → 探针 → CNI

"服务不通"类故障的完整取证链（006 §6.9 的地图落地）：

```bash
# ① 名字解析对不对
kubectl run tmp --rm -it --image=busybox --restart=Never -- nslookup web-svc
# ② Endpoints 有没有名单（006 §6.5 三分法）
kubectl get endpoints web-svc
# ③ 绕过 Service 直连 Pod（隔离 Service/转发层问题）
kubectl get pods -l app=web -o wide      # 拿 Pod IP
kubectl run tmp --rm -it --image=busybox --restart=Never -- wget -qO- -T 3 10.244.1.5:8080
# ④ 到此仍不通 → 网络策略/CNI
kubectl get networkpolicy -A
```

四步的判定逻辑：**①挂 = DNS 问题；②空 = label/探针问题；③通但 Service 不通 = 转发层（kube-proxy）问题；③也不通 = CNI/策略问题**。每一步都有明确归属，不会在"网络问题"这个大筐里打转。

## 9.4 节点故障：NotReady 的原因清单与恢复

节点 `NotReady` 的本质是 kubelet 失联（心跳超时）。原因按概率排：

| 原因 | 验证 |
|---|---|
| kubelet 进程挂/没起 | 节点上 `systemctl status kubelet` |
| 容器运行时（containerd）挂 | `systemctl status containerd` |
| 节点磁盘压力（DiskPressure） | `describe node` 的 Conditions 列 |
| 网络分区（节点与 apiserver 失联） | 节点上 `curl -k https://<apiserver>/healthz` |
| 机器本身宕机 | ping 不通 / 云控制台看状态 |

恢复顺序原则：**先修节点，别急着手动删 Pod**——节点不可达后，K8s 等一段时间会把该节点 Pod 标记为 Evicted 并在其他节点重建（有 pod-eviction-timeout 机制），人为干预反而乱。确认节点长期回不来再 `kubectl delete node` 让系统彻底收尾。

NotReady 期间的连带现象要预期到：该节点 Pod 被驱逐重排 → 其他节点水位上涨 → 若没有 008 的 requests 纪律，可能引发连锁驱逐。**节点故障的半场戏在资源管理**。

另一个高频卡点：**Pod 卡在 Terminating 不消失**——节点失联时 kubelet 收不到删除确认，对象就一直挂着。两解按序试：重启该节点的 kubelet（恢复心跳后自动清）；急了用 `kubectl delete pod <名> --force --grace-period=0` 强删（注意：**强删只是从 API 里抹掉记录**，节点上的真实容器要手动清）。旧 Pod 不清，新 Pod 可能因卷/网络资源未释放而起不来。

## 9.5 应用日志：--previous、多容器、收集对接

`kubectl logs` 的四个关键用法：

```bash
kubectl logs web-7d9f8-x1 --previous        # 上一次崩溃前的输出（CrashLoop 必看）
kubectl logs web-7d9f8-x1 -c sidecar-name   # 多容器 Pod 指定容器
kubectl logs -l app=web --tail=50 --prefix  # 按 label 拉一组，带 Pod 名前缀
kubectl logs -f --since=10m web-7d9f8-x1    # 跟随 + 时间窗
```

`--previous` 前提是容器**本轮重启后**日志还在（容器重建会清，logging driver 决定保留），所以崩溃类问题的取证要快——更稳的路径是集中采集：日志打 stdout（004 §4.5）→ 节点级采集器 → 集中式存储。K8s 生态的口径与「监控」册一致：**节点上跑 DaemonSet 采集，而不是每个应用各写文件**。

## 9.6 资源取证：kubectl top 与 describe node

资源类问题（慢、被驱逐、调度不上）的两个仪表：

```bash
kubectl top pods -A --sort-by=memory    # 谁在吃内存（metrics-server 提供）
kubectl describe node node-1
```

`describe node` 是最被低估的一条命令，两段最有价值：

- **`Allocated resources`**：节点上所有 Pod 的 requests 汇总 vs 节点容量——"集群看着空却调度不上 Pod"的答案在这（CPU/内存 requests 已被记账占满，实际用量可能很低）；
- **`Conditions`**：节点的健康判定（MemoryPressure / DiskPressure / PIDPressure）——磁盘压力是驱逐的头号触发器（008 §8.6）。

`kubectl top` 的读数是**瞬时值**，与 requests 的比值（8.5 的校准依据）才是重点。要趋势就得进监控系统（Prometheus 口径），kubernetes 的指标对接在「监控」册。

## 9.7 生产清单：上生产前的十项自查

把 005–008 的纪律压缩成发布前的自查表，十项全勾才上：

| # | 检查项 | 出处 |
|---|---|---|
| 1 | 副本数 ≥ 2（单副本没有高可用可言） | 005 §5.5 |
| 2 | requests/limits 必填且校准过 | 008 §8.5 |
| 3 | readiness/liveness 已配，liveness 不含外部依赖 | 008 §8.4 |
| 4 | 反亲和/拓扑分散（`podAntiAffinity` 或 `topologySpreadConstraints`）——副本别挤一个节点 | 005 §5.7 |
| 5 | PDB 已配（drain 不中断） | 008 §8.8 |
| 6 | 数据在 PVC 上且回收策略 Retain | 007 §7.6 |
| 7 | 镜像 tag 锁死，不是 latest | 002 §2.8 |
| 8 | Namespace 有 ResourceQuota/LimitRange | 005 §5.8 |
| 9 | 发布有 undo 路径且数据库兼容旧版 | 008 §8.3 |
| 10 | 日志打 stdout、监控指标在暴露 | 004 §4.5 |

这份清单的本质是 000 §0.5 那句话的落地：**声明式系统的可靠性是"声明"出来的**——上面十项没声明的，K8s 一个都不会替你补。

## 9.8 etcd 备份与恢复演练

etcd 备份是自建集群的唯一后悔药（5.3）。备份一条命令：

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%F).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

三条纪律：**定期**（cron，至少每日）+ **异地**（备份与 etcd 不同机）+ **演练**（没恢复过的备份等于没有）。恢复是反向操作：停 apiserver → `etcdctl snapshot restore` 生成新数据目录 → etcd 指向新目录重启。**恢复演练在测试集群做**——生产上第一次练恢复 = 事故现场练手。云托管用户此节可跳过（控制面归云厂商），但换来自卫责任：YAML 全部进 Git（「CICD」册的仓库纪律），应用层状态自己备份。

### 工作负载级备份：Velero + Minio

etcd 备份是**集群级**的（整库恢复，颗粒度粗），**按命名空间/按资源类型的细颗粒备份交给 Velero**——它还能把 PVC 数据一起备份到对象存储。最小闭环：

```bash
# ① Minio 起一个 S3 兼容对象存储（备份仓库）
# ② Velero 安装：带节点代理（node-agent 备份 PVC 数据）、默认文件系统备份
velero install \
  --provider aws --plugins velero/velero-plugin-for-aws:v1.9.0 \
  --bucket velero --backup-location-config s3Url=http://<minio>:9000,s3ForcePathStyle=true \
  --secret-file ./credentials-velero \
  --use-node-agent --default-volumes-to-fs-backup --use-volume-snapshots=false

# ③ 备份 / 恢复 / 定时
velero backup create web-full --include-namespaces web
velero restore create --from-backup web-full
velero schedule create web-daily --schedule="@daily" --include-namespaces web
```

资源过滤参数覆盖细颗粒需求：`--include-namespaces / --exclude-namespaces / --include-resources / --exclude-resources / --include-cluster-scoped-resources` 等；不想被备份的的工作负载贴一个标签 `velero.io/exclude-from-backup: "true"` 即跳过。恢复钩子（InitContainer 等数据就绪、Exec 跑恢复后命令）处理"恢复后要先做点什么"的场景。

分工一句话：**etcd 快照管"集群没了怎么重建"，Velero 管"某个命名空间/某批资源坏了怎么还原"**——两层都在，备份体系才算闭环。

## 9.9 集群升级：一次一个 minor

kubeadm 集群升级的纪律浓缩为四句：

1. **一次只升一个 minor 版本**（1.28 → 1.29 → 1.30），跨版本升级不被支持；
2. **先控制平面，后节点**；每台节点先 `drain` 再升级组件再 `uncordon`（008 §8.8 的流程派上用场）；
3. **升级前看两份文档**：K8s 官方的版本弃用说明 + 你所用 CNI/CSI 的兼容表——**插件版本不匹配是升级翻车的第一名**；
4. **先测试集群后生产**，生产逐节点滚动，每步 `get nodes` 确认 Ready 再继续。

云托管用户的风险前移：控制面升级由云厂商发起，你要做的是**在通知期内让工作负载兼容新版本**（弃用的 API 在新版本会被拒绝），本质是把 9.9 的第 3 条变成常态。
