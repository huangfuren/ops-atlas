## 10.1 资源清单五要素与三类资源层级

005 册立过"一切皆资源"的世界观，这里补齐清单的两个框架。顶层结构固定五要素：**apiVersion**（组/版本）、**kind**（类型）、**metadata**（名字/标签/ns）、**spec**（期望状态——唯一的内容区）、**status**（系统回写，只读不手写）。

资源按作用域分三类，决定它放在哪、被谁管：

| 层级 | 例子 | 说明 |
|---|---|---|
| 名称空间级 | Pod / Deployment / Service / ConfigMap | 必须属于某个 ns，日常资源的主场 |
| 集群级 | Namespace / Node / ClusterRole / PV | 全集群共享，跨 ns 生效 |
| 元数据级 | HPA / LimitRange / PodTemplate | 作用于其他资源的"规则"对象 |

排障时的用法：报错先核对 apiVersion/kind 是否匹配集群版本——**清单写错层级是 apply 被拒的头号原因**。

## 10.2 Pod 生命周期全流程：initC → main → 关闭

一个 Pod 从创建到销毁的完整时间线：

```plain
initC（线性串行，逐个成功）
   ▼
main 容器启动命令执行
   ├── postStart 钩子（紧随启动，不保证在命令前）
   ├── 三探针并行巡逻（startup → liveness + readiness）
   ▼
收到关闭信号（SIGTERM）
   ├── preStop 钩子（与 grace period 并行跑，不互相等）
   ▼
grace period 到期 → SIGKILL → 容器终止
```

**initC 的三特性**：逐个跑到成功为止（失败按 restartPolicy 重试）；**不可定义 readinessProbe**（它的任务就是阻塞）；危险工具放这里（等待依赖、改内核参数、拉配置）。

**preStop 与 grace period 的并行陷阱**：默认 `terminationGracePeriodSeconds: 30`，preStop 钩子与宽限期**并行计时**——preStop 里 sleep 20 秒再让应用收尾，实际只剩 10 秒给应用。**K8s 不等 preStop 完成**，超时照样 SIGKILL。优雅退出的正确姿势：preStop 只做"发停止信号"，收尾靠应用自己处理 SIGTERM。

## 10.3 三探针行为矩阵与五个参数

三种探针的失败后果完全不同（008 §8.4 的展开），课堂笔记补全了**成功/失败/未知**的完整行为矩阵：

| 探针 | 成功 | 失败 | 未知 | 回答的问题 |
|---|---|---|---|---|
| startupProbe | 停用其他两探针 | 重启容器（按 restartPolicy） | – | 慢启动的宽限到了吗 |
| livenessProbe | – | **重启容器** | 不动 | 进程死锁了吗 |
| readinessProbe | 进 Endpoints 接流量 | **摘出 Endpoints**（不重启） | 不进 | 现在能接流量吗 |

Handler 三种：`httpGet`（状态码 ≥200 <400）、`tcpSocket`（端口能建连）、`exec`（命令退出码 0）。五个参数决定检查节奏：`initialDelaySeconds`（首检延迟）、`periodSeconds`（周期）、`timeoutSeconds`（单次超时）、`successThreshold`（连续成功次数——liveness 固定 1）、`failureThreshold`（连续失败判死）。

 startupProbe 的妙用：`failureThreshold × periodSeconds` 就是启动宽限总长（如 30×10s=300 秒），比调大 liveness 的 initialDelay 优雅得多。

## 10.4 控制器族谱：RC → RS → Deployment → 专用控制器

控制器的演进是一条收敛线：**RC**（初代，等值匹配）→ **RS**（集合式 selector，Deployment 的手下）→ **Deployment**（RS 的编排者：版本与滚动）。专用场景各有专职控制器：

| 控制器 | 场景 | 关键参数 |
|---|---|---|
| **DaemonSet** | 每节点一个：日志/监控/存储 agent | node-exporter、fluentd 都是它 |
| **Job** | 跑完即止的批处理 | `completions`（完成数）、`parallelism`（并行）、`activeDeadlineSeconds`（总时限）；restartPolicy 只认 Never/OnFailure |
| **CronJob** | 定时批处理 | `concurrencyPolicy: Allow/Forbid/Replace`（上一轮没跑完怎么办）、`startingDeadlineSeconds`、成功历史留 3 / 失败留 1 |

金丝雀发布的"三板斧"（patch 节奏 → set image → rollout pause）是 Deployment 的原生气场（008 §8.1），不需要外部工具——记住这条，灰度发布的工具选型就省了。

## 10.5 调度器：预选五算法与优选三策略

scheduler 的决策分两步，理解两步就理解了"Pod 为什么 Pending、为什么落在这台节点"：

**第一步：预选（过滤，硬条件）**——不满足直接淘汰：

| 算法 | 过滤什么 |
|---|---|
| PodFitsResources | 节点剩余 requests 额度够不够 |
| PodFitsHostPorts | 端口冲突 |
| PodSelectorMatches / PodFitsHost | 亲和性/nodeName 硬指定 |
| NoDiskConflict | 盘冲突 |

**第二步：优选（打分，软偏好）**——从幸存者里打分选最高：

| 策略 | 倾向 |
|---|---|
| LeastRequestedPriority | 资源越空闲分越高 |
| BalancedResourceAllocation | CPU/内存使用率越均衡分越高 |
| ImageLocalityPriority | 本节点已有大镜像分越高（省拉取） |

预选失败的 Pod 进入 **Pending 并持续重试**——"Pod 一直 Pending"的根因在 Events 里一定写着，`describe` 是唯一入口。

## 10.6 亲和与污点：软硬约束的六种组合

调度的人为控制有两套旋钮：

**亲和性（affinity）**——把 Pod 往哪放，nodeAffinity / podAffinity / podAntiAffinity 各有硬（required，不满足不跑）与软（preferred，尽量满足）两档。典型用法：核心服务 anti 自身（副本打散）、报表任务 soft 靠近数据节点。

**污点与容忍（taint / toleration）**——把节点"涂上味道"拒绝 Pod，除非 Pod 声明容忍。三种 effect 递进：

| effect | 行为 |
|---|---|
| NoSchedule | 不调度新 Pod（存量不动） |
| PreferNoSchedule | 尽量不调度 |
| NoExecute | 不调度 **且驱逐存量** |

toleration 的通配技巧：不写 key/value/effect = **容忍一切污点**（排障 Pod 用）；`tolerationSeconds` 给 NoExecute 加"驱逐宽限"。多 Master 集群记得**去掉控制平面节点的污点**——三个 Master 只跑控制平面纯浪费。

## 10.7 自定义调度器：把黑盒打开

调度器不是黑盒：**K8s 的调度就是一个 HTTP 调用**——scheduler 监听"没绑定节点的 Pod"，算出目标节点后 POST 一个 Binding 对象。自己写一个极简调度器（shell + jq 轮询）：

```bash
# 轮询未调度的 Pod，POST Binding 到
# /api/v1/namespaces/default/pods/<pod>/binding/
```

这个实验把"调度"还原成一次 API 写入——K8s 的两大扩展点（调度器、控制器）都能用最少代码讲透。生产用不到自定义调度器，但**理解 Binding 机制后，"Pod 为什么在这台机器上"就永远不是玄学**。

## 10.8 六个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | initC 里放 readinessProbe | 清单直接被拒 | initC 只有主流程 |
| 2 | preStop 里 sleep 占满宽限期 | 应用收尾被 SIGKILL 截断 | preStop 只发信号，收尾交给应用 |
| 3 | liveness 探外部依赖 | 依赖抖动引发重启风暴 | liveness 只探进程自身（008 §8.4） |
| 4 | 核心服务没做反亲和 | 副本挤同一节点，节点挂全没 | podAntiAffinity / topologySpread |
| 5 | 污点用 NoExecute 不加容忍 | 存量 Pod 直接被驱逐 | NoExecute 上线前评估存量 |
| 6 | 多 Master 污点不清理 | 控制平面资源闲置 | 去掉 master 污点让负载混部 |
