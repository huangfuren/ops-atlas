## 12.1 安全全景：三道门都围着 apiserver 转

000 册讲过 apiserver 是唯一入口，安全机制就是入口前的三道门，**顺序固定、缺一不可**：

```plain
请求 ──▶ ① 认证（Authentication：你是谁）
      ──▶ ② 鉴权（Authorization：你能不能做这件事）
      ──▶ ③ 准入（Admission：这个请求合不合规、要不要改写）
      ──▶ 写入 etcd
```

三道门全过才落库。任何一道拒绝，请求终止——排障时按门定位：401 = 认证失败，403 = 鉴权/准入拒绝。

## 12.2 认证：证书 / Token / ServiceAccount

集群里两类"人"：**人用客户端证书**，**程序用 ServiceAccount（SA）**。

| 模式 | 载体 | 场景 |
|---|---|---|
| 客户端证书 | `~/.kube/config` 里的 client-certificate | 人类管理员（12.4 实验） |
| SA Token（JWT） | Pod 内自动挂载 `/run/secrets/kubernetes.io/serviceaccount/token` | Pod 里的程序调 apiserver |
| Bootstrap Token | 引导令牌 | 新节点加入（TLS Bootstrapping，013 册） |

SA 的三件套自动挂载进每个 Pod：**token（JWT，apiserver 私钥签名）+ ca.crt（验证 apiserver）+ namespace**。Pod 内程序用它调 apiserver 的标准姿势：

```bash
TOKEN=$(cat /run/secrets/kubernetes.io/serviceaccount/token)
curl -s --cacert /run/secrets/kubernetes.io/serviceaccount/ca.crt \
  -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api
```

安全基线：**给不需要调 apiserver 的 Pod 关掉自动挂载**（`automountServiceAccountToken: false`）——少一份可窃取的凭证。

## 12.3 鉴权：RBAC 四对象与资源匹配表

K8s 默认鉴权是 **RBAC（基于角色）**，四个对象组成两两配对：

| 对象 | 是什么 | 作用域 |
|---|---|---|
| Role / ClusterRole | 一组规则（哪些资源、哪些动词） | Role 限 ns / ClusterRole 全集群 |
| RoleBinding / ClusterRoleBinding | 把角色授予谁（用户/组/SA） | Binding 决定作用域 |

**关键设计：RoleBinding 可以引用 ClusterRole**——角色定义一次（如"只读"），在每个 ns 里绑定一次，实现跨 ns 复用而不重复定义。这是 RBAC 最常用的姿势。

预定义的四个 ClusterRole 的分界要背：

| 角色 | 能做什么 | 与相邻角色的分界 |
|---|---|---|
| `cluster-admin` | 一切 | 超级用户，只给管理员 |
| `admin` | ns 内一切，**含 Role/RoleBinding** | 能改权限，所以它其实是 ns 管理员 |
| `edit` | ns 内资源增删改，**不含 Role/RoleBinding** | edit 与 admin 的分界 = 能否改权限 |
| `view` | 只读 | 看得见，改不了 |

三条书写纪律：**权限只增不减**（RBAC 是叠加模型，没有拒绝规则——想拒绝就用拆 ns 或 admission）；**子资源用斜杠**（`pods/logs` 授权读日志，与 `pods` 的删改分开）；**`system:` 前缀是系统保留**，自建角色别撞名。

## 12.4 实验：给 dev 用户签发证书并授权一个 ns

完整走一遍"新同事入职"的权限交付，四步全部可复现：

```bash
# ① 用 cfssl 签发 dev 用户证书（CA 用集群的 /etc/kubernetes/pki/ca.crt/ca.key）
cfssl gencert -ca=ca.crt -ca-key=ca.key \
  -profile=kubernetes dev-csr.json | cfssljson -bare dev
# ② 构造 kubeconfig 四步：set-cluster / set-credentials / set-context / use-context
kubectl config set-credentials devuser --client-certificate=dev.crt --client-key=dev.key --embed-certs=true
kubectl config set-context dev --cluster=kubernetes --user=devuser --namespace=dev
# ③ 授权：在 dev ns 里把 admin ClusterRole 绑给 devuser
kubectl create rolebinding dev-admin --clusterrole=admin --user=devuser --namespace=dev
# ④ 验证：dev 用户能管 dev ns，碰别的 ns 被拒
kubectl --context=dev get pods -n dev      # 通
kubectl --context=dev get pods -n prod     # Forbidden
```

这四步就是生产上权限交付的标准流程——**"授一个 ns 的 admin"比"授 cluster-admin"专业十倍**。

## 12.5 准入与 Pod 安全：从 PSP 到 PSA

鉴权回答"你能不能做这个操作"，**准入回答"这个操作产出的对象合不合规"**——它在对象落库前跑一组插件（ResourceQuota、LimitRange 都在此工作）。

Pod 安全的演进要记住一次**制度更替**：**PSP（PodSecurityPolicy，v1.25 已删除）被 PSA（Pod Security Admission）取代**。PSA 的模型极简：

| 维度 | 取值 |
|---|---|
| 策略（LEVEL） | `privileged` / `baseline` / `restricted`（约束递增） |
| 模式（MODE） | `enforce`（拒绝）/ `audit`（留痕）/ `warn`（提示） |

挂载方式是给 Namespace 打标签（三模式可同时开——enforce 拦截、audit/warn 只记录不动手）：

```bash
kubectl label ns prod pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/audit=restricted pod-security.kubernetes.io/warn=restricted
```

PSA 的两条局限要清楚：**只查不改**（不能自动改写 Pod 来"让它合规"）、**策略固定三种不能自定义**——细粒度治理要上 admission webhook（如 Kyverno/OPA），超出本册范围。

## 12.6 安全上下文七实验：Pod 的自我约束

安全上下文（securityContext）是 Pod/容器级的自我约束开关，七个渐进实验覆盖全部常用项：

| # | 字段 | 实验内容 | 踩的坑 |
|---|---|---|---|
| 1 | `runAsUser: 1000` | 以 UID 1000 运行 | 镜像内无此用户也能跑（数字即身份） |
| 2 | `runAsNonRoot: true` | 强制非 root | **镜像默认用户是 root 时直接拒绝启动**（UID 与宿主/镜像用户不匹配的陷阱） |
| 3 | `privileged: true` | 特权模式 | 等于把节点权限交出去——只在节点级 agent 上用 |
| 4 | `capabilities.add: NET_ADMIN` | 追加网络管理能力 | 按需加，别全加 |
| 5 | `capabilities.drop: ["CHOWN"]` | 剔除 CHOWN | **nginx 启动报 chown 失败**——真实输出复现，说明默认能力并非全无 |
| 6 | `readOnlyRootFilesystem: true` | 根文件系统只读 | 应用写 /tmp 要配 emptyDir |
| 7 | `fsGroup: 2000` | 挂载卷的组属主 | 解决卷文件的组读写 |

渐进实验的读法：从"默认全开"到"restricted 全关"，每一格收紧都会暴露应用的一个真实依赖——**安全上下文的调优过程就是把应用的隐藏需求逼问出来的过程**。

## 12.7 审计：让每个操作留痕

审计（audit）记录"谁在什么时候对什么对象做了什么、结果如何"。四阶段（RequestReceived / ResponseStarted / ResponseComplete / Panic）与四级别（None / Metadata / Request / RequestResponse）组合成 policy：

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: RequestResponse
    resources:
      - group: ""
        resources: ["secrets"]      # 敏感资源的读写全量留痕（注意：Response 级会记明文值，密钥类用 Metadata 级）
  - level: Metadata
    resources:
      - group: ""
        resources: ["pods"]
  - level: None                     # 其余不记，控制日志量
```

启用方式是给 apiserver 挂 policy 与日志路径（静态 Pod 场景改 manifest 挂载四个参数：`--audit-policy-file / --audit-log-path / --audit-log-maxsize / --audit-log-maxbackup`）。审计日志本身是安全事件——**限制读取权限，并与 011 的日志采集链路打通**（Loki 收一份做检索）。

## 12.8 五个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 新人直接给 cluster-admin | 一份 kubeconfig 泄漏 = 全集群沦陷 | 按.ns 授 admin（12.4 流程） |
| 2 | automountSA 全局不关 | 每个 Pod 都揣着一份 apiserver 凭证 | 不需要的 Pod 显式关闭 |
| 3 | 以为 base64 是加密 | Secret 当公开数据管 | 三道门 + etcd 加密（007 §7.3） |
| 4 | 只靠 PSA 做治理 | PSA 只查不改、策略固定 | PSA + admission webhook 分层 |
| 5 | 审计只开不收 | 日志写满控制面磁盘 | policy 分级 + 日志轮转 + 集中采集 |
