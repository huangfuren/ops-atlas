# Java 应用方法论

> **这一册回答**：管 Java 应用的底层方法论——「先分区再处理、证据链排障、形态决定交付、对照两国语言」四条，以及怎么用它们判断一次排障/一次部署做得对不对。
> **给谁读**：接手 Java 应用的运维/SRE——不需要会写 Java，但需要懂 JVM 这台「机器」的脾气。
> **工具无关**：jstat 参数、Tomcat 配置项在正文册；本册给的是它们要服务的原则。

## 先分区，再处理

JVM 内存四区（堆/元空间/线程栈/直接内存）**报错信息指明区域，处理方式完全不同**：

1. **`java.lang.OutOfMemoryError: Java heap space`** → 堆：dump 对比找增长点，或加大 -Xmx（先确认不是泄漏）。
2. **`Metaspace`** → 元空间：类加载器泄漏（热部署/redeloy 反复加载），加 -Xmx 没用。
3. **`unable to create new native thread`** → 线程栈：线程数爆炸，查线程池配置与泄漏，不是内存不够。
4. **`Direct buffer memory`** → 直接内存：NIO 堆外，-XX:MaxDirectMemorySize 与堆分开算（011 §4）。

**盲目加内存是最常见的误处理**——掩盖泄漏，把「几天后复现」变成「几周后更严重地复现」。

## 证据链排障：从现象到 dump 逐级取证

Java 排障的证据链有固定顺序，**跳级取证会浪费 dump 的机会**：

- **GC 日志先行**：生产必开 GC 日志——判断「慢是不是 GC 引起」的第一证据，开销极小（011 §3）。
- **jstat 看趋势**：GC 频率与堆占用趋势——泄漏是「每次 GC 后水位爬升」，正常是「锯齿回落」。
- **jstack 看现场**：CPU 高或请求 hang 时抓线程栈——死锁、热点线程一次定位。
- **jmap dump 收尾**： dump 是最后手段（STW 且文件大）——先 histo 直方图看类实例数，确认值得再全量 dump，MAT 对比两个时点找增长点。

## 形态决定交付

war 与 fat jar 是两种交付形态，**部署与回滚方式完全不同，混用必出事**：

| | war + 外置 Tomcat | fat jar（Spring Boot） |
| --- | --- | --- |
| 部署 | webapps 目录 + Tomcat 重启 | `java -jar` 直接跑 |
| 回滚 | 替换 war + 重启 | 换回旧 jar + 重启 |
| 版本管理 | Tomcat 侧统一管 | 应用自己带（jar 版本即应用版本） |
| 配置 | Tomcat 全局 + 应用内 | application.yml + 环境变量覆盖 |

不管哪种形态：**回滚 = 换回上一个可用的产物 + 重启**——产物不可变原则（「CICD」123），禁止在生产上「改一下再试」。

## 对照两国语言

Go 与 JVM 解决同一组问题，**对照着学最快**：

- GC：Go 的低暂停并发 GC ↔ JVM 分代/region GC——都为压 STW，取舍不同（「Go」132）。
- 性能分析：pprof ↔ jstack/jmap/arthas——采样剖面 ↔ 事件现场（「Go」133）。
- 内存模型：Go 值语义/GC 全托管 ↔ JVM 分区+可调参——一个交给运行时，一个交给运维。

## 反模式

- ❌ OOM 一律重启 + 加内存——泄漏型过几天复现，且更严重。
- ❌ 生产不开 GC 日志——排障时失去第一证据。
- ❌ 一上来就全量 dump——STW 秒级 + 文件 GB 级，先用直方图确认。
- ❌ -Xmx 设成容器 limit——堆外内存（元空间/线程栈/直接内存）不在 -Xmx 里，总量超 limit 被 OOMKilled（退出码 137）。
- ❌ Tomcat 线程池拉满——瓶颈通常在下游连接池，线程多了只增加切换开销。
