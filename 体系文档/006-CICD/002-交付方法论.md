# 交付方法论

> **这一册回答**：自动化交付为什么是这三条性质——可重复、可回退、可追溯——以及怎么用它们判断你的流水线够不够格。
> **给谁读**：手动部署累了想上流水线的运维；也用于评审一条流水线「敢不敢交给新人按按钮」。
> **工具无关**：Jenkins/Ansible 的用法在模块册；本册给的是它们要服务的性质。

## 交付三性质

一条合格的交付链路只看三条性质，全部从「手动交付翻过的车」倒推：

1. **可重复**：测试环境跑过的那个制品，原样上生产——不是「重新构建一次赌它一样」。依赖升级、基础镜像变动都可能让两次构建产物不同，**晋级制品而不是重建制品**（123 的晋级链路）。
2. **可回退**：从按下发布键那一刻起，回退路径就存在且演练过（131 的预案 + 135 的镜像在库）。「回滚靠记忆」是事故放大的第一根导火索。
3. **可追溯**：线上跑的是哪版、谁在什么时候部署的、从哪个 commit 来——三个问题三分钟内答出（111 的 tag 锚点、112 的构建记录、134 的 GitOps 审计）。

## 流水线即代码

- **构建步骤不能在人的脑子里**：Freestyle 的配置存在 Jenkins 数据库里，不在版本控制内——一切配置进 Git（Jenkinsfile / .gitlab-ci.yml / playbook）。
- **配置越集中越好**：模板仓库统一 stages/门禁，几十个仓库一次演进（113 的模板化）；工具越少越好——每个新工具都是一条新的故障路径。
- **每段产出物是下一段的唯一输入**：不跳段、不旁路；每段失败都停线并通知——静默失败比失败更危险（133）。

## 发布策略的判断框架

按「停机容忍 × 回滚速度 × 流量比例」选策略，不为炫技上复杂方案：

| 场景 | 策略 | 落地 |
| --- | --- | --- |
| 可停机窗口 | 停机重启 | 131 |
| 不可停机、状态简单 | 滚动 | 131 / K8s 124 |
| 灰度验证 | 金丝雀/蓝绿 | 131 |
| 集群声明式 | GitOps | 134 |

**原则**：回滚预案与发布策略同步设计——没有回滚的灰度是裸奔。

## 自动化边界

**决策默认不自动化**：预案可以自动化（131 的回滚演练），但「回滚与否、扩大影响面与否」需要人的判断。自动化扩大的是执行速度，不是决策权。

## 反模式

- ❌ 重新构建代替晋级制品——两次构建不一样，测试等于白测。
- ❌ 流水线静默失败——绿灯不等于上线，通知缺失让绿灯变成谎言。
- ❌ 回滚无演练——第一次跑回滚剧本不应该在生产事故里。
- ❌ 凭据进流水线配置——密钥进 Git 即泄露，走凭据管理（112 的 credentials）。

## 与其他板块衔接

- 制品的标准形态（镜像）与运行时 → 「容器」板块；本板块 123 管仓库与晋级。
- 发布的流量切分（Nginx/HAProxy 层）→ 「接入层」板块；131 管策略语义。

## 自测

1. 交付三性质是什么？（可重复、可回退、可追溯）
2. 为什么晋级制品而不是重建？（两次构建产物可能不同）
3. 流水线静默失败为什么比失败更危险？（绿灯失真，人不再看流水线）
4. 自动化的边界在哪？（执行可自动化，决策默认不自动化）
