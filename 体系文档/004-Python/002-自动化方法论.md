# 自动化方法论

> **这一册回答**：什么任务值得写成 Python 脚本、怎么写到「敢放进 crontab」——判断框架，不重复任何库用法。
> **给谁读**：会用 Python 但不确定自己的脚本够不够格进生产调度的运维。
> **工具无关**：库与语法在各模块册；本册给的是取舍与纪律。

## 三语言取舍口诀

**先 Shell——能一行管道解决就不写脚本；Shell 超过 50 行或需要数据结构，切 Python；需要常驻、高并发或分发给非运维用户，切 Go。**

判断依据不是语言优劣，是**维护成本拐点**：Shell 的可维护性在 50 行附近崩塌；Python 的强项是「数据结构 + 生态」；Go 的强项是「单二进制交付 + 并发」。三者退出码、日志、幂等纪律必须一致（见「SRE」板块）。

## 配得上进 crontab 的四条底线

1. **幂等**——跑一遍和跑十遍结果一样；写文件用原子替换（tmp + rename），不产生半截产物。
2. **可观测**——开始、结束、结果条数进日志；失败退出码非 0，成功只输出摘要。
3. **有限资源**——超时自限、重试有上限、不无界吃内存；批量任务分批处理。
4. **配置外置**——地址、账号、阈值不硬编码；密钥不进代码仓。

**落地**：骨架与 `argparse`/`logging` 在 111；系统交互的安全姿势在 112；上线与调度在 122。

## API 优先于解析

- **有 API 不解析文本**：调监控/云平台/Grafana 的 HTTP API（113），不 grep 它们的页面输出——接口是契约，页面是实现。
- **有结构化不猜格式**：JSON 先于 CSV，CSV 先于正则抠日志；正则抠日志是「日志未结构化的过渡期方案」，不是终态。
- **鉴权凭据走环境变量或密钥文件**，不进命令行历史。

## 演进路径

一个自动化任务的正常生长：**一次性脚本 → 参数化（argparse）→ 调度化（crontab/timer + 日志）→ 服务化（API/队列）**。每进一步，补的是上一步欠的纪律：参数化补配置外置、调度化补幂等与可观测、服务化补并发与降级。不要跳级——跳级的技术债会在故障夜还。

## 反模式

- ❌ 用 Python 重写一行管道能干的事——杀鸡用牛刀还多一层维护。
- ❌ 脚本里写死 IP 和密码——换环境即坏，泄露即事故。
- ❌ 无超时的批量任务——卡一台机器，整批任务挂死。
- ❌ 成功也刷屏——日志信噪比低到没人看，等于没有日志。

## 与其他板块衔接

- 批量配置下发优先 Ansible（「CICD」板块 124/125 线），Python 脚本管 Ansible 之外的轻量场景。
- 脚本的调度监控与失败告警 → 「监控」板块。
- 数据出报表后的存储与检索 → 「数据库」/「日志」板块。

## 自测

1. 三语言取舍的拐点各是什么？（Shell 50 行/数据结构；Python 生态与常驻不必；Go 交付与并发）
2. 进 crontab 的四条底线？（幂等、可观测、有限资源、配置外置）
3. 为什么 API 优先于解析文本？（接口是契约，页面是实现）
4. 自动化任务演进四级？（一次性 → 参数化 → 调度化 → 服务化）
