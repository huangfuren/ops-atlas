## 5.1 三个必须回答的问题

任何备份方案，先回答这三个：

| 问题 | 指标 | 含义 |
|---|---|---|
| 能丢多少数据？ | **RPO**（恢复点目标） | 最多容忍丢失多长时间的数据 |
| 多久能恢复？ | **RTO**（恢复时间目标） | 从故障到恢复服务要多久 |
| 备份放哪？ | 3-2-1 原则 | 3 份副本、2 种介质、1 份异地 |

### 5.1.1 RPO 决定备份频率

| RPO | 需要的方案 |
|---|---|
| 24 小时 | 每天全量备份 |
| 1 小时 | 每天全量 + binlog 持续归档 |
| 1 分钟 | 主从同步 + binlog 实时传输 |
| 0 | 同步复制（MGR / 云上多可用区） |

**关键认知：只有全量备份，RPO 就等于备份间隔。** 每天凌晨 2 点备一次，下午 3 点故障，最多丢 13 小时数据。

要缩小 RPO，必须靠 **binlog**——它是"从上次备份到现在"所有变更的记录。

### 5.1.2 RTO 决定方案复杂度

| 数据量 | 逻辑备份恢复 | 物理备份恢复 |
|---|---|---|
| 10 GB | 10–30 分钟 | 1–3 分钟 |
| 100 GB | 1–3 小时 | 10–20 分钟 |
| 1 TB | 半天以上 | 1–2 小时 |

**这就是为什么大库必须用物理备份**：`mysqldump` 恢复是"逐条执行 INSERT"，数据量一大就慢得不可接受。

### 5.1.3 3-2-1 原则

| 数字 | 含义 | 反例 |
|---|---|---|
| **3** 份副本 | 生产 + 本地备份 + 异地 | 只有一份备份文件 |
| **2** 种介质 | 磁盘 + 对象存储/磁带 | 生产和备份在同一块磁盘 |
| **1** 份异地 | 不同机房/不同云 | 备份和数据库在同一可用区 |

**最常见的致命错误**：备份文件和生产库在同一台机器、同一块盘。磁盘坏了，两个一起没。

## 5.2 备份的四种分类

| 分类维度 | 类型 | 特点 |
|---|---|---|
| **形式** | 逻辑备份 | 导出 SQL 文本，可读、跨版本、慢 |
| | 物理备份 | 直接拷贝数据文件，快、绑定版本 |
| **范围** | 全量 | 所有数据 |
| | 增量 | 只备份上次之后的变化 |
| | 差异 | 备份上次**全量**之后的变化 |
| **时机** | 冷备 | 停库备份，一致但影响业务 |
| | 热备 | 运行中备份，需要工具支持 |
| **一致性** | 一致性备份 | 数据在同一个时间点 |
| | 非一致性 | 备份过程中数据在变，有风险 |

**生产组合（最常见）**：

```
每天 02:00  全量物理备份（XtraBackup）
持续       binlog 归档到对象存储
每周日     全量逻辑备份（mysqldump，用于跨版本迁移）
```

## 5.3 mysqldump：逻辑备份

### 5.3.1 基础用法

```bash
# 单库
mysqldump -h127.0.0.1 -uroot -p \
  --single-transaction \
  --routines --triggers --events \
  --set-gtid-purged=OFF \
  app_db > app_db_20261028.sql

# 多库
mysqldump -uroot -p --databases db1 db2 > multi.sql

# 全库（不含系统库）
mysqldump -uroot -p --all-databases \
  --ignore-table=mysql.general_log > all.sql

# 单表
mysqldump -uroot -p app_db orders > orders.sql

# 只要结构
mysqldump -uroot -p --no-data app_db > schema.sql

# 只要数据
mysqldump -uroot -p --no-create-info app_db > data.sql

# 按条件导出部分数据
mysqldump -uroot -p app_db orders --where="created_at >= '2026-10-01'" > orders_oct.sql
```

### 5.3.2 关键参数

| 参数 | 作用 | 不加会怎样 |
|---|---|---|
| **`--single-transaction`** | 在一个事务里备份，保证一致性且**不锁表** | 备份期间数据不一致 |
| `--routines` | 导出存储过程和函数 | 恢复后存储过程丢失 |
| `--triggers` | 导出触发器 | 恢复后触发器丢失 |
| `--events` | 导出事件调度器 | 定时任务丢失 |
| `--set-gtid-purged=OFF` | 不写 GTID 信息 | 恢复到已有 GTID 的实例会报错 |
| `--quick` | 逐行取数据，不缓存到内存 | 大表会 OOM |
| `--default-character-set=utf8mb4` | 指定字符集 | 中文乱码 |
| `--hex-blob` | BLOB 用十六进制导出 | 二进制数据损坏 |

**`--single-transaction` 只对 InnoDB 有效。** 如果库里还有 MyISAM 表，备份期间它们的变更会不一致——这也是"必须全用 InnoDB"的原因之一。

### 5.3.3 恢复

```bash
# 建库（如果备份里没有 CREATE DATABASE）
mysql -uroot -p -e "CREATE DATABASE app_db CHARACTER SET utf8mb4"

# 导入
mysql -uroot -p app_db < app_db_20261028.sql

# 或进客户端用 source
mysql> USE app_db;
mysql> SOURCE /backup/app_db_20261028.sql;
```

**导入加速的三个设置**（只在导入期间改，导完改回来）：

```sql
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
SET GLOBAL sync_binlog = 0;
SET GLOBAL unique_checks = 0;
SET GLOBAL foreign_key_checks = 0;
-- 导入完必须改回 1/1/1/1
```

**这些设置会牺牲持久性换速度，导入过程中绝不能有业务写入。**

### 5.3.4 压缩与并行

```bash
# 边备边压（省 80% 空间）
mysqldump -uroot -p --single-transaction app_db | gzip > app_db.sql.gz

# 恢复
gunzip < app_db.sql.gz | mysql -uroot -p app_db

# 并行导出单表（8.0 的 mysqlpump，或 mydumper）
mydumper -u root -p xxx -B app_db -o /backup/app/ -t 8
```

`mydumper` / `myloader` 是第三方工具，多线程，大库比 `mysqldump` 快数倍。

## 5.4 XtraBackup：物理备份

### 5.4.1 什么时候用它

| 场景 | 用哪个 |
|---|---|
| 数据量 < 20 GB | `mysqldump` 够用 |
| 数据量 20–100 GB | 建议 XtraBackup |
| **数据量 > 100 GB** | **必须 XtraBackup** |
| 需要跨版本迁移 | `mysqldump`（逻辑备份跨版本兼容） |
| 需要快速恢复 | XtraBackup |

### 5.4.2 全量备份

```bash
xtrabackup --backup \
  --user=root --password=xxx \
  --target-dir=/backup/full/20261028 \
  --parallel=4 \
  --compress
```

### 5.4.3 恢复流程（三步，不能跳）

```bash
# 1. prepare：让备份文件达到一致状态（这一步最容易漏）
xtrabackup --prepare --target-dir=/backup/full/20261028

# 2. 清空数据目录（危险！确认目标实例是空的）
systemctl stop mysqld
rm -rf /var/lib/mysql/*

# 3. 拷回
xtrabackup --copy-back --target-dir=/backup/full/20261028 \
  --datadir=/var/lib/mysql
chown -R mysql:mysql /var/lib/mysql

systemctl start mysqld
```

**`--prepare` 必须做**：备份过程中有未提交的事务和未刷盘的 redo，`prepare` 会做崩溃恢复，让数据文件一致。**跳过这一步直接启动会失败。**

### 5.4.4 增量备份

```bash
# 第一次增量（基于全量）
xtrabackup --backup --target-dir=/backup/inc/20261029 \
  --incremental-basedir=/backup/full/20261028

# 恢复时按顺序合并
xtrabackup --prepare --apply-log-only --target-dir=/backup/full/20261028
xtrabackup --prepare --apply-log-only --target-dir=/backup/full/20261028 \
  --incremental-dir=/backup/inc/20261029
xtrabackup --prepare --target-dir=/backup/full/20261028     # 最后一步不加 --apply-log-only
```

**增量恢复的顺序和细节很容易出错**，建议优先用全量 + binlog，而不是复杂的增量链。

## 5.5 binlog 与时间点恢复

### 5.5.1 前提检查

```sql
SHOW VARIABLES LIKE 'log_bin';           -- 必须 ON
SHOW VARIABLES LIKE 'binlog_format';     -- 必须 ROW
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';  -- 保留时长
SHOW BINARY LOGS;                        -- 现有文件列表
```

### 5.5.2 恢复流程

**目标：把数据恢复到 2026-10-28 14:25:00 这个时刻。**

```bash
# 1. 恢复最近一次全量备份
mysql -uroot -p < /backup/full_20261028_0200.sql

# 2. 找到全量备份对应的 binlog 位置
#    备份文件头部通常有 -- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000123', MASTER_LOG_POS=456789;
head -30 /backup/full_20261028_0200.sql | grep "CHANGE MASTER"

# 3. 从那个位置开始重放到目标时间
mysqlbinlog \
  --start-position=456789 \
  --stop-datetime="2026-10-28 14:25:00" \
  --database=app_db \
  /var/lib/mysql/binlog.000123 /var/lib/mysql/binlog.000124 \
  | mysql -uroot -p app_db
```

**多文件重放要按文件名顺序排列**，不能乱序。

### 5.5.3 误删的反向操作

如果误删操作在 14:20，要恢复到 14:19:59：

```bash
mysqlbinlog \
  --start-position=456789 \
  --stop-datetime="2026-10-28 14:19:59" \
  /var/lib/mysql/binlog.000123 \
  | mysql -uroot -p app_db
```

**跳过误操作再继续**（如果需要保留误操作之后的其他变更）：

```bash
# 重放 14:19:59 之前
mysqlbinlog --stop-datetime="2026-10-28 14:19:59" binlog.000123 | mysql -uroot -p

# 跳过误操作区间（14:20:00 - 14:20:05），重放之后的
mysqlbinlog --start-datetime="2026-10-28 14:20:06" binlog.000123 | mysql -uroot -p
```

**这个方法要求你精确知道误操作的时间点**，所以要养成"变更操作记录下来时间"的习惯。

## 5.6 备份验证

**这一节是本章的核心。备份文件存在 ≠ 备份可用。**

### 5.6.1 三个层次的验证

| 层次 | 做法 | 能证明什么 |
|---|---|---|
| **第一层：文件完整** | 检查文件大小、gzip 能否解压、SQL 文件末尾有 `-- Dump completed` | 文件没被截断 |
| **第二层：能导入** | 导入到临时实例 | 结构和数据能恢复 |
| **第三层：数据正确** | 对比关键表的行数、抽样数据、校验和 | 数据完整无缺 |

**大部分团队只做到第一层。** 而真正出事时，第二层和第三层才是关键。

### 5.6.2 第一层：快速完整性检查

```bash
# SQL 文件：末尾必须有这行
tail -3 backup.sql
# -- Dump completed on 2026-10-28  2:15:33

# 没有这个标记 → 备份中断了，不可用

# gzip 文件：测试能否完整解压
gzip -t backup.sql.gz && echo "完整" || echo "损坏"

# 大小变化告警：和昨天比小 20% 就要查
ls -lh /backup/*.sql.gz
```

### 5.6.3 第二层：定期导入演练

```bash
#!/bin/bash
# verify_backup.sh —— 每周跑一次

BACKUP=/backup/app_db_latest.sql.gz
TEST_DB=verify_db_$(date +%Y%m%d)

# 1. 建临时库
mysql -uroot -p"$PASS" -e "DROP DATABASE IF EXISTS $TEST_DB; CREATE DATABASE $TEST_DB"

# 2. 导入
gunzip < "$BACKUP" | mysql -uroot -p"$PASS" "$TEST_DB"
if [ $? -ne 0 ]; then
  echo "FAIL: 备份导入失败" | mail -s "备份验证失败" ops@example.com
  exit 1
fi

# 3. 校验关键表行数
SRC=$(mysql -N -uroot -p"$PASS" -e "SELECT COUNT(*) FROM app_db.orders")
DST=$(mysql -N -uroot -p"$PASS" -e "SELECT COUNT(*) FROM $TEST_DB.orders")
if [ "$SRC" -ne "$DST" ]; then
  echo "FAIL: orders 行数不一致 src=$SRC dst=$DST" | mail -s "备份验证失败" ops@example.com
  exit 1
fi

# 4. 清理
mysql -uroot -p"$PASS" -e "DROP DATABASE $TEST_DB"
echo "OK: 备份验证通过"
```

**这个脚本的价值远大于"每天生成备份文件"**——它把"备份"从"有文件"变成了"已验证"。

### 5.6.4 第三层：校验和

MySQL 8.0 支持表级校验和：

```sql
-- 生产库
CHECKSUM TABLE orders;
-- 恢复库
CHECKSUM TABLE orders;
-- 两个值必须相同
```

或者用 `pt-table-checksum` 做主从/备份的一致性校验。

## 5.7 恢复演练

**演练和真实恢复的区别：演练可以失败，真实恢复不能。**

### 5.7.1 演练清单

| 步骤 | 内容 | 常见问题 |
|---|---|---|
| 1 | 准备一台干净实例 | 没有可用的测试实例 |
| 2 | 从备份恢复到指定时间点 | 不知道 binlog 位置 |
| 3 | 验证数据正确 | 没有校验方法 |
| 4 | **计时** | 不知道实际 RTO |
| 5 | 记录卡点 | 权限不足、路径不对、版本不匹配 |

### 5.7.2 演练必须暴露的问题

| 问题 | 为什么演练才发现 |
|---|---|
| 备份文件的权限/属主不对 | 平时只 `ls -l` 看大小 |
| MySQL 版本不一致，备份无法导入 | 测试实例版本和生产不同 |
| binlog 已被清理，无法 PITR | 保留期设得太短 |
| 恢复后应用连不上（账号权限没备份） | `mysqldump` 默认不导 `mysql` 库 |
| 恢复耗时远超预期 | 从没实际跑过 |

**建议频率**：核心库每月一次，非核心库每季度一次。

## 5.8 误删找回实战

### 5.8.1 场景：14:20 误执行了 DELETE

```
14:00  全量备份（binlog.000123, pos 456789）
14:20  误执行 DELETE FROM orders WHERE status='paid'  ← 删了 5 万行
14:25  发现异常
```

### 5.8.2 方案一：从 binlog 反解（推荐，影响最小）

```bash
# 1. 解析 binlog，找到 DELETE 语句的区间
mysqlbinlog --base64-output=DECODE-ROWS -v \
  --start-datetime="2026-10-28 14:19:00" \
  --stop-datetime="2026-10-28 14:21:00" \
  /var/lib/mysql/binlog.000123 > delete_events.sql

# 2. 查看内容，ROW 格式会显示每一行的完整字段值
grep -A 20 "DELETE FROM" delete_events.sql | head -40
```

输出类似：

```
### DELETE FROM `app`.`orders`
### WHERE
###   @1=1001
###   @2='张三'
###   @3=299.00
###   @4='2026-10-20 10:30:00'
```

**`@1`、`@2`... 是列的顺序**，按 `SHOW CREATE TABLE orders` 的字段顺序对应。

把这些 `DELETE` 改写成 `INSERT`：

```bash
# 用工具自动转换（推荐）
pip install mysqlbinlog2sql  # 或用官方 my2sql
mysqlbinlog2sql -h127.0.0.1 -uroot -p xxx \
  --start-file=binlog.000123 \
  --start-datetime="2026-10-28 14:19:00" \
  --stop-datetime="2026-10-28 14:21:00" \
  -B > rollback.sql
# -B 表示生成回滚 SQL（DELETE → INSERT）
```

```bash
# 3. 确认 rollback.sql 内容后执行
mysql -uroot -p app_db < rollback.sql
```

### 5.8.3 方案二：全量 + binlog 到误操作前（较重）

见 5.5.3。适合"误操作影响面很大"或"binlog 反解不可行"的情况。

**代价**：要在临时实例上恢复，再把数据导回生产，耗时且影响业务。

### 5.8.4 方案三：从从库/备份表捞

```sql
-- 如果从库有延迟，可能还没执行到误操作
-- 立刻停从库的复制
STOP REPLICA;
-- 从从库导出数据
```

**这个方案时效性极强**，必须在延迟窗口内操作。如果从库延迟是 10 秒，你只有 10 秒。

## 5.9 数据迁移

### 5.9.1 迁移的四种场景

| 场景 | 方案 |
|---|---|
| 同版本、同机房，小数据量 | `mysqldump` 导出导入 |
| 同版本、大数据量 | XtraBackup 物理拷贝 |
| 跨版本（5.7 → 8.0） | **必须逻辑备份**（物理文件不兼容） |
| 跨数据库（MySQL → PG） | 用 ETL 工具或自研脚本 |

### 5.9.2 跨版本迁移的三个检查点

```sql
-- 1. 字符集
SHOW VARIABLES LIKE 'character_set%';
-- 5.7 默认 latin1，8.0 默认 utf8mb4，迁移前统一

-- 2. sql_mode
SELECT @@sql_mode;
-- 8.0 的 ONLY_FULL_GROUP_BY 更严格，老 SQL 可能报错

-- 3. 保留字
-- 8.0 新增了一些保留字（RANK、GROUPS、SYSTEM 等）
-- 表名或列名用了会报错
```

8.0 升级检查工具：

```bash
mysqlsh -- util check-for-server-upgrade root@localhost --output-format=JSON
```

### 5.9.3 大数据量迁移的注意点

| 注意点 | 说明 |
|---|---|
| **分批导入** | 一次导 5000 万行会撑爆 redo 和 binlog |
| **关闭唯一性检查** | 导入期间 `unique_checks=0`，导完改回 |
| **导入完成后再建索引** | 先导数据后建索引，比边导边维护索引快数倍 |
| **监控主从延迟** | 迁移期间的写入会让从库跟不上 |
| **校验行数和校验和** | 迁移完必须对账 |

**"先导数据后建索引"这一条能省一半时间**：1000 万行建索引，一次性建比逐行维护快得多。

## 5.10 备份脚本模板

```bash
#!/bin/bash
# backup_mysql.sh —— 每日全量逻辑备份

set -euo pipefail

DATE=$(date +%Y%m%d_%H%M)
BACKUP_DIR=/backup/mysql
KEEP_DAYS=7

DB_USER=backup
DB_PASS_FILE=/etc/mysql/backup.cnf     # 权限 600，不要写在脚本里
DATABASES="app_db order_db"

mkdir -p "$BACKUP_DIR"

for db in $DATABASES; do
  FILE="$BACKUP_DIR/${db}_${DATE}.sql.gz"

  mysqldump \
    --defaults-extra-file="$DB_PASS_FILE" \
    --single-transaction \
    --quick \
    --routines --triggers --events \
    --set-gtid-purged=OFF \
    --default-character-set=utf8mb4 \
    --hex-blob \
    "$db" | gzip > "$FILE"

  # 完整性检查
  if ! gzip -t "$FILE" 2>/dev/null; then
    echo "ERROR: $FILE 损坏" >&2
    exit 1
  fi

  SIZE=$(du -h "$FILE" | cut -f1)
  echo "$(date '+%F %T') $db 备份完成 $SIZE"
done

# 清理旧备份
find "$BACKUP_DIR" -name "*.sql.gz" -mtime +$KEEP_DAYS -delete

# 同步到异地（可选）
# rclone copy "$BACKUP_DIR" remote:mysql-backup/$(date +%Y%m%d)
```

## 5.11 十个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 备份文件和生产库在同一块磁盘 | 磁盘坏了两个一起没 | 异地/对象存储 |
| 2 | 只用 `mysqldump` 备 500 GB 的库 | 恢复要一整天 | 用 XtraBackup |
| 3 | 不加 `--single-transaction` | 备份数据不一致 | 必加 |
| 4 | 备份后从不验证 | 出事时才发现文件损坏 | 每周自动导入演练 |
| 5 | binlog 保留 1 天 | 出问题无法 PITR | 至少 7 天 |
| 6 | XtraBackup 恢复跳过 `--prepare` | 启动失败 | 必做 |
| 7 | 备份不导 `mysql` 库 | 恢复后账号权限全丢 | 单独备份账号，或用 `--all-databases` |
| 8 | 密码写在脚本里 | 泄露，且进 `history` | `--defaults-extra-file` |
| 9 | 备份文件权限 644 | 任何用户能读全部数据 | `chmod 600` |
| 10 | 迁移完不对账 | 数据悄悄少了几万行 | 行数 + 校验和对比 |

第 7 条很隐蔽：`mysqldump` 导单库时不包含 `mysql` 系统库，所以**用户、权限、授权信息都不会被备份**。恢复到新实例后，应用连不上，而且不知道为什么。要么单独备 `mysql` 库，要么用 `--all-databases`。
