## 8.1 日常巡检

**巡检的价值是"在用户发现问题之前发现"。** 分三个频率，每项都有明确的判断标准。

### 8.1.1 每日（5 分钟）

| # | 检查项 | 命令 | 判断标准 |
|---|---|---|---|
| 1 | 实例存活 | `mysqladmin ping` | 有 `mysqld is alive` |
| 2 | 复制状态 | `SHOW REPLICA STATUS\G` | 两个 Running 都 Yes |
| 3 | 复制延迟 | 同上 | `Seconds_Behind_Source` < 5 |
| 4 | 连接数 | `SHOW STATUS LIKE 'Threads_connected'` | < `max_connections` × 80% |
| 5 | 磁盘水位 | `df -h /var/lib/mysql` | < 80% |
| 6 | 错误日志 | `tail -100 error.log` | 无 ERROR / crash |
| 7 | 慢查询数 | `SHOW STATUS LIKE 'Slow_queries'` | 与昨日比无突增 |

一条命令跑完前 5 项：

```bash
#!/bin/bash
# daily_check.sh
MYSQL="mysql -uroot -p$PASS -N -B"

echo "=== 存活 ==="
mysqladmin -uroot -p$PASS ping 2>/dev/null || echo "FAIL: 实例不可达"

echo "=== 复制 ==="
$MYSQL -e "SHOW REPLICA STATUS\G" | grep -E "Replica_IO_Running|Replica_SQL_Running|Seconds_Behind_Source"

echo "=== 连接 ==="
CONN=$($MYSQL -e "SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Threads_connected'")
MAX=$($MYSQL -e "SELECT VARIABLE_VALUE FROM performance_schema.global_variables WHERE VARIABLE_NAME='max_connections'")
echo "连接 $CONN / $MAX"

echo "=== 磁盘 ==="
df -h /var/lib/mysql | tail -1

echo "=== 错误日志（最近 20 条 ERROR） ==="
grep ERROR /var/log/mysql/error.log | tail -20
```

### 8.1.2 每周（30 分钟）

| # | 检查项 | 命令 / 方法 | 判断标准 |
|---|---|---|---|
| 1 | 备份验证 | 导入测试实例 + 对行数 | 能导入且行数一致 |
| 2 | 大表增长 | `information_schema.TABLES` | 周增长 > 10% 要评估 |
| 3 | 长事务 | `INNODB_TRX` | 无 > 60 秒的 |
| 4 | 无用索引 | `sys.schema_unused_indexes` | 记录，观察 1 个月后删 |
| 5 | 冗余索引 | `sys.schema_redundant_indexes` | 有则清理 |
| 6 | 无主键表 | 2.11.1 的 SQL | 无 |
| 7 | 慢查询 TOP 10 | `pt-query-digest` | 与上周对比无恶化 |
| 8 | 账号审计 | `mysql.user` | 无过期/僵尸账号 |

**备份验证是每周最不能省的一项**。第 5 章给了完整脚本。

### 8.1.3 每月（半天）

| # | 检查项 | 说明 |
|---|---|---|
| 1 | **恢复演练** | 从备份完整恢复一次，计时，记录卡点 |
| 2 | 容量趋势 | 按过去 3 个月增长速率预测何时需要扩容 |
| 3 | 参数复审 | 业务量变化后，缓冲池、连接数是否还合适 |
| 4 | 版本与安全补丁 | 关注 MySQL 安全公告 |
| 5 | 权限最小化复审 | 清理不再需要的授权 |
| 6 | 慢查询治理 | 挑 3 条最耗时的，优化并验证 |
| 7 | 死锁统计 | `Innodb_deadlocks` 增量，持续增长要专项分析 |

### 8.1.4 巡检记录表模板

| 日期 | 实例 | 存活 | 复制 | 延迟 | 连接% | 磁盘% | 慢查询 | 异常说明 | 处理人 |
|---|---|---|---|---|---|---|---|---|---|
| 10-28 | db-01 | ✓ | ✓ | 0s | 35% | 62% | 12 | — | 张三 |
| 10-28 | db-02 | ✓ | ✗ | — | 40% | 58% | 8 | IO 线程断，已重启 | 张三 |

**"异常说明"和"处理人"两列不能省**——一个月后回看时，只有这两列有用。

## 8.2 变更管理规范

### 8.2.1 变更分级

| 级别 | 定义 | 审批 | 时间窗 |
|---|---|---|---|
| **P1 高危** | 删表、删库、大表 DDL、主从切换、版本升级 | **双人复核** | 低峰期 + 提前通知 |
| **P2 中危** | 加索引、改表结构、批量数据更新、参数调整 | 单人审批 | 低峰期 |
| **P3 低危** | 加账号、改权限、加监控、查询优化 | 记录即可 | 随时 |

**"删表"和"删库"必须是 P1**，而且要双人复核——一个人执行，一个人盯着屏幕念。

### 8.2.2 变更前检查清单

```markdown
- [ ] 变更内容写在工单里，含完整 SQL
- [ ] 已确认目标实例（生产 / 测试，名字要说出来）
- [ ] 已确认影响范围（多少行、多少表、多长时间）
- [ ] 已备份（或已确认有可用备份 + binlog 位置）
- [ ] 已在测试库验证过
- [ ] 已准备回滚方案
- [ ] 已通知相关方（应用负责人、值班）
- [ ] 已确认不在业务高峰
```

**"已确认目标实例"这一条看起来多余，但生产事故里有相当比例是"连错库"。** 把实例名念出来，是最低成本的防呆。

### 8.2.3 变更时的三个习惯

```sql
-- 1. 每次连上先确认自己在哪
SELECT @@hostname, @@port, DATABASE(), CURRENT_USER();

-- 2. 危险操作前先看时间，记录下来
SELECT NOW();

-- 3. 操作都在事务里，确认无误再提交
BEGIN;
-- ... DML ...
-- 检查结果
COMMIT;   -- 或 ROLLBACK
```

### 8.2.4 回滚方案必须提前准备

| 变更类型 | 回滚方案 |
|---|---|
| 加索引 | `DROP INDEX`（快） |
| 加字段 | `DROP COLUMN`（8.0 支持 INSTANT，快） |
| 改字段类型 | **难回滚**，可能锁表，必须备份 |
| 批量 UPDATE | 备份表 + 反向 UPDATE |
| 删表 | 只能靠备份恢复，**必须有备份** |

**"改字段类型"是最难回滚的**，因为它通常要重建表。做之前必须有完整备份，且评估锁表时间。

## 8.3 十个故障剧本

每个剧本按 **现象 → 判断 → 处理 → 根因 → 预防** 组织。

### 8.3.1 剧本一：连接数打满

**现象**

```
ERROR 1040 (08004): Too many connections
```

应用全部报错，连运维都连不上（因为连接数已满）。

**判断**

```bash
# 先用 root 通过 socket 连（不受 TCP 连接数限制）
mysql -uroot -p --socket=/var/lib/mysql/mysql.sock

# 或临时调大（已连接的会话可以执行）
mysql -e "SET GLOBAL max_connections = 1000"
```

```sql
-- 看连接分布
SELECT user, host, command, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
GROUP BY user, host, command
ORDER BY cnt DESC;

-- 看 Sleep 连接
SELECT COUNT(*) FROM information_schema.PROCESSLIST WHERE command='Sleep';
```

**处理**

```sql
-- 如果是僵尸 Sleep 连接（应用没关连接）
-- 批量杀掉超过 600 秒的 Sleep
SELECT CONCAT('KILL ', id, ';')
FROM information_schema.PROCESSLIST
WHERE command='Sleep' AND time > 600;

-- 执行生成的语句
```

```bash
# 一条命令批量杀
mysql -N -e "SELECT id FROM information_schema.PROCESSLIST WHERE command='Sleep' AND time>600" \
  | xargs -I{} mysql -e "KILL {}"
```

**根因判断**

| 特征 | 根因 |
|---|---|
| 大量 `Sleep` 且 `time` 很大 | **应用连接池没配 `maxLifetime`**，连接不回收 |
| 大量 `Query` 且 `time` 大 | 有慢查询占着连接 |
| 连接数缓慢爬升 | 连接泄漏（部分代码路径没 `close`） |
| 瞬间打满 | 应用扩容 / 突发流量 / 连接池配置错误 |

**预防**

```ini
# 服务端：让空闲连接自动断开
wait_timeout = 600
interactive_timeout = 600
```

```
# 应用侧（以 Java HikariCP 为例）必须配
maximumPoolSize = 20
minimumIdle = 5
maxLifetime = 300000      # 5 分钟，必须小于 wait_timeout
idleTimeout = 60000
connectionTimeout = 3000
```

**`maxLifetime` 必须小于 `wait_timeout`**，否则连接被服务端断了应用还在用，报 "connection closed"。

### 8.3.2 剧本二：CPU 100%

**现象**：`top` 显示 mysqld 占用 800%（8 核满载），QPS 下降，请求超时。

**判断**

```bash
# 1. 确认是 MySQL 还是别的进程
top -bn1 | head -15

# 2. 看是用户态还是内核态
#    us 高 → 计算（SQL 问题）
#    sy 高 → 系统调用（IO / 锁争用）
#    wa 高 → IO 等待
top -bn1 | grep "Cpu(s)"

# 3. 看 MySQL 内部在干什么
```

```sql
-- 当前在跑的 SQL（按耗时排序）
SELECT id, user, host, db, command, time, state, LEFT(info, 120) AS sql
FROM information_schema.PROCESSLIST
WHERE command != 'Sleep'
ORDER BY time DESC
LIMIT 15;

-- 看是否有大量并发相同 SQL（可能是缓存击穿）
SELECT LEFT(info, 80) AS sql, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
WHERE command='Query'
GROUP BY sql
ORDER BY cnt DESC
LIMIT 10;
```

**处理**

```sql
-- 杀掉最耗 CPU 的查询
KILL 12345;

-- 如果是大量相同 SQL，说明是应用侧问题（缓存失效 → 击穿）
-- 临时方案：限流或加缓存
```

**根因**

| 特征 | 根因 | 处理 |
|---|---|---|
| `us` 高 + 有全表扫描 SQL | 缺索引 | 补索引 |
| `us` 高 + `Using filesort` | 排序数据量大 | 加索引或减少排序量 |
| `sy` 高 + `%util` 高 | IO 密集 | 加缓冲池 |
| 大量相同 SQL 并发 | 缓存击穿 | 应用加互斥锁/缓存预热 |
| CPU 高但 QPS 低 | 单条 SQL 极耗 CPU（如正则、大排序） | 优化或限流 |

### 8.3.3 剧本三：磁盘满

**现象**：写入报错 `ERROR 1114 (HY000): The table 'xxx' is full`，或 `No space left on device`。

**判断**

```bash
# 1. 哪个分区满
df -h

# 2. 哪个目录大
du -sh /var/lib/mysql/* | sort -rh | head -10
du -sh /var/log/mysql/* | sort -rh | head

# 3. 如果是 binlog 大
ls -lh /var/lib/mysql/binlog.* | tail -20
```

```sql
-- 表大小排序
SELECT table_schema, table_name,
       ROUND((data_length+index_length)/1024/1024/1024, 2) AS gb
FROM information_schema.TABLES
ORDER BY (data_length+index_length) DESC
LIMIT 10;

-- binlog 占用
SHOW BINARY LOGS;
```

**处理（按安全顺序）**

```sql
-- ① 清 binlog（最安全，且通常最大）
PURGE BINARY LOGS BEFORE DATE_SUB(NOW(), INTERVAL 7 DAY);

-- ② 清慢日志 / 错误日志（先备份或确认不需要）
-- shell: > /var/log/mysql/slow.log

-- ③ 清 undo（如果有独立的 undo 表空间且不再需要）
-- 慎重，通常不建议手动删

-- ④ 归档历史数据（不是删，是迁走）
```

```bash
# 确认 binlog 是否还能清（从库是否还需要）
# 先看从库消费到哪个位置
mysql -e "SHOW REPLICA STATUS\G" | grep -E "Relay_Master_Log_File|Exec_Master_Log_Pos"
```

**绝对不能做的**

| 操作 | 后果 |
|---|---|
| `rm` 删 binlog 文件 | 索引断裂，复制挂掉 |
| 删 `.ibd` 文件 | **数据永久丢失** |
| 删 `ibdata1` | 数据库报废 |
| 删 `#innodb_redo` | 崩溃后无法恢复 |

**预防**

```ini
# binlog 自动过期
binlog_expire_logs_seconds = 604800    # 7 天
max_binlog_size = 512M
```

```bash
# 监控：磁盘 > 75% 告警，> 85% 紧急
```

### 8.3.4 剧本四：主从复制中断

**现象**：`Replica_IO_Running` 或 `Replica_SQL_Running` 变成 `No`。

**判断**

```sql
SHOW REPLICA STATUS\G
```

看两个错误字段：

```
Last_IO_Error:  ...
Last_SQL_Error: ...
```

| 错误 | 含义 | 处理 |
|---|---|---|
| `Last_IO_Error: Got fatal error 1236` | binlog 被清理了，从库要的找不到 | 重建从库 |
| `Last_IO_Error: Can't connect` | 网络/账号/主库挂了 | 查网络、账号 |
| `Last_SQL_Error: Duplicate entry` | 主键冲突 | 见下 |
| `Last_SQL_Error: Table doesn't exist` | 表不存在（DDL 没同步） | 手工建表或重建 |
| `Last_SQL_Error: Error 1062` | 同上，唯一键冲突 | 见下 |

**处理：SQL 线程错误（谨慎）**

```sql
STOP REPLICA;

-- ① 先看具体是哪条语句出错
SELECT * FROM performance_schema.replication_applier_status_by_worker\G

-- ② 分析冲突：是数据不一致，还是可以跳过
--    如果是从库被人写过 → 数据不一致，跳过会扩大问题

-- ③ 如果确认是单条可跳过的错误
SET GLOBAL sql_replica_skip_counter = 1;
START REPLICA;

-- ④ 如果是 GTID 模式
SET GTID_NEXT = 'xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx:123';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
START REPLICA;
```

**`sql_replica_skip_counter` 跳过意味着永久数据不一致**，必须记录，事后用 `pt-table-sync` 修复。

**处理：IO 线程错误（binlog 丢失）**

```bash
# 只能重建从库
# 1. 主库全量备份
mysqldump -uroot -p --single-transaction --set-gtid-purged=ON --all-databases > full.sql

# 2. 从库导入
mysql -uroot -p < full.sql

# 3. 重建复制
```

```sql
STOP REPLICA;
RESET REPLICA ALL;
CHANGE REPLICATION SOURCE TO SOURCE_HOST='...', SOURCE_AUTO_POSITION=1, ...;
START REPLICA;
```

### 8.3.5 剧本五：死锁频发

**现象**：应用日志里大量 `Deadlock found when trying to get lock`（1213），`Innodb_deadlocks` 持续增长。

**判断**

```sql
-- 死锁累计数
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';

-- 最近一次死锁详情
SHOW ENGINE INNODB STATUS\G
-- 找 LATEST DETECTED DEADLOCK
```

**处理**

如果只是偶发（每天几次），应用重试即可。**如果是高频（每小时几十次），必须改代码**：

| 原因 | 改法 |
|---|---|
| 加锁顺序不一致 | 统一按主键升序处理 |
| 缺索引导致锁范围过大 | 补索引 |
| RR 下间隙锁冲突 | 改 RC |
| 批量操作逐条加锁 | 改成一次锁定或排序后批量 |

**预防**

```sql
-- 监控死锁增长率
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';
-- 每小时增量 > 10 就要排查
```

### 8.3.6 剧本六：慢查询突增

**现象**：慢查询从每小时 5 条突然涨到 500 条，应用响应时间上升。

**判断**

```bash
# 看慢日志最近的记录
tail -200 /var/log/mysql/slow.log

# 按 SQL 模板聚合
pt-query-digest --since "1 hour ago" /var/log/mysql/slow.log
```

```sql
-- 看当前是否在跑异常 SQL
SELECT id, time, state, LEFT(info, 150)
FROM information_schema.PROCESSLIST
WHERE command='Query' AND time > 2
ORDER BY time DESC;
```

**三个常见原因**

| 原因 | 判断方法 |
|---|---|
| **突发流量** | QPS 监控突增 |
| **执行计划变了**（统计信息过期） | `EXPLAIN` 和之前对比，`ANALYZE TABLE` 后恢复 |
| **索引被删/被改** | 查 `information_schema.STATISTICS`，看是否有近期变更 |

**统计信息过期是最隐蔽的**：

```sql
-- 大批量导入/删除后必须更新
ANALYZE TABLE orders;

-- 看上次更新时间
SELECT table_name, update_time FROM information_schema.TABLES
WHERE table_schema='app_db';
```

### 8.3.7 剧本七：表损坏

**现象**：查询报 `Incorrect key file for table`、`Table 'xxx' is marked as crashed`。

**判断**

```sql
CHECK TABLE orders;
-- 或
CHECK TABLE orders EXTENDED;
```

**处理**

```sql
-- MyISAM 表
REPAIR TABLE orders;

-- InnoDB 表
-- ① 先尝试在线恢复
ALTER TABLE orders ENGINE=InnoDB;

-- ② 如果不行，用强制恢复模式（需改 my.cnf 并重启）
-- innodb_force_recovery = 1   到 6，逐级尝试
-- 能启动后立刻 mysqldump 导出数据
-- 然后重建表并导入
```

**`innodb_force_recovery` 是最后手段**：能启动后数据库是只读的，必须立刻导出数据，然后重建实例。级别越高，丢数据越多。

**预防**

| 做法 | 说明 |
|---|---|
| 用 InnoDB | MyISAM 更容易损坏 |
| `innodb_flush_log_at_trx_commit=1` | 保证 redo 完整 |
| 定期 `CHECK TABLE` | 主动发现 |
| 硬件检查 | 磁盘坏道是表损坏的主因 |

### 8.3.8 剧本八：误删数据

**这是最需要按流程走的场景**，慌乱中做错一步就无法挽回。

**第一时间（30 秒内）**

```bash
# ① 立刻停止应用写入（宁可停服，也别继续污染）
#    改配置、摘流量、或直接
mysql -e "SET GLOBAL super_read_only = ON"

# ② 记录当前时间
date
```

**第二步：判断影响范围**

```sql
-- 删了什么？删了多少行？什么时候删的？
-- 从 PROCESSLIST 看不到了（已经执行完），只能靠 binlog

# ① 找到误操作的 binlog 位置
mysqlbinlog --base64-output=DECODE-ROWS -v \
  --start-datetime="2026-10-28 14:00:00" \
  /var/lib/mysql/binlog.000123 | grep -B5 -A30 "DELETE FROM"

# ② 确认是不是你要找的那条
```

**第三步：选方案**

| 方案 | 适用 | 代价 |
|---|---|---|
| **binlog 反解恢复** | 能定位到具体时间点 | 最小，几十分钟 |
| 从库数据补回 | 从库有延迟或未执行 | 依赖延迟窗口 |
| 全量恢复 + PITR | 影响面很大 | 几小时 |

**binlog 反解（推荐）**

```bash
# 生成回滚 SQL
mysqlbinlog2sql -h127.0.0.1 -uroot -p xxx \
  --start-file=binlog.000123 \
  --start-datetime="2026-10-28 14:19:00" \
  --stop-datetime="2026-10-28 14:21:00" \
  -B > rollback.sql
# -B 表示反向（DELETE → INSERT）

# 检查内容
head -50 rollback.sql

# 执行
mysql -uroot -p app_db < rollback.sql
```

**第四步：验证与恢复**

```sql
-- 行数核对
SELECT COUNT(*) FROM orders;
-- 抽样核对
SELECT * FROM orders WHERE id IN (1001, 1002, 1003);

-- 确认无误后恢复写入
SET GLOBAL super_read_only = OFF;
```

**预防**

| 做法 | 说明 |
|---|---|
| `binlog_format=ROW` | 必须，否则无法反解 |
| binlog 保留 ≥ 7 天 | 出事后有时间窗口 |
| 变更走工单 | 强制两个人看 |
| 危险操作先 `SELECT` | 四步法 |
| 生产库不给 `DROP` 权限 | 按需申请 |

### 8.3.9 剧本九：主库宕机

**现象**：监控告警主库不可达，应用全部报错。

**判断**

```bash
# 是机器挂了还是 MySQL 挂了
ping <主库IP>
ssh <主库IP> "systemctl status mysqld"

# 如果是 MySQL 挂了
tail -200 /var/log/mysql/error.log
```

**决策树**

```
主库能否快速恢复？
├─ 能（重启即好，如 OOM → 调参后重启）
│   └─ 直接恢复，观察 10 分钟
└─ 不能（磁盘坏、机器故障、数据损坏）
    └─ 切换主从
```

**切换流程（详见 006 的 6.7）**

```sql
-- ① 确认从库已追平
SHOW REPLICA STATUS\G
-- Retrieved_Gtid_Set == Executed_Gtid_Set

-- ② 停复制、提升为主
STOP REPLICA;
RESET REPLICA ALL;
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

-- ③ 应用切流量
-- ④ 其他从库改指向
```

**关键点：切换前必须确认旧主已停止写入**，否则脑裂。

### 8.3.10 剧本十：备份失败

**现象**：备份脚本报错退出，或者备份文件比昨天小很多。

**判断**

```bash
# 看备份日志
tail -100 /var/log/mysql/backup.log

# 看文件大小趋势
ls -lh /backup/mysql/*.sql.gz | tail -10

# 完整性检查
gzip -t /backup/mysql/latest.sql.gz
tail -3 /backup/mysql/latest.sql      # 要有 -- Dump completed
```

**常见原因**

| 原因 | 处理 |
|---|---|
| 磁盘满 | 清旧备份 / 扩容 |
| `mysqldump` 锁等待超时 | 检查长事务 |
| 权限不足 | 检查备份账号 |
| 表损坏，导出中断 | `CHECK TABLE` |
| 网络中断（传到异地） | 重试 + 断点续传 |

**处理**

```bash
# 立刻手工补一次备份，确认可用
mysqldump -uroot -p --single-transaction --all-databases | gzip > /backup/emergency_$(date +%Y%m%d).sql.gz
gzip -t /backup/emergency_*.sql.gz && echo OK
```

**备份失败必须当故障处理**，不能"明天再看"——万一今晚出事，就没有退路了。

## 8.4 容量规划

### 8.4.1 三个必须算的数

```sql
-- ① 当前数据量
SELECT
  ROUND(SUM(data_length)/1024/1024/1024, 2) AS data_gb,
  ROUND(SUM(index_length)/1024/1024/1024, 2) AS index_gb
FROM information_schema.TABLES
WHERE table_schema NOT IN ('mysql','sys','information_schema','performance_schema');

-- ② 增长速率（需要历史数据，建议每天采集存到监控库）
-- 用今天的 data_gb 减去 30 天前的 data_gb

-- ③ 索引占比
-- index_gb / data_gb，正常 20-50%，超过 100% 说明索引过多
```

### 8.4.2 预测扩容时间

```
可用天数 = (磁盘总容量 × 80% - 当前使用量) / 每日增长量
```

**建议在剩余 90 天时启动扩容**，因为采购/审批/迁移都要时间。

### 8.4.3 单表多大的上限

| 数据量 | 状态 | 建议 |
|---|---|---|
| < 500 万行 | 舒适 | 不用管 |
| 500 万 – 2000 万 | 可接受 | 关注索引和慢查询 |
| 2000 万 – 1 亿 | 有压力 | 考虑归档、分区 |
| > 1 亿 | 必须处理 | 分表 / 归档 / 冷热分离 |
| 单表 > 500 GB | 危险 | 备份恢复都很困难 |

**这些数字不是硬线**，取决于访问模式和索引设计。但"单表 1 亿行"是一个该主动规划的信号。

### 8.4.4 四种治理手段

| 手段 | 适用 | 代价 |
|---|---|---|
| **归档** | 历史数据很少访问 | 应用要能接受"查不到老数据" |
| **分区** | 按时间范围查询 | 分区键必须在主键里 |
| **分表** | 单表太大，写入也高 | 应用改造大 |
| **冷热分离** | 热数据小、冷数据大 | 架构复杂 |

**优先顺序：归档 > 分区 > 分表**。归档最简单，分表最复杂。

## 8.5 账号与权限

### 8.5.1 最小权限原则

```sql
-- ❌ 应用账号给 ALL
GRANT ALL ON *.* TO 'app'@'%';

-- ✅ 只给需要的
GRANT SELECT, INSERT, UPDATE, DELETE ON app_db.* TO 'app'@'10.0.0.%';
```

### 8.5.2 四类账号

| 账号 | 权限 | 用途 |
|---|---|---|
| **应用账号** | 业务库的 `SELECT/INSERT/UPDATE/DELETE` | 应用连接 |
| **只读账号** | 业务库的 `SELECT` | 报表、排查 |
| **备份账号** | `SELECT/SHOW VIEW/TRIGGER/LOCK TABLES/RELOAD/REPLICATION CLIENT/PROCESS` | 备份 |
| **DBA 账号** | 按需申请，用后回收 | 变更操作 |

**四类账号不能混用。** 应用账号绝不能有 `DROP`、`ALTER`、`GRANT`。

### 8.5.3 限制来源

```sql
-- 只允许内网段
CREATE USER 'app'@'10.0.0.%' IDENTIFIED BY 'xxx';

-- 不允许 %
-- ❌ 'app'@'%'
```

### 8.5.4 审计

```sql
-- 看所有账号
SELECT user, host, account_locked, password_expired, password_last_changed
FROM mysql.user
ORDER BY user;

-- 找长期没改密码的
SELECT user, host, password_last_changed
FROM mysql.user
WHERE password_last_changed < DATE_SUB(NOW(), INTERVAL 180 DAY);

-- 找权限过大的
SELECT user, host FROM mysql.user WHERE Super_priv = 'Y';
```

**每月审一次**：僵尸账号（已离职）、过期权限（项目结束）、`%` host。

### 8.5.5 密码管理

```sql
-- 密码强度插件
INSTALL PLUGIN validate_password SONAME 'validate_password.so';
SET GLOBAL validate_password.policy = MEDIUM;

-- 密码过期
ALTER USER 'app'@'10.0.0.%' PASSWORD EXPIRE INTERVAL 180 DAY;
```

**密码不能明文存在任何代码仓库里**，用配置中心或密钥管理。

## 8.6 版本升级

### 8.6.1 升级前检查（5.7 → 8.0）

```bash
mysqlsh -- util check-for-server-upgrade root@localhost --output-format=JSON
```

**必须检查的四项**：

| 项 | 命令 | 风险 |
|---|---|---|
| 字符集 | `SHOW VARIABLES LIKE 'character_set%'` | 5.7 可能是 latin1 |
| `sql_mode` | `SELECT @@sql_mode` | 8.0 的 `ONLY_FULL_GROUP_BY` 更严 |
| 保留字 | 检查表名/列名 | 8.0 新增 `RANK`、`GROUPS` 等 |
| 认证插件 | `SELECT plugin FROM mysql.user` | 8.0 默认 `caching_sha2_password`，老客户端连不上 |

### 8.6.2 升级路径

**不支持跳版本**：

```
5.6 → 5.7 → 8.0     ✅
5.6 → 8.0           ❌
```

### 8.6.3 升级步骤（主从架构）

```
① 先升从库 → 验证 → 切换流量到从库 → 再升原主库
② 升级前全量备份
③ 升级后跑 CHECK TABLE + 业务验证
④ 保留回滚路径（旧版本二进制、备份）
```

**"先升从库"是关键**：出问题只影响读流量，可以切回来。

## 8.7 九个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 危险操作前不确认实例 | 改了生产库 | 先 `SELECT @@hostname, @@port` |
| 2 | 磁盘满时 `rm` 删 binlog | 复制挂掉 | `PURGE BINARY LOGS` |
| 3 | 复制报错就 skip | 数据永久不一致 | 先分析原因，记录跳过 |
| 4 | 备份失败"明天再看" | 当晚出事无退路 | 当故障处理，立刻补备 |
| 5 | 应用账号给 `ALL` | 一次注入全库沦陷 | 最小权限 |
| 6 | 巡检只看"有没有报错" | 漏掉趋势性恶化 | 看趋势和增长速率 |
| 7 | 主库宕机直接切，不确认延迟 | 丢数据 | 先对比 GTID |
| 8 | 误删后继续让应用写入 | 新数据覆盖，无法恢复 | 立刻 `super_read_only` |
| 9 | 升级跳版本 | 失败，且可能无法回滚 | 逐版本升级 |

第 8 条最重要：**误删后的第一动作是停止写入，不是查原因**。每一秒的继续写入都在覆盖可恢复的现场。
