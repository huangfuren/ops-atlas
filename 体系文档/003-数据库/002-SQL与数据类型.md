## 2.1 运维的 SQL 边界

| 你要会 | 你不用管 |
|---|---|
| 查数据、核数据、验证变更结果 | 写复杂业务报表 SQL |
| 安全地 UPDATE / DELETE 单表数据 | 优化器的内部实现 |
| 看懂别人的查询慢在哪 | 存储过程开发 |
| 建表、改表、加索引 | 复杂窗口函数、CTE 递归 |
| 导出数据做审计/核对 | ORM 生成的 SQL 怎么调优 |

**核心能力是"判断力"**：看到一条 SQL，能判断它会不会全表扫描、会不会锁太多行、跑起来大概多久。

## 2.2 四个基本语句

### 2.2.1 查：SELECT

```sql
-- 基本形式
SELECT id, name, created_at
FROM users
WHERE status = 'active'
  AND created_at > '2026-01-01'
ORDER BY created_at DESC
LIMIT 20;
```

**执行的逻辑顺序**（和书写顺序不同，这个必须记）：

```
书写：SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
执行：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

为什么重要：**`WHERE` 里不能用 `SELECT` 里起的别名**（因为 WHERE 先执行），而 `ORDER BY` 可以。很多人在这里踩坑。

```sql
-- 报错：Unknown column 'total'
SELECT price * qty AS total FROM orders WHERE total > 100;

-- 正确：WHERE 里重复表达式，或包一层
SELECT * FROM (SELECT price*qty AS total FROM orders) t WHERE t.total > 100;
```

### 2.2.2 增：INSERT

```sql
-- 单行
INSERT INTO users (name, email) VALUES ('张三', 'a@b.com');

-- 多行（比循环单条快几十倍）
INSERT INTO users (name, email) VALUES
  ('张三', 'a@b.com'),
  ('李四', 'c@d.com');

-- 冲突时更新（幂等导入的关键）
INSERT INTO users (id, name) VALUES (1, '张三')
ON DUPLICATE KEY UPDATE name = VALUES(name);

-- 冲突时忽略
INSERT IGNORE INTO users (id, name) VALUES (1, '张三');
```

`ON DUPLICATE KEY UPDATE` 是数据同步、幂等重跑的必备写法，比"先查再决定插还是改"少一次往返，也不会并发冲突。

### 2.2.3 改：UPDATE

```sql
UPDATE users SET status = 'inactive' WHERE id = 100;
```

**`UPDATE` 不带 `WHERE` 会改全表**，这是运维最经典的事故。2.3 专门讲怎么防。

### 2.2.4 删：DELETE

```sql
DELETE FROM users WHERE id = 100;

-- 清空表（两种方式差别巨大）
DELETE FROM users;          -- 逐行删，写 undo/redo/binlog，10 亿行能跑几小时
TRUNCATE TABLE users;       -- 直接重建表，秒级，但不能回滚、不能带 WHERE
```

| | `DELETE` | `TRUNCATE` |
|---|---|---|
| 速度 | 慢（逐行） | 快（重建表） |
| 能否回滚 | 能 | **不能** |
| 能否带 WHERE | 能 | 不能 |
| 是否写 binlog | 写（可恢复） | 写（但内容极少） |
| 自增 ID | 不重置 | **重置为 1** |
| 触发器 | 触发 | 不触发 |

**大表清空要谨慎**：`TRUNCATE` 不可回滚，且会短暂锁表。如果需要保留部分数据，只能 `DELETE`，而且必须分批（见 2.3.4）。

## 2.3 危险操作的标准姿势

这一节是本章最重要的内容。**运维改数据的每一次操作，都该按这个流程。**

### 2.3.1 UPDATE / DELETE 的四步法

```sql
-- 第一步：用同样的 WHERE 先 SELECT，确认影响范围
SELECT COUNT(*) FROM users WHERE status = 'pending' AND created_at < '2026-01-01';
-- 返回 1523

-- 第二步：看几条样本，确认是"该改的那些"
SELECT id, name, status FROM users
WHERE status = 'pending' AND created_at < '2026-01-01'
LIMIT 10;

-- 第三步：加 LIMIT 先小批量试
UPDATE users SET status = 'expired'
WHERE status = 'pending' AND created_at < '2026-01-01'
LIMIT 100;
-- 检查：Affected rows: 100，符合预期

-- 第四步：确认无误后全量执行，且分批
UPDATE users SET status = 'expired'
WHERE status = 'pending' AND created_at < '2026-01-01'
LIMIT 1000;
-- 重复执行直到 Affected rows: 0
```

**四步的核心是"每一步都能撤回"**。直接一条大 UPDATE，出错了只能靠 binlog 反解，代价极高。

### 2.3.2 显式事务包起来

```sql
BEGIN;

UPDATE users SET status = 'expired' WHERE id BETWEEN 100 AND 200;
-- 看结果
SELECT id, status FROM users WHERE id BETWEEN 100 AND 200;

-- 对就提交，错就回滚
COMMIT;
-- 或
ROLLBACK;
```

**注意**：事务没提交前，锁一直持有。别开了事务去开会。

### 2.3.3 先备份要改的数据

```sql
-- 改动前把原数据存一份到备份表
CREATE TABLE users_bak_20261028 AS
SELECT * FROM users WHERE status = 'pending' AND created_at < '2026-01-01';

-- 出问题了从备份表恢复
UPDATE users u
JOIN users_bak_20261028 b ON u.id = b.id
SET u.status = b.status;
```

这张备份表用完确认无误再删。**它比 binlog 反解快得多**，是误操作的第一道防线。

### 2.3.4 大批量操作必须分批

```sql
-- ❌ 一条删 500 万行：锁大量行、undo 暴涨、主从延迟几十分钟
DELETE FROM logs WHERE created_at < '2025-01-01';

-- ✅ 分批删，每批 1000 行，批间 sleep
DELETE FROM logs WHERE created_at < '2025-01-01' LIMIT 1000;
-- 重复执行，直到 Affected rows: 0
```

命令行循环：

```bash
while true; do
  n=$(mysql -N -e "DELETE FROM logs WHERE created_at < '2025-01-01' LIMIT 1000; SELECT ROW_COUNT();" your_db)
  echo "deleted $n"
  [ "$n" -eq 0 ] && break
  sleep 0.5
done
```

**分批的三个理由**：① 锁范围小，不阻塞业务 ② undo 能及时清理 ③ binlog 分散，从库能跟上。

### 2.3.5 大表加索引/加字段

```sql
-- 5.7+ 支持在线 DDL，但要显式指定
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at),
  ALGORITHM=INPLACE, LOCK=NONE;
```

`LOCK=NONE` 表示不阻塞读写。**如果 MySQL 说做不到，会直接报错，而不是偷偷降级**——这正是我们要的。

大表（千万级以上）用专业工具：

```bash
# gh-ost：主库创建影子表，逐步拷贝，最后原子切换
gh-ost --host=127.0.0.1 --database=app --table=orders \
       --alter="ADD INDEX idx_user_created (user_id, created_at)" \
       --allow-on-master --execute
```

## 2.4 JOIN：看清数据怎么拼

### 2.4.1 五种 JOIN

```sql
-- ① INNER JOIN：两边都匹配才留下
SELECT u.name, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- ② LEFT JOIN：左表全留，右表没匹配则为 NULL
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
-- 没有订单的用户也会出现，amount 为 NULL

-- ③ RIGHT JOIN：右表全留（很少用，改成 LEFT JOIN 交换表顺序更易读）
-- ④ FULL OUTER JOIN：MySQL 不支持，用 UNION 模拟
-- ⑤ CROSS JOIN：笛卡尔积，慎用
```

### 2.4.2 LEFT JOIN 的两个陷阱

**陷阱一：把右表的过滤条件写在 WHERE 里，JOIN 退化成 INNER**

```sql
-- ❌ 想保留所有用户，但 WHERE 把 NULL 过滤掉了
SELECT u.name, o.amount
FROM users u LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'paid';
-- 没订单的用户 o.status 是 NULL，NULL != 'paid'，被过滤 → 等价于 INNER JOIN

-- ✅ 条件放 ON 里
SELECT u.name, o.amount
FROM users u LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'paid';
```

**陷阱二：一对多 JOIN 导致行数膨胀**

```sql
-- users 有 1000 行，orders 有 50000 行，一个用户 50 个订单
-- 这条查出来是 50000 行，不是 1000 行
SELECT u.*, o.amount FROM users u LEFT JOIN orders o ON u.id = o.user_id;
```

如果需要"每个用户一行"，得用聚合：

```sql
SELECT u.id, u.name, COUNT(o.id) AS order_cnt, SUM(o.amount) AS total
FROM users u LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;
```

### 2.4.3 JOIN 的性能要点

| 要点 | 说明 |
|---|---|
| **关联字段必须有索引** | `ON u.id = o.user_id`，`o.user_id` 上没索引 → 全表扫描 → 灾难 |
| **小表驱动大表** | 优化器会自动选，但你可以用 `STRAIGHT_JOIN` 强制，前提是你确定 |
| **JOIN 表数量** | 超过 3 张就该审视设计，超过 5 张基本是设计问题 |
| **`ON` 里的字段类型必须一致** | 一边 `int` 一边 `varchar` → 隐式转换 → 索引失效（见 2.9） |

## 2.5 聚合与分组

```sql
SELECT status, COUNT(*) AS cnt, AVG(amount) AS avg_amt
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY status
HAVING cnt > 100
ORDER BY cnt DESC;
```

`WHERE` 和 `HAVING` 的区别：

| | `WHERE` | `HAVING` |
|---|---|---|
| 执行时机 | 分组**前** | 分组**后** |
| 能用聚合函数 | 不能 | 能 |
| 作用对象 | 单行 | 分组结果 |

**能写在 `WHERE` 里的，不要写在 `HAVING` 里**——`WHERE` 先过滤能减少分组的数据量。

### 2.5.1 `COUNT` 的三种写法

```sql
SELECT COUNT(*) FROM users;           -- 数行数，InnoDB 要扫描（选最小的索引扫）
SELECT COUNT(1) FROM users;           -- 和 COUNT(*) 等价
SELECT COUNT(name) FROM users;        -- 只数 name 非 NULL 的行
```

`COUNT(*)` 和 `COUNT(1)` 在 InnoDB 里性能相同。**但 `COUNT(column)` 语义不同**——它跳过 NULL。

### 2.5.2 `ONLY_FULL_GROUP_BY`

```sql
-- 8.0 默认开启 ONLY_FULL_GROUP_BY，这条会报错
SELECT id, name, COUNT(*) FROM orders GROUP BY id;
-- ERROR 1055: name isn't in GROUP BY

-- 正确：所有非聚合列都要出现在 GROUP BY 里
SELECT id, name, COUNT(*) FROM orders GROUP BY id, name;
```

`ONLY_FULL_GROUP_BY` 是 SQL 标准的要求。老代码从 5.7 之前迁移过来时最容易撞这个错，**不要关掉这个 sql_mode，要改 SQL**。

## 2.6 子查询 vs JOIN

```sql
-- 子查询
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);

-- JOIN
SELECT DISTINCT u.* FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.amount > 1000;
```

| | 子查询 | JOIN |
|---|---|---|
| 可读性 | 高（逻辑分层） | 中 |
| 性能 | `IN` 子查询在旧版 MySQL 会物化，可能很慢 | 通常更优 |
| 结果去重 | 自动（`IN`） | 需要 `DISTINCT` |

**判断标准**：能用 `EXPLAIN` 确认子查询走了索引就用子查询，否则改 JOIN。8.0 的优化器已经能把很多 `IN` 子查询改写成 semi-join，性能差异不大了。

`EXISTS` 通常比 `IN` 更适合"判断存在"：

```sql
-- 只关心有没有，不关心有几个
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000);
```

## 2.7 数据类型选型

类型选错不会立刻报错，但会在半年后表现为"磁盘涨得离谱""查询越来越慢"。这是运维该管的事。

### 2.7.1 整数

| 类型 | 字节 | 范围 |
|---|---|---|
| `TINYINT` | 1 | -128 ~ 127 |
| `SMALLINT` | 2 | -32768 ~ 32767 |
| `MEDIUMINT` | 3 | -8388608 ~ 8388607 |
| `INT` | 4 | -21 亿 ~ 21 亿 |
| `BIGINT` | 8 | 约 ±9.2×10¹⁸ |

**选型原则：够用就好，不要一律 `BIGINT`。**

```sql
-- ❌ 状态字段用 BIGINT：一个字段浪费 7 字节，1 亿行就是 700MB
status BIGINT

-- ✅ 状态只有几个值
status TINYINT

-- ❌ 主键用 INT：21 亿会耗尽（日志、订单类表很容易到）
id INT

-- ✅ 主键用 BIGINT UNSIGNED
id BIGINT UNSIGNED AUTO_INCREMENT
```

**主键用 `INT` 是个定时炸弹。** 达到 2147483647 后自增会报错，改类型要锁表几小时。订单、日志、流水类表一律 `BIGINT UNSIGNED`。

### 2.7.2 字符串

| 类型 | 特点 | 用在哪 |
|---|---|---|
| `CHAR(n)` | 定长，不足补空格 | 固定长度：MD5、身份证、国家代码 |
| `VARCHAR(n)` | 变长，额外 1-2 字节存长度 | **绝大多数场景** |
| `TEXT` | 变长，大文本 | 文章内容、JSON 原文 |
| `BLOB` | 二进制 | 图片、文件（**不推荐**，见坑 6） |

`VARCHAR(n)` 的 `n` 是**字符数不是字节数**（utf8mb4 下 1 个中文占 3-4 字节）。

**长度不要一律 `VARCHAR(255)`**：

```sql
-- ❌ 全表都用 255，索引变大，内存临时表更容易溢出
name VARCHAR(255)
email VARCHAR(255)

-- ✅ 按实际
name VARCHAR(50)
email VARCHAR(100)
```

`VARCHAR(255)` 在索引里要占 255×4+2 = 1022 字节，而 `VARCHAR(50)` 只占 202 字节。**联合索引里有大 VARCHAR，索引会非常臃肿。**

### 2.7.3 时间

| 类型 | 字节 | 范围 | 时区 |
|---|---|---|---|
| `DATETIME` | 5（8.0） | 1000-01-01 ~ 9999-12-31 | **不带时区**，存什么读什么 |
| `TIMESTAMP` | 4 | 1970-01-01 ~ 2038-01-19 | **带时区**，存储转 UTC，读取转会话时区 |
| `DATE` | 3 | 日期 | — |
| `BIGINT` | 8 | Unix 时间戳 | 自己管 |

**推荐 `DATETIME`**，理由：

1. `TIMESTAMP` 有 2038 年问题（4 字节 int 溢出），**这是真实的到期日，不是危言耸听**。
2. `TIMESTAMP` 随会话时区变化，同一个值在不同连接里显示不同，排查问题时增加困惑。
3. `DATETIME` 语义明确：存什么就是什么。

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

这两个默认值能省掉大量应用层代码。

### 2.7.4 JSON

```sql
extra JSON
```

能用，但要知道限制：

| 限制 | 说明 |
|---|---|
| 不能直接建索引 | 要对虚拟列建索引（8.0 支持函数索引） |
| 查询有解析开销 | 每次都要解析 JSON 文本 |
| 无法约束结构 | 应用写什么就是什么 |

```sql
-- 8.0 支持直接在 JSON 字段上建函数索引
ALTER TABLE orders ADD INDEX idx_ext_no ((CAST(extra->>'$.order_no' AS CHAR(32))));
```

**适合**：结构不固定的扩展字段、原始报文存档。
**不适合**：需要频繁查询和统计的核心业务字段——那些应该拆成独立列。

### 2.7.5 DECIMAL：钱不能用 FLOAT

```sql
-- ❌ FLOAT/DOUBLE 是二进制浮点，0.1+0.2 != 0.3
amount DOUBLE

-- ✅ DECIMAL 精确
amount DECIMAL(12,2)     -- 最多 12 位，小数 2 位，最大 9999999999.99
```

```sql
SELECT 0.1 + 0.2 = 0.3;              -- 0（false）
SELECT CAST(0.1 AS DECIMAL(10,1)) + CAST(0.2 AS DECIMAL(10,1)) = 0.3;  -- 1
```

**金额、单价、余额一律 `DECIMAL`。** 用 `DOUBLE` 会导致对账差几分钱，而且很难查。

## 2.8 字符集与排序规则

### 2.8.1 必须用 utf8mb4

| 字符集 | 最大字节 | 能存 emoji | 结论 |
|---|---|---|---|
| `utf8`（MySQL 的别名，实际是 utf8mb3） | 3 | **不能** | 废弃 |
| `utf8mb4` | 4 | 能 | **唯一正确选择** |
| `latin1` | 1 | 不能 | 只在历史遗留 |

**MySQL 里的 `utf8` 是 `utf8mb3` 的别名，不是真正的 UTF-8**——它只支持最多 3 字节的字符，存不了 emoji 和部分生僻字。8.0 已经把默认改成 `utf8mb4`，但老库要检查。

```sql
-- 检查库和表的字符集
SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA;

SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_COLLATION
FROM information_schema.TABLES
WHERE TABLE_COLLATION NOT LIKE 'utf8mb4%';
```

改造：

```sql
ALTER DATABASE your_db CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;

ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
```

大表 `CONVERT` 会锁表重建，用 gh-ost。

### 2.8.2 排序规则（collation）怎么选

| 规则 | 特点 |
|---|---|
| `utf8mb4_general_ci` | 快，比较粗糙（不区分大小写） |
| `utf8mb4_unicode_ci` | 按 Unicode 标准，更准，稍慢 |
| `utf8mb4_0900_ai_ci` | **8.0 默认**，基于 Unicode 9.0，最快 |
| `utf8mb4_bin` | 按字节比较，**区分大小写** |

**同一个 JOIN 的两边排序规则不一致会导致索引失效**：

```sql
-- a.name 是 utf8mb4_general_ci，b.name 是 utf8mb4_0900_ai_ci
-- JOIN 时会做隐式转换，索引用不上
SELECT * FROM a JOIN b ON a.name = b.name;
```

所以**同一套表必须统一排序规则**，注意查。

## 2.9 隐式转换

**这是索引失效的第一大原因，也是运维最该会查的问题。**

MySQL 在比较不同类型时会自动转换，转换后就无法用索引：

```sql
-- user_id 是 VARCHAR，但传了数字
SELECT * FROM users WHERE user_id = 12345;
-- 等价于 WHERE CAST(user_id AS SIGNED) = 12345
-- 字段被函数包裹 → 索引失效 → 全表扫描
```

**规则：字符串字段用数字查，索引失效；数字字段用字符串查，索引仍可用。**

```sql
-- ✅ 数字字段用字符串查：字符串被转成数字，字段不变
SELECT * FROM orders WHERE id = '100';   -- 索引有效

-- ❌ 字符串字段用数字查：字段被转成数字
SELECT * FROM users WHERE phone = 13800138000;   -- 索引失效
-- ✅
SELECT * FROM users WHERE phone = '13800138000';
```

四种必须避免的隐式转换：

| 写法 | 问题 |
|---|---|
| `WHERE varchar_col = 123` | 字段被 CAST，索引失效 |
| `WHERE int_col = '123'` | 可以，但要养成加引号的习惯 |
| `WHERE date_col = '2026-10-28'` | 隐性转换，能走索引（推荐 `>= '2026-10-28' AND < '2026-10-29'`） |
| 两个表的关联字段类型不同 | JOIN 无法走索引，性能灾难 |

**排查方法**：`EXPLAIN` 里 `type=ALL` 或 `key=NULL`，且 `rows` 接近表行数，就怀疑隐式转换。看 `SHOW WARNINGS` 能看到改写后的 SQL。

## 2.10 深翻页问题

```sql
-- 第 1 页：快
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 0;

-- 第 5 万页：极慢
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;
```

**为什么慢**：MySQL 要**先读出 100 万零 20 行，再丢掉前 100 万行**。`LIMIT` 不减少扫描量。

三种优化：

```sql
-- 方案一：游标分页（推荐，前提是按索引有序）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
-- 每次都从上一页最后一个 id 之后开始，跳过 OFFSET

-- 方案二：延迟关联（先只查主键，再回表）
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 1000000) t ON o.id = t.id;

-- 方案三：业务限制（超过 N 页不允许翻）
-- 最省事，很多大厂就是这么做的
```

**方案一是唯一真正解决问题的**，方案二只是减少回表次数，扫描量没变。

## 2.11 运维常用 SQL 片段

### 2.11.1 找没有主键的表

```sql
SELECT t.table_schema, t.table_name, t.table_rows
FROM information_schema.TABLES t
LEFT JOIN information_schema.TABLE_CONSTRAINTS c
  ON t.table_schema = c.table_schema
  AND t.table_name = c.table_name
  AND c.constraint_type = 'PRIMARY KEY'
WHERE c.table_name IS NULL
  AND t.table_schema NOT IN ('mysql','sys','information_schema','performance_schema')
  AND t.table_type = 'BASE TABLE';
```

**没有主键的 InnoDB 表是运维隐患**：MySQL 会建一个隐藏的 6 字节 row_id 做聚簇索引，无法用于复制定位，且删除大量数据后空间不回收。

### 2.11.2 找重复索引

```sql
SELECT table_schema, table_name,
       GROUP_CONCAT(DISTINCT index_name) AS idx_names,
       GROUP_CONCAT(column_name ORDER BY seq_in_index) AS cols
FROM information_schema.STATISTICS
WHERE table_schema = 'your_db'
GROUP BY table_schema, table_name, cols
HAVING COUNT(DISTINCT index_name) > 1;
```

`(a)` 和 `(a,b)` 同时存在就是冗余——`(a,b)` 能覆盖 `(a)` 的所有用途，前者可以删。

### 2.11.3 找从未使用过的索引

```sql
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0
  AND object_schema NOT IN ('mysql','sys');
```

**注意**：MySQL 重启后统计清零，要观察足够长的时间（至少一个完整业务周期，比如一周）才能下结论。

### 2.11.4 找大表和大字段

```sql
-- 按大小排序
SELECT table_name,
       ROUND(data_length/1024/1024) AS data_mb,
       ROUND(index_length/1024/1024) AS index_mb,
       table_rows
FROM information_schema.TABLES
WHERE table_schema = 'your_db'
ORDER BY data_length + index_length DESC
LIMIT 20;
```

### 2.11.5 检查表的碎片

```sql
-- 删除大量数据后，.ibd 文件不会自动缩小
SELECT table_name, data_free, ROUND(data_length/1024/1024) AS data_mb
FROM information_schema.TABLES
WHERE table_schema = 'your_db' AND data_free > 100*1024*1024;
```

`data_free` 是碎片空间。回收方式：

```sql
-- 会锁表（大表用 gh-ost）
ALTER TABLE orders ENGINE=InnoDB;
```

## 2.12 八个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | `UPDATE` / `DELETE` 不带 `WHERE` | 改/删全表 | 四步法，先 `SELECT COUNT(*)` |
| 2 | 直接跑大事务 | 锁表、undo 暴涨、主从延迟 | 分批 + 批间 sleep |
| 3 | `VARCHAR` 字段用数字查 | 索引失效，全表扫描 | 加引号 |
| 4 | 金额用 `DOUBLE` | 对账差几分钱 | `DECIMAL(12,2)` |
| 5 | 主键用 `INT` | 21 亿后写入失败 | `BIGINT UNSIGNED` |
| 6 | 图片存 `BLOB` | 单表几百 GB，备份恢复极慢 | 存对象存储，库里只存 URL |
| 7 | 用 `utf8` 当 utf8mb4 | 存 emoji 报错 | 统一 `utf8mb4` |
| 8 | `LEFT JOIN` 的右表条件写在 `WHERE` | 退化成 `INNER JOIN` | 条件写在 `ON` 里 |

第 6 条展开：`BLOB` 存文件会导致表极大、备份慢、`SELECT *` 把几百 MB 数据拉进内存。**正确做法是文件存 S3/MinIO/OSS，库里存 path 或 URL。**
