## 7.1 先分清是哪一种"慢"

**"数据库慢"至少有五种不同的含义**，诊断路径完全不同：

| 现象 | 实际含义 | 主因 |
|---|---|---|
| 所有查询都慢 | 整体性能下降 | 缓冲池不足、磁盘 IO 打满、CPU 饱和 |
| 某些查询慢 | 个别 SQL 问题 | 索引缺失、执行计划选错 |
| 平时快，偶尔卡 | 间歇性阻塞 | 锁等待、大事务、DDL、备份 |
| 写入慢，读取正常 | 写路径问题 | 索引太多、redo 刷盘、binlog 同步 |
| 连接建立慢 | 连接层问题 | DNS 反解、连接数满、网络 |

**第一步永远是分类**。把"所有查询都慢"当成"某条 SQL 慢"去优化索引，会白干。

```sql
-- 快速分类：看整体指标
SHOW GLOBAL STATUS LIKE 'Questions';              -- QPS
SHOW GLOBAL STATUS LIKE 'Threads_running';        -- 并发线程数
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_current_waits';  -- 当前锁等待
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';       -- 物理读
```

## 7.2 诊断顺序

**这个顺序不能跳，跳步是浪费时间的主要原因。**

```
① 系统层：CPU / 内存 / 磁盘 IO / 网络，哪一项饱和？
        ↓ 都没饱和
② 连接层：连接数是否打满？是否有大量 Sleep？
        ↓ 正常
③ 锁：有没有锁等待、长事务？
        ↓ 没有
④ 慢查询：哪几条 SQL 占了大部分耗时？
        ↓ 定位到具体 SQL
⑤ 执行计划：这条 SQL 为什么慢？
        ↓ 定位到具体原因
⑥ 优化：加索引 / 改 SQL / 改表结构 / 改业务逻辑
```

### 7.2.1 第①步：系统层

```bash
# CPU
top -bn1 | head -20
mpstat -P ALL 1 3          # 看每个核，单核 100% 说明有单线程瓶颈

# 内存
free -h
# 关注 available，不是 free。buffer/cache 是可回收的

# 磁盘 IO
iostat -x 1 3
# 关注 %util（>80% 饱和）和 await（>20ms 偏高）

# 网络
sar -n DEV 1 3

# 谁在占 IO
iotop -o
```

**系统层的关键判断**：

| 现象 | 可能原因 |
|---|---|
| CPU 高 + `%util` 低 | 计算密集：全表扫描、排序、函数计算 |
| CPU 低 + `%util` 高 | IO 等待：缓冲池不足、大量随机读 |
| 内存不足 + swap 使用 | 缓冲池配太大，和 OS 抢内存 |
| 单核 100% | MySQL 有单线程瓶颈（如 SQL 线程、某个大查询） |

### 7.2.2 第②步：连接层

```sql
-- 连接数
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';       -- 真正在跑的，> CPU 核数就要注意
SHOW STATUS LIKE 'Max_used_connections';
SHOW VARIABLES LIKE 'max_connections';

-- 连接状态分布
SELECT command, COUNT(*) AS cnt, MAX(time) AS max_idle
FROM information_schema.PROCESSLIST
GROUP BY command
ORDER BY cnt DESC;
```

**判断标准**：

| 指标 | 健康值 |
|---|---|
| `Threads_running` | < CPU 核数 × 2 |
| `Threads_connected` / `max_connections` | < 80% |
| `Sleep` 连接占比 | < 70%，且 `max_idle` < 300 秒 |

`Sleep` 连接很多且空闲时间长 = **连接池配置有问题**，不是数据库的问题。

### 7.2.3 第③步：锁

```sql
-- 当前锁等待
SELECT * FROM sys.innodb_lock_waits\G

-- 长事务
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs,
       trx_rows_locked, trx_state, LEFT(trx_query,100)
FROM information_schema.INNODB_TRX
ORDER BY trx_started
LIMIT 10;

-- 元数据锁等待（DDL 被卡）
SELECT * FROM sys.schema_table_lock_waits\G
```

**有锁等待时，优化索引是没用的**——先把锁解开。

### 7.2.4 第④步：慢查询

```sql
-- 确认慢日志开着
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'slow_query_log_file';
```

```bash
# 按总耗时排序前 10
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 更详细的分析
pt-query-digest /var/log/mysql/slow.log > report.txt
```

## 7.3 慢查询的完整分析流程

定位到一条慢 SQL 后，按这个流程：

```
① EXPLAIN 看 type / key / rows / Extra
② 索引问题？
   ├─ 没索引 → 建索引
   ├─ 有索引但没用 → 查八种失效情况（003 的 3.6）
   └─ 用了但 rows 很大 → 区分度不够，考虑联合索引或改条件
③ 不是索引问题？
   ├─ Using filesort + rows 大 → 排序没走索引
   ├─ Using temporary → GROUP BY 没索引
   ├─ rows 很小但仍慢 → 可能是锁等待或网络传输
   └─ 都正常 → EXPLAIN ANALYZE 看预估 vs 实际
④ 数据量本身大？
   ├─ 是 → 归档、分区、分表、改业务
   └─ 否 → 回到第②步
```

### 7.3.1 一个完整的分析实例

```sql
-- 慢查询日志里的 SQL
SELECT * FROM orders
WHERE shop_id = 100 AND status IN ('paid','shipped')
ORDER BY created_at DESC
LIMIT 20;
-- Query_time: 8.2s  Rows_examined: 12000000
```

**第①步：EXPLAIN**

```
| type | key | rows     | Extra                       |
| ALL  | NULL| 12000000 | Using where; Using filesort |
```

**结论**：全表扫描 + 文件排序，没有可用索引。

**第②步：看现有索引**

```sql
SHOW INDEX FROM orders;
-- 只有 PRIMARY(id) 和 idx_shop(shop_id)
```

**问题**：`idx_shop` 只有 `shop_id`，能过滤掉大部分数据，但还要对结果排序（`created_at`），所以走了 `filesort`。而且 `status IN (...)` 用不上索引。

**第③步：设计索引**

```sql
-- 按"等值在前、范围/排序在后"
ALTER TABLE orders ADD INDEX idx_shop_status_created (shop_id, status, created_at);
```

**第④步：验证**

```sql
EXPLAIN SELECT * FROM orders
WHERE shop_id = 100 AND status IN ('paid','shipped')
ORDER BY created_at DESC LIMIT 20;
```

```
| type | key                      | rows | Extra                    |
| range| idx_shop_status_created  | 820  | Using index condition    |
```

从 `ALL` + 1200 万行 → `range` + 820 行，**耗时从 8.2 秒降到 0.03 秒**。

**注意 `IN` 的细节**：`status IN ('paid','shipped')` 是两个等值，MySQL 8.0 会做"范围扫描"，所以 `created_at` 的排序无法完全利用索引顺序，仍可能有 `filesort`。但 `rows` 只有 820，内存排序无影响。

## 7.4 pt-query-digest 报告怎么读

```bash
pt-query-digest --limit 100% /var/log/mysql/slow.log > report.txt
```

报告分三段：

### 7.4.1 第一段：总体概况

```
# 12.3s user time, 90ms system time, 25.4M rss, 210.2M vsz
# Overall: 1.2M total, 48 unique, 0.00 QPS, 0.00x concurrency
# Time range: 2026-10-20 00:00:00 to 2026-10-27 00:00:00
# Attribute    total     min     max     avg     95%  stddev  median
# ============ ======= ======= ======= ======= ======= ======= =======
# Exec time      3200s    1ms     12s     3ms     8ms    89ms     2ms
# Lock time       120s      0    800ms   100us   200us     3ms    50us
# Rows sent       5.2M       0   10.0k    4.5    20     100      1
# Rows examine    980M       0   12.0M   820    100    50k      10
```

**关键看 `Rows examine` / `Rows sent` 的比值**：

```
820 / 4.5 ≈ 180
```

**扫描了 180 行才返回 1 行**，说明索引效率很差。

| 比值 | 评价 |
|---|---|
| < 10 | 好 |
| 10–100 | 一般，有优化空间 |
| **> 100** | **差，索引设计有问题** |

### 7.4.2 第二段：按总耗时排序的 SQL

```
# Profile
# Rank Query ID           Response time   Calls R/Call  V/M   Item
# ==== ================== =============== ===== ======= ===== ============
#    1 0x1234ABCD...      1200.0000 37.5% 80000 0.0150  0.20 SELECT orders
#    2 0x5678EFGH...       800.0000 25.0%  2000 0.4000  1.50 SELECT users
```

**`Response time` 是总耗时，`R/Call` 是单次平均耗时。**

**优先处理 `Response time` 占比高的**，即使单次不快。第 1 条虽然单次 15ms，但调用了 8 万次，总耗时 1200 秒 —— 这才是大头。

**这就是"总耗时排序"和"单次耗时排序"的区别**。很多人只优化最慢的那一条，忽略了高频的"小慢"。

### 7.4.3 第三段：具体的 SQL 和执行统计

```
# Query 1: 0 QPS, 0x concurrency, ID 0x1234ABCD at byte 12345
# This item is included in the report because it matches --limit.
# Scores: V/M = 0.20
# Time range: 2026-10-20 00:00:00 to 2026-10-27 00:00:00
# Attribute    pct   total     min     max     avg     95%  stddev  median
# ============ === ======= ======= ======= ======= ======= ======= =======
# Count         12   80000
# Exec time     37   1200s     5ms     50ms    15ms    30ms     8ms    12ms
# Rows examine   2   180M       10    5000    2250    1000     800     500
# Rows sent      1   400k        0      20       5      10       3       5
# String:
# Databases    app_db
# Hosts        app-01, app-02
# Users        app
# Query_time distribution
#   1us
#  10us
# 100us
#   1ms  ########
#  10ms  ########################################
# 100ms
#    1s
# SELECT * FROM orders WHERE shop_id = 100 AND status IN (...)
```

**`Query_time distribution` 是直方图**，看耗时是否集中在某个区间。如果出现双峰（一部分 1ms 一部分 1s），说明有锁等待或者缓存命中率不稳定。

## 7.5 SQL 改写七招

### 7.5.1 避免 `SELECT *`

```sql
-- ❌ 拉了 30 个字段，无法用覆盖索引
SELECT * FROM users WHERE id = 100;

-- ✅ 只取需要的，可能走覆盖索引
SELECT id, name, email FROM users WHERE id = 100;
```

### 7.5.2 用 `EXISTS` 代替 `IN`（子查询场景）

```sql
-- ❌ 子查询结果集可能很大
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);

-- ✅ 短路判断，找到就停
SELECT * FROM users u WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000
);
```

### 7.5.3 深翻页改游标

```sql
-- ❌ 扫描 100 万行
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;

-- ✅ 从上一次的最后一个 id 之后开始
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
```

### 7.5.4 `OR` 改 `UNION`

```sql
-- ❌ 一边没索引就全表扫
SELECT * FROM t WHERE a = 1 OR b = 2;

-- ✅ 两边都能走索引
SELECT * FROM t WHERE a = 1
UNION
SELECT * FROM t WHERE b = 2;
```

### 7.5.5 `COUNT(*)` 优化

```sql
-- ❌ 大表精确计数，扫全表
SELECT COUNT(*) FROM orders WHERE status = 'paid';

-- ✅ 如果只是展示"约多少"，用近似值
SELECT TABLE_ROWS FROM information_schema.TABLES
WHERE TABLE_SCHEMA='app_db' AND TABLE_NAME='orders';
-- 误差可能 10-40%

-- ✅ 或者维护计数表，写入时 +1/-1
```

### 7.5.6 批量代替循环

```sql
-- ❌ 1000 次往返
INSERT INTO t (a) VALUES (1);
INSERT INTO t (a) VALUES (2);

-- ✅ 一次
INSERT INTO t (a) VALUES (1),(2),(3);

-- ✅ 大批量分 500-1000 条一批
```

### 7.5.7 用 `JOIN` 替代相关子查询

```sql
-- ❌ 每行执行一次子查询
SELECT u.name, (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS cnt
FROM users u;

-- ✅ 一次 JOIN + 聚合
SELECT u.name, COUNT(o.id) AS cnt
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

## 7.6 参数调优

### 7.6.1 优先级

| 优先级 | 参数 | 收益 |
|---|---|---|
| **1** | `innodb_buffer_pool_size` | 影响最大，占 60% 以上的收益 |
| 2 | `innodb_io_capacity` / `innodb_io_capacity_max` | SSD 上默认值偏保守 |
| 3 | `innodb_flush_log_at_trx_commit` / `sync_binlog` | 性能 vs 安全，见 001 |
| 4 | `innodb_log_file_size` | 大一点减少 checkpoint |
| 5 | 连接相关 | `max_connections`、`wait_timeout` |
| 6 | 临时表 | `tmp_table_size` |

### 7.6.2 缓冲池

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- 在线调整（8.0 支持动态调整，但要时间）
SET GLOBAL innodb_buffer_pool_size = 10737418240;   -- 10G
-- 持久化
SET PERSIST innodb_buffer_pool_size = 10737418240;
```

**判断是否够用**：

```sql
-- 命中率
SELECT
  (1 - (
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Innodb_buffer_pool_reads')
    /
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Innodb_buffer_pool_read_requests')
  )) * 100 AS hit_rate;
-- 应 > 99%
```

**注意**：命中率 99% 也可能不够。看 `Innodb_buffer_pool_wait_free`（等待空闲页的次数）如果 > 0，说明缓冲池在频繁淘汰，还是不够。

### 7.6.3 IO 能力

```sql
SHOW VARIABLES LIKE 'innodb_io_capacity';

-- SSD：可以设 2000-4000（默认 200 是给机械盘的）
SET PERSIST innodb_io_capacity = 2000;
SET PERSIST innodb_io_capacity_max = 4000;
```

设太小会导致脏页刷不出去，checkpoint 跟不上，写入突然卡顿。

### 7.6.4 并发

```sql
SHOW VARIABLES LIKE 'innodb_thread_concurrency';   -- 默认 0（不限制）
SHOW VARIABLES LIKE 'innodb_read_io_threads';      -- 默认 4
SHOW VARIABLES LIKE 'innodb_write_io_threads';     -- 默认 4
```

**`innodb_thread_concurrency` 保持 0**，除非有明确的并发争抢问题。手动限制通常是负优化。

`read/write_io_threads` 在高 IOPS 的 SSD 上可以调到 8-16。

## 7.7 performance_schema 与 sys 库

### 7.7.1 sys 库：最好用的封装

`sys` 库把 `performance_schema` 的复杂表封装成了易读的视图。

```sql
-- 最耗时的 SQL TOP 10
SELECT query, exec_count, total_latency, avg_latency, rows_examined_avg
FROM sys.statement_analysis
ORDER BY total_latency DESC
LIMIT 10;

-- 全表扫描最多的表
SELECT * FROM sys.schema_tables_with_full_table_scans
ORDER BY rows_full_scanned DESC LIMIT 10;

-- 没用到索引的 SQL
SELECT * FROM sys.statements_with_full_table_scans
ORDER BY total_latency DESC LIMIT 10;

-- 用了临时表的 SQL
SELECT * FROM sys.statements_with_temp_tables
ORDER BY total_latency DESC LIMIT 10;

-- 用了文件排序的 SQL
SELECT * FROM sys.statements_with_sorting
ORDER BY total_latency DESC LIMIT 10;

-- 冗余索引
SELECT * FROM sys.schema_redundant_indexes;

-- 未使用的索引
SELECT * FROM sys.schema_unused_indexes;

-- 当前锁等待
SELECT * FROM sys.innodb_lock_waits;

-- 表锁等待
SELECT * FROM sys.schema_table_lock_waits;

-- IO 最多的表
SELECT * FROM sys.io_global_by_file_by_bytes
ORDER BY total DESC LIMIT 10;
```

**`sys` 库是运维最该先熟悉的库**，上面这几条 SQL 能解决 70% 的性能排查。

### 7.7.2 常用 performance_schema 表

| 表 | 用途 |
|---|---|
| `events_statements_summary_by_digest` | 按 SQL 模板聚合的统计（`sys.statement_analysis` 的数据源） |
| `events_waits_summary_global_by_event_name` | 各类等待事件的耗时 |
| `table_io_waits_summary_by_index_usage` | 索引使用统计 |
| `metadata_locks` | 元数据锁 |
| `data_locks` / `data_lock_waits` | InnoDB 行锁 |
| `replication_applier_status` | 复制状态 |

### 7.7.3 等待事件分析

```sql
-- 时间都花在哪了
SELECT event_name, COUNT_STAR, SUM_TIMER_WAIT/1e12 AS total_sec
FROM performance_schema.events_waits_summary_global_by_event_name
WHERE COUNT_STAR > 0
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 15;
```

常见的高占比等待事件：

| 事件 | 含义 | 优化方向 |
|---|---|---|
| `wait/io/file/innodb/innodb_data_file` | 数据文件 IO | 缓冲池不够 / 磁盘慢 |
| `wait/io/redo_log_flush` | redo 刷盘 | 磁盘慢 / `flush_log_at_trx_commit=1` |
| `wait/io/sync/atomic` | 原子操作 | 高并发 |
| `wait/lock/table/sql/handler` | 表锁 | 有表锁操作 |
| `wait/lock/metadata/sql/mdl` | MDL | 有 DDL 在等 |

## 7.8 监控指标体系

### 7.8.1 必须监控的十二项

| 类别 | 指标 | 告警阈值 |
|---|---|---|
| **可用性** | 端口存活、`SELECT 1` 成功 | 失败即告警 |
| **连接** | `Threads_connected` / `max_connections` | > 80% |
| **并发** | `Threads_running` | > CPU 核数 × 2 |
| **QPS** | `Questions` 增量 | 突降 50%（可能是故障） |
| **TPS** | `Com_commit + Com_rollback` 增量 | — |
| **慢查询** | `Slow_queries` 增量 | 突然翻倍 |
| **锁** | `Innodb_row_lock_current_waits` | > 0 持续 10 秒 |
| **锁等待时长** | `Innodb_row_lock_time_avg` | > 100ms |
| **缓冲池** | 命中率 | < 99% |
| **复制** | `Replica_*_Running`、延迟 | 任一异常 |
| **磁盘** | datadir 使用率 | > 80% |
| **磁盘 IO** | `%util`、`await` | `%util` > 80% |

### 7.8.2 Prometheus 采集

用 `mysqld_exporter`：

```yaml
# mysqld_exporter 配置
# ~/.my.cnf
[client]
user=exporter
password=xxx
```

```sql
CREATE USER 'exporter'@'localhost' IDENTIFIED BY 'xxx';
GRANT PROCESS, REPLICATION CLIENT, SELECT ON *.* TO 'exporter'@'localhost';
```

关键告警规则示例：

```yaml
- alert: MySQLDown
  expr: mysql_up == 0
  for: 1m

- alert: MySQLTooManyConnections
  expr: mysql_global_status_threads_connected / mysql_global_variables_max_connections > 0.8
  for: 5m

- alert: MySQLSlowQueries
  expr: rate(mysql_global_status_slow_queries[5m]) > 10
  for: 5m

- alert: MySQLReplicationLag
  expr: mysql_slave_status_seconds_behind_master > 10
  for: 2m

- alert: MySQLBufferPoolHitRateLow
  expr: |
    (1 - rate(mysql_global_status_innodb_buffer_pool_reads[5m])
       / rate(mysql_global_status_innodb_buffer_pool_read_requests[5m])) < 0.99
  for: 10m
```

## 7.9 三个优化实战

### 7.9.1 案例一：QPS 突然腰斩

**现象**：QPS 从 5000 掉到 2000，应用超时增多，CPU 和 IO 都不高。

**排查**：

```sql
-- 看锁等待
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_current_waits';
-- 结果是 47，有 47 个在等锁

-- 找到源头
SELECT * FROM sys.innodb_lock_waits\G
```

**根因**：有一个跑了 40 分钟的 `UPDATE`（`WHERE` 条件列没索引，锁了全表），所有写操作排队。

**处理**：

```sql
KILL 12345;
-- 补索引
ALTER TABLE orders ADD INDEX idx_status (status);
```

**教训**：**CPU 和 IO 都不高但 QPS 掉了，第一反应查锁。**

### 7.9.2 案例二：每天 10 点准时卡

**现象**：每天上午 10 点，数据库响应变慢 3-5 分钟，其他时间正常。

**排查**：

```sql
-- 看慢查询日志的时间分布
grep "Query_time" /var/log/mysql/slow.log | awk '{print $NF}' | cut -c1-13 | sort | uniq -c
```

**根因**：10 点有个定时报表任务，跑了 6 条无索引的 `GROUP BY` 大查询。

**处理**：

1. 报表任务挪到从库
2. 给报表涉及的字段加索引
3. 报表改到低峰执行

**教训**：**"准时"出现的性能问题，一定是定时任务。**

### 7.9.3 案例三：写入越来越慢

**现象**：上线 3 个月，写入 TPS 从 3000 降到 800，读正常。

**排查**：

```sql
-- 看表数量
SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA='app_db';
-- 从 120 涨到 180（分表）

-- 看某个慢 INSERT 的执行计划
EXPLAIN INSERT INTO orders (...) VALUES (...);
```

**根因**：单表索引从 3 个涨到 9 个（业务不断加），每次插入要维护 9 个索引。而且有 3 个冗余索引。

**处理**：

```sql
-- 找出冗余索引
SELECT * FROM sys.schema_redundant_indexes;
-- 删掉 3 个冗余 + 2 个从未使用的
```

写入 TPS 恢复到 2200。

**教训**：**索引是双刃剑，每次加索引都要评估写入代价。定期清理冗余索引。**

## 7.10 十个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 一上来就调参数 | 没解决根因，加了不稳定性 | 先看慢查询和索引 |
| 2 | 只优化最慢的一条 SQL | 忽略了高频"小慢" | 按总耗时排序 |
| 3 | CPU 不高就认为没问题 | 漏掉锁等待 | 查 `Innodb_row_lock_current_waits` |
| 4 | 缓冲池设成物理内存 90% | 和 OS 抢内存，OOM | 50–70% |
| 5 | 建了一堆索引 | 写入越来越慢 | 控制数量，定期清理 |
| 6 | 在从库跑报表 | 主从延迟飙升 | 报表走独立实例 |
| 7 | 忽略 `Rows_examined / Rows_sent` | 索引效率长期低下 | 比值 > 100 就要优化 |
| 8 | `EXPLAIN` 看 `key` 有值就放心 | `type=index` 是全索引扫描 | 看 `type` 和 `rows` |
| 9 | 用 `SHOW TABLE STATUS` 做容量规划 | 行数是估算，误差大 | 按 `data_length` 算大小 |
| 10 | 优化后不验证 | 以为改好了，实际没生效 | 前后对比 `EXPLAIN` 和耗时 |
