## 9.1 为什么必须懂三类

| 类型 | 代表 | 占运维工作量 | 你必须会 |
|---|---|---|---|
| **关系型** | MySQL / PostgreSQL | 70% | 备份恢复、变更安全、慢查询 |
| **缓存** | Redis | 25% | 内存管理、持久化、大 key |
| **文档型** | MongoDB | 5% | 基本操作、副本集 |

**MySQL 的知识有 60% 可以迁移到 PG**（索引、执行计划、事务、备份思路），但**命令和默认行为差异很大**，照着 MySQL 的习惯操作 PG 会出事故。

**Redis 是完全不同的东西**——它不是"小 MySQL"，用关系型思维用 Redis 是故障的主要来源。

## 9.2 PostgreSQL：和 MySQL 的十二个差异

### 9.2.1 结构差异

| 项 | MySQL | PostgreSQL |
|---|---|---|
| **数据库/模式** | database 直接包含表 | **database → schema → table** 三层 |
| 默认 schema | 无 | `public` |
| 跨库查询 | `db1.t1 JOIN db2.t2` | **不支持**，必须用 `postgres_fdw` 或应用层拼 |
| 表空间 | 有 | 有（用法不同） |
| 大小写 | 表名大小写取决于文件系统 | **未加引号的标识符自动转小写** |

**"三层结构"是最容易踩的点**：

```sql
-- MySQL：db1 和 db2 可以直接 JOIN
SELECT * FROM db1.users u JOIN db2.orders o ON u.id = o.user_id;

-- PostgreSQL：不行，跨 database 无法 JOIN
-- 要么放同一个 database 的不同 schema
SELECT * FROM app.users u JOIN app.orders o ON u.id = o.user_id;
-- 要么用 fdw
```

**大小写**：`CREATE TABLE Users` 实际建的是 `users`；要用大写必须加双引号 `CREATE TABLE "Users"`，之后每次查询都要加引号。**永远不要用大写表名。**

### 9.2.2 命令差异

| 目的 | MySQL | PostgreSQL |
|---|---|---|
| 列出数据库 | `SHOW DATABASES` | `\l` 或 `SELECT datname FROM pg_database` |
| 列出表 | `SHOW TABLES` | `\dt` |
| 表结构 | `DESC t` / `SHOW CREATE TABLE t` | `\d t` |
| 索引 | `SHOW INDEX FROM t` | `\di` / `SELECT * FROM pg_indexes WHERE tablename='t'` |
| 当前库 | `SELECT DATABASE()` | `SELECT current_database()` |
| 当前用户 | `SELECT CURRENT_USER()` | `SELECT current_user` |
| 进程列表 | `SHOW PROCESSLIST` | `SELECT * FROM pg_stat_activity` |
| 杀连接 | `KILL id` | `SELECT pg_terminate_backend(pid)` |
| 执行计划 | `EXPLAIN` | `EXPLAIN` / **`EXPLAIN (ANALYZE, BUFFERS)`** |
| 版本 | `SELECT VERSION()` | `SELECT version()` |
| 表大小 | `information_schema.TABLES` | `pg_total_relation_size('t')` |

**`EXPLAIN (ANALYZE, BUFFERS)` 是 PG 的杀手级功能**：

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 100;
```

它给出**实际耗时 + 缓存命中情况**，比 MySQL 的 `EXPLAIN ANALYZE` 信息更全：

```
Index Scan using idx_user on orders  (cost=0.43..8.45 rows=1 width=64) (actual time=0.015..0.017 rows=3 loops=1)
  Index Cond: (user_id = 100)
  Buffers: shared hit=5
Planning Time: 0.085 ms
Execution Time: 0.032 ms
```

`Buffers: shared hit=5` 表示 5 个页全部命中缓存。如果出现 `read=` 说明读了磁盘。

### 9.2.3 自增主键

```sql
-- MySQL
id BIGINT AUTO_INCREMENT PRIMARY KEY

-- PostgreSQL 三种写法
-- ① SERIAL（老写法，仍支持）
id SERIAL PRIMARY KEY

-- ② IDENTITY（SQL 标准，推荐）
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- ③ 显式序列
CREATE SEQUENCE orders_id_seq;
id BIGINT DEFAULT nextval('orders_id_seq') PRIMARY KEY
```

**推荐 `GENERATED ALWAYS AS IDENTITY`**，`SERIAL` 已被官方标记为不推荐。

**坑**：`INSERT` 时手动指定了 id，序列不会自动前进，之后自增会冲突。修复：

```sql
SELECT setval('orders_id_seq', (SELECT MAX(id) FROM orders));
```

### 9.2.4 事务与隔离级别

| 项 | MySQL | PostgreSQL |
|---|---|---|
| 默认隔离级别 | **REPEATABLE READ** | **READ COMMITTED** |
| 实现方式 | 锁 + MVCC（undo log） | 纯 MVCC（行版本） |
| 幻读 | RR 下靠间隙锁避免 | RC 下允许；RR 下靠 SSI 检测 |
| DDL 是否可回滚 | **不能** | **能**（事务性 DDL） |

**PG 支持事务性 DDL**，这是巨大优势：

```sql
BEGIN;
ALTER TABLE orders ADD COLUMN note TEXT;
-- 发现搞错了
ROLLBACK;
-- 字段真的没了，表没被破坏
```

MySQL 里 `ALTER TABLE` 会隐式提交，回滚不了。

### 9.2.5 VACUUM：PG 独有的必需操作

**这是从 MySQL 转 PG 最容易出事故的地方。**

MySQL 的 `UPDATE` 是"原地更新 + undo log 存旧版本"，PG 的 `UPDATE` 是**插入新版本，旧版本留在表里**。

```
UPDATE users SET name='新名' WHERE id=1;
→ 表里现在有两行：
   [id=1, name=旧名, xmin=100, xmax=105]  ← 死元组
   [id=1, name=新名, xmin=105]            ← 活元组
```

**死元组（dead tuple）要靠 `VACUUM` 回收**：

```sql
-- 手动
VACUUM orders;              -- 标记空间可复用，不锁表
VACUUM FULL orders;         -- 真正归还磁盘，但会锁表（等于重建）

-- 看死元组数量
SELECT relname, n_live_tup, n_dead_tup,
       ROUND(n_dead_tup*100.0/NULLIF(n_live_tup+n_dead_tup,0), 2) AS dead_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

**autovacuum 默认是开的，但经常跟不上**：

| 问题 | 表现 |
|---|---|
| 大表更新频繁 | 死元组堆积，表膨胀 |
| 长事务阻塞 | autovacuum 无法清理比最老事务更旧的版本 |
| 参数太保守 | 大表要很久才触发一次 |

```sql
-- 调整 autovacuum 对大表更激进
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.05);
ALTER TABLE orders SET (autovacuum_vacuum_threshold = 1000);
```

**表膨胀的后果**：磁盘占用远大于实际数据、全表扫描变慢、索引变大。

```sql
-- 看膨胀
SELECT schemaname, tablename,
       pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size
FROM pg_tables
WHERE schemaname='public'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 10;
```

**需要 `VACUUM FULL` 时用 `pg_repack` 替代**（在线重建，不长时间锁表）。

### 9.2.6 连接模型：进程不是线程

| | MySQL | PostgreSQL |
|---|---|---|
| 每个连接 | 一个线程 | **一个操作系统进程** |
| 单连接内存 | 约 256KB–1MB | 约 5–10MB |
| 连接数上限 | 几千 | **几百**（进程开销大） |

**PG 的连接数比 MySQL 敏感得多**。500 个连接可能吃掉 5GB 内存。

**必须用连接池**：

| 方案 | 说明 |
|---|---|
| `pgbouncer` | 最常用，支持 transaction 模式（连接复用率高） |
| `pgpool-II` | 功能更多（读写分离、负载均衡），但更复杂 |
| 应用侧连接池 | 基础，但多实例时会翻倍 |

```
连接数规划：
数据库 max_connections = 200
pgbouncer 到数据库的连接 = 50
应用 → pgbouncer 的连接 = 2000
```

### 9.2.7 其他五个差异

| 项 | MySQL | PostgreSQL |
|---|---|---|
| **大小写敏感** | 取决于配置 | 字符串比较**区分大小写**（除非用 `ILIKE`） |
| `LIKE` | 区分大小写取决于 collation | **区分**，忽略大小写用 `ILIKE` |
| 分页 | `LIMIT n OFFSET m` | 同，但推荐 `LIMIT n OFFSET m` 或 `FETCH FIRST n ROWS` |
| 空字符串 | `''` 和 `NULL` 不同 | 同，但**`''` 不能转成数字** |
| 布尔类型 | `TINYINT(1)` | **原生 `BOOLEAN`** |
| JSON | `JSON`（文本） | **`JSONB`（二进制，可索引）** |

**`JSONB` 是 PG 的强项**：

```sql
CREATE TABLE events (id BIGSERIAL, data JSONB);
CREATE INDEX idx_data_gin ON events USING GIN (data);
SELECT * FROM events WHERE data @> '{"type":"login"}';
```

比 MySQL 的 JSON 查询强很多。

## 9.3 PostgreSQL 运维要点

### 9.3.1 备份

```bash
# 逻辑备份（等于 mysqldump）
pg_dump -Fc -h localhost -U postgres app_db > app_db.dump
# -Fc = 自定义格式，压缩且支持并行恢复

# 恢复
pg_restore -d app_db -j 4 app_db.dump

# 全库
pg_dumpall > all.sql

# 物理备份：pg_basebackup
pg_basebackup -D /backup/base -Ft -z -P -h localhost -U replicator
```

**`-Fc` + `pg_restore -j` 支持并行，大库比纯 SQL 快很多。**

### 9.3.2 复制

PG 的复制和 MySQL 完全不同：

| | MySQL | PostgreSQL |
|---|---|---|
| 方式 | 逻辑（binlog） | **物理（WAL 流复制）** |
| 从库 | 可写（不建议） | **只读，无法写入** |
| 延迟判断 | `Seconds_Behind_Source` | `pg_stat_replication` 的 `replay_lag` |

```sql
-- 主库看从库状态
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn,
       replay_lag
FROM pg_stat_replication;
```

**PG 的从库是"块级复制"**，所以主从数据必然一致（不会有 MySQL 那种重放报错）。代价是从库完全只读，不能做任何写入。

### 9.3.3 常用巡检

```sql
-- 当前活动
SELECT pid, usename, datname, state, query_start,
       NOW() - query_start AS duration, LEFT(query, 100)
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC;

-- 长事务（阻塞 vacuum）
SELECT pid, now() - xact_start AS duration, state, LEFT(query,100)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 10;

-- 锁等待
SELECT * FROM pg_locks WHERE NOT granted;

-- 阻塞关系
SELECT
  blocked.pid AS blocked_pid,
  blocked.query AS blocked_query,
  blocking.pid AS blocking_pid,
  blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- 表大小
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;

-- 索引使用率（找没用的索引）
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

### 9.3.4 PG 的三个高频故障

| 故障 | 原因 | 处理 |
|---|---|---|
| **表膨胀** | autovacuum 跟不上 | 调参数 + `pg_repack` |
| **事务 ID 回卷** | 事务 ID 是 32 位，约 21 亿后回卷 | **必须监控 `age(datfrozenxid)`** |
| **连接数耗尽** | 进程模型开销大 | 上 pgbouncer |

**事务 ID 回卷是新运维最容易忽略的致命问题**：

```sql
-- 监控这个值，超过 15 亿就危险
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

**超过 20 亿数据库会强制停机**，需要停机做 `VACUUM FULL`（可能几小时）。必须提前监控告警。

## 9.4 Redis：运维视角

### 9.4.1 它不是"小 MySQL"

| 维度 | MySQL | Redis |
|---|---|---|
| 数据位置 | 磁盘为主，内存做缓存 | **内存为主，磁盘做持久化** |
| 数据安全 | 提交即持久 | **可能丢数据**（取决于持久化配置） |
| 查询能力 | SQL，任意条件 | **只有 key 查找**，没有条件查询 |
| 容量 | TB 级 | **受内存限制**，通常几十 GB |
| 成本 | 低 | **高**（内存贵） |

**用 Redis 的第一原则：它随时可能丢数据或清空，不能作为唯一数据源。**

### 9.4.2 持久化：RDB vs AOF

| | RDB | AOF |
|---|---|---|
| 原理 | 定时快照（fork 子进程写文件） | 记录每条写命令 |
| 数据安全 | 丢最后一次快照后的所有数据 | 取决于 `appendfsync` |
| 文件大小 | 小（压缩的二进制） | 大 |
| 恢复速度 | 快 | 慢（要重放命令） |
| 对性能影响 | fork 时短暂卡顿 | 持续写盘 |

**生产推荐：RDB + AOF 同时开**。

```conf
# RDB
save 900 1          # 900 秒内至少 1 次修改就快照
save 300 10
save 60 10000
dbfilename dump.rdb
dir /data/redis

# AOF
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec         # 每秒刷盘，最多丢 1 秒
# appendfsync always         # 每条都刷，性能差 10 倍
# appendfsync no             # 交给 OS，可能丢 30 秒

# AOF 重写（防止文件无限增长）
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

**`appendfsync everysec` 是绝大多数场景的正确选择**：最多丢 1 秒数据，性能损失可接受。

### 9.4.3 内存管理与淘汰

```conf
maxmemory 8gb
maxmemory-policy allkeys-lru
```

**六种淘汰策略**：

| 策略 | 行为 | 适用 |
|---|---|---|
| `noeviction` | **不淘汰，写入报错** | 不能丢数据的场景（此时要监控内存） |
| `allkeys-lru` | 所有 key 里淘汰最久未用的 | **纯缓存，最常用** |
| `allkeys-lfu` | 淘汰访问频率最低的 | 有明显热点 |
| `allkeys-random` | 随机淘汰 | 少用 |
| `volatile-lru` | 只淘汰设了过期时间的 | 混合用途（缓存 + 持久数据） |
| `volatile-ttl` | 淘汰快过期的 | 少用 |

**最危险的配置是 `noeviction` + 内存满**：所有写命令报 `OOM command not allowed`，业务直接失败。

```bash
# 看内存使用
redis-cli INFO memory
# used_memory_human: 7.2G
# maxmemory_human: 8.0G
# mem_fragmentation_ratio: 1.35   ← 碎片率，> 1.5 要关注
```

`mem_fragmentation_ratio` 大于 1.5 说明内存碎片严重，可以开启 `activedefrag yes`。

### 9.4.4 大 key：Redis 的头号杀手

**大 key 的定义**：

| 类型 | 阈值 |
|---|---|
| String | > 10 KB |
| Hash / List / Set / ZSet | 元素 > 5000，或总大小 > 1 MB |

**大 key 的四个危害**：

| 危害 | 说明 |
|---|---|
| **阻塞主线程** | Redis 单线程，操作大 key 时所有请求排队 |
| **删除卡顿** | `DEL` 一个百万元素的 Hash 会卡几百毫秒，要用 `UNLINK` |
| **网络拥塞** | 一次拉取几十 MB |
| **内存不均** | 集群模式下导致数据倾斜 |

**排查**：

```bash
# 扫大 key（--bigkeys 会全库扫描，生产慎用，建议从从库扫）
redis-cli --bigkeys -i 0.1

# 更精确：用 MEMORY USAGE
redis-cli MEMORY USAGE mykey

# 离线分析 RDB（最安全）
rdb -c memory dump.rdb --bytes 10240 -f bigkeys.csv
```

**处理**：

```bash
# ❌ DEL 大 key 会阻塞
DEL bighash

# ✅ UNLINK 异步删除
UNLINK bighash

# ✅ 分片：把一个大 hash 拆成 key:1, key:2, ...
```

### 9.4.5 热 key

**热 key**：某个 key 的 QPS 极高（比如秒杀的商品信息），打满单个 Redis 节点的 CPU。

```bash
# 用 redis-cli --hotkeys（需要 maxmemory-policy 是 lfu）
redis-cli --hotkeys
```

**处理**：

| 方案 | 说明 |
|---|---|
| 本地缓存 | 应用内存缓存一份，减少 Redis 访问 |
| key 打散 | `hotkey:1`、`hotkey:2`… 分散到不同节点 |
| 读写分离 | 从库分担读 |

### 9.4.6 集群模式

| 模式 | 特点 |
|---|---|
| **主从** | 一主多从，手动切换，读扩展 |
| **哨兵（Sentinel）** | 主从 + 自动故障切换 |
| **Cluster** | 分片，16384 个槽，自动分片和切换 |

**Cluster 的三个限制**：

| 限制 | 说明 |
|---|---|
| 不支持跨槽多 key 操作 | `MGET k1 k2` 要求 k1、k2 在同一槽 |
| 不支持跨槽事务 | `MULTI` 里的 key 必须同槽 |
| 不支持 `SELECT` 切库 | 只有 db0 |

**用 `{tag}` 强制同槽**：

```bash
SET {user100}:name "张三"
SET {user100}:age 20
# 大括号里的内容决定槽位，两个 key 会落在同一节点
```

## 9.5 Redis 五大故障场景

### 9.5.1 内存满，写入失败

```
OOM command not allowed when used memory > 'maxmemory'
```

**处理**：

```bash
# ① 临时调大（如果能）
redis-cli CONFIG SET maxmemory 12gb

# ② 清理无用 key
redis-cli --scan --pattern "tmp:*" | head -1000 | xargs redis-cli UNLINK

# ③ 检查是否有 key 没设过期时间
redis-cli INFO keyspace
# db0:keys=1000000,expires=100,avg_ttl=0
#                              ↑ 只有 100 个设了过期，其余永久
```

**根因通常是"缓存 key 没设 TTL"**，这在代码里非常常见。

### 9.5.2 主从延迟大

```bash
redis-cli INFO replication
# master_repl_offset: 1234567890
# slave_repl_offset:  1200000000     ← 差 3400 万字节
```

**原因**：

| 原因 | 处理 |
|---|---|
| 主库写入太快 | 业务限流 |
| 从库配置低 | 升级从库 |
| 网络带宽不足 | 检查网络 |
| 大 key 同步 | 拆分大 key |
| 从库执行了慢命令（`KEYS`） | 禁止生产用 `KEYS` |

### 9.5.3 主从切换丢数据

**异步复制下，主库刚写入还没同步就挂了，切换后这部分数据丢失。**

这是 Redis 的固有问题。缓解手段：

```conf
# 主库至少有 N 个从库确认才返回
min-replicas-to-write 1
min-replicas-max-lag 10
```

**代价**：从库全挂时主库变成只读，影响可用性。要权衡。

### 9.5.4 慢命令阻塞

```bash
# 查慢日志
redis-cli SLOWLOG GET 10
```

**必须禁止的命令**：

| 命令 | 危险原因 |
|---|---|
| `KEYS *` | 全库扫描，百万 key 卡几十秒 |
| `FLUSHALL` / `FLUSHDB` | 清库 |
| `HGETALL` 大 hash | 一次拉几百 MB |
| `SMEMBERS` 大 set | 同上 |
| `DEL` 大 key | 同步删除阻塞 |

**替代方案**：

```bash
# ❌ KEYS *
# ✅ SCAN 游标遍历
redis-cli --scan --pattern "user:*" --count 100

# ❌ HGETALL bighash
# ✅ HSCAN 分批
redis-cli HSCAN bighash 0 COUNT 100
```

### 9.5.5 缓存击穿 / 雪崩

| 问题 | 定义 | 后果 |
|---|---|---|
| **缓存穿透** | 查不存在的数据，请求直达 DB | DB 被打挂 |
| **缓存击穿** | 某个热点 key 过期，大量请求同时回源 | DB 瞬间压力 |
| **缓存雪崩** | 大量 key 同时过期 | DB 崩溃 |

**三种解法**：

| 问题 | 解法 |
|---|---|
| 穿透 | 缓存空值（短 TTL）+ 布隆过滤器 |
| 击穿 | **互斥锁**（只放一个请求回源）+ 热点 key 永不过期 |
| 雪崩 | **过期时间加随机值**（`TTL + rand(0, 300)`） |

```go
// 击穿的互斥锁写法（Go）
func Get(key string) (string, error) {
    if v, err := redis.Get(key); err == nil {
        return v, nil
    }
    // 只有拿到锁的请求才回源
    if ok := redis.SetNX("lock:"+key, "1", 10*time.Second); ok {
        defer redis.Del("lock:" + key)
        v := loadFromDB(key)
        redis.Set(key, v, 5*time.Minute+randDuration())
        return v, nil
    }
    // 没拿到锁，短暂等待后重试
    time.Sleep(50 * time.Millisecond)
    return Get(key)
}
```

## 9.6 MongoDB 简述

运维遇到 MongoDB 时，只需要知道四件事：

| 项 | 要点 |
|---|---|
| **副本集** | 一主两从（PSA），主节点挂自动选举，需要奇数个投票成员 |
| **分片** | `mongos` + `config` + `shard`，按分片键分布数据 |
| **备份** | `mongodump` / `mongorestore`（逻辑），或文件系统快照 |
| **连接** | 默认 27017，无认证是重大风险（历史上多起勒索事件） |

**必须检查的两项**：

```javascript
// ① 是否开了认证
db.adminCommand({getCmdLineOpts: 1})
// 看 security.authorization 是否为 enabled

// ② 是否只监听内网
db.adminCommand({getCmdLineOpts: 1}).parsed.net.bindIp
// 必须是内网 IP 或 127.0.0.1，绝不能是 0.0.0.0
```

**MongoDB 未授权访问是安全事件的高发点**，公网暴露 + 无认证 = 数据被删要赎金。

## 9.7 选型对照表

| 需求 | 首选 | 备选 |
|---|---|---|
| 事务型业务（订单、支付） | MySQL / PostgreSQL | — |
| 复杂查询、分析、JSON | **PostgreSQL** | — |
| 高并发缓存 | **Redis** | Memcached |
| 会话存储 | Redis | — |
| 排行榜 / 计数器 | Redis（ZSet / INCR） | — |
| 分布式锁 | Redis（RedLock 慎用） | etcd / ZooKeeper |
| 消息队列（轻量） | Redis Stream | Kafka / RabbitMQ |
| 文档型数据 | MongoDB | PostgreSQL JSONB |
| 时序数据（监控指标） | Prometheus / InfluxDB | TimescaleDB |
| 全文搜索 | Elasticsearch | PostgreSQL 全文索引 |
| 图数据 | Neo4j | — |
| 超大规模 KV | Cassandra / HBase | — |

**给运维的判断原则**：

```
有事务需求 → 关系型（MySQL / PG）
纯缓存 → Redis
需要复杂查询和 JSON → PG
不确定 → 先用 MySQL，撑不住再换
```

**不要为了"技术先进"选型**。运维成本是选型里最贵的部分。

## 9.8 八个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 拿 MySQL 习惯操作 PG | 跨库 JOIN 报错、大小写混乱 | 记住 schema 三层 + 标识符转小写 |
| 2 | PG 不监控 `age(datfrozenxid)` | **事务 ID 回卷，数据库强制停机** | 监控 < 15 亿，及时 VACUUM |
| 3 | PG 不关心 autovacuum | 表膨胀，磁盘翻倍 | 大表调 `scale_factor` |
| 4 | Redis 当唯一数据源 | 重启/淘汰/故障丢数据 | 只做缓存，或接受可丢 |
| 5 | Redis 缓存 key 不设 TTL | 内存涨满，写入失败 | 所有缓存 key 必须有 TTL |
| 6 | 生产用 `KEYS *` | 阻塞主线程几十秒 | 用 `SCAN` |
| 7 | `DEL` 大 key | 卡顿几百毫秒 | 用 `UNLINK` |
| 8 | MongoDB 公网暴露无认证 | 数据被删、被勒索 | 只监听内网 + 开认证 |

第 2 条是 PG 最容易被忽略的致命问题：**它不是"性能问题"，是"数据库会停机"**。从 MySQL 转过来的运维几乎都不知道这件事。
