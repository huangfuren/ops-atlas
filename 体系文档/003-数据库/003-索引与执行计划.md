## 3.1 索引是什么：B+ 树

**一句话：索引是把"逐行扫描"变成"按树查找"的数据结构。**

没有索引时，查 `WHERE id = 1000000` 要读 100 万行；有索引时，B+ 树 3-4 层就能定位，只读 3-4 个页。

### 3.1.1 为什么是 B+ 树

| 数据结构 | 问题 |
|---|---|
| 数组 | 插入删除 O(n) |
| 链表 | 查找 O(n) |
| 哈希 | 只能等值查询，**不支持范围查询**（`WHERE id > 100` 用不了） |
| 二叉树 | 树太高，磁盘 IO 次数多 |
| **B+ 树** | 矮胖、有序、支持范围查询和排序 |

**B+ 树的两个关键特征**：

1. **只有叶子节点存数据，非叶子节点只存键**。这样一个 16KB 的页能存上千个键，3 层就能支撑上千万行。
2. **叶子节点用链表相连**。这让范围查询（`BETWEEN`、`>`）和 `ORDER BY` 可以顺序扫描，不用回树里跳。

```
                 [ 50 | 100 ]                  ← 根节点（只存键）
                /      |      \
        [20|35]    [60|80]    [120|150]        ← 中间节点
        /  |  \    /  |  \     /   |   \
      叶子 → 叶子 → 叶子 → 叶子 → ...          ← 叶子存数据 + 双向链表
```

**为什么树高是 3-4 层**：每个页 16KB，主键 BIGINT 占 8 字节 + 指针 6 字节 = 14 字节，一页能存约 1170 个键。三层能存 1170³ ≈ **16 亿行**。

所以**查任何一行最多 3 次磁盘 IO**（通常第一二层还在缓冲池里，实际只有 1 次）。这是 InnoDB 的核心竞争力。

## 3.2 聚簇索引与回表

### 3.2.1 聚簇索引

**InnoDB 的表就是一棵以主键为键的 B+ 树，叶子节点直接存整行数据。** 这叫聚簇索引（clustered index）。

```
主键索引的叶子节点：
[ id=100 | name=张三 | email=a@b.com | created_at=2026-01-01 | ... ]
    ↑ 整行数据都在这
```

**推论：**

| 事实 | 原因 |
|---|---|
| 一张表只能有一个聚簇索引 | 数据只能按一种顺序存 |
| 主键必须短 | 所有二级索引的叶子都要存主键值 |
| 主键最好自增 | 随机主键（如 UUID）会导致页分裂，插入性能暴跌 |
| 没主键时用第一个非空唯一索引 | 都没有则建 6 字节隐藏 `row_id` |

**为什么主键要用自增 `BIGINT`**：

```sql
-- ❌ UUID 主键：每次插入的位置随机，会导致频繁页分裂和随机 IO
id VARCHAR(36) PRIMARY KEY

-- ✅ 自增 BIGINT：每次插到最后一页，顺序写
id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
```

用 UUID 做主键的表，插入性能通常只有自增主键的 **1/5 到 1/10**，而且索引体积大 3 倍。

### 3.2.2 二级索引与回表

**二级索引（普通索引）的叶子节点只存"索引列 + 主键值"，不存整行。**

```sql
CREATE INDEX idx_name ON users(name);
```

```
二级索引 idx_name 的叶子：
[ name=张三 | id=100 ]
[ name=李四 | id=205 ]
      ↑ 只有索引列和主键，没有 email 等其他字段
```

查 `SELECT * FROM users WHERE name='张三'` 的过程：

```
1. 在 idx_name 上找到 name='张三' → 得到 id=100
2. 拿 id=100 去聚簇索引再查一次 → 拿到整行
   ↑ 这一步叫"回表"
```

**回表的代价**：每匹配一行就多一次聚簇索引查找。如果 `name='张'` 匹配了 1 万行，就要回表 1 万次。

**优化器会判断**：如果预估要回表太多行（比如超过全表的 20-30%），它会**放弃索引直接全表扫描**——因为顺序扫描比随机回表快。这就是"索引明明有却不用"的常见原因之一。

```sql
-- 比如 users 有 100 万行，其中 status='active' 有 90 万行
SELECT * FROM users WHERE status = 'active';
-- 优化器算了一下：走索引要回表 90 万次，不如全表扫 → 弃用索引
```

**这不是 bug，是正确决策。** 但如果你确实需要频繁查这类条件，说明索引选错了列——应该选区分度高的列。

### 3.2.3 区分度

```sql
-- 区分度 = 不重复值数 / 总行数，越接近 1 越好
SELECT
  COUNT(DISTINCT status) / COUNT(*) AS status_cardinality,
  COUNT(DISTINCT user_id) / COUNT(*) AS user_cardinality
FROM orders;
-- status_cardinality: 0.000005   ← 极低，不适合单独建索引
-- user_cardinality:   0.85       ← 高，适合
```

**区分度低于 0.01 的列不适合单独建索引**（性别、状态、类型这类）。它们适合作为联合索引的后续列，或者配合其他条件使用。

## 3.3 五种索引类型

```sql
-- ① 主键索引（聚簇索引）
PRIMARY KEY (id)

-- ② 唯一索引：值不能重复，可以有 NULL
UNIQUE KEY uk_email (email)

-- ③ 普通索引
KEY idx_name (name)

-- ④ 联合索引：多列组成一个索引
KEY idx_user_status (user_id, status)

-- ⑤ 前缀索引：只索引字符串的前 N 个字符
KEY idx_email_prefix (email(20))
```

### 3.3.1 前缀索引的取舍

长字符串（如 URL、email）全字段索引太占空间，用前缀：

```sql
-- 先算多长的前缀区分度够
SELECT
  COUNT(DISTINCT LEFT(url, 10)) / COUNT(*) AS p10,
  COUNT(DISTINCT LEFT(url, 20)) / COUNT(*) AS p20,
  COUNT(DISTINCT LEFT(url, 30)) / COUNT(*) AS p30,
  COUNT(DISTINCT url) / COUNT(*) AS full
FROM requests;
-- 选一个接近 full 的最短长度
```

**前缀索引的代价**：**不能用于覆盖索引，也不能用于 `ORDER BY` 和 `GROUP BY`**，因为前缀相同但完整值不同的行无法区分。

## 3.4 联合索引与最左前缀

```sql
CREATE INDEX idx_abc ON t (a, b, c);
```

**这个索引相当于建了三个索引**：`(a)`、`(a,b)`、`(a,b,c)`。

### 3.4.1 能用索引的情况

```sql
-- ✅ 全部命中
WHERE a=1 AND b=2 AND c=3
-- ✅ 命中 a
WHERE a=1
-- ✅ 命中 a,b
WHERE a=1 AND b=2
-- ✅ 范围查询后，后面的列用不上索引，但前面命中
WHERE a=1 AND b>2 AND c=3      -- 用到 a,b；c 用不上（因为 b 是范围）
-- ✅ 顺序无关，优化器会调整
WHERE b=2 AND a=1
```

### 3.4.2 用不上索引的情况

```sql
-- ❌ 缺最左列 a
WHERE b=2 AND c=3
-- ❌ 缺 a
WHERE c=3
-- ❌ 跳列（只有 a 和 c，缺 b）
WHERE a=1 AND c=3              -- 只能用到 a
```

### 3.4.3 范围查询会截断

```sql
INDEX (a, b, c)

WHERE a=1 AND b>2 AND c=3
-- 用到 a 和 b。c 用不上，因为 b 是范围扫描，c 在这之后无序
```

**设计启示：等值条件放前面，范围条件放后面。**

```sql
-- 查询模式：WHERE user_id=? AND status=? AND created_at>?
-- ✅ 好：等值在前，范围在后
INDEX (user_id, status, created_at)

-- ❌ 差：范围在中间，后面的 status 用不上
INDEX (user_id, created_at, status)
```

### 3.4.4 排序也能用索引

```sql
INDEX (user_id, created_at)

-- ✅ 索引天然有序，不需要额外排序
SELECT * FROM orders WHERE user_id=1 ORDER BY created_at DESC;

-- ❌ 排序方向冲突（8.0 之前），会导致 filesort
SELECT * FROM orders WHERE user_id=1 ORDER BY created_at ASC, id DESC;
```

`EXPLAIN` 里如果出现 `Using filesort`，说明排序没走索引。**`filesort` 不一定慢**（数据量小时在内存里排），但数据量大时会用磁盘临时文件，那就慢了。

## 3.5 覆盖索引

**查询需要的所有列都在索引里，就不用回表。** 这是最有效的优化手段之一。

```sql
INDEX idx_user_created (user_id, created_at)

-- ✅ 覆盖索引：只查 user_id 和 created_at，索引里都有
SELECT user_id, created_at FROM orders WHERE user_id = 1;
-- EXPLAIN 的 Extra 会显示 Using index

-- ❌ 要回表：需要 amount 列，索引里没有
SELECT user_id, created_at, amount FROM orders WHERE user_id = 1;
```

**`Using index` 就是覆盖索引的标志**，看到它就说明没有回表，性能最好。

### 3.5.1 用覆盖索引优化深翻页

```sql
-- 原查询：要回表 100 万次
SELECT * FROM orders ORDER BY created_at LIMIT 20 OFFSET 1000000;

-- 优化：先在索引上翻页拿到主键，再回表 20 次
SELECT o.* FROM orders o
JOIN (
  SELECT id FROM orders ORDER BY created_at LIMIT 20 OFFSET 1000000
) t ON o.id = t.id;
```

内层子查询如果能用覆盖索引（`ORDER BY created_at` 上有索引，叶子带主键 id），就只扫索引不回表。

## 3.6 索引失效的八种情况

这是本章最实用的部分。**遇到"索引没用"，逐条对照。**

### 3.6.1 字段被函数包裹

```sql
-- ❌ 索引失效
WHERE DATE(created_at) = '2026-10-28'
WHERE YEAR(created_at) = 2026
WHERE UPPER(name) = 'TOM'

-- ✅ 改成范围查询
WHERE created_at >= '2026-10-28' AND created_at < '2026-10-29'
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE name = 'TOM'    -- 排序规则 ci 本身就不区分大小写
```

### 3.6.2 隐式类型转换

```sql
-- phone 是 VARCHAR
-- ❌ 字段被转成数字，索引失效
WHERE phone = 13800138000
-- ✅
WHERE phone = '13800138000'
```

**规则：字符串字段用数字查 → 索引失效；数字字段用字符串查 → 索引仍可用。**

### 3.6.3 前导模糊匹配

```sql
-- ❌ 无法确定起点，只能全扫
WHERE name LIKE '%张%'
WHERE name LIKE '%张'

-- ✅ 可以用索引
WHERE name LIKE '张%'
```

需要前后模糊搜索时，用全文索引（`FULLTEXT`）或外部搜索引擎（ES）。

### 3.6.4 违反最左前缀

见 3.4.2。

### 3.6.5 `OR` 连接的条件有列没索引

```sql
INDEX (a)

-- ❌ b 没索引，整个条件退化为全表扫描
WHERE a=1 OR b=2

-- ✅ 两边都有索引，可能用 index merge
-- 或者改写为 UNION
SELECT * FROM t WHERE a=1
UNION
SELECT * FROM t WHERE b=2;
```

### 3.6.6 `!=` / `NOT IN` / `NOT LIKE`

```sql
-- ❌ 通常不走索引（要扫描大部分数据才能排除）
WHERE status != 'deleted'
WHERE id NOT IN (1,2,3)
WHERE name NOT LIKE '张%'
```

**但如果 `!=` 排除了绝大多数数据**（比如 `status != 'deleted'` 只剩 100 行），优化器可能仍用索引。**看 `EXPLAIN` 确认，不要凭规则猜。**

### 3.6.7 索引列参与运算

```sql
-- ❌
WHERE id + 1 = 100
WHERE amount * 2 > 1000

-- ✅ 把运算移到右边
WHERE id = 99
WHERE amount > 500
```

### 3.6.8 排序规则 / 字符集不一致

```sql
-- 两个表的关联字段 collation 不同
SELECT * FROM a JOIN b ON a.name = b.name;
-- 会做隐式转换，索引失效
```

检查：

```sql
SHOW FULL COLUMNS FROM a LIKE 'name';
-- Collation 列必须一致
```

## 3.7 EXPLAIN 逐列详解

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 'paid';
```

输出：

```
+----+-------------+--------+------+------------------+---------+---------+-------+------+-------------+
| id | select_type | table  | type | possible_keys    | key     | key_len | ref   | rows | Extra       |
+----+-------------+--------+------+------------------+---------+---------+-------+------+-------------+
|  1 | SIMPLE      | orders | ref  | idx_user_status  | idx_u_s | 8       | const |   12 | Using where |
+----+-------------+--------+------+------------------+---------+---------+-------+------+-------------+
```

### 3.7.1 各列含义

| 列 | 含义 | 怎么看 |
|---|---|---|
| `id` | 查询序号 | 相同 id 从上往下执行；不同 id 越大越先执行（子查询） |
| `select_type` | 查询类型 | `SIMPLE`（无子查询/UNION）、`PRIMARY`、`SUBQUERY`、`DERIVED`、`UNION` |
| `table` | 表名 | `<derived2>` 表示派生表 |
| **`type`** | **访问类型** | **最重要，见 3.8** |
| `possible_keys` | 可能用的索引 | 有值但 `key` 为 NULL = **优化器算过但放弃了** |
| **`key`** | **实际用的索引** | NULL = 没用索引 |
| `key_len` | 用了索引的多少字节 | 判断联合索引用到第几列 |
| `ref` | 和索引比较的值 | `const`、`NULL`、具体列名 |
| **`rows`** | **预估扫描行数** | 越小越好；接近表行数 = 全表扫 |
| `filtered` | 扫描后剩余百分比 | 越低说明过滤效果越好 |
| **`Extra`** | **额外信息** | **第二重要，见 3.9** |

### 3.7.2 `key_len` 判断用了几列

`key_len` 是按字节算的，能反推出联合索引用到了第几列。

| 类型 | 索引占字节 |
|---|---|
| `TINYINT` | 1 |
| `INT` | 4 |
| `BIGINT` | 8 |
| `DATETIME` | 5 |
| `VARCHAR(n)` utf8mb4 | n×4 + 2 |
| 允许 NULL | 额外 +1 |

```sql
INDEX idx_abc (a INT, b INT, c INT)

-- WHERE a=1                  → key_len = 4    （用了 a）
-- WHERE a=1 AND b=2          → key_len = 8    （用了 a,b）
-- WHERE a=1 AND b=2 AND c=3  → key_len = 12   （用了 a,b,c）
-- WHERE a=1 AND c=3          → key_len = 4    （只用了 a，c 跳过了）
```

**这个技巧能精确验证"到底用了几列索引"**，比看 `key` 有没有值更有用。

## 3.8 type：最重要的列

**从好到坏**，记住这个顺序：

| type | 含义 | 评价 |
|---|---|---|
| `system` | 表只有一行 | 最好 |
| `const` | 主键或唯一索引的等值查询，最多一行 | **极好** |
| `eq_ref` | 联表时用主键/唯一索引关联，每次一行 | **好**，联表的理想状态 |
| `ref` | 普通索引等值查询，可能多行 | **可接受**，最常见的理想状态 |
| `range` | 索引范围扫描（`>`、`BETWEEN`、`IN`） | **可接受** |
| `index` | 扫描整个索引树（全索引扫描） | **差**，虽然比全表快 |
| `ALL` | 全表扫描 | **最差，必须优化** |

### 3.8.1 判断标准

```
看到 ALL     → 必须处理
看到 index   → 看数据量，大表必须处理
看到 range   → 可接受，看 rows
看到 ref     → 正常
看到 const / eq_ref → 很好
```

**但 `type` 不能孤立看，要和 `rows` 一起**：

```sql
-- type = range，但 rows = 500 万（全表 600 万）→ 实际上就是全表扫
-- type = ALL，但 rows = 50（小表）→ 完全没问题
```

**`type=ALL` + `rows` 接近表总行数**，才是真正要处理的。

### 3.8.2 一个真实例子

```sql
-- 表 1000 万行
EXPLAIN SELECT * FROM orders WHERE status = 'paid' ORDER BY created_at DESC LIMIT 20;
```

```
| type | key  | rows    | Extra                        |
| ALL  | NULL | 9982341 | Using where; Using filesort  |
```

**三个问题同时存在**：全表扫描、没用索引、文件排序。执行时间可能是 20 秒。

优化：

```sql
-- 建联合索引（等值列在前，排序列在后）
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
```

再查：

```
| type | key                | rows  | Extra       |
| ref  | idx_status_created | 41230 | Using index |
```

从 `ALL` + 998 万行 → `ref` + 4 万行，**这就是索引的全部价值**。

## 3.9 Extra：第二重要的列

| Extra | 含义 | 好坏 |
|---|---|---|
| `Using index` | **覆盖索引**，不回表 | **最好** |
| `Using where` | 在 Server 层过滤（正常） | 中性 |
| `Using index condition` | 索引下推（ICP），减少回表 | 好 |
| `Using temporary` | 用了临时表（`GROUP BY`、`DISTINCT`） | **差** |
| `Using filesort` | 额外排序，没走索引顺序 | **差** |
| `Using join buffer` | 联表没索引，用了 join buffer | **差** |
| `Using MRR` | 多范围读优化 | 好 |
| `Impossible WHERE` | 条件恒假，不会执行 | 注意逻辑错误 |
| `Select tables optimized away` | 优化器直接从索引算出结果 | 极好 |

### 3.9.1 `Using filesort` 要处理吗

**不一定。** 判断标准是数据量：

```sql
-- 只排 20 行（LIMIT 20），filesort 在内存里做，无所谓
SELECT * FROM orders WHERE user_id=1 ORDER BY amount LIMIT 20;

-- 要排 100 万行，filesort 会用磁盘临时文件，非常慢
SELECT * FROM orders ORDER BY amount;
```

看到 `Using filesort` 先看 `rows`：
- `rows < 1000`：可以忽略
- `rows > 10000`：考虑建索引让排序走索引顺序

### 3.9.2 `Using temporary` 通常来自 GROUP BY

```sql
-- ❌ 如果 group_col 没索引，会建临时表
SELECT group_col, COUNT(*) FROM t GROUP BY group_col;

-- 有索引就避免临时表
CREATE INDEX idx_group ON t(group_col);
```

临时表分内存临时表和磁盘临时表。超过 `tmp_table_size`（默认 16M）就落盘，性能差 10 倍以上。

## 3.10 EXPLAIN ANALYZE

`EXPLAIN` 是**预估**，`EXPLAIN ANALYZE`（8.0.18+）是**实际执行**并给出真实耗时：

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100;
```

输出：

```
-> Index lookup on orders using idx_user (user_id=100)  (cost=12.5 rows=98) (actual time=0.045..0.312 rows=102 loops=1)
```

| 字段 | 含义 |
|---|---|
| `cost` | 优化器预估代价 |
| `rows` | 优化器预估行数 |
| `actual time` | 实际耗时（毫秒），`开始..结束` |
| `rows` | **实际返回行数** |
| `loops` | 执行次数 |

**最有价值的用法：对比预估行数和实际行数。**

```
(cost=12.5 rows=98) (actual ... rows=102)
                    ↑ 预估 98，实际 102，很准

(cost=12.5 rows=98) (actual ... rows=520000)
                    ↑ 预估 98，实际 52 万 → 统计信息过期，执行计划选错了
```

**预估和实际差 10 倍以上，就要 `ANALYZE TABLE` 更新统计信息。**

```sql
ANALYZE TABLE orders;
```

表数据变化超过 10% 后统计信息就会不准，大批量导入/删除后应该手动 `ANALYZE`。

## 3.11 索引设计原则

### 3.11.1 四步法

```
1. 先看最常用的查询是什么（从慢日志 / 业务代码里找）
2. 把这些查询的 WHERE、ORDER BY、JOIN 条件列出来
3. 按"等值在前、范围在后"排成联合索引
4. 用 EXPLAIN 验证，看 type 和 key_len
```

### 3.11.2 具体规则

| 规则 | 说明 |
|---|---|
| **区分度高的列放前面** | 除了等值条件优先这条之外 |
| **等值条件在前，范围条件在后** | 范围条件会截断后面的列 |
| **尽量覆盖常用查询** | 让高频查询走 `Using index` |
| **控制索引数量** | 单表不超过 5-6 个 |
| **避免冗余** | `(a)` 和 `(a,b)` 只需后者 |
| **主键要短** | 所有二级索引都存主键 |
| **长字符串用前缀索引** | 但会失去覆盖索引能力 |

### 3.11.3 一个实例

业务有三条高频查询：

```sql
Q1: SELECT * FROM orders WHERE user_id=? AND status=? ORDER BY created_at DESC LIMIT 20;
Q2: SELECT * FROM orders WHERE user_id=? ORDER BY created_at DESC LIMIT 20;
Q3: SELECT COUNT(*) FROM orders WHERE status=? AND created_at>?;
```

设计：

```sql
-- Q1 和 Q2 可以共用一个索引
INDEX idx_user_status_created (user_id, status, created_at)
-- Q2 用 user_id 前缀就能命中（最左前缀）
-- Q1 三列全用上，且 created_at 天然有序，无 filesort

-- Q3 单独建
INDEX idx_status_created (status, created_at)
```

**注意 Q3 的 `created_at` 是范围条件，但它放在最后，所以不影响前面的等值列。**

## 3.12 索引的代价

索引不是免费的。**每个索引的成本**：

| 成本 | 说明 |
|---|---|
| **磁盘** | 每增加一个索引，大约增加表数据的 10-30% |
| **写入变慢** | 每次 `INSERT` / `UPDATE` / `DELETE` 都要维护所有索引 |
| **DDL 变慢** | 加字段要重建所有索引 |
| **优化器变慢** | 索引太多，选错计划的概率上升 |
| **缓冲池压力** | 索引页也要占内存 |

**判断标准**：

```
如果某个索引在慢日志里从来没被用到 → 删掉
如果两个索引是前缀关系 → 删短的
如果某个索引只在月报查询里用 → 考虑删掉，月报时临时加
```

用 2.11.3 的 SQL 找从未使用的索引，观察一周再删。

## 3.13 诊断流程

遇到"这个查询慢"，按这个顺序走：

```
① 拿到 SQL，先看 WHERE / ORDER BY / JOIN 用了哪些列
       ↓
② EXPLAIN 看 type 和 key
       ↓
   type=ALL 或 key=NULL？
       ├─ 是 → 有没有索引？
       │        ├─ 没有 → 建索引（按 3.11 设计）
       │        └─ 有 → 为什么没用？查 3.6 的八种失效情况
       └─ 否 → 继续
       ↓
③ 看 rows，和表总行数对比
       ├─ rows 很大 → 索引区分度不够，或条件不够精确
       └─ rows 不大 → 继续
       ↓
④ 看 Extra
       ├─ Using filesort + rows 大 → 加排序列到索引
       ├─ Using temporary → GROUP BY 列加索引
       └─ Using index → 已经最优了
       ↓
⑤ 还慢？EXPLAIN ANALYZE 看预估 vs 实际
       ├─ 差 10 倍以上 → ANALYZE TABLE
       └─ 一致但开销大 → 数据量本身大，考虑归档/分表/改业务逻辑
       ↓
⑥ 最后才考虑参数（缓冲池、IO 能力）
```

**顺序不能跳。** 直接去调 `innodb_buffer_pool_size` 是最常见的错误——索引没建，缓冲池再大也是全表扫。

## 3.14 十个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 索引列上用函数 | 索引失效 | 改成范围查询 |
| 2 | `VARCHAR` 用数字查 | 隐式转换，索引失效 | 加引号 |
| 3 | `LIKE '%x%'` | 全表扫描 | 前缀匹配或全文索引 |
| 4 | 联合索引顺序错（范围在前） | 后续列用不上 | 等值在前，范围在后 |
| 5 | 用 UUID 做主键 | 页分裂，写入慢 5-10 倍 | 自增 `BIGINT` |
| 6 | 建了一堆低区分度索引（性别、状态） | 优化器不用，白占空间 | 单独低区分度列不建索引 |
| 7 | 只看 `key` 有值就以为走索引了 | `type=ALL` 时 `key` 可能仍有值 | 看 `type` 和 `rows` |
| 8 | 索引太多（单表 10 个以上） | 写入慢、优化器选错 | 控制在 5-6 个 |
| 9 | 统计信息过期 | 预估行数差 10 倍，选错计划 | 大批量变更后 `ANALYZE TABLE` |
| 10 | `SELECT *` 导致无法覆盖索引 | 每次都回表 | 只查需要的列 |

第 7 条值得强调：**`key` 有值不代表走好了**。有时候 `possible_keys` 有值、`key` 也有值，但 `type=index`（全索引扫描），实际比全表扫还慢——因为它扫了整个索引树还要回表。
