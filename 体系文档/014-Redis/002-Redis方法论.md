# Redis 方法论

> **这一册回答**：缓存为什么立得住——「可丢/不可丢判定、命中率意识、淘汰策略、一致性权衡」四条方法论，以及怎么用它们判断你的缓存设计够不够格。
> **给谁读**：准备给系统上缓存的运维；也用于评审一个缓存设计「出了事数据丢不丢、人慌不慌」。
> **工具无关**：redis-cli 命令、配置项在模块册；本册给的是它们要服务的原则。

## 可丢 / 不可丢判定

上缓存的第一问不是「用什么结构」，而是「这份数据丢了会怎样」：

1. **可再生缓存**（源在数据库，丢了回源重建）：可以接受丢失，选性能优先——不持久化或仅 RDB。绝大多数缓存属于此类。
2. **不可丢主存储**（会话、分布式锁、计数器）：丢了就是事故——必须开 AOF（everysec 起步）+ 副本，并接受持久化对延迟的代价（112 的取舍）。
3. **判定挂在容量规划上**：内存不够时驱逐谁——`maxmemory-policy` 淘汰策略就是「可丢判定」的机器表达（111/121）。

**先判定再选型**：把「可丢」的当主存储用是事故之源，把「不可丢」的当纯缓存用是数据丢失之源。

## 命中率意识

- **命中率不是虚荣指标**：它直接决定数据库的死活——命中率跌 5%，数据库 QPS 可能翻倍（123 §5 的指标映射）。
- **看趋势与分层**：整体命中率掩盖热点差异——按 key 前缀/业务维度看局部命中率，冷 key 该踢就踢（121 的三件套防御）。
- **miss 是设计问题**：穿透（查不存在的 key）、击穿（热 key 过期瞬间）、雪崩（批量同时过期）三种 miss 有三种防御，不是加机器能解决的（121）。

## 淘汰策略即业务决策

`maxmemory-policy` 不是运维随手配的参数，是业务问题的回答：

| 场景 | 策略取向 | 落地 |
| --- | --- | --- |
| 纯缓存、全可丢 | `allkeys-lru` / `allkeys-lfu` | 121 |
| 有不可丢 key 混存 | `volatile-*`（只淘汰带 TTL 的） | 111/121 |
| 不许丢（主存储） | `noeviction` + 容量预警 | 112/122 |

**配了淘汰策略就等于承认会丢**——「不可丢」的 key 在 `allkeys-*` 策略下一样会被驱逐。

## 一致性权衡

缓存与数据库的一致性没有免费午餐，只有权衡：

- **先更库再删缓存**（Cache-Aside 主流）：窗口期内脏读可容忍的场景用之（121）。
- **强一致要付出代价**：延迟双删、订阅 binlog 异步删除——复杂度上去了， still 有窗口（121 的边界注记）。
- **运维兜底**：一致性方案出问题时的最后手段是手动清缓存——清缓存脚本要幂等、要限流（回源风暴）（122）。

## 反模式

- ❌ 把分布式锁存进纯缓存实例——内存紧张时锁被驱逐，两个客户端同时进临界区。
- ❌ 无 TTL 的 key 占满内存——`noeviction` 下写满即报错，`allkeys-lru` 下不可丢数据被驱逐。
- ❌ 大 key 当队列用——`LRANGE 0 -1` 全量拉取是慢查询元凶（111 的 List 注记）。
- ❌ 缓存雪崩靠扩容解决——过期时间加随机抖动比加机器便宜得多（121）。

## 自测

1. 上缓存的第一问是什么？（可丢/不可丢判定，先判定再选型）
2. 三种 miss 是什么？各怎么防？（穿透/击穿/雪崩，见 121）
3. `allkeys-lru` 下不可丢数据安全吗？（不安全——配了淘汰策略就等于承认会丢）
4. 先更库再删缓存的窗口期怎么接受？（脏读窗口可容忍才用；强一致要付出复杂度代价）
