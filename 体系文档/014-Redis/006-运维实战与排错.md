## 1. 内存管理

三个内存口径先分清（`INFO memory`）：

| 指标 | 含义 | 关注点 |
|---|---|---|
| `used_memory` | Redis 自行记账的数据占用 | 与 maxmemory 比较的是它 |
| `used_memory_rss` | 操作系统实际分配的物理页 | 与机器内存比较的是它 |
| `mem_fragmentation_ratio` | rss ÷ used_memory | **>1.5 碎片重**，<1 说明 swap 了（更糟） |

maxmemory 只约束 used_memory——**碎片、复制缓冲、客户端缓冲都在 rss 里另算**，容量规划要留出这部分。碎片治理：4.0+ 开启 `activedefrag yes`（主动整理，CPU 换内存）或错峰重启重建。

## 2. 大 key

**发现**（生产环境用抽样版，不用全量版）：

```bash
redis-cli --bigkeys                  # 抽样扫描五种类型的最大 key
redis-cli --memkeys                  # 按内存占用扫描
MEMORY USAGE <key> SAMPLES 0         # 精确查单个 key（⚠️ 大集合全量计算会卡）
```

**危害**：DEL 一个百万元素集合同步释放会卡实例；热读打满网卡；迁移/过期都受累。

**治理**：⚠️ 删除大 key 用 **`UNLINK`**（异步后台释放）替代 `DEL`；7.4 起支持 `maxmemory-eviction-...` 配合异步删除。拆分方案按 001 §6：大 Hash 按 field 分桶、大 List 按 range 切段，逐步迁移后删旧 key（UNLINK）。

## 3. 热 key

**发现**：`redis-cli --hotkeys`（需 LFU 策略，按访问频次抽样）；或客户端侧统计；Cluster 下看哪个分片 CPU/QPS 独高反推。

**危害**：单分片打满（Cluster 下其他分片闲着）、带宽打满、该 key 失效瞬间引发击穿（005 §3）。

**治理**：应用侧加**本地缓存**（二级缓存挡大部分读）；热 key 加随机后缀打散到多槽（读场景可行，写场景慎用）；读写分离让从库分担读。

## 4. 慢查询

```bash
CONFIG SET slowlog-log-slower-than 10000   # 10ms 阈值（微秒单位）
CONFIG SET slowlog-max-len 128             # 保留条数
SLOWLOG GET 10                             # 最近 10 条
SLOWLOG RESET
```

常见元凶：`KEYS *`（⚠️ 生产禁用——全量阻塞）、`HGETALL` 大 Hash、`SMEMBERS` 大 Set、`LRANGE 0 -1`、`DEL` 大 key、`SORT`。治理：全量遍历一律换 `SCAN` 族渐进遍历（`SCAN 0 MATCH user:* COUNT 100` 游标轮询）。

## 5. 延迟排查

毫秒级抖动的四大来源，按概率排查：

| 来源 | 判定 | 处理 |
|---|---|---|
| swap | `mem_fragmentation_ratio < 1` 或系统 free 低 | 容量调整，杜绝 swap |
| fork（bgsave/重写） | `latest_fork_usec` 高 | 控实例大小、错峰（002 §3） |
| AOF fsync | `aof_delayed_fsync` 增长 | 磁盘 IO 升级或 everysec 保持 |
| 淘汰风暴 | `evicted_keys` 增长 | 内存与淘汰策略治理（005 §5） |

工具：`redis-cli --latency -h <host>`（持续采样）、`--latency-history`；配合系统侧 `iostat -x 1` 看 IO。**网络与客户端**也是常见嫌疑：连接池打满、Nagle、DNS——先在 Redis 同机用 redis-cli 基准，排除网络后再看服务端。

## 6. INFO 命令族

`INFO <段>` 分段读取，运维最常看的四段与关键指标：

| 段 | 关键指标 | 告警建议 |
|---|---|---|
| memory | used_memory/maxmemory 比例、fragmentation_ratio | >90% 告警；ratio >1.5 关注 |
| clients | connected_clients、blocked_clients | 连接数打满前告警 |
| stats | instantaneous_ops_per_sec、keyspace_hits/misses（**命中率**）、evicted_keys、latest_fork_usec | 命中率骤降、evicted 增长告警 |
| replication | master_link_status（从库视角）、connected_slaves（主库） | down 告警——主从断连是 HA 前兆 |

## 7. 排错决策树

```plain
Redis 有问题？
├─ 写不进（OOM）→ maxmemory 满了？→ 策略/容量（005 §5）
├─ 慢查询堆积 → SLOWLOG GET → 全量命令/大 key？（§4）
├─ 偶发抖动 → latest_fork_usec / fsync / swap / 淘汰（§5）
├─ 连接不上 → bind/防火墙/ACL/连接数（007）
├─ 主从断连 → 网络分区 / repl_backlog 不够 / 全量风暴（003 §1）
└─ 集群报 MOVED → 槽表迁移或客户端协议（004 §3）
```

## 8. 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 生产用 `KEYS *` | 全量阻塞，全网抖动 | `SCAN` 渐进遍历 |
| 2 | `DEL` 百万级大 key | 同步释放卡实例 | `UNLINK` 异步删除 |
| 3 | `FLUSHALL/FLUSHDB` 不加确认 | 误删全库 | ACL 禁用（007 §2）+ 二次确认 |
| 4 | 只看 used_memory 不看 rss | 机器 OOM 而"内存没满" | 两口径一起监控 |
| 5 | 慢查询阈值用默认 10ms 不调 | 与业务 SLO 不匹配 | 按业务延迟 SLO 设阈值 |
