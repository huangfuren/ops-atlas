## 1. 结构总览

选型就是这张表——**先对场景，再看运维影响**：

| 结构 | 底层编码 | 典型场景 | 运维影响 |
|---|---|---|---|
| String | int / embstr / raw | 计数器、缓存对象、分布式锁 | 单值过大 = 大 key |
| List | listpack / quicklist | 消息缓冲、最新列表 | 长度百万级时 lp 遍历慢 |
| Hash | listpack / hashtable | 对象属性、购物车 | field 数大 + value 大 = 大 key 之最 |
| Set | intset / hashtable | 去重、标签、共同关注 | SRANDMEMBER 大集合全量危险 |
| ZSet | listpack / skiplist | 排行榜、延迟队列 | ZRANGE 全量拉取危险 |
| Bitmap | String 位操作 | 签到、活跃天数 | 极省内存，偏移量过大要警惕 |
| HyperLogLog | 稠密/稀疏编码 | UV 计数 | 固定 12KB，误差 0.81% |
| GEO | ZSet 封装 | 附近的人/门店 | 就是 ZSet，按 GeoHash 排序 |
| Stream | radix tree | 消息队列、事件流 | 与专业 MQ 的边界见「消息队列」004 |

## 2. 五大基础结构：场景与运维注意

### 2.1 String——默认选项

定义：最简单的 KV，value 上限 512MB。三个编码：整数用 int、短字符串（≤44 字节）用 embstr、长的用 raw。

场景：对象缓存（JSON 序列化）、计数器（`INCR` 原子自增）、分布式锁（`SET lock NX EX 30`）。运维注意：**缓存大 JSON 前先估体积**；计数器要配 TTL，否则只增不减。

### 2.2 List——有序可重复的队列壳

机制：7.0 后 quicklist = 双向链表串起多个 listpack 小块——兼顾尾部插入性能与内存。

场景：最新消息列表（`LPUSH + LRANGE`）、简单任务缓冲。运维注意：**List 不是消息队列的正解**——没有 ack 与消费组，消息语义见 004 /「消息队列」004；`LRANGE 0 -1` 全量拉大列表是慢查询元凶。

### 2.3 Hash——对象属性包

机制：field 少（≤128）且 value 短时用 listpack 一块内存存完，大了转 hashtable——**从小编码到大编码的内存跳变可达数倍**。

场景：用户属性、购物车（field=商品 ID，value=数量）。运维注意：Hash 是大 key 重灾区——`HGETALL` 全量拉取、几百个 field 各存大 JSON 都要避免；渐进遍历用 `HSCAN`。

### 2.4 Set——去重与关系

场景：去重（UV 的小数据版）、标签、共同关注（`SINTER` 交集）。运维注意：`SMEMBERS` 全量拉大集合同样危险；随机抽奖用 `SRANDMEMBER` 别用全量。

### 2.5 ZSet——排序即服务

机制：skiplist 跳表 + dict 双结构，按 score 排序 O(logN) 插入。

场景：排行榜（`ZADD` + `ZREVRANGE`）、延迟队列（score=执行时间戳，轮询 `ZRANGEBYSCORE`）、滑动窗口限流（score=时间戳计数）。运维注意：`ZRANGE 0 -1` 全量拉取排行榜要注意分页；score 是 double——秒级时间戳精度够用。

## 3. 三种特殊结构

| 结构 | 场景 | 一笔账 |
|---|---|---|
| **Bitmap** | 签到、活跃天数、布隆过滤器的底层 | 1 亿用户签到只要 ~12MB（1 人 1 位） |
| **HyperLogLog** | UV 等基数计数（允许 0.81% 误差） | 固定 12KB 计上亿 UV——不能取明细只能取数 |
| **GEO** | 附近的人/门店 | `GEOADD` + `GEOSEARCH`；本质是 ZSet |

## 4. Stream：Redis 自己的消息队列

机制：radix tree 存储、消费组（Consumer Group）、ack 确认、PEL 待处理列表——有专业 MQ 的核心语义。

边界：**小流量事件流与轻量队列可用**；大规模、需要高吞吐分区与重平衡的场景用专业 MQ（对比见「消息队列」000/004）。运维注意：Stream 不会自动删除消息——配 `MAXLEN` 限定长度，否则只增不减成大 key。

## 5. 编码与内存：结构是壳，编码是芯

同一个 key 的编码会随内容**自动转换**——`OBJECT ENCODING key` 查看当前编码：

| 触发条件 | 转换 | 内存后果 |
|---|---|---|
| String ≤44 字节 → 更长 | embstr → raw | 翻倍级 |
| Hash/Set/ZSet 元素少且短 → 超阈值 | listpack → hashtable/skiplist | 数倍级 |

运维意义：**阈值参数（`hash-max-listpack-entries` 等）默认保守**——生产上按业务尺寸调优，能在数 GB 规模省出可观内存；改阈值是双刃剑，必须压测验证。

## 6. 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | Hash 单 key 存整个大对象（几 MB JSON） | 大 key：删除卡实例、热更打满带宽 | 拆 field 或改 String 分片 |
| 2 | `LRANGE/HGETALL/SMEMBERS 0 -1` 全量拉 | 慢查询 + 网络打满 | `SCAN/HSCAN` 渐进或 LIMIT 分页 |
| 3 | 计数器不设 TTL | 只增不减成大 key | `INCR` 后配 `EXPIRE` |
| 4 | 用 List 当专业消息队列 | 无 ack、无消费组，丢了没法查 | 有消息语义的用 Stream 或 MQ |
| 5 | Bitmap 偏移量随意上亿 | 单 String 位数过大 | 按 id 段分 key |
| 6 | 拿 HyperLogLog 存需要明细的数据 | HLL 只能取数不能取明细 | 要明细换 Set |
