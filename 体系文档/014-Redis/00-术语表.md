# 00 术语表

> **这一文档回答**：某个词是什么意思、两个混用词的分界、「只知道现象不知道翻哪册」往哪走。  
> **怎么用**：按名字（按主题分组）、按缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和命令回对应册；这里只保证你「认得出、分得清、找得到」。

## 01 数据结构与场景

| 术语 | 英文 | 一句话 |
|---|---|---|
| 缓存命中 | cache hit | 请求的数据在 Redis 里拿到了——命中率是缓存体系第一指标 |
| TTL | Time To Live | key 的存活秒数，到期按惰性+定期两种方式删除 |
| 大 key | big key | 单个 key 的 value 过大（String 数 MB、集合数万成员）——删除与迁移都是事故源 |
| 热 key | hot key | 访问频率极度集中的 key——单分片被打满，集群下是热点难题 |
| 分布式锁 | distributed lock | 用 SET NX EX 实现跨进程互斥，必须带过期与唯一值 |
| 布隆过滤器 | Bloom filter | 空间高效的概率结构，"一定不存在"可信——防穿透的第一道闸 |

## 02 持久化与内存

| 术语 | 英文 | 一句话 |
|---|---|---|
| RDB | Redis Database | 二进制快照：save/bgsave 生成，恢复快但有丢数据窗口 |
| AOF | Append Only File | 写命令追加日志：appendfsync 三档控制持久度，重写压缩体积 |
| 混合持久化 | hybrid persistence | aof-use-rdb-preamble：重写时 RDB 头 + 增量 AOF，7.x 默认 |
| fork | fork | bgsave/重写靠 fork 子进程——大实例 fork 是卡顿元凶 |
| 写时复制 | copy-on-write | fork 后父子共享内存页，谁改谁复制——内存翻倍风险的来源 |
| maxmemory | — | 内存使用上限，到顶后按 maxmemory-policy 淘汰或拒绝写入 |
| 淘汰策略 | eviction policy | 8 种：noeviction 默认（到顶拒绝写）、lru/lfu/lru×过期样本组合 |
| 内存碎片率 | mem_fragmentation_ratio | used_memory_rss ÷ used_memory——大于 1.5 说明碎片重 |
| SDS | Simple Dynamic Strings | Redis 自研字符串结构：长度头 + 空间预分配，O(1) 取长度 |

## 03 高可用与集群

| 术语 | 英文 | 一句话 |
|---|---|---|
| 主从复制 | replication | replicaof 让从库复制主库数据——全量 RDB + 增量命令流 |
| repl_backlog | replication backlog | 主库环形缓冲区，断线重连增量同步靠它，太小触发全量 |
| 哨兵 | Sentinel | 独立进程监控主库：主观下线→客观下线→选新主→通知客户端 |
| 客观下线 | objective down | quorum 个哨兵都认为主挂了——够数才切换，防误判 |
| 脑裂 | split-brain | 旧主在网络分区里仍接写入，恢复后数据丢失——min-replicas-to-write 防 |
| Cluster | Redis Cluster | 16384 槽分片集群：数据按 crc16(key) mod 16384 分布 |
| 槽 | slot | 集群数据分配的最小单位——key 归属槽决定它在哪个节点 |
| hash tag | — | `{user1000}.follow` 强制同槽——多 key 操作的前提 |
| MOVED | — | key 不归本节点时的永久重定向——客户端应更新槽表 |
| ASK | — | 迁移中的临时重定向——下次还先问原节点 |

## 04 缓存设计与安全

| 术语 | 英文 | 一句话 |
|---|---|---|
| 缓存穿透 | cache penetration | 查询**不存在**的数据，每次都打到数据库 |
| 缓存击穿 | cache breakdown | **热点 key 过期瞬间**，并发全打到数据库 |
| 缓存雪崩 | cache avalanche | **大批 key 同时失效**或缓存整体宕机 |
| Cache-Aside | — | 应用先查缓存、未中查库回填——最主流的一致性模式 |
| 延迟双删 | double delete | 更新库后先删缓存、延迟再删一次——应对并发脏读窗口 |
| 逻辑过期 | logical expiry | value 里存过期时间不真删——配合互斥重建防击穿 |
| ACL | Access Control List | 6.0+ 用户级权限：按用户限定命令类别与 key 模式 |
| 慢查询日志 | slowlog | 超过 slowlog-log-slower-than 的命令记录——排障第一入口 |

## 缩写速查

| 缩写 | 全称 | 意思与出处 |
|---|---|---|
| RDB | Redis Database | 二进制快照持久化（002） |
| AOF | Append Only File | 命令追加日志持久化（002） |
| TTL | Time To Live | key 存活时长（005） |
| LRU | Least Recently Used | 最近最少使用淘汰——按访问时间（005 §5） |
| LFU | Least Frequently Used | 最不经常使用淘汰——按访问频率（005 §5） |
| ACL | Access Control List | 用户级权限体系（007 §3） |
| PSYNC | Synchronization (partial) | 复制协议：全量 SYNC 的升级版，支持增量（003 §1） |
| QPS | Queries Per Second | 每秒查询数——容量与压测的基本单位 |

## 最容易混的 12 对

| 容易混 | 一句话差别 | 去哪 |
|---|---|---|
| 持久化 vs 备份 | 持久化保宕机重启；备份保误删灾难——**两件事** | 002 §5 |
| RDB vs AOF | 快照（恢复快丢得多）vs 日志（丢得少文件大） | 002 §1 |
| 主从 vs 哨兵 vs Cluster | 主从是复制；哨兵加自动切换；Cluster 再加分片容量 | 003/004 |
| 穿透 vs 击穿 vs 雪崩 | 查不存在 / 热点过期瞬间 / 大批失效或宕机 | 005 §1 |
| 惰性删除 vs 定期删除 | 访问时顺带查 / 周期性抽样清理——到期≠立即消失 | 005 §6 |
| LRU vs LFU | 按最近访问 / 按访问频率——偶发扫描会污染 LRU | 005 §5 |
| used_memory vs rss | Redis 自己记账 / 操作系统实际给页——差值即碎片 | 006 §1 |
| 大 key vs 热 key | 体积大 / 访问挤——一个是删除事故源，一个是热点故障源 | 006 §2/3 |
| MOVED vs ASK | 槽已固定归属 / 槽正在迁移中 | 004 §3 |
| 哨兵 vs Cluster 的高可用 | 哨兵切换主从（不解决容量）；Cluster 槽级故障转移（容量+HA） | 004 §1 |
| 过期 vs 淘汰 | 过期是 key 到了自己 TTL；淘汰是内存到顶被策略请出去 | 005 §5/6 |
| 缓存 vs 主存储 | 同一份 Redis 数据可能是可丢缓存，也可能是不能丢的主存储 | 000 §3 |

## 按症状反查

| 现象 | 大概率病根 | 去哪 |
|---|---|---|
| 内存到顶，写入报 OOM command not allowed | maxmemory + noeviction 默认策略 | 005 §5 |
| 每隔几分钟卡一下，毫秒到秒级 | bgsave/重写 fork，或大 key 删除 | 002 §3 · 006 §2 |
| 命中率骤降，数据库压力陡增 | 雪崩（大批同时过期）或穿透 | 005 §1~3 |
| 重启后数据全丢 | 没配持久化或 appendfsync no | 002 §6 |
| 主从切换后部分数据没了 | 脑裂期间旧主仍接写 | 003 §4 |
| 客户端报 MOVED，多 key 操作报错 | key 不在同槽——用 hash tag | 004 §3 |
| 连接数打满，新建连接被拒 | 连接池泄漏或 timeout 没配 | 006 §4 |
| 单分片 QPS 打满，其他分片空闲 | 热 key 集中在一个槽 | 006 §3 |
| Redis 偶发延迟毫秒级抖动 | swap、AOF fsync、淘汰、fork 四选一 | 006 §5 |
| `KEYS *` 一执行全网卡死 | 生产用了阻塞命令 | 006 §4 |
| 升级后老应用连不上 | 6.0 起 requirepass 换成 ACL 体系 | 007 §3 |
| 大 key 删除时整个实例卡死 | DEL 同步释放——改 UNLINK | 006 §2 |
