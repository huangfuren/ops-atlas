> **解决**：数据与写入超单机容量怎么分片——16384 槽、MOVED/ASK、倾斜与迁移。

## 1. 为什么需要 Cluster

哨兵（003）解决的是**高可用**（挂了自动切），不解决两个问题：**单机内存上限**（数据装不下）与**单机写入瓶颈**（QPS 打满）。Cluster 把数据切成 16384 个槽分布到多个主节点——容量与写入水平扩展，同时内置故障转移（不需要哨兵）。

## 2. 架构：16384 槽与 Gossip

| 要素 | 说明 |
|---|---|
| 16384 槽 | key 归属 = `crc16(key) mod 16384`；槽是数据分配与迁移的最小单位 |
| 主节点 | 各持有部分槽段（如 3 主 = 0~5460 / 5461~10922 / 10923~16383） |
| 从节点 | 复制对应主节点，主挂后集群内部自动故障转移（无需哨兵） |
| Gossip | 节点间 PING/PONG 交换集群状态——去中心化，无中心调度器 |

## 3. 数据分布与重定向

客户端把命令发到**任意节点**，节点算槽：

| 响应 | 含义 | 客户端应做 |
|---|---|---|
| 正常返回 | key 归本节点 | — |
| **MOVED** | key 归属**固定在另一个节点** | 更新本地槽表，重发到新节点 |
| **ASK** | key 正在**迁移中**，目标节点可能有 | 先发 ASKING 到目标节点再执行；槽表不变 |

**多 key 操作的槽限制**：`MGET`/事务/Lua 脚本里的所有 key 必须同槽——否则报 `CROSSSLOT`。解法是 **hash tag**：key 里放 `{...}` 片段，Redis 只对花括号内的部分算槽——`{user1000}.profile` 与 `{user1000}.orders` 永远同槽。代价：tag 设计不当会让数据挤进同一槽，制造倾斜。

## 4. 搭建与验证

```bash
# 六节点（3 主 3 从）一键组建
redis-cli --cluster create 10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
  10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 --cluster-replicas 1

# 验证
redis-cli -c -h 10.0.0.1 cluster info      # state:ok, slots_assigned:16384
redis-cli -c -h 10.0.0.1 cluster nodes     # 槽段与主从关系
```

关键配置：`cluster-enabled yes`；`cluster-node-timeout 15000`（判失联阈值）；节点间总线端口 = 服务端口 + 10000，**防火墙必须放行**。

## 5. 运维要点

| 主题 | 要点 |
|---|---|
| **数据倾斜** | 大 key 或 hash tag 集中把某个槽撑大——`redis-cli --cluster` 看各节点内存；治理见 006 §2 |
| **扩缩容** | `--cluster reshard` 迁移槽（ASK 过渡态）；线上迁移限速，避免打满节点 |
| **故障转移** | 主挂后其从节点自动竞选提升——半数以上主节点存活才能选（多数派原则） |
| **半数主挂 = 集群只读** | 6 节点挂 2 主 → 集群整体失效——**主节点必须分散在不同物理机** |

## 6. 什么时候不用 Cluster

| 场景 | 结论 |
|---|---|
| 单机内存 / QPS 够用 | 上 Cluster 只增加复杂度——**主从 + 哨兵足够** |
| 大量多 key 操作与 Lua | hash tag 设计负担重，误用触发 CROSSSLOT |
| 超大 key 多 | 单 key 无法再分，倾斜无解——先治理大 key |

## 7. 坑表

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 客户端不支持 Cluster 协议 | 收到 MOVED 不跟随，全量报错 | 用支持 Cluster 的客户端/驱动 |
| 2 | hash tag 大粒度（如 `{app}`） | 所有 key 挤一个槽，单节点倾斜 | tag 按业务实体粒度（{user1000}） |
| 3 | 总线端口（+10000）没放行 | 节点间 Gossip 不通，集群起不来 | 防火墙放行服务与总线两个端口 |
| 4 | 主节点同物理机 | 一台机器挂掉多个主，集群可能失效 | 主从跨物理机/机架部署 |
| 5 | reshard 不限速 | 迁移打满节点，业务抖动 | `--cluster reshard` 配批大小与 sleep |
| 6 | 挂 2 个主（6 节点）就整集群只读 | 多数派不保，故障转移无法完成 | 监控主节点存活数，告警提前介入 |

## 8. 检查清单

| # | 问题 |
|---|---|
| 1 | 你的规模真的需要 Cluster 吗（容量/QPS 数据）？ |
| 2 | hash tag 的粒度设计过吗？ |
| 3 | 总线端口与 node-timeout 配了吗？ |
| 4 | 主节点跨物理机分布吗？挂 2 主会怎样？ |
| 5 | reshard 限速策略定了吗？ |
| 6 | 客户端支持 MOVED/ASK 跟随吗？ |
