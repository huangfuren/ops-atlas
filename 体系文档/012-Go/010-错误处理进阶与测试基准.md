## 1. 错误处理进阶

### 1.1 三种错误形态

```go
// 1. 哨兵错误：可预知的特定错误，用 errors.Is 判断
var ErrNotFound = errors.New("not found")

// 2. 自定义错误类型：需要携带字段，用 errors.As 取
type ValidationError struct {
	Field string
	Msg   string
}
func (e *ValidationError) Error() string {
	return e.Field + ": " + e.Msg
}

// 3. 动态错误：需要格式化消息
return fmt.Errorf("连接 %s 失败: %w", addr, err)
```

### 1.2 包装链的判断

```go
// Is：判断链上是否有某个哨兵错误
if errors.Is(err, os.ErrNotExist) { ... }

// As：把链上某个类型的错误提取出来
var ve *ValidationError
if errors.As(err, &ve) {
	fmt.Println("字段:", ve.Field)
}

// Unwrap：继续向上拆（也可以用 errors.Unwrap 手动拆）
```

**`errors.Is` 不要拿来做字符串比较**，要比较错误值本身。

### 1.3 一次包装，别重复包装

```go
// ❌ 每层都加前缀，最后日志里是 5 层堆叠
func a() error { return fmt.Errorf("a failed: %w", err) }
func b() error { return fmt.Errorf("b failed: %w", err) }

// ✅ 只在跨层边界包装一次，同层内直接 return err
```

判断标准：**包装是为了给上层提供新信息**（哪个资源、哪个 ID），如果只是加个函数名，别加。

### 1.4 panic 的边界

| 该用 error | 该用 panic |
|---|---|
| 文件不存在、网络超时、参数校验失败 | 初始化时配置缺失（`main` 里 `log.Fatal`） |
| 业务逻辑错误 | 代码 bug：不可达分支、类型断言失败 |
| 可恢复、需要调用方决策 | 程序无法继续 |

**库代码不要 panic**，除非是在 `init` 或明确文档化的情况下。库 panic 会迫使每个调用方写 recover。

### 1.5 错误处理反模式

```go
// ❌ 忽略错误
_ = f.Close()

// ❌ 只打日志不返回（错误被吞，上层以为成功）
if err != nil {
	log.Println(err)
}

// ❌ 用 panic 传递业务错误
if user == nil {
	panic("user not found")
}

// ❌ 错误信息没有上下文
return err                    // 上层不知道是哪一步失败

// ✅
return fmt.Errorf("加载用户 %d 的配置: %w", id, err)
```

## 2. 测试与基准

### 2.1 表驱动测试

Go 测试的标准写法：

```go
func TestAdd(t *testing.T) {
	tests := []struct {
		name string
		a, b int
		want int
	}{
		{"正数", 1, 2, 3},
		{"零", 0, 0, 0},
		{"负数", -1, 1, 0},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Add(tt.a, tt.b); got != tt.want {
				t.Errorf("Add(%d,%d) = %d, want %d", tt.a, tt.b, got, tt.want)
			}
		})
	}
}
```

`t.Run` 的子测试可以单独跑：`go test -run 'TestAdd/正数'`。

### 2.2 并行测试

```go
func TestParallel(t *testing.T) {
	t.Parallel()          // 和其他 t.Parallel 的测试并行
	// ...
}
```

注意：并行测试**不能修改共享的包级变量**。

### 2.3 辅助函数

```go
func mustJSON(t *testing.T, s string) map[string]any {
	t.Helper()                     // 报错时指向调用方行号，不是这里
	var m map[string]any
	if err := json.Unmarshal([]byte(s), &m); err != nil {
		t.Fatalf("解析 JSON 失败: %v", err)
	}
	return m
}
```

`t.Fatalf` 和 `t.Errorf` 的区别：前者立即终止当前测试，后者继续执行。

### 2.4 基准测试

```go
func BenchmarkConcat(b *testing.B) {
	for i := 0; i < b.N; i++ {
		var s string
		for j := 0; j < 100; j++ {
			s += "x"
		}
	}
}
```

```bash
go test -bench=. -benchmem
```

```
BenchmarkConcat-8   10000   105000 ns/op   48000 B/op   99 allocs/op
                          ↑ 每次耗时    ↑ 内存   ↑ 分配次数
```

`-benchmem` 必须加，`B/op` 和 `allocs/op` 是判断有没有优化的关键。

**对比改动前后的性能**，用 benchstat：

```bash
go test -bench=. -count=10 > old.txt
# 改代码
go test -bench=. -count=10 > new.txt
benchstat old.txt new.txt
```

### 2.5 覆盖率

```bash
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out      # 浏览器里看哪几行没覆盖
```

覆盖率 60-80% 是合理区间。**100% 覆盖率不等于没有 bug**，但核心逻辑（金额计算、权限判断）应该覆盖到。

### 2.6 httptest

测 HTTP handler 不用起真服务：

```go
func TestHealth(t *testing.T) {
	req := httptest.NewRequest("GET", "/health", nil)
	w := httptest.NewRecorder()

	healthHandler(w, req)

	resp := w.Result()
	if resp.StatusCode != 200 {
		t.Fatalf("状态码 %d", resp.StatusCode)
	}
}
```

### 2.7 模糊测试

Go 1.18+ 内置 fuzz，用于找边界崩溃：

```go
func FuzzParse(f *testing.F) {
	f.Add("123")                       // 种子
	f.Fuzz(func(t *testing.T, s string) {
		Parse(s)                       // 不 panic、不越界就算过
	})
}
```

```bash
go test -fuzz=FuzzParse -fuzztime=30s
```

找到的崩溃输入会自动写进 `testdata/fuzz/`，变成回归用例。

## 3. 新手坑：defer 与返回值

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 在 goroutine 里 recover 后不记录 | 崩溃静默丢失 | recover 里必须打日志 + 堆栈 |
| 2 | `defer` 里改命名返回值搞混 | 返回值被意外覆盖 | 命名返回值 + defer 要谨慎 |

## 4. 检查清单

| # | 问题 | 判据 |
|---|---|---|
| 1 | `%w` 与 `%v` 包装差别？ | `%w` 可被 `errors.Is/As` 穿透，`%v` 只留文本、断链 |
| 2 | `errors.Is` 与 `errors.As` 各查什么？ | `Is` 比值（哨兵错误），`As` 提取具体类型并赋给目标 |
| 3 | panic 用在什么场景？recover 放在哪层？ | 只用于不可恢复的程序错误；recover 放在 goroutine 最外层并记录堆栈 |
| 4 | 表驱动测试的结构？ | `tests := []struct{name string; in, want ...}` + `t.Run(tc.name, ...)` |
| 5 | `-benchmem` 输出里该看哪两个数？ | `allocs/op` 与 `B/op`，用来发现隐藏分配 |
| 6 | fuzz 发现的崩溃用例存到哪？ | 自动写入 `testdata/fuzz/<Fuzz名>/`，成为回归用例 |
