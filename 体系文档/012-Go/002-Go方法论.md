# Go 方法论

> **这一册回答**：用 Go 写运维工具为什么围绕「值语义想得清、错误不吞、并发可控」三件事，以及怎么用它们判断一段 Go 代码够不够格上生产。
> **给谁读**：会 Shell 与 Python 的运维，第一次系统学 Go；也用于评审一个 Go 工具「敢不敢常驻在服务器上跑」。
> **工具无关**：语法与库的用法在正文册；本册给的是语言设计要服务的性质。

## 三条能力线

Go 对运维的价值按三档能力排布，与板块三条线一一对应：

1. **会写（111~116）**：环境、语法、复合类型、错误处理、标准库与并发第一课——目标是「20 行以上的粘合逻辑不再用 Python 硬凑」，编译出单二进制直接交付。
2. **会维护（121~125）**：接口底层、切片陷阱、并发模式、测试、工程化——目标是「读得懂别人的 Go、改得动别人的 Go」，不是只会写自己的。
3. **会调优救火（131~136）**：GMP、GC、pprof、交付与事故复盘——目标是「Go 程序在生产上出了事，你有办法定位」，而不是重启碰运气。

## 值语义是 Go 的地基

Go 与 Python 最大的心智差异不是类型声明，是**值语义**：赋值与传参默认拷贝，slice/map 是例外（引用头结构）。理解了这一条：

- `append` 为什么有时改原数组有时不改（114 的切片三要素）；
- 方法为什么有时要指针接收者（115）；
- goroutine 里共享变量为什么必须同步（123 的 channel 与 131 的内存模型）。

判断框架：一段 Go 代码的行为看不懂时，先问「这里拷贝的是值还是头」，再谈并发。

## 错误是值，不是异常

Go 把错误当普通返回值处理，这决定了运维工具的可靠性上限：

- `if err != nil` 不省略——吞掉错误 = 静默失败（与「CICD」133 同型问题）；
- `%w` 包装建错误链，`errors.Is/As` 解包判定——上层能区分「网络断了」和「文件没了」（115 的错误包装链）；
- panic 只留给程序性 bug，可预期失败一律 error——常驻工具被 panic 打死是最廉价的故障。

## 并发可控才敢常驻

Go 的并发便宜（goroutine 起步 2KB），便宜不等于免费：

- **泄漏纪律**：每个 goroutine 都要有退出路径——channel 未关闭、ctx 未取消就是泄漏（123）；
- **共享纪律**：跨 goroutine 共享要么 channel 传递要么锁保护，「应该没事」不是同步原语；
- **观测纪律**：常驻工具自带 pprof 入口——内存/CPU 异常时你能拿出证据（133）。

## 反模式

- ❌ 用 Go 写一次性文本处理——awk/sed 一行的事，编译语言是负资产。
- ❌ 滥用 goroutine 池不设上限——并发便宜，但下游连接数不便宜。
- ❌ `_ = err` 静默吞错——出问题时连现场都没有。
- ❌ map 并发读写不加锁——fatal error 不是 panic，recover 也接不住。
- ❌ 不做交叉编译就交付——GOOS/GOARCH 矩阵在 135，二进制交付的第一步。

## 自测

1. 三条能力线各解决什么？（会写、会维护、会调优救火）
2. 值语义的核心例外是什么？（slice/map 引用头结构——append 行为的根源）
3. 为什么错误是值？（不吞错、可包装、可判定——常驻工具的可靠性上限）
4. goroutine 泄漏的根源是什么？（没有退出路径——未关闭 channel/未取消 ctx）
