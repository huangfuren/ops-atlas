## 1. 并发高级

### 1.1 原子操作

```go
import "sync/atomic"

var counter atomic.Int64
counter.Add(1)
counter.Load()
counter.Store(0)
counter.CompareAndSwap(old, new)

// 指针
var p atomic.Pointer[Config]
p.Store(cfg)
c := p.Load()
```

Go 1.19 起的 `atomic.Int64` 等类型比 `atomic.AddInt64(&x, 1)` 更安全——**旧的函数式 API 如果忘了用 `atomic.Load` 读，就会混入非原子读写**，竞态检测也查不出来。

**用原子操作替换锁的条件**：单个变量、操作简单（加减、交换）、不需要多个变量的原子性。

### 1.2 锁 vs channel 怎么选

| 场景 | 选 |
|---|---|
| 保护结构体的内部状态 | `sync.Mutex` |
| 传递数据所有权 | channel |
| 等待事件/信号 | channel + `close` |
| 限流、排队 | channel |
| 简单计数 | `atomic` |
| 读多写少的缓存 | `sync.RWMutex` 或 `sync.Map` |

**经验法则：用锁写出来的代码更短、更好读，就用锁。** "用 channel 才优雅"是误解——Go 官方也强调 channel 不是万能替代品。

### 1.3 RWMutex 的陷阱

`RWMutex` 在**读远多于写**时才比 Mutex 快。如果读写比例接近 1:1，RWMutex 因为内部维护读者计数反而更慢。

另一个坑：**读锁里不能再获取写锁**（会死锁），且 RWMutex 不支持锁升级：

```go
mu.RLock()
if needUpdate {
	mu.RUnlock()      // 必须先释放
	mu.Lock()
	// 重新检查条件（可能别人已经改了）
	mu.Unlock()
	mu.RLock()
}
```

### 1.4 单飞与缓存

```go
type Cache struct {
	mu   sync.RWMutex
	data map[string]string
	sf   singleflight.Group
}

func (c *Cache) Get(key string) (string, error) {
	c.mu.RLock()
	if v, ok := c.data[key]; ok {
		c.mu.RUnlock()
		return v, nil
	}
	c.mu.RUnlock()

	// 缓存未命中，同 key 只放一个请求到后端
	v, err, _ := c.sf.Do(key, func() (any, error) {
		return c.load(key)
	})
	if err != nil {
		return "", err
	}
	return v.(string), nil
}
```

这是缓存击穿的标准解法。注意 `singleflight` 期间**所有等待者共享同一个结果**，包括错误。

### 1.5 并发安全的数据结构

标准库只提供了 `sync.Map`。其他常用的在 `golang.org/x/sync`：

| 包 | 用途 |
|---|---|
| `errgroup` | 并发任务 + 错误传播 |
| `singleflight` | 请求合并 |
| `semaphore` | 加权信号量（按权重限流） |
| `sync/atomic` | 原子类型 |

第三方的高性能结构（`ants` 协程池、`fastcache`、`ristretto`）在需要时再引，别一开始就上。

## 2. 泛型

### 2.1 基本用法

```go
func Max[T int | float64 | string](a, b T) T {
	if a > b {
		return a
	}
	return b
}

// 类型集用 ~ 支持底层类型
type Number interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 | ~float32 | ~float64
}

func Sum[T Number](vs []T) T {
	var total T
	for _, v := range vs {
		total += v
	}
	return total
}

type MyInt int
Sum([]MyInt{1, 2})       // 可以，~int 覆盖了底层是 int 的类型
```

### 2.2 常用约束

```go
// comparable：可用 == 比较（map key 的要求）
func Contains[T comparable](s []T, v T) bool {
	for _, x := range s {
		if x == v {
			return true
		}
	}
	return false
}

// any：无约束
func Map[T, R any](s []T, f func(T) R) []R {
	out := make([]R, 0, len(s))
	for _, v := range s {
		out = append(out, f(v))
	}
	return out
}
```

`cmp.Ordered`（Go 1.21+）已经包含了所有可比较大小的类型，不用自己写 `Number`。

### 2.3 什么时候不该用泛型

| 场景 | 不要用泛型 |
|---|---|
| 只有一种类型 | 直接写具体类型 |
| 需要不同类型有不同逻辑 | 用接口 |
| 需要运行时类型判断 | 用 `any` + 类型断言 |
| 参数超过 3 个类型参数 | 泛型会变得比重复代码更难读 |

**泛型解决的是"逻辑完全相同、只有类型不同"的问题。** 一旦逻辑有分叉，就该用接口。

### 2.4 迭代器（Go 1.23+）

```go
func Count(n int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for i := 0; i < n; i++ {
			if !yield(i) {
				return
			}
		}
	}
}

for v := range Count(3) {
	fmt.Println(v)          // 0 1 2
}
```

`yield` 返回 false 表示调用方 break 了，生成方要立即停止——这是 `iter.Seq` 的约定。

## 3. 反射与 unsafe

### 3.1 反射三定律

```go
import "reflect"

var x float64 = 3.4
v := reflect.ValueOf(x)

v.Type()                 // float64
v.Kind()                 // reflect.Float64
v.Float()                // 3.4
v.CanSet()               // false —— 因为传的是副本

// 要修改必须传指针
p := reflect.ValueOf(&x)
p.Elem().SetFloat(7.1)
```

| 定律 | 内容 |
|---|---|
| 1 | 反射可以把接口值拆成 `Value` 和 `Type` |
| 2 | 反射对象可以还原成接口值（`Interface()`） |
| 3 | **要修改值，必须从指针出发**（`CanSet` 为 true） |

### 3.2 反射的代价与场景

| 指标 | 反射 vs 直接调用 |
|---|---|
| 耗时 | 慢 10-100 倍 |
| 分配 | 显著增加 |
| 编译期检查 | 完全没有 |

合理的用武之地：序列化库（json/yaml）、ORM、依赖注入、配置映射、通用校验。

**业务代码里不要用反射。** 需要类型分派用 `type switch`，需要动态行为用接口。

### 3.3 unsafe.Pointer 的三条规则

```go
// 1. *T1 → unsafe.Pointer → *T2（类型转换）
p := unsafe.Pointer(&floatVal)
intVal := (*int64)(p)

// 2. unsafe.Pointer ↔ uintptr（算偏移，但必须在同一个表达式里用）
// 3. 不要保存 uintptr 再转回 Pointer（GC 可能已经移动了对象）
```

生产代码里用 unsafe 的正当理由基本只有两个：

```go
// 1. 零拷贝 string ↔ []byte（性能关键路径，且已用 pprof 证明值得）
func StringToBytes(s string) []byte {
	return unsafe.Slice(unsafe.StringData(s), len(s))
}

// 2. 结构体对齐优化（减少 padding）
```

其余场合，性能收益抵不上维护成本和出错风险。**`unsafe` 一旦用错，是内存踩踏，不是报错。**

## 4. 常见坑：锁、泛型与 unsafe

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | 读写比例接近 1:1 仍用 RWMutex | 比 Mutex 更慢，读者计数本身有开销 | 只有读远多于写才用 RWMutex；否则直接 Mutex |
| 2 | 读锁里想再取写锁 | 直接死锁，程序挂住 | RWMutex 不支持锁升级；先 `RUnlock` 再 `Lock`，并重查条件 |
| 3 | 升级锁后不重查条件 | 用了别人已经改过的旧值 | `Lock` 之后必须重新判断，读锁期间的状态已失效 |
| 4 | 认为 channel 一定比锁优雅 | 代码更长、更难读，还多出 goroutine | 保护内部状态用 Mutex；channel 用于传所有权、等事件、限流 |
| 5 | 忽略 singleflight 的错误共享 | 一个请求失败，同 key 的所有等待者一起失败 | 明确是否要共享错误；需要各自重试就别合并 |
| 6 | 逻辑有分叉还硬套泛型 | 类型参数堆到 3 个以上，比重复代码更难读 | 泛型只解决「逻辑完全相同、只有类型不同」；有分叉用接口 |
| 7 | 反射传值后想改值 | `CanSet()` 为 false，改了不生效 | 从指针出发：`reflect.ValueOf(&x).Elem().Set...` |
| 8 | 保存 `uintptr` 之后再转回 `Pointer` | GC 移动对象后指针失效，内存踩踏 | `uintptr` 只能在同一表达式内用；不要跨语句存 |
| 9 | 业务代码里用反射做类型分派 | 慢 10~100 倍，且失去编译期检查 | 用 `type switch` 或接口；反射留给序列化、ORM、配置映射 |

## 5. 检查清单

| # | 问题 | 判据 |
|---|---|---|
| 1 | 该用锁还是 channel？判据是什么？ | 保护内部状态用 Mutex；传所有权/等事件/限流用 channel |
| 2 | 用 RWMutex 的前提是什么？ | 读远多于写；且代码里没有「读锁内升级写锁」的路径 |
| 3 | 缓存击穿怎么防？ | `singleflight` 按 key 合并；并清楚错误是否要被共享 |
| 4 | 泛型与该用接口的边界？ | 逻辑相同只有类型不同 → 泛型；逻辑有分叉 → 接口 |
| 5 | 反射改值为什么改不动？ | 传的是副本，`CanSet()` 为 false；必须从指针出发 |
| 6 | `unsafe` 用得正当吗？ | 只在零拷贝或对齐优化，且 pprof 已证明收益；否则不用 |
