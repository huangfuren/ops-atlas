## 3.1 为什么可写层不能放数据

001 §1.2/1.3 给过结论，这里把它变成三条硬理由，作为本册的出发点：

1. **寿命不匹配**：可写层随容器生、随容器死。`docker rm`、升级换镜像、节点迁移——任何一种"重建容器"都等于数据清零。而重建容器恰恰是容器化运维的日常（改参数、换版本、漂移到新节点）；
2. **性能不对路**：overlay2 的写时复制意味着首写要整文件拷贝，数据库这种持续大写的负载在可写层上是持续的 I/O 放大；
3. **备份对不上**：可写层藏在 `/var/lib/docker/overlay2/<id>/diff` 里，没有名字、没有元数据，备份系统既发现不了也恢复不了。

一句话：**可写层是给"临时产物"用的，凡是"关机再开机还要在"的数据，都必须绕过它**。绕过的通道有三种，就是 3.2 的三种挂载。

## 3.2 三种挂载：volume、bind mount、tmpfs 的取舍

| | volume | bind mount | tmpfs |
|---|---|---|---|
| 写法 | `-v mydata:/var/lib/mysql` | `-v /data/web:/usr/share/nginx/html` | `--tmpfs /run` |
| 存在哪 | Docker 管理区 `/var/lib/docker/volumes/` | 宿主任意目录 | 内存（不落盘） |
| 谁管生命周期 | Docker（有名字、可列出可备份） | 你自己（就是普通目录） | 容器停即消失 |
| 内容迁移 | 容易（卷可导出，3.7） | 目录级 rsync 即可 | 无需迁移 |
| 典型用途 | **数据库、有状态服务的数据** | 配置文件、代码热更新、日志落宿主 | 敏感临时数据、会话缓存 |

三条选择规则，覆盖 90% 的决策：

1. **应用产生的、要长期留的数据 → volume**；
2. **你提前准备好的、要灌进去的文件 → bind mount**（配置、静态资源、代码）；
3. **写了就行、不能落盘、丢了无所谓 → tmpfs**（比如放着 session 或临时密钥）。

一个容易忽略的细节：**同一个镜像重复 `docker run` 而不挂卷，每次都会得到一个空的匿名卷**——这是匿名卷垃圾的来源，3.8 收尾处理。

## 3.3 具名卷：创建、复用、查看内容

具名卷是 volume 的标准用法——起个名字，容器重建后按名字接回来：

```bash
# 显式创建
docker volume create mysql-data

# 运行时挂载（没预先创建也会自动建具名卷）
docker run -d --name mysql-prod -v mysql-data:/var/lib/mysql mysql:8.0

# 重建容器，数据原样接回
docker rm -f mysql-prod
docker run -d --name mysql-prod -v mysql-data:/var/lib/mysql mysql:8.0
```

管理命令四个，覆盖日常：

```bash
docker volume ls                    # 列出所有卷
docker volume inspect mysql-data    # 看挂载点路径（Mountpoint 字段）
docker volume rm mysql-data         # 删除（在用的卷会拒绝）
docker volume prune                 # 清理所有未被引用的卷 ⚠️ 删的是数据
```

`inspect` 的 `Mountpoint` 告诉你数据实际躺在 `/var/lib/docker/volumes/mysql-data/_data`——排障时直接进这个目录 `du`/`ls` 完全合法，但要清楚：**绕过容器直接写这个目录，属主和权限容易写坏**，紧急取证可以，长期操作走容器。

## 3.4 bind mount：挂代码热更新、挂配置文件、`:ro` 只读

bind mount 把宿主任意目录/文件原样映射进容器，三种典型场景：

**① 代码热更新（开发场景）**：

```bash
docker run -d --name web -p 8080:80 -v $(pwd)/src:/usr/share/nginx/html nginx:alpine
```

宿主改一个 HTML 文件，容器里立刻生效——因为就是同一个目录。生产不用这个姿势（代码进镜像），但本地联调它最快。

**② 配置文件下发**：

```bash
-v /etc/myapp/nginx.conf:/etc/nginx/nginx.conf:ro
```

**:ro（read-only）是配置挂载的默认姿势**：容器里应该读配置，不应该写配置——被改写的配置文件既是故障也是安全隐患。

**③ 日志落宿主**：`-v /var/log/myapp:/var/log/myapp`，让宿主的日志采集（rsyslog/filebeat）不用感知容器存在。

CentOS 的 SELinux 注记：bind mount 的文件带 SELinux 标签，容器进程默认读不到宿主文件。解决是在挂载后缀加 `:z`（共享标签，多容器可读）或 `:Z`（私有标签，仅本容器）：

```bash
-v /data/web:/usr/share/nginx/html:Z
```

Ubuntu 无此问题。加了 `:z/:Z` 的宿主目录标签会被**递归改写**，对挂系统关键目录要谨慎。

## 3.5 挂载的权限与属主：容器内 UID 与宿主文件的关系

bind mount 最常翻车的地方：容器里写不进挂载目录，或写出来的文件宿主上"没人认识"。

原因一句话：**容器内外只有 UID 数字是同一个，用户名是各看各的**。容器里 `app` 用户的 UID 若是 1000，它写出的文件在宿主上属主就是"UID 1000 对应的名字"（可能是 `nobody`，可能是你）；反过来，宿主目录属主是 UID 1000，容器里 UID 是 33 的 nginx 进程就写不进。

处理办法按场景选：

| 场景 | 办法 |
|---|---|
| 镜像是自己的 | 构建时对齐 UID：`USER 1000`，宿主目录 `chown 1000` |
| 官方镜像不可改 | bind mount 场景调整宿主目录属主；volume 场景多数量名卷首启由镜像初始化属主 |
| 只是读取 | `:ro` 挂载 + 宿主给 others 读权限 |

MySQL 官方镜像是个好范例：首启检测到空的 volume，会用镜像内 mysql 用户的 UID 去初始化属主——所以官方镜像 + 具名卷几乎不踩权限坑；自己挂 bind mount 才需要手动对齐。

## 3.6 数据库容器的数据目录：必须卷化的清单

不同应用"必须留在卷里的路径"不一样，把常用的列成清单（挂载目标一律用卷，别用可写层）：

| 应用 | 数据路径 | 说明 |
|---|---|---|
| MySQL 8.0 | `/var/lib/mysql` | 数据 + redo/undo 都在这 |
| PostgreSQL | `/var/lib/postgresql/data` | 注意 PG 的 PGDATA 常挂到这个目录 |
| Redis | `/data` | RDB/AOF 落盘点 |
| MongoDB | `/data/db` | |
| Nginx | `/etc/nginx`（配置）、`/var/log/nginx`（日志） | 配置 `:ro` |

验证卷化有没有生效的土办法：**写点数据 → `docker rm -f` → 重建 → 数据还在**。这一步既是验证也是演练，005 册的升级流程里它是标准动作。

## 3.7 备份与迁移：一条 tar 命令导出卷

卷的备份不需要停容器（一致性要求高的场景例外，见下），用临时容器把卷打成 tar：

```bash
docker run --rm \
  -v mysql-data:/source:ro \
  -v /backup:/backup \
  alpine tar czf /backup/mysql-data-$(date +%F).tar.gz -C /source .
```

读法：起一个 alpine 临时容器，把 `mysql-data` 卷以只读方式挂成 `/source`，把宿主 `/backup` 挂成 `/backup`，在里面打包。`--rm` 保证临时容器用完即删。恢复就是反向：

```bash
docker run --rm \
  -v mysql-data:/target \
  -v /backup:/backup:ro \
  alpine tar xzf /backup/mysql-data-2026-10-31.tar.gz -C /target
```

一致性注意：上面这样备份**正在写入的数据库卷，得到的是"任意时刻"的状态**，不是一致性快照。数据库类要么走数据库自己的备份工具（mysqldump / XtraBackup，见「数据库」005——容器只改变命令的执行位置，不改变备份原理），要么先 `docker pause` 冻结再打包。

迁移到另一台机器：把 tar 包 `scp` 过去，在目标机先 `docker volume create` 同名卷再解包。

## 3.8 匿名卷垃圾：怎么找出来、怎么清

三种卷垃圾里最常见的：**匿名卷（anonymous volume）**——`docker run` 时不带 `-v` 但镜像声明了 VOLUME（如 mysql 镜像），或 `-v /var/lib/mysql` 只写了容器路径。它们有 64 位哈希当名字，没人认领。

排查与清理：

```bash
docker volume ls -f dangling=true     # 找出所有无引用卷
docker volume rm <name>               # 逐个确认后删
docker volume prune                   # ⚠️ 一把全清 dangling 卷
```

**`prune` 删的是真数据**：执行前必须逐个 `docker volume inspect` 确认哈希卷不是某个在用容器丢下来的。纪律是：**具名卷 + 显式管理，让 dangling 列表永远接近空**——列表不空说明有操作不规范，先查清楚再清。

## 3.9 八个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 数据写可写层没挂卷 | 重建容器数据清零 | 有状态数据一律具名卷（3.1） |
| 2 | `docker volume prune` 当普通清理跑 | 在用的孤儿卷数据被删 | 先 `ls -f dangling` 逐个确认 |
| 3 | bind mount 挂单个文件后重建 | 编辑器/挂载点 inode 更换，容器里看到旧文件 | 挂目录不挂单文件，或重建容器 |
| 4 | 配置文件挂载忘 `:ro` | 容器内进程改写配置，故障难复现 | 配置一律只读 |
| 5 | SELinux 机器上 bind mount 读不到 | 权限明明 644 还是 Permission denied | 后缀 `:z` / `:Z` |
| 6 | 容器内外 UID 对不上 | 写不进 / 文件属主变 nobody | 对齐 UID 或卷内初始化（3.5） |
| 7 | 备份"正在写的数据库卷"当一致性备份 | 恢复出来的是撕裂状态 | 数据库走自身备份工具，或先 pause |
| 8 | 卷挂在 `/var/lib/docker` 同盘 | 磁盘满连累镜像与容器，扩容互相拖 | 数据卷大盘单独规划（与 004 §4.7 呼应） |

第 3 条展开一下，它非常反直觉：bind mount 挂**单个文件**时，Docker 记住的是文件的 inode。`vim` 保存配置时会"写临时文件再改名"，inode 换了，而容器里还绑着旧 inode——你怎么改容器里都看不到新内容，`docker restart` 都没用（重启不换挂载点）。**挂目录永远比挂单文件可靠**；必须挂单文件的（如 `/etc/resolv.conf` 类），改完配置 `docker restart` 不行就直接重建容器。
