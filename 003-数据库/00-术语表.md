# 00 术语表

> **这一文档回答**：某个词是什么意思、两个长得像的概念差在哪、「只知道现象、不知道该翻哪一篇」时往哪走。  
> **怎么用**：三种查法——按名字（下面按篇分组）、按英文或缩写（缩写速查）、按现象（症状反查）。  
> **只有一句话**：要原理和命令回对应篇；这里只保证你「认得出、分得清、找得到」。

## 000 数据库全貌

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 关系型 OLTP | relational database | 行存 + 事务 + SQL。业务主库，MySQL / PostgreSQL / Oracle 都在这类 |
| 缓存 / 键值 | cache / key-value store | 挡在数据库读前面的内存库。Redis 是事实标准，etcd 是配置协调用的另一路 |
| 文档型 | document database | 无固定表结构，按 JSON 类文档存。主流基本只有 MongoDB |
| 分析型 OLAP / MPP | analytical / Massively Parallel Processing | 报表与大屏用的列存库。ClickHouse / Doris / StarRocks / Greenplum |
| HTAP | Hybrid Transactional / Analytical Processing | 交易与分析一体。TiDB / OceanBase / PolarDB，只当交易库用就按关系型对待 |
| 检索引擎 | search engine | 倒排索引做全文检索。Elasticsearch，日志与搜索 |
| 时序数据库 | time-series database | 按时间线优化的库，监控指标用。InfluxDB / TDengine / VictoriaMetrics |
| 国产数据库 | domestic database | 达梦 / 人大金仓 / openGauss / GaussDB / TDSQL / OceanBase 等，运维经验不能直接从 MySQL 平移，要看它是哪一派 |
| 信创 | Xinchuang（信息技术应用创新） | 国产化替代的合规要求。选型约束见 000 §0.9 |
| 云数据库 RDS | Relational Database Service | 云厂商托管的 MySQL / PG。内核还是那个，**你不再管备份机器与高可用搭建，但参数、慢查、账号还在你手上**（000 §0.15） |

## 001 MySQL 架构与基础

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| Server 层 | server layer | 连接器、分析器、优化器、执行器所在层，管「SQL 怎么执行」，与存储引擎解耦 |
| 存储引擎层 | storage engine | 真正存数据取数据的层。MySQL 只认真考虑 InnoDB |
| InnoDB | InnoDB | 默认且几乎唯一该用的引擎：事务、行锁、崩溃恢复都靠它 |
| WAL | Write-Ahead Logging | 先写日志再刷数据页。崩溃恢复和顺序写性能都靠它 |
| buffer pool | buffer pool | InnoDB 的内存数据页缓存。读命中在这里，大小就是 `innodb_buffer_pool_size` |
| 表空间 | tablespace (.ibd) | 表的物理文件。8.0 默认每表一个 `.ibd` |
| redo log | redo log | 物理页变更日志，**崩溃恢复**用，循环写 |
| undo log | undo log | 旧版本日志，回滚和 MVCC 都靠它，长事务会让它无限增长 |
| binlog | binary log | Server 层的逻辑变更日志，**主从复制、时间点恢复、误删找回**全靠它，追加写 |
| error log | error log | 第一现场。服务起不来、莫名重启，先看它 |
| slow query log | slow query log | 超过 `long_query_time` 的 SQL。数据库慢先开它 |
| general log | general log | 所有到达的 SQL。临时抓请求用，**生产慎开**，磁盘杀手 |

## 002 SQL 与数据类型

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| DDL | Data Definition Language | 建表改表结构。会锁元数据，大表上执行要慎重（004 的 MDL） |
| DML | Data Manipulation Language | 增删改查数据。`UPDATE`/`DELETE` 不带 WHERE 是运维头号事故 |
| JOIN | join | 按关联键拼两张表。运维看得懂 INNER / LEFT 就够，性能归 003 |
| 聚合与分组 | aggregation / GROUP BY | `COUNT`/`SUM` 按维度汇总。巡检报表的常用 SQL 都在这 |
| 字符集 | charset | 存中文用 **utf8mb4**，MySQL 的 `utf8` 是残缺的三字节实现 |
| 排序规则 | collation | 字符怎么比大小、怎么排序。同列混排序规则会导致索引失效 |
| 隐式转换 | implicit conversion | 类型不一致时 MySQL 偷偷转。字符串列传数字会让索引失效（003 §3.6） |
| 深翻页 | deep pagination | `LIMIT 1000000, 10` 要扫过前 100 万行才取 10 行。解法是游标或子查询定位（002 §2.10） |
| 大表变更 | large table alteration | 大表加字段 / 加索引走 Online DDL 或 gh-ost，见 008 §8.2 |

## 003 索引与执行计划

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| B+ 树 | B+ tree | InnoDB 索引的数据结构。矮胖多叉，叶子节点串成有序链表 |
| 聚簇索引 | clustered index | 主键索引，叶子节点就是整行数据。**表本身就是按主键组织的一棵 B+ 树** |
| 二级索引 | secondary index | 主键以外的索引，叶子存的是主键值而不是整行 |
| 回表 | back to table | 二级索引查到主键后，再去聚簇索引取整行。回表次数多就慢 |
| 覆盖索引 | covering index | 查的列都在索引里，不用回表。`EXPLAIN` 的 `Extra` 显示 `Using index` |
| 联合索引 | composite index | 多列组成的索引。**按最左前缀生效**，顺序不是随便排的 |
| 最左前缀 | leftmost prefix | 联合索引 (a,b,c) 只能命中「从 a 开始连续」的条件，跳过 a 就用不上 |
| 索引失效 | index invalid | 八种情况让索引用不上：函数包裹、隐式转换、前导 `%`、`OR` 混列等（003 §3.6） |
| EXPLAIN | EXPLAIN | 看执行计划的命令。重点看 `type`、`key`、`rows`、`Extra` 四列 |
| type（访问类型） | access type | 从 `system/const` 到 `index/ALL` 的扫描等级。**出现 ALL 就是全表扫** |
| Extra | Extra | 执行计划的第二重要列。`Using filesort`、`Using temporary` 都是要警惕的信号 |
| EXPLAIN ANALYZE | EXPLAIN ANALYZE | 8.0 起真跑一遍给实际耗时，计划与实际对不上时用它 |
| 选择性 | selectivity | 列里不同值的占比。选择性太低的列（如性别）建索引不值得 |

## 004 事务、锁与 MVCC

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| ACID | Atomicity / Consistency / Isolation / Durability | 原子、一致、隔离、持久。四个字母各对应一类机制与一类故障 |
| 隔离级别 | isolation level | RU / RC / RR / Serializable 四档。MySQL 默认 RR，**生产很多团队改用 RC**（004 §4.4） |
| 脏读 | dirty read | 读到别人还没提交的数据。最低级别才有 |
| 不可重复读 | non-repeatable read | 同一事务里两次读结果不一样（别人改了已提交的） |
| 幻读 | phantom read | 两次范围查询行数不一样（别人插了新行）。RR 下靠间隙锁缓解 |
| MVCC | Multi-Version Concurrency Control | 多版本并发控制，**读不加锁**的原因：靠 undo 旧版本 + Read View 拍快照 |
| Read View | read view | 事务开始时拍下的「哪些版本对我可见」的判断依据 |
| S 锁 / X 锁 | shared / exclusive lock | 读锁共享、写锁排他。S 之间兼容，遇到 X 全互斥 |
| 意向锁 | intention lock | 表级的「我在行上加锁了」声明，让表锁判断不用逐行扫 |
| 间隙锁 / Next-Key | gap lock / next-key lock | 锁住记录之间的空隙，防止插入造成幻读。RR 特有，也是死锁高发区 |
| 死锁 | deadlock | 两个事务互相等对方手里的锁。InnoDB 自动挑一个回滚，`SHOW ENGINE INNODB STATUS` 看 |
| MDL | Metadata Lock | 元数据锁。**长事务没结束，DDL 拿不到 MDL，后面的所有查询全被堵死**（004 §4.8） |
| 长事务 | long-running transaction | 开着不提交的事务。undo 不敢清、MDL 占着、MVCC 版本堆着，三宗罪 |

## 005 备份恢复与数据迁移

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 逻辑备份 | logical backup | 导出 SQL 语句。mysqldump，慢但跨版本、可读 |
| 物理备份 | physical backup | 直接拷数据文件。XtraBackup，快但受版本与平台限制 |
| 全量 / 增量 | full / incremental backup | 整库一份 / 只备上次以来的变化。XtraBackup 支持增量，mysqldump 没有 |
| `--single-transaction` | — | mysqldump 的关键参数：在一个一致性快照里导 InnoDB，**不锁表** |
| PITR | Point-In-Time Recovery | 时间点恢复：全量备份 + 重放 binlog 到出事前一刻 |
| GTID | Global Transaction Identifier | 全局事务编号，复制与恢复按事务定位，**比文件名+位点可靠得多** |
| 备份验证 | backup verification | 备份文件能打开 ≠ 能用。定期恢复到临时实例验一遍 |
| 恢复演练 | restore drill | 真的恢复一次并验数据。**没演练过的备份不算备份** |
| 误删找回 | accidental deletion recovery | binlog 还在就有救：先停写入 → 找最近全量 → 重放 binlog 到误删前 |
| 数据迁移 | data migration | 换库 / 换机 / 上云。停机窗口、双写、校验三类方案（005 §5.9） |

## 006 主从复制与高可用

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 主从复制 | replication | 主库写、从库实时重放。高可用与读写分离的基础 |
| Binlog Dump 线程 | binlog dump thread | **主库**上的线程：读 binlog 发给从库 |
| IO 线程 | IO thread | **从库**上的线程：接收 binlog 写成本地 relay log |
| SQL 线程 | SQL thread | **从库**上的线程：重放 relay log。延迟通常就卡在这 |
| relay log | relay log | 从库的中转 binlog。看到它堆积说明 SQL 线程重放不过来 |
| 异步复制 | asynchronous replication | 默认模式：主库提交就返回，不等从库。最快，宕机可能丢最新数据 |
| 半同步复制 | semi-sync replication | 至少一个从库确认收到 binlog 才返回。对数据敏感的场景用它 |
| 组复制 MGR | Group Replication | 多数派表决的复制，8.0 的官方高可用方案 |
| 主从延迟 | replication lag | 从库重放跟不上主库。六大原因见 006 §6.5，`Seconds_Behind_Master` 看数 |
| `Seconds_Behind_Master` | — | `SHOW SLAVE STATUS` 里的延迟秒数。**0 不一定没延迟**，大事务会骗它 |
| pt-table-checksum | — | 主从数据一致性校验工具。延迟清零 ≠ 数据一致 |
| 故障切换 | failover | 主库挂了，把一台从库提升为新主。切完**务必校验**旧主不会复活写入 |
| 读写分离 | read/write splitting | 写主库、读从库。坑在主从延迟：刚写完就读，读到旧数据（006 §6.8） |
| VIP | Virtual IP | 浮动的虚拟 IP。切换时 VIP 漂到新主，应用不用改配置 |

## 007 性能诊断与优化

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 慢查询 | slow query | 超过 `long_query_time` 的 SQL。分析入口，不是问题本身 |
| QPS / TPS | Queries / Transactions Per Second | 每秒查询数 / 事务数。先问清楚指标口径再对比 |
| pt-query-digest | — | 慢日志聚合分析工具。按指纹汇总，看 TOP SQL 而不是逐条看 |
| performance_schema | performance schema | 8.0 内置的运行时统计库：谁在等锁、哪条 SQL 耗在哪一步 |
| sys 库 | sys schema | performance_schema 的「人话视图」，日常巡检从这查 |
| 参数调优 | parameter tuning | buffer pool 大小、redo 大小、连接数。**先 SQL 后参数，顺序不能反**（007 §7.6） |
| SQL 改写 | SQL rewriting | 七招：覆盖索引、拆深翻页、改写子查询等。多数慢查是写法问题不是参数问题 |
| 锁等待 | lock wait | `sys.innodb_lock_waits` 直接看谁堵谁 |

## 008 日常运维与故障处理

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 巡检 | routine inspection | 每天固定看的几项：错误日志、慢查询、主从延迟、磁盘水位（008 §8.1） |
| 变更管理 | change management | 改动先评审、可回滚、有人盯。**十个故障一半来自没走流程的变更** |
| 故障剧本 | runbook | 预先写好的处置步骤。出事时照单执行，不临场发挥（008 §8.3 十个剧本） |
| 容量规划 | capacity planning | 磁盘 / 连接数 / 内存水位提前规划，别等报警再扩 |
| 最小权限 | least privilege | 账号只给需要的库和权限。`GRANT ALL ON *.*` 是事故放大器 |
| Online DDL | online DDL | 8.0 大部分 DDL 不锁表，但拿 MDL 那一下仍可能被长事务卡住 |
| gh-ost / pt-osc | — | 大表变更的影子表工具：建新表 → 拷数据 → 原子改名，全程可控可暂停 |
| 版本升级 | version upgrade | 5.7 → 8.0 是跨版本：先看废弃参数与字符集默认值变化（008 §8.6） |

## 009 其他数据库

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 流复制 | streaming replication | PostgreSQL 的主从复制，物理复制，和 MySQL 逻辑复制思路不同 |
| VACUUM | VACUUM | PG 的 MVCC 靠旧版本留在表里，VACUUM 负责清。不跑表会膨胀（与 MySQL undo 的区别） |
| RDB | Redis Database (snapshot) | Redis 的快照持久化，定时全量落盘。宕机丢最后一段 |
| AOF | Append Only File | Redis 的命令日志持久化。比 RDB 丢得少，文件大恢复慢 |
| 大 Key | big key | 单个 value 过大的 Redis 键。删除与迁移都会卡住实例 |
| 缓存穿透 | cache penetration | 查**不存在**的数，缓存永远不命中全打到 DB。布隆过滤器或缓存空值 |
| 缓存击穿 | cache breakdown | 一个**热 key 过期**瞬间，请求全压到 DB。互斥重建或逻辑过期 |
| 缓存雪崩 | cache avalanche | **大批 key 同时过期**或缓存整体挂掉。过期时间加随机、多级缓存 |
| 副本集 | replica set | MongoDB 的高可用单元，主节点挂了自动选举 |

## 最容易混的 16 对

数据库的困惑多半是成对的。这张表只回答「差别在哪、怎么一眼确认」。

| 容易混 | 一句话差别 | 怎么确认 | 篇 |
| --- | --- | --- | --- |
| redo log vs binlog | InnoDB 物理页日志，管崩溃恢复 / Server 层逻辑日志，管复制与恢复 | 文件名 `ib_logfile*` vs `binlog.000001` | 001 |
| redo log vs undo log | 重放已提交的变更 / 回滚未提交的并供 MVCC 读旧版本 | 崩溃恢复看 redo，长事务膨胀看 undo | 001 / 004 |
| binlog vs relay log | 主库写的 / 从库收下来再重放的 | `SHOW SLAVE STATUS` 看 `Relay_Master_Log_File` | 006 |
| drop vs truncate vs delete | 连表删（可闪回难）/ 清空表保留结构（DDL，快）/ 逐行删可带 WHERE | 删了想找回只有 binlog 一条路 | 002 / 005 |
| 字符集 vs 排序规则 | 字符怎么编码存储 / 字符怎么比较排序 | `SHOW CREATE TABLE` 里 `CHARSET` 与 `COLLATE` | 002 |
| 聚簇索引 vs 二级索引 | 叶子是整行 / 叶子是主键值 | 二级索引查询多一步「回表」 | 003 |
| 回表 vs 覆盖索引 | 拿主键再查一次 / 索引里就有不用回去 | `Extra`：无提示 vs `Using index` | 003 |
| RR vs RC | MySQL 默认可重复读 / 生产常用读已提交 | `SELECT @@transaction_isolation` | 004 |
| 死锁 vs 锁等待 | 互相等，自动回滚一个 / 单向等，等超时 | 报错 `Deadlock found` vs `Lock wait timeout` | 004 |
| MDL vs 行锁 | 锁的是表结构定义 / 锁的是数据行 | DDL 被堵查 MDL，`UPDATE` 被堵查锁等待 | 004 |
| 逻辑备份 vs 物理备份 | 导出 SQL 语句 / 拷贝物理文件 | mysqldump 生成 `.sql` vs XtraBackup 生成数据目录 | 005 |
| 异步 vs 半同步复制 | 提交即返回 / 至少一个从库确认才返回 | `Rpl_semi_sync_master_status` | 006 |
| 主从延迟 vs 数据不一致 | 重放滞后，会追上 / 重放过了但结果不同 | `Seconds_Behind_Master` vs `pt-table-checksum` | 006 |
| QPS vs TPS | 每秒 SQL 请求数 / 每秒事务数 | 一个请求可能含多条 SQL，口径先问清 | 007 |
| 慢日志 vs general log | 只记超阈值的 / 全都记 | 生产只常开慢日志 | 001 / 007 |
| 穿透 vs 击穿 vs 雪崩 | 查不存在的 key / 单个热 key 过期 / 大批 key 同时失效 | 布隆过滤 / 互斥重建 / 过期加随机 | 009 |

## 按症状反查

值班时只有一个现象、不知道该翻哪一篇，从这里进。

| 现象 | 大概是 | 去哪 |
| --- | --- | --- |
| 服务起不来 / 莫名重启 | error log 第一现场 | 001 §1.5 → 008 §8.3 |
| 突然全体查询变慢 | 慢日志 + 系统资源两头看 | 007 §7.1 / §7.2 |
| 单条 SQL 慢，别的正常 | 执行计划问题：`type=ALL`、回表多、索引失效 | 003 §3.7–3.8 |
| 分页越往后越慢 | 深翻页 | 002 §2.10 |
| `UPDATE` / `DELETE` 卡住不动 | 行锁等待 | 004 §4.10 |
| DDL 卡住，后面查询全堵 | 长事务压着 MDL | 004 §4.8 |
