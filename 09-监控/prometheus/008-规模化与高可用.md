# 008 规模化与高可用

> **解决**：监控对象从几十台涨到几千台，一台 Prometheus 存不下、查不动、挂不起——怎么扩。

> **口径**：先用好单机再谈扩展——绝大多数"Prometheus 撑不住"是基数问题，不是规模问题。

## 8.1 单机的天花板：先确认真的需要扩展

Prometheus 是单机数据库——它没有"分布式模式"，扩展全部靠外围架构。但先别急着上架构，对照症状定位瓶颈：

| 症状 | 瓶颈 | 先做的动作 |
|---|---|---|
| 内存持续上涨直到 OOM | active series 基数 | 查 `/api/v1/status/tsdb`（8.5） |
| 查询越来越慢、超时 | 查询扫的 series 太多 / 磁盘 IO | 预聚合 recording rule（006 §6.1） |
| 磁盘涨满 | retention 过长或样本量过大 | 缩 retention 或降采样 |
| 重启后追不上 WAL | 崩溃前写入量太大 | 减基数，不是加机器 |

**单机的经验量级**：百万级 active series、15s 抓取间隔、本地保留 15 天，是一台 8C16G 机器可以舒服跑掉的规模。低于这个量级，把 8.5 的基数治理做扎实，比上任何分布式方案都有效。

Prometheus 自身也要被监控（meta-monitoring）：`prometheus_tsdb_head_series`（当前基数）、`prometheus_tsdb_head_samples_appended_total`（写入速率）、`process_resident_memory_bytes`。这几条指标是 8.6 容量估算的原始数据。

## 8.2 HA 双实例：最便宜的高可用

Prometheus 官方推荐的高可用不是集群，而是**两台配置完全相同的实例抓同一批 target**。数据双份、查询任选一台、挂一台不影响采集：

```yaml
# prom-1 与 prom-2 的唯一区别：
global:
  external_labels:
    replica: A        # 实例 2 配 replica: B

alerting:
  alertmanagers:
    - static_configs:
        - targets: [alertmanager:9093]
  # 关键：把 replica 标签从告警里去掉，Alertmanager 才能去重
  alert_relabel_configs:
    - action: labeldrop
      regex: replica
```

三个要点：

1. **告警去重靠 Alertmanager**：两台实例发出 labels 完全相同的告警，Alertmanager 的 group 机制天然去重（006 §6.4）。但 `replica` 标签必须先用 `alert_relabel_configs` 剥掉——否则两台的 labels 不同，去重失效，告警翻倍。
2. **查询侧不做自动 failover 也能用**：Grafana 配两台任选一台；要真正的查询高可用，把两台都接入 8.4 的全局查询层（Thanos Query 自动按 `replica` 标签去重）。
3. **存储是双份的**：本地磁盘各存一份，成本 ×2。这换来了"任一实例随时可死"的简单性，是中小规模的性价比之选。

它的局限：本地存储的 retention 有限（磁盘换Retention不划算），历史数据要长期留存就得进 8.4。

## 8.3 Federation：层级式聚合

Federation 让上层 Prometheus 定期拉取下层的**部分指标**，形成树状结构：

```yaml
# 上层（全局）Prometheus 的配置
scrape_configs:
  - job_name: federate
    honor_labels: true
    metrics_path: /federate
    params:
      'match[]':
        - '{__name__=~"job:.*"}'      # 只拉 recording rule 产物
        - 'up'
    static_configs:
      - targets:
          - prom-dc1:9090
          - prom-dc2:9090
```

**纪律：只 federate 聚合结果，不 federate 原始明细**。下层的 recording rule（`job:node_cpu:sum_util` 这类 `job:` 前缀命名）预先算好聚合值，上层只拉这些——如果把原始 series 全拉上来，上层立刻被打爆，等于把规模问题平移。

适用判断：

| 场景 | 适合吗 |
|---|---|
| 总部只看各机房的汇总大盘 | ✅ 典型场景 |
| 按团队分区域采集，全局只看 SLO | ✅ |
| 想"全局任意查询任意明细" | ❌ 用 8.4 的全局查询层 |
| 历史数据长期留存 | ❌ Federation 不负责存储，明细留在下层 |

## 8.4 Remote write 与长期存储：Thanos / Mimir / VictoriaMetrics

本地 TSDB 只适合短期数据。长期存储的标准做法是 **remote write 把样本流式推给专职存储**，Prometheus 本地只留短期热数据：

```yaml
remote_write:
  - url: http://vminsert:8480/insert/0/prometheus   # 以 VictoriaMetrics 为例
    queue_config:
      max_samples_per_send: 10000
      capacity: 20000
```

三个主流方案的定位：

| 方案 | 架构形态 | 存储介质 | 运维复杂度 | 适合谁 |
|---|---|---|---|---|
| **Thanos** | Prometheus 旁挂 Sidecar，把本地块上传对象存储，Query 聚合全局视图 | 对象存储（S3/MinIO） | 中（组件多：Sidecar/Query/Compactor/Store Gateway） | 已有多台 Prometheus 想要全局查询与去重 |
| **Mimir** | 原生水平扩展集群，写路径分片 | 对象存储 | 中高（多组件 + 多租户配置） | 大规模、多团队多租户 |
| **VictoriaMetrics** | 单二进制（集群版三角色：vminsert/vmselect/vmstorage） | 自有格式（本地盘或 NFS） | 低（资源占用约为前两者几分之一） | 想要"最低运维成本扛大规模" |

选型口径一句话：**小规模要全局查询选 Thanos（贴着 Prometheus 原生走），大规模省资源选 VictoriaMetrics，多租户大团队选 Mimir**。三者都兼容 PromQL（VM 有少量函数差异），Grafana 侧几乎无感。

配合 8.2 的 HA：Thanos 的 Query 会按 external label `replica=A/B` 自动去重——这就是 8.2 里两台实例要配不同 `replica` 的原因；而告警通道里那个标签被 `alert_relabel_configs` 剥掉，两条路各取所需。

## 8.5 基数治理：九成的"规模问题"

**Cardinality（基数）= 一个指标下所有 label 组合出的 series 总数**。它是单机 Prometheus 的头号杀手：一个 `http_requests_total` 加上 `user_id` 标签，基数就从几十涨到几百万。

诊断入口：

```bash
# TSDB 状态：基数最高的指标与 label 值
curl -s http://prom:9090/api/v1/status/tsdb | head -100

# 当前 head 里的 series 总数（Prometheus 自监控指标）
prometheus_tsdb_head_series
```

高危 label 清单（出现即报警）：

| 危险 label | 为什么 |
|---|---|
| `user_id` / `uuid` / `email` | 值域无界，用户有多少 series 就有多少 |
| `pod` 名带随机后缀 | 重建即换值，旧 series 变僵尸 |
| 错误信息 / URL 原文 | 一个新错误一种新值 |
| `container_id` / `trace_id` | 值域等于实例数 × 生命周期 |

治理三板斧：

1. **抓取侧丢弃**（`metric_relabel_configs`，在样本进 TSDB 之前生效）：

```yaml
scrape_configs:
  - job_name: app
    metric_relabel_configs:
      - action: labeldrop
        regex: 'pod_uid|container_id|trace_id'
```

2. **预聚合**：高频查询的明细 series 用 recording rule 聚合成低基数指标（006 §6.1），面板与告警只查聚合结果。
3. **流程卡口**：业务指标上线前过一遍基数评审——"这个 label 的值域有多大？"是和"这个接口的 SLA 是多少"同级的问题。

## 8.6 容量估算与多集群选型

估算公式（经验值，落地前以自监控实测校准）：

| 项 | 估算 | 例子（100 万 series，15s，15 天） |
|---|---|---|
| 样本速率 | series ÷ 抓取间隔 | ≈ 6.7 万 samples/s |
| 内存 | series × 2~4 KB（head 区）+ 查询缓冲 | 8~16 GB |
| 磁盘 | samples × 1~2 B（压缩后）× 保留期 | 100~150 GB |

按规模选架构的决策表：

| 规模 / 需求 | 方案 |
|---|---|
| < 50 万 series，单机房 | 单机 + 本地存储，把基数治理做实 |
| 50 万~300 万，要求监控自身不中断 | 8.2 的 HA 双实例 |
| 多机房 / 多集群要全局查询与长期历史 | remote write（8.4）+ Thanos 或 VM |
| 每百万 series 磁盘预算敏感 | VictoriaMetrics（压缩率高于 Thanos 数倍） |
| 团队多、租户隔离硬需求 | Mimir 多租户 |

K8s 内多集群的常见拓扑：**每个集群一套独立 Prometheus（HA 双实例），remote write 到中央 VictoriaMetrics/Thanos**；中央层只做存储与全局查询，告警在各集群本地算（网络分区时本地告警仍然工作）。

## 8.7 六个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | HA 两台 external label 不一致又没剥 | 告警全部翻倍 | `alert_relabel_configs` 剥掉 `replica` |
| 2 | Federation 拉原始明细 | 上层被打爆，规模问题平移 | 只 federate recording rule 产物 |
| 3 | remote write 队列堆积才发现 | 数据悄悄丢失，历史有洞 | 监控 `prometheus_remote_storage_*` 指标 |
| 4 | 高基数 label 上线才爆 | 内存暴涨、OOM，全网监控瘫痪 | 基数评审 + `/api/v1/status/tsdb` 巡检 |
| 5 | 对象存储不配降采样 | 存储成本随时间线性失控 | Compactor 配 5m/1h 降采样块 |
| 6 | Prometheus 自身无监控 | 挂了没人知道，监控全盲 | 自监控 job + meta 告警（head series、WAL） |

第 1 条展开：这是 HA 方案里最高频的事故。两台 Prometheus 发出 labels 仅差一个 `replica=A/B` 的相同告警，Alertmanager 视为两组不同告警各发各的——值班手机响两遍，且恢复通知也两遍。解法就一行 `alert_relabel_configs`，务必在第一次配 HA 时就写上。
