## 0.1 运维为什么用 Python：生态位决定

不是"Python 好"所以要学，而是**运维的周边生态长在 Python 上**：写 Ansible 模块、改 ELK 采集脚本、调云 SDK（阿里云/boto3）、给监控写自定义 exporter、读同事留下的历史脚本——这些场景的材料全是 Python。不会它，你只能"用"这些工具而不能"改"。

第二个理由是**能力空档**：Shell 擅长拼命令，超过 100 行就开始失控（状态、错误处理、数据结构都要命）；Go 适合常驻服务与高并发，写个"调 API 拉数据出报表"又太重。**20–500 行、有逻辑、要调 API、要处理数据**——这个区间是 Python 的舒适区。

## 0.2 三语言分工：Shell / Python / Go

| | Shell | Python | Go |
|---|---|---|---|
| 舒适区 | < 20 行的命令胶水 | 20–500 行的逻辑脚本与工具 | 并发、常驻、跨平台二进制 |
| 强项 | 管道串联、系统命令即语言 | 生态（API/数据/解析）、可读、可测试 | 编译单文件、并发、内存 |
| 弱项 | 错误处理与数据结构 | 并发与分发 | 开发成本高 |
| 本库 | 「Linux」008 | 本套 | 「Go」板块 |

判断口诀：**先 Shell——能一行管道解决就不写脚本；Shell 超过 50 行或需要数据结构，切 Python；需要常驻、高并发或分发给非运维用户，切 Go**。三者的退出码、日志、幂等纪律完全一致（SRE 004 的安全带）。

## 0.3 工具链三件套：venv · pip · ruff

```bash
# ① 隔离：每个项目一个 venv（永远不往系统 Python 装包）
python3 -m venv .venv
source .venv/bin/activate
# 激活后：which python3 → .venv/bin/python3

# ② 依赖：装进 venv，锁进清单
pip install requests
pip freeze > requirements.txt

# ③ 质量：ruff 一体（格式化 + 静态检查）
pip install ruff
ruff check . && ruff format .
```

三条铁律：**不建 venv 不 pip install**（污染系统 Python，与「容器」003 的"数据不进可写层"同级别的红线）；**requirements.txt 写死版本**（`requests==2.32.3`——可重现，与 001 §1.10 Git 纪律同源）；**新工具可看 uv**（Rust 写的 pip/venv 替代，快很多——2024 起快速普及，存量环境仍是 venv+pip 为主）。

## 0.5 六个误解

| # | 误解 | 实际 |
|---|---|---|
| 1 | 会 Shell 就不用学 Python | Shell 没有 venv、没有像样的异常处理与数据结构 |
| 2 | Python 慢不能用 | 运维脚本的瓶颈是网络与磁盘，不是语言 |
| 3 | 直接往系统 Python 装包 | venv 隔离是第一课 |
| 4 | 脚本不需要测试 | 006 的 pytest 十分钟能上手 |
| 5 | Python 2 脚本还能凑合 | Python 2 已 EOL（2020），旧脚本迁移是负债 |
| 6 | 学了 Python 就不用 Shell | 三语言分工（0.2），Shell 永远在 |
