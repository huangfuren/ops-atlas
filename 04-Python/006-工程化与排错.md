## 6.1 ruff：格式化与静态检查一体

ruff 一个工具覆盖格式化（black 的活）与静态检查（flake8 的活），速度快两个量级：

```bash
ruff check .          # 静态检查：未用变量、裸 except、可疑写法
ruff check --fix .    # 可自动修复的问题顺手修
ruff format .         # 统一格式——团队不再争论空格与引号
```

它抓的典型运维 bug：未使用的变量（参数拼错）、f-string 里没插值、裸 except、未 await、重复 key。**接进提交流程**（pre-commit 或编辑器保存即跑——「CICD」009 的防线的脚本层形态）。类型注解想再进一步可加 mypy 注记——先 ruff 后 mypy，别一口吃成胖子。

## 6.2 pytest 入门：巡检逻辑的测试

pytest 的门槛低到"写个函数 + assert"：

```python
# test_disk_check.py
from disk_check import judge

def test_critical():
    assert judge(used=95, threshold=90) == 2

def test_normal():
    assert judge(used=60, threshold=90) == 0

def test_boundary():
    assert judge(used=90, threshold=90) == 2      # 边界：恰好等于阈值算命中
```

```bash
pytest -v
```

测试的真正收益不是"证明没 bug"，是**让你敢改代码**：有了这三个测试，把 `judge()` 重构、换采集实现（005 §5.5 的 collect），跑一遍 pytest 就知道行为没变。测试的选材纪律：**测纯函数**（judge 这类"输入→输出"的逻辑），不测 print 与 subprocess（那些用集成验证）。前提是 001 §1.3 的骨架——逻辑在函数里才测得了。

## 6.3 打包分发：pip install -e 与 pipx

脚本被三个同事要走了——分发两级：

```bash
# 开发机：可编辑安装（改代码立即生效）
pip install -e .

# 同事机器：pipx 隔离安装成全局命令
pipx install /path/to/disk-check-1.0.0-py3-none-any.whl
disk-check web-1 db-1 -t 80        # 任意目录直接敲
```

让 `pip install` 生成命令，需要在项目里声明 entry_points（`pyproject.toml`）：

```toml
[project]
name = "disk-check"
version = "1.0.0"
dependencies = ["requests>=2.32"]

[project.scripts]
disk-check = "disk_check.cli:main"
```

分工口径一句话：**库装进 venv，CLI 工具用 pipx**——pipx 给每个工具独立环境又把命令暴露到全局，正好解决"工具 A 和工具 B 依赖冲突"的问题。版本号语义与 005 §5.5 的"可分发的产物"衔接（「CICD」000 §0.6）。

## 6.4 traceback 阅读：从最后一行往上

报错一大屏不会读？**traceback 的读法是从最后一行往上**：

```plain
Traceback (most recent call last):        ← 往上：调用链（谁调到了谁）
  File "disk_check.py", line 12, in main
    code, msg = check(host, args.threshold)
  File "disk_check.py", line 6, in check
    used = shutil.disk_usage(f"/data/{host}").percent   ← 最后一行：异常类型+消息
FileNotFoundError: [Errno 2] No such file or directory: '/data/web-1'
```

读法三步：**最后一行 = 异常类型与消息**（本例：`/data/web-1` 不存在——-host 是错的或机器挂了）；**往上找自己代码的最近一行**（定位行号）；**对照上下文**（哪个循环第几台机器）。三条高频报错的速查：`ModuleNotFoundError`（venv 没进/包没装，001 §1.2）、`KeyError`（字典取了不存在的键——先 `in` 判断或 `.get`）、`IndentationError`（混用 Tab 与空格）。

## 6.5 项目模板：运维工具的标准结构

超过 200 行的工具就该有目录结构（000 §0.2 的上限信号）：

```plain
disk-check/
├── pyproject.toml          # 元数据 + entry_points + 依赖
├── README.md               # 用法一页
├── src/
│   └── disk_check/
│       ├── __init__.py
│       ├── cli.py          # argparse + main（001 §1.3）
│       ├── core.py         # judge/collect 纯逻辑（可测）
│       └── notify.py       # webhook（005 §5.2）
└── tests/
    └── test_core.py        # pytest（6.2）
```

结构纪律：**纯逻辑（core）与 IO（cli/notify）分离**——6.2 的可测性由此而来；README 的用法示例直接从 `--help` 复制，保证与实现同步。

## 6.6 六个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 逻辑写死在顶层 | 无法测试与复用 | main + 函数（001 §1.3） |
| 2 | 不跑 ruff | 风格漂移 + 低级 bug 存活 | check + format 进提交流程 |
| 3 | 零测试大重构 | 改完靠祈祷 | 先给纯函数补 3 个测试再改（6.2） |
| 4 | 全局 pip install 分发工具 | 依赖冲突 | pipx（6.3） |
| 5 | traceback 只看第一行 | 谜语人排障 | 从最后一行往上（6.4） |
| 6 | 工具无版本无 README | 交接即失传 | pyproject + README（6.5） |

第 5 条展开：traceback 最下面的 `XxxError: 消息` 是**答案**，中间的调用链是**路线图**——从答案往上找到第一个属于你自己的文件行号，那一行就是案发现场。多层异常链（`During handling of the above exception`）时，**最底下的块才是最终原因**，上面的是"处理它时又炸了"。
