## 1.1 面向 Shell 用户的语法地图

给写过 Bash 的人一张速换表——同样的运维意图，两边写法：

| 意图 | Shell | Python |
| --- | --- | --- |
| 变量 | `HOST="web1"` | `host = "web1"` |
| 插值 | `echo "deploy to $HOST"` | `print(f"deploy to {host}")` |
| 条件 | `if [ "$rc" -ne 0 ]; then` | `if rc != 0:` |
| 循环 | `for h in $HOSTS; do` | `for h in hosts:` |
| 命令输出 | ``R=$(df -h)`` | `r = subprocess.run(...)`（002） |
| 退出 | `exit 1` | `sys.exit(1)` |

三个最值钱的语法点：

```python
# ① f-string：所有格式化的首选
print(f"{host}:{port} → {'OK' if ok else 'FAIL'}")

# ② 列表推导：一行完成过滤与变换
errors = [line for line in lines if "ERROR" in line]

# ③ 元组解包：一个 return 带回多个值
code, message = check(host)
```

与 Shell 的思维差异：Shell 靠"命令的文本输出"传递信息，**Python 靠数据结构传递信息**——列表、字典、对象。这是切语言的真正门槛，也是收益（002 §2.4 的 json/csv 处理会让你体会更深）。

## 1.2 venv 与依赖隔离

每个项目一个 venv，三步成为肌肉记忆：

```bash
python3 -m venv .venv          # ① 建（每项目一次）
source .venv/bin/activate      # ② 激活（提示符出现 (.venv)）
pip install requests           # ③ 装包——只进这个 venv
deactivate                     # 退出
```

为什么不直接 `pip install` 到系统：系统 Python 的包被 OS 工具依赖（yum/apt 的 Python 组件），**全局装包可能弄坏系统工具**；且多项目依赖会互相冲突（A 要 requests 2.x、B 要 2.y）。venv 就是"每个项目一个干净副本"——与「容器」003 的依赖隔离思想完全同源。

验证在哪个环境：`which python3` 与 `pip -V`（后者同时显示来源路径）。**cron/流水线里跑脚本不激活 venv 的替代写法**：直接用绝对路径 `/opt/myapp/.venv/bin/python3 script.py`（002 §2.6 的定时任务坑与这里相连）。

## 1.3 脚本骨架：argparse + main() + 退出码

运维脚本的标准骨架——参数解析、主逻辑、退出码三段分离：

```python
#!/usr/bin/env python3
"""磁盘巡检：超阈值返回 2 并输出告警行。"""
import argparse
import sys

def check(host: str, threshold: int) -> tuple[int, str]:
    """单机检查：返回 (状态码, 消息)。实际采集见 002/005。"""
    used = 87  # 示例：真实实现见 005 §5.5
    if used >= threshold:
        return 2, f"{host} 磁盘 {used}% ≥ {threshold}%"
    return 0, f"{host} 磁盘 {used}% 正常"

def main() -> int:
    parser = argparse.ArgumentParser(description="磁盘巡检")
    parser.add_argument("hosts", nargs="+", help="主机列表")
    parser.add_argument("-t", "--threshold", type=int, default=90)
    args = parser.parse_args()

    worst = 0
    for host in args.hosts:
        code, msg = check(host, args.threshold)
        print(msg)
        worst = max(worst, code)
    return worst

if __name__ == "__main__":
    sys.exit(main())
```

```plain
$ ./disk_check.py web-1 db-1 -t 80
web-1 磁盘 87% ≥ 80%
db-1 磁盘 62% 正常
$ echo $?
2
```

三个骨架纪律：**逻辑进函数、`main()` 只做编排**（可测试的前提，006）；**退出码表达结果**（0 正常 / 1 一般失败 / 2 告警阈值命中——cron 与流水线只看它）；**argparse 自动生成 `-h` 帮助**（交接成本大降）。

## 1.4 异常处理：try/except/finally 与失败哲学

```python
try:
    resp = call_api(host)          # 可能失败的操作
except TimeoutError as e:
    log.error("API 超时：%s", e)
    return 1                        # 处理并给出失败出口
except Exception as e:              # 兜底——记录后决定传播或退出
    log.exception("未预期异常")     # exception() 自动带 traceback
    raise
finally:
    cleanup()                       # 无论成败都执行：关连接、删临时文件
```

四条纪律：

1. **except 要指明异常类型**——裸 `except:` 会吞掉 `KeyboardInterrupt`（Ctrl-C）和一切 bug，排障噩梦；
2. **能处理就处理，不能处理就 raise**——吞掉异常 = 静默失败（「CICD」009 §9.7 同型问题）；
3. **异常消息写上下文**——`raise RuntimeError(f"连接 {host} 失败：{e}") from e`，把现场带上；
4. **退出码有约定**——与 1.3 的骨架一致，调用方（cron/流水线）靠它判断。

## 1.5 logging：别用 print 交差

`print` 没有级别、没有时间戳、没有输出目标——上生产的脚本一律 `logging`：

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
log = logging.getLogger("disk-check")

log.info("开始巡检 %d 台主机", len(hosts))     # 占位符而非 f-string：日志库惰性求值
log.error("%s 检查失败：%s", host, reason)
```

这与「日志」005 的规范完全对齐：级别契约（ERROR 可告警）、格式统一、输出可路由（stdout → 采集器）。调试期临时加详细日志：`logging.basicConfig(level=logging.DEBUG)` 一行切换，不用改语句。

## 1.6 六个坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 不建 venv 直接装包 | 污染系统 Python，冲突难查 | 每项目一个 venv（1.2） |
| 2 | 裸 `except:` | 吞掉 Ctrl-C 与所有 bug | 指明异常类型，兜底后 raise |
| 3 | 逻辑全写在顶层 | 无法测试、无法被 import 复用 | main() + 函数（1.3） |
| 4 | 用 print 交差 | 无级别无时间戳，不可路由 | logging（1.5） |
| 5 | 退出码全是 0 | cron/流水线永远认为成功 | 退出码表达结果（1.3） |
| 6 | requirements.txt 不锁版本 | 半年后环境对不上 | `pip freeze` 锁定 |

第 6 条展开：requirements.txt 的最低要求是**精确版本**（`requests==2.32.3` 而非 `requests>=2`）——依赖漂移会让"半年前能跑的脚本"静默坏掉（「CICD」000 §0.6 制品思维在脚本层的形态）。进阶做法是锁到传递依赖（`pip freeze` 全量导出），至少做到直接依赖精确锁。
