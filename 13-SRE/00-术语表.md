# 00 术语表

> **这一文档回答**：某个词的准确定义、两个混用词的分界、「症状出现时病根在哪个机制」往哪走。  
> **怎么用**：按名字（按册分组）、按缩写（缩写速查）、按症状（症状反查）。  
> **只有一句话**：要落地动作回对应册；这里保证「认得出、分得清、找得到」。

## 000 SRE 全貌

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| SRE | Site Reliability Engineering | 用软件工程方法做运维：可靠性是可度量、可预算、可持续改进的属性 |
| SLO 思维 | SLO thinking | 从"保机器不死"转向"保用户体验指标在承诺内" |
| 可靠性 | reliability | 服务在承诺的范围内持续可用的属性——SRE 的产品 |
| 方法论 | methodology | SLO/错误预算/待命/复盘/自动化五件机制的总称 |
| 生产就绪 | production readiness | 服务上线前满足一组可靠性清单（各册检查清单的汇总视角） |

## 001 SLO 与错误预算

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| SLI | Service Level Indicator | 服务等级指标：用户视角的可度量信号（成功率、P99 延迟） |
| SLO | Service Level Objective | 对 SLI 设定的内部目标（如"30 天成功率 ≥ 99.9%"） |
| SLA | Service Level Agreement | 对外的合同承诺（含赔偿条款）——SLO 是 SLA 的内部安全垫 |
| 错误预算 | error budget | 1 − SLO：允许不完美的额度。**烧完就冻结发布、优先修可靠性** |
| burn rate | 消耗速率 | 错误预算的烧钱速度——快烧触发紧急告警，慢烧触发工单 |
| 滑动窗口 | rolling window | SLO 的统计周期（28 天常见）——比自然月更能反映当前状态 |
| P99 | 99th percentile | 99% 的请求快于该延迟——比平均值更能反映用户痛感 |

## 002 待命与应急响应

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| on-call | 待命 | 轮流承担"告警响了我来"的值班制度 |
| 轮换 | rotation | 待命的排班：主备双岗、固定周期、交接清单 |
| 升级链 | escalation chain | 响应无进展时的逐级上报路径——**有截止时间才算存在** |
| IC | Incident Commander | 应急指挥：故障期间唯一的决策与分派人，不亲手修 |
| CL | Communications Lead | 沟通负责人：对内对外同步进展，把工程师从"边修边汇报"里解放 |
| runbook | 处置手册 | 告警到动作的预先文档——**告警必须链接 runbook** |
| page | 告警呼叫 | 打断人的高优先级告警。每个 page 必须可行动 |
| 告警疲劳 | alert fatigue | 噪音告警让人麻木——漏掉真故障的组织病灶 |
| MTTA / MTTR | Mean Time To Acknowledge / To Recover | 平均确认时长 / 平均恢复时长——响应效率的两个度量 |

## 003 故障复盘与改进

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| 无指责复盘 | blameless postmortem | 追系统缺陷不追个人过错的复盘文化——**怕背锅就没人说真话** |
| 时间线 | timeline | 故障从诱因到恢复的关键事件序列（精确到分钟） |
| 根因 | root cause | 引发故障的系统缺陷——**通常不止一个** |
| 5-Why | 五问法 | 连问五层"为什么"，从症状挖到机制缺陷 |
| 行动项 | action item | 复盘产出的整改任务——**有认领人、有死线、有跟踪才算数** |
| 游戏日 | game day | 主动注入故障的演练——验证预案与待命体系的真实性 |

## 004 Toil 治理与自动化

| 术语 | 英文 | 一句话 |
| --- | --- | --- |
| toil | 琐事 | 与生产规模线性增长的、重复的、无创造性的手工运维 |
| toil 配额 | toil budget | 每个 SRE 的琐事占比上限（Google 经验值 50%）——超了就启动自动化 |
| 渐进自动化 | — | 先流程化 → 再脚本化 → 最后平台化，不跳级 |
| 幂等前提 | idempotency | 自动化的安全带：重跑不出事（「CICD」004 §4.7 的同源要求） |
| SRE 健康度 | — | toil 占比、告警质量、复盘行动项完成率——SRE 团队自身的指标 |

## 缩写速查

| 缩写 | 全称 | 意思与出处 |
| --- | --- | --- |
| IC | Incident Commander | 应急指挥（002） |
| MTTA | Mean Time To Acknowledge | 平均确认时长（002） |
| MTTR | Mean Time To Recover（或 Repair） | 平均恢复时长——R 的含义团队要约定清楚（002） |
| OTel | OpenTelemetry | 可观测性数据标准（000 引「日志」000 §0.1） |
| RCA | Root Cause Analysis | 根因分析，复盘的核心环节（003） |
| SLO / SLI / SLA | Objective / Indicator / Agreement | 目标 / 指标 / 协议，三者递进（001） |
| SRE | Site Reliability Engineering | 站点可靠性工程（全册） |

## 最容易混的 12 对

| 容易混 | 一句话差别 | 怎么确认 | 册 |
| --- | --- | --- | --- |
| SLI vs SLO | 度量的信号 / 信号的目标值 | SLI 是温度计，SLO 是"体温不超 37.5"的承诺 | 001 |
| SLO vs SLA | 内部目标 / 对外合同（含赔付） | SLA 铁定比 SLO 松——留出安全垫 | 001 |
| 错误预算 vs 错误率 | 允许烧的额度 / 已发生的比例 | 错误率是分母上的消耗，预算是余额 | 001 |
| burn rate vs 错误率 | 预算消耗速度（多窗口比）/ 单纯错误比例 | burn rate 用"当前 vs 应耗"的倍数表达 | 001 |
| MTTR 的 R | 恢复 Recover / 修复 Repair——语义不同数字不同 | 团队约定并写进看板口径 | 002 |
| runbook vs playbook | 单个告警的动作手册 / 一类场景的整套剧本 | 一本 playbook 含多份 runbook | 002 |
| IC vs 值班人 | 指挥与分派 / 动手修复 | 大故障时 IC 亲手修=失职 | 002 |
| 复盘 vs 问责 | 改进系统 / 追究个人 | 复盘里说出真话的人不受罚——文化试金石 | 003 |
| toil vs 正常运维工作 | 线性增长、重复、无创造 / 有分析价值的工程 | 四问：重复吗？可自动化吗？增长会要更多人力吗？ | 004 |
| 游戏日 vs 真故障演练 | 主动注入故障 / 被动等故障 | 预案没经过游戏日=没验证 | 003 |
| SLO vs KPI | 用户可靠性的承诺 / 团队业务考核 | SLO 烧完要停发布——KPI 没有这种机制 | 001 |
| 预案 vs runbook | "出事怎么办"的方案集 / 可直接照做的步骤 | runbook 能被执行，预案只是描述 | 002 |

## 按症状反查

| 症状 | 病根在哪个机制 | 去哪 |
| --- | --- | --- |
| 告警响个没人理 | 告警不可行动 / 没绑 runbook | 002 §2.2 |
| 同样故障第三次发生 | 复盘没有行动项或没跟踪 | 003 §3.4 |
| 复盘会变成追责会 | 无指责文化未立 | 003 §3.1 |
| SLO 定了没人看 | SLO 没接告警（burn rate） | 001 §1.4 |
| on-call 频繁告警疲劳 | 噪音告警 / 无分级 / 无轮换保护 | 002 §2.1–2.2 |
| 故障现场没人指挥 | 应急角色未定义 | 002 §2.3 |
| 发布与稳定的争论不休 | 没有错误预算做仲裁 | 001 §1.3 |
| 演练走过场 | 游戏日没有注入真实故障 | 003 §3.5 |
| 琐事挤占工程时间 | toil 无配额、无自动化立项 | 004 §4.1–4.2 |
| 大故障时老板进群指挥 | 升级链与决策权未约定 | 002 §2.4 |
| 新人不敢响应告警 | runbook 缺失或过时 | 002 §2.5 |
| "我们很稳"但拿不出数 | 没有 SLI 度量 | 001 §1.1 |
